# Feature 9.3: Dummy-hash verify on unknown email

**Phase:** 9 — Security
**Status:** completed
**Estimated effort:** 1–2 hours
**Depends on:** nothing
**Blocks:** 9.4 (throttle wraps the same `authorizeCredentials`)

## Goal

A login for an address that is not in `users` still runs the password verifier, so wall-clock time does not advertise which emails exist. Copy stays “Invalid email or password”.

## Scope

Include:

- `DUMMY_PASSWORD_HASH` — a bcryptjs hash of a constant dummy secret, stored as a string literal in `lib/auth/authorize.ts` (or `lib/db/password.ts` if that keeps hashing in one module). Generated once offline; not hashed on every request
- `authorizeCredentials` always calls `verify(password, user ? user.passwordHash : DUMMY_PASSWORD_HASH)`
- Still returns `null` when there is no user **or** when verify is false. Never returns a user object for the dummy path
- Tests: unknown email invokes `verify` exactly once; known email + wrong password invokes `verify` exactly once; known + right password still returns id/email/tenantId/role without `passwordHash`

Exclude (for now):

- 9.4 throttle
- Logging the email or the password
- Changing login copy
- Dummy work on signup’s `findByEmail` (signup already maps hits to generic `unavailable`; timing there is a later mailer problem)
- Session revocation

## Files to create

- None required (extend `lib/auth/authorize.test.ts`)

## Files to modify

- `lib/auth/authorize.ts` — dummy hash constant + always-verify
- `lib/auth/authorize.test.ts` — spy/counting `verify`

## Spec

1. Empty email or empty password still returns `null` **without** calling `verify` (no work to do; this is not an oracle for membership).
2. Non-empty credentials always call `verify` once, with the real hash or `DUMMY_PASSWORD_HASH`.
3. `DUMMY_PASSWORD_HASH` starts with `$2b$` or `$2a$` and is a 60-character bcrypt modular crypt. A test asserts that prefix so nobody ships `"dummy"`.
4. The dummy plaintext is **not** a user password in seed and is not `AUTH_OWNER_PASSWORD`. It is a random string baked into the hash; the plaintext itself must not appear in the repo. Only the hash is committed.
5. Existing cases still hold: unknown email → `null`; wrong password → `null`; match → `{ id, email, tenantId, role }`; client `tenantId` in credentials ignored.
6. `verifyPassword` in `lib/db/password.ts` is unchanged (bcryptjs `compare`).

## Acceptance criteria

1. [x] Unknown email with a non-empty password calls the injected `verify` exactly once
2. [x] That path still returns `null`
3. [x] `DUMMY_PASSWORD_HASH` matches `/^\$2[ab]\$\d{2}\$.{53}$/`
4. [x] Happy path and “ignores tenantId in credentials” tests still pass
5. [x] `env -u DATABASE_URL npm test` and `AUTH_SECRET=ci-build-placeholder npm run build` pass
6. [x] No new dependencies

## Implementation notes

- Generate the hash once with a local `node -e` using bcryptjs, paste only the hash. Do not commit the dummy plaintext. Do not print `AUTH_*` values.
- Do not `hash()` the dummy inside `authorizeCredentials` — that would add a hash *plus* a compare on the miss path and make misses *slower* than hits, which is another oracle.
- The existing unknown-email test does not count `verify`; update it rather than adding a parallel case that could drift.
- Do not run prettier on a directory.

## Shipped notes (2026-09-11)

`DUMMY_PASSWORD_HASH` is a `$2b$10$` bcrypt modular crypt in `lib/auth/authorize.ts`. The plaintext was generated with `crypto.randomBytes` and never written to the repo. `authorizeCredentials` still returns immediately (no `verify`) when email or password is empty; otherwise it always calls `verify(password, user ? user.passwordHash : DUMMY_PASSWORD_HASH)` and returns `null` if there is no user **or** the compare fails, so a dummy hit cannot mint a session.

The old unknown-email test returned before `verify` (`if (!user) return null`). It now asserts `hashes` is exactly `[DUMMY_PASSWORD_HASH]`. Wrong-password and happy-path tests count one call with the real hash. Empty credentials assert zero calls. `lib/db/password.ts` is byte-identical to `origin/main`.

Verified: `env -u DATABASE_URL npm test` 668 passed (104 files, up from 666/104); `AUTH_SECRET=ci-build-placeholder npm run build` exit 0. No Playwright (timing is not observable from 6.4). No new dependencies.
