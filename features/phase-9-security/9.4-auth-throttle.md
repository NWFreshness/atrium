# Feature 9.4: Auth attempt throttle

**Phase:** 9 — Security
**Status:** specced
**Estimated effort:** 3–4 hours
**Depends on:** 9.3
**Blocks:** nothing

## Goal

Five failed logins (or signups) for the same mailbox in 15 minutes, or twenty from the same IP, fail closed for the rest of that window. Copy stays generic. Phase 6’s named residual (“bots can open empty tenants”) is closed without a mailer.

## Scope

Include:

- `lib/auth/throttle.ts` — policy: subjects, limits, window, `assertNotThrottled` / `recordFailure` / `clearFailures`. Returns `{ ok: true } | { ok: false }`. Throws nothing. Imports neither `SignUpError` nor login types
- Memory repository for unit tests; Drizzle repository for production
- Table `auth_throttles` (no `tenantId`, not demo-reset, not in the 7.3 tenant-index list)
- Generated migration; read it; `IF NOT EXISTS`; no RLS
- `authorizeCredentials` consults the throttle **after** empty-field checks and **before** `findByEmail` / `verify`. A throttled subject returns `null` without bcrypt. A failed verify calls `recordFailure`. A successful auth calls `clearFailures` for that email (and IP if present)
- `signUp` consults the same helper **after** the flag check and **before** `findByEmail`. Throttled → `SignUpError("unavailable")`. Failed create (including duplicate) records a failure. Successful create clears
- Injectable clock and store so `env -u DATABASE_URL npm test` covers allow, deny, window expiry, success-clears

Exclude (for now):

- CAPTCHA, mailer, MFA
- Distinct “too many attempts” copy
- Logging plaintext email or IP
- Throttling authenticated app POSTs (import is 9.5)
- Reset-demo / Groove
- Renaming `middleware.ts`

## Spec

1. Constants (one definition): `EMAIL_FAILURE_LIMIT = 5`, `IP_FAILURE_LIMIT = 20`, `WINDOW_MS = 15 * 60 * 1000`.
2. Subjects: `email:${lowerTrimmedEmail}` and, when `ip` is a non-empty string, `ip:${ip}`. Do not store the raw email column; the subject string is the key.
3. Window: first failure inserts `failedCount = 1`, `windowStartedAt = now`. Later failures in the same window increment. `now - windowStartedAt >= WINDOW_MS` starts a new window at count 1.
4. `assertNotThrottled`: if email subject count `>= 5` or ip subject count `>= 20` inside the window → `{ ok: false }`. Otherwise `{ ok: true }`.
5. `clearFailures` deletes both subjects for that attempt.
6. Login: throttled → `null`, same as wrong password. Do not call `verify`.
7. Signup: throttled → `SignUpError("unavailable")` (generic, same as duplicate). Flag-closed still wins first (`closed`).
8. Schema: `auth_throttles` columns `id` uuid pk, `subject` text not null unique, `failedCount` integer not null, `windowStartedAt` timestamp not null. No FK to users. No `tenantId`.
9. `schema.test.ts` tenant-index derived list still equals the tables that have `tenantId`. Adding this table must not fail 7.3 — that is the proof it is unscoped on purpose.
10. Groove still has no tables. Demo reset does not touch `auth_throttles`.
11. IP is taken from `x-forwarded-for` first hop **only if** Auth.js hands the request in. Spoofed IP is residual behind Vercel; do not add a new env trust list.

## Acceptance criteria

1. [ ] `auth_throttles` exists, has no `tenantId`, unique on `subject`
2. [ ] 7.3’s tenant-index test still passes without listing this table
3. [ ] Five failures for one email inside 15 minutes: sixth `assertNotThrottled` is `{ ok: false }`; after 15 minutes it is `{ ok: true }`
4. [ ] Twenty failures for one IP: twenty-first denied; a different IP is unaffected
5. [ ] Success `clearFailures` lets the next attempt through
6. [ ] `authorizeCredentials` on a throttled email does not call `verify`
7. [ ] `signUp` on a throttled email throws `SignUpError("unavailable")` and does not insert
8. [ ] Generated migration is additive (CREATE TABLE / unique index), idempotent `IF NOT EXISTS`, no DROP of users/tenants
9. [ ] `env -u DATABASE_URL npm test` and `AUTH_SECRET=ci-build-placeholder npm run build` pass
10. [ ] No new runtime dependencies (no Redis, no Upstash)
