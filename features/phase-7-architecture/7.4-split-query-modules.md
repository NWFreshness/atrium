# Feature 7.4: Split query modules

**Phase:** 7 — Architecture
**Status:** completed
**Estimated effort:** 4–6 hours
**Depends on:** 7.2
**Blocks:** 7.5

## Goal

CRM, Space, and Rolodex query helpers stay the same functions, but memory-store and Drizzle no longer live in one 900–1200 line file. `queries.ts` remains the import path for `*-actions` and tests.

## Scope

Include:

- For each of `lib/crm`, `lib/space`, `lib/rolodex`: move the in-memory repository + in-memory CRUD into one module, Drizzle CRUD into another, leave types + `createMemoryXRepository` re-exported from `queries.ts`
- Existing imports from `./queries` or `@/lib/<app>/queries` keep compiling without edits (barrel). If a test file must change because it imported a now-private helper, that is allowed; public functions do not rename
- Tests still pass with `env -u DATABASE_URL`

Exclude (for now):

- Hexagonal ports, `IRepository` interfaces, dependency-injection frameworks
- New query helpers or `listXBySearch` parallels
- Moving `*-actions.ts` or changing `*ForSession` / `requireTenant`
- Splitting Groove (already split: domain vs `audio/`)
- 7.5’s client-import grep (do not add it here; do not “fix” circles-board here unless a move breaks it — leave that leak for 7.5)

## Files to create

Per app, names can vary but the split must be real:

- `lib/crm/queries-memory.ts` and `lib/crm/queries-drizzle.ts` (or `memory-repo.ts` / `drizzle-repo.ts`)
- Same pair under `lib/space/` and `lib/rolodex/`

## Files to modify

- `lib/crm/queries.ts`, `lib/space/queries.ts`, `lib/rolodex/queries.ts` — become barrels that re-export the same names they export today
- Tests only if they imported non-exported helpers

## Spec

1. Public exports today (types, `createMemoryXRepository`, `listX` / `getX` / `createX` / `updateX` / `deleteX`, and any other function tests import from `queries.ts`) remain exported from `queries.ts`.
2. The Drizzle file is the only one that calls `getDb()` for that app. The memory file does not import `../db`.
3. `queries.ts` may import both and re-export; it must not grow the CRUD bodies back in.
4. Do not change SQL, ordering, error messages, or `tenantId is required` behaviour.
5. Prettier / import order only on files this feature touches. Do not run prettier on a directory.

## Acceptance criteria

1. [x] `lib/crm/queries.ts`, `lib/space/queries.ts`, and `lib/rolodex/queries.ts` no longer contain the Drizzle `db.select` / `db.insert` implementations (those live in the drizzle module)
2. [x] Memory repository factories still live in the memory module and are re-exported
3. [x] `grep` from `lib/crm/org-actions.ts` (and Space/Rolodex action files) still imports from `./queries`
4. [x] `env -u DATABASE_URL npm test` passes with the same cases as before this split
5. [x] `AUTH_SECRET=ci-build-placeholder npm run build` passes
6. [x] No new npm dependencies

## Implementation notes

- Mechanical move. Do not “improve” adjacent helpers.
- Vitest has no `@/` unless `vitest.config.ts` already maps it; prefer relative imports in `lib/`.
- If 7.2 added bulk-delete helpers inside `queries.ts`, they move with the Drizzle half.

## Shipped notes

Each app's query module is now four files. `queries.ts` stays the import path for
every action, seed, reset and test, and re-exports the same names; the stores sit
behind it.

| App | barrel | shared | memory | drizzle |
| --- | --- | --- | --- | --- |
| CRM | 942 → **399** | 198 | 353 | 436 |
| Space | 1281 → **615** | 161 | 576 | 583 |
| Rolodex | 1015 → **481** | 250 | 356 | 462 |

The barrel keeps what the public API is: the `requireTenantId` guard, the row
construction (so both stores receive an identical row), the dispatch
(`repo ? …InMemory : …InDrizzle`) and, for Space, `insertBlockAt` / `reorderBlocks`
— which compose the public `listBlocks`/`updateBlock`/`createBlock` and are called in
production with `repo` undefined (`block-actions.ts` forwards a possibly-undefined
repo), so they belong to neither half. `createMemory<App>Repository` lives in the
memory module; the Drizzle module is the only file per app that imports `../db`.

**One module beyond the spec's pair, and why.** `queries-shared.ts` holds the types
plus the store-agnostic pure helpers (`requireTenantId`, `newId`, `now`, `clone`,
the search predicates and comparators). Both halves need them — the Drizzle create
paths return `clone(row)`, the Drizzle list paths re-filter with the same JS
predicates — so without a shared module they would have to import each other or the
barrel, which is a runtime cycle. The spec allowed the pair's names to vary; it did
not foresee that a third module is what keeps the graph acyclic.

Acceptance criteria and their evidence:

1. No `db.select`/`db.insert`/`db.update`/`db.delete`, no `getDb(`/`require*Db(` in
   any barrel — asserted mechanically, not by eye.
2. `createMemoryCrmRepository` (`queries-memory.ts`), `createMemorySpaceRepository`,
   `createMemoryRolodexRepository` are defined in the memory halves and re-exported
   from the barrels.
3. Every `*-actions.ts` in the three apps still imports `./queries` (12 files), and
   nothing outside the app directory imports the halves.
4. `env -u DATABASE_URL npm test` → **633 passed (99 files)**, the same count as
   before the split, with no test file touched.
5. `AUTH_SECRET=ci-build-placeholder npm run build` → exit 0.
6. `git diff -- package.json package-lock.json` is empty.

**Equivalence evidence, because "the tests still pass" is weak for a refactor this
mechanical.** The runtime export list of each barrel was captured *before* the split
and compared after: 21/33/27 names, nothing missing, nothing added. Per app, the
token counts in the new modules equal HEAD's exactly for `.select/.insert/.update/
.delete/.values/.returning/.where/.limit/eq/and/max/desc(clone(/now()/newId(`; the
`new Error` message sets are identical; every create/update memory impl still returns
`clone(...)` (no live-array aliasing); `now()`/`newId()` are called only in the
barrels, so no row gets two timestamps; `orderBy` clauses and filter order are
unchanged.

### Review round

Two subagents ran against the finished split — spec compliance plus an adversarial
pass aimed at what token counts cannot see (aliasing, doubled timestamps, order of
operations, lost guards, wrong dispatch target). **No blocking findings.** They
independently confirmed: guard calls equal public-function counts per app (20/32/26),
every tenant predicate still leads its `WHERE`, the 7.2 batch guards are intact
(CRM 1 + Space 4, exactly as before), no helper vanished, no comparator is defined
twice, and nothing new drags `../db` into a client boundary. Five fixes came out of
it, all applied:

- **`lib/space/queries-drizzle.ts` imported 17 types without the `type` keyword** —
  the only file of the twelve that did. It elides today, but `isolatedModules` is on
  and any non-eliding transform would turn it into a runtime import error. Prefixed.
- **Rolodex named its Drizzle create impls `create<X>InDrizzle`** while CRM and Space
  used `insert<X>`; renamed for the one convention, since 7.5 will be grepping these
  modules.
- **Space's Drizzle position helpers lacked the `InDrizzle` suffix** their memory
  twins carry; renamed to `next*PositionInDrizzle`.
- **Twelve create-in-memory impls took an unused `scoped` parameter** (CRM 4,
  Rolodex 8); dropped from the signatures and call sites. Space had already omitted
  it.
- **`lastContactedFor` / `latestNewsFor` were exported** while only `enrichPerson`
  uses them; now file-private.

### Deliberate limits

- **The split is not a byte-for-byte move in three places, all verified equivalent.**
  (a) Six Rolodex list functions (`listFacts`, `listGifts`, `listImportantDates`,
  `listInteractions`, `listNews`, `listReminders`) now validate `tenantId` in the
  barrel rather than one level down inside `listChildren` — +5 `requireTenantId`
  calls, same message for the same input (checked by calling all eight with a blank
  tenant). (b) CRM's `nextBoardOrderInMemory` is synchronous where HEAD's
  `nextBoardOrder` was `async`, so `createdAt: now()` is captured one microtask
  earlier on the memory path; unobservable, and no test asserts it. (c) Space's memory
  impls are `async` without an `await` where CRM's and Rolodex's are synchronous — no
  behavioural difference, just the three agents' styles.
- **Dispatch style differs across the three apps** (CRM `if (repo) { … } return …`,
  Space/Rolodex ternaries) and the barrel re-export sits before the type block in
  Space but after it in CRM/Rolodex. Cosmetic, left alone: the spec asked for a
  mechanical move, not a restyle, and reformatting 81 dispatchers would bury the diff.
- **The client leak is untouched, as the spec requires** (`components/rolodex/
  circles-board.tsx` → `move-person.ts` → `queries.ts` still value-imports the
  barrel). The split does not make it worse: HEAD's `queries.ts` already imported
  `../db` and already contained every in-memory branch, so that chunk gained no new
  module edge — it is the same code in different files. 7.5 fixes it.
- **The barrels still hold row construction.** Read against the spec's item 3 ("must
  not grow the CRUD bodies back in"), the Drizzle *implementations* are out; row
  building was never in a half, and both stores receiving the identical row is what
  keeps the batch path (7.2) working. The compliance review flagged this as
  "ambiguous, leaning PASS"; recorded here so the reading is explicit.
