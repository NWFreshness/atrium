# Feature 7.3: tenantId indexes

**Phase:** 7 — Architecture
**Status:** in_progress
**Estimated effort:** 2–3 hours
**Depends on:** 7.2
**Blocks:** none

## Goal

Every tenant-scoped table has a B-tree index on `tenantId`, proven by a schema test and a generated migration. Queries do not change.

## Scope

Include:

- Drizzle `index` on `tenantId` for: `users`, `organizations`, `contacts`, `deals`, `activities`, `pages`, `blocks`, `properties`, `propertyOptions`, `rowValues`, `views`, `people`, `interactions`, `importantDates`, `facts`, `news`, `reminders`, `gifts`, `connections`
- Generated migration (`CREATE INDEX`); do not hand-write unless drizzle-kit emits something destructive
- Schema tests that each of those tables declares a `tenantId` column and an index whose columns include `tenantId`

Exclude (for now):

- Postgres RLS, policies, `FORCE ROW LEVEL SECURITY`, `SET LOCAL`
- Composite `(tenantId, id)` unless drizzle-kit’s default single-column index is what it emits — single-column `tenantId` is enough
- Changing unique indexes (`users.email`, `tenants.name`)
- Case-insensitive `lower(email)` unique index (6.1 follow-up, not this feature)
- Query helper changes, new list filters

## Files to create

- None required beyond `drizzle/` migration files drizzle-kit generates

## Spec

1. `pgTable` third argument (or equivalent in this Drizzle version) adds `index("…_tenantId_idx").on(table.tenantId)` — name stably, one per table, no two tables sharing an index name.
2. `npm run db:generate` is the source of the SQL. Read the generated file before committing: it must be `CREATE INDEX` (or `CREATE INDEX IF NOT EXISTS`), never `DROP TABLE`.
3. Existing unit tests that read table columns still pass. Do not change query signatures.
4. Groove still has no tables.

Every tenant-scoped table now carries a B-tree index on `tenantId`. Nineteen tables:
`users`; CRM's `organizations`, `contacts`, `deals`, `activities`; Space's `pages`,
`blocks`, `properties`, `propertyOptions`, `rowValues`, `views`; Rolodex's `people`,
`interactions`, `importantDates`, `facts`, `news`, `reminders`, `gifts`,
`connections`. Each declares `index("<table>_tenantId_idx").on(table.tenantId)` in a
`pgTable` third argument, appended to the arrays that already existed — `pages` keeps
its self-referencing FK, `rowValues` and `views` keep their composite primary keys.
No query changed, no route, no dependency.

`drizzle/0005_uneven_prodigy.sql` is exactly nineteen
`CREATE INDEX IF NOT EXISTS "<table>_tenantId_idx" ON "<table>" USING btree ("tenantId");`
statements — no drop, no alter, no RLS, no enum change. `IF NOT EXISTS` is a hand
edit (drizzle-kit omits it), the same choice 0004 made for `ADD VALUE IF NOT EXISTS`,
with the caveat written into the file: Postgres matches an existing index by *name*
only, not by definition. `npm run db:generate` now reports "No schema changes", so
schema and migration agree, and `drizzle/meta/0005_snapshot.json` lists exactly these
nineteen indexes and nothing else.

Acceptance criteria, with the evidence each rests on:

1. All nineteen tables declare the index (verified table by table, and by a test that
   reads them through the barrel).
2. The test bites. Proven twice by injection, not by reading: deleting `activities`'
   index failed with `activities indexes tenantId: expected [] to deeply equal
   [activities_tenantId_idx]`, and after the review's tightening, a composite

3. The migration creates indexes and nothing else — asserted statement by statement

   LEVEL SECURITY|DELETE FROM|TRUNCATE`. `db:generate` emitting no second migration
   proves the file is the schema's exact delta.
4. Groove is untouched: `lib/groove/**` still has no schema, seed or table, and the
   barrel test asserting no Groove export is retained.
5. `env -u DATABASE_URL npm test` → **633 passed (99 files)**;
   `AUTH_SECRET=ci-build-placeholder npm run build` → exit 0.
6. No RLS anywhere in the migration (same assertion as 3; the snapshot's

Two review subagents ran before the commit. Spec compliance passed criteria 1–4 and 6,
confirmed the snapshot delta is exactly nineteen index additions with no column, enum
or FK change, and found no table carrying a `tenantId` without an index. The quality
review reproduced the schema/migration/snapshot agreement and probed the test's
sensitivity against synthetic tables (wrong column fails, wrong name fails, missing
index fails). **No blocking findings**; three should-fix items, all fixed:

- **The index assertion was too weak.** It asked whether the index's columns *include*
  `tenantId`, so `index("activities_tenantId_idx").on(table.tenantId, table.type)`
  passed while not serving `where tenantId = ?`. It now asserts the columns are exactly
  `["tenantId"]`, with `method === "btree"` and `unique === false` — and that composite
  is the second injection above.
- **The migration test compared only the set of tables**, so swapping two tables' index
  names would have passed. It now captures the name and asserts it belongs to the table
  in the same statement.
- **The hand-added `IF NOT EXISTS` carried no rationale** where 0004 documents its
  identical choice; the migration now explains it in the file.

### Deliberate limits

- **`IF NOT EXISTS` matches by name only.** A branch that already carries an index with
  one of these names but a different definition would be skipped silently, and the
  snapshot would still claim the intended index. The names are new in this migration, so
  the risk is a hand-made index from before it — acceptable, and the alternative (a hard
  failure) wedges the migrator on a dev branch.
- **Single-column `tenantId` does not help the secondary predicates** (`pageId`,
  `databaseId`, `personId`, `rowId`+`propertyId`) or the `order by position/date` sorts:
  the planner can use the index for the tenant filter and still sorts. The spec says
  single-column is enough; `(tenantId, x)` composites are the lever if a plan ever
  asks for one.
- **The migration is not concurrent.** `npm run db:migrate` runs the file in one
  transaction, so all nineteen `CREATE INDEX` statements take write-blocking SHARE locks
  until commit. Sub-second at this size (hundreds of rows per table); a large table
  would want `CREATE INDEX CONCURRENTLY`, which cannot run inside the migrator's
  transaction.
- **`lower(email)` in `lib/auth/users.ts` is still a scan** — the known 6.1 follow-up,
  not tenant-scoped, and explicitly excluded here.
- **The dev branch is not migrated yet**, per the spec ("after merge"): `HANDOFF.md` now
  says to run `npm run db:migrate` for `0005`, and that the file is additive.
- **Prettier reflowed the four schema files** (~660 diff lines for nineteen one-line
  additions) because a third `pgTable` argument breaks the compact call form; the files
  were prettier-clean before, so this is the formatter's own churn, not a hidden change
  — `git diff -w` shows one import plus one line per table.
