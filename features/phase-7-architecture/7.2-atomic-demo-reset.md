# Feature 7.2: Atomic demo reset

**Phase:** 7 — Architecture
**Status:** completed
**Estimated effort:** 4–6 hours
**Depends on:** 0.5
**Blocks:** none (7.3–7.5 do not require it; do not start them in parallel)

## Goal

Reset demo is one Neon HTTP transaction. If any wipe or reseed statement fails, the demo tenant is left as it was. CRM wipe matches Space and Rolodex (`DELETE WHERE tenantId`), not per-row deletes.

## Scope

Include:

- A real `runInTransaction` for production that collects statements and executes `db.batch([...])` (same atomicity signup already uses)
- Authenticated layout’s `resetDemo` call uses that runner (today it does not pass one; `defaultRunInTransaction` is `await work(undefined)`)
- CRM reset wipes with tenant-scoped deletes, like `lib/space/reset.ts` / `lib/rolodex/reset.ts`
- Memory-repo path unchanged: tests still inject an in-memory store / fake transaction
- Unit tests: a failing resetter does not keep earlier wipes; CRM no longer loops `listX` + `deleteX` on the Drizzle path
- Source-grep: `defaultRunInTransaction` is not a no-op

Exclude (for now):

- RLS (7.3 indexes only; RLS is a phase non-goal)
- Speeding up seed beyond batching; no new seed content
- Reset for owner or member
- Changing who sees the Reset demo button
- `db.transaction()` (the driver throws)
- Playwright that clicks Reset demo unless an existing spec already covers it — this feature’s gate is unit tests + build. Say so in Verification.

## Files to create

- Optional: `lib/db/batch-transaction.ts` (or similar) — the Neon HTTP batch runner, tested with a stub `Database` like signup’s 23505 tests
- `lib/tenancy/reset-demo` tests extended; `lib/crm/reset.test.ts` for the wipe shape

## Files to modify

- `lib/tenancy/reset-demo.ts` — production runner
- `app/(authenticated)/layout.tsx` — pass the runner into `resetDemo`
- `lib/crm/reset.ts` — tenant-scoped deletes on the Drizzle path
- `lib/space/reset.ts`, `lib/rolodex/reset.ts`, `lib/crm/seed.ts`, `lib/space/seed.ts`, `lib/rolodex/seed.ts` — only as needed so wipe+reseed statements participate in the batch (do not rewrite seed content)
- `lib/crm/reset.test.ts`, `lib/tenancy/reset-demo.test.ts`

## Spec

1. `resetDemo(getSession, extra)` still: `requireTenant`; throw `Forbidden` unless `role === "demo"`; ignore client `tenantId`.
2. When `extra.runInTransaction` is omitted, the default runner must run the resetters’ writes as one `db.batch`. It must not be `await work(undefined)` with each resetter calling `getDb()` on its own.
3. The batch includes, for the demo `tenantId` only: delete CRM rows, delete Space rows, delete Rolodex rows, then the seed inserts for those three apps. Owner data is unreachable (role check + that `tenantId`).
4. CRM Drizzle wipe is `delete from organizations/contacts/deals/activities where tenantId = ?` (order that respects FKs, same idea as Space’s `views → … → pages`). Do not `listActivities` then `deleteActivity` per id on the Drizzle path.
5. Memory repo: wipe in memory then `seedX(tenantId, repo)` as today. Injected `runInTransaction` in existing tests still rolls back on a thrown resetter.
6. If `db.batch` throws, the helper throws and the layout still returns `{ ok: false, message: "Reset failed." }`. No partial commit from that batch.
7. Do not log row contents. Do not take `tenantId` from the form.

If Neon’s batch has a practical size limit, chunk into successive batches only after documenting it in the spec’s Shipped notes, and keep wipe-all-three in the first batch so a failed seed cannot sit on a half-wiped CRM while Space still has old rows. Prefer one batch.

## Shipped notes

`resetDemo` is now one Neon transaction. `lib/db/batch-transaction.ts` adds a
`WriteBatch` — a write that is collected, not run — plus `createBatchRunner(getDb)`,
which is `resetDemo`'s production `runInTransaction`. Each app's resetter and seed
thread a trailing `opts?: WriteOpts` through the `createX` helpers, so a batched
reset builds every statement (app-generated ids, seed-assigned positions) and the
runner sends them in one `db.batch([...])`. Nothing touches the database until then:
a failure anywhere rolls the whole thing back, so the demo tenant can no longer end
up half-wiped. CRM's wipe stopped being `listActivities` → `deleteActivity` per row
and is now four tenant-scoped deletes like Space and Rolodex.

**Measured**: the whole reset is **one batch of 717 statements** (18 deletes in FK
order, 699 inserts — 3 orgs, 4 contacts, 6 deals, 4 activities, 32 people and their
children, 51 pages, 499 blocks, 11 properties, 14 options, 61 row values, 3 views),
about 89 KB of SQL and 4,767 bind parameters. The spec allows chunking only after a
practical limit shows up; it did not, so it stays one batch.

Live walk against the Neon **dev** branch (dev server on the repo's own `.env`,
demo credentials, no value printed):

- one Reset demo click → one `POST` on `app/(authenticated)/layout.tsx`, **~1.1 s**
  of application time, no server error, no client console error;
- the Space tree went from 44 sidebar links (accumulated e2e rows) to **38**, and the
  Home page's id changed — the wipe and the reseed both really ran, and they ran as
  one request;
- CRM listed **3** organizations and Rolodex **32** people afterwards, so all three
  resetters participated in the same batch;
- a second reset produced identical counts (no duplication, nothing left behind).

Notable design decisions and their reasons:

- **An explicitly bound memory store wins over the batch.** `resetCrm(tx, tenantId, repo)`
  checks `repo` (or a repo-shaped `tx`) first, and only then the batch. Production
  resetters are registered with no repo, so they always batch; tests that bind a repo
  never need a database at all — which is also what made the default runner testable.
- **The Space seed assigns its own positions.** A batched reseed cannot ask the
  database for `max(position)`: while statements are still being collected the rows it
  is about to insert are not visible to any query, and the wipe travels in that same
  batch. Positions now come from a per-parent counter the seed keeps (`page:`,
  `block:`, `property:`, `option:` namespaces), which is deterministic and drops the
  **575** position reads main's seed issued per reset — 51 pages + 499 blocks + 11
  properties + 14 options, one `select max(...)` each; the batched seed issues none.
  This is not a position-value change: main's reset `await`ed the wipes before it
  seeded, so its `max(position)` always saw an empty table too, and the new counter
  produces the same 0..n ordering (verified: every parent's children are contiguous
  from 0, no duplicate `(parentId, position)`). The tree's page ids travel back from
  `seedTree` for the same reason: "Trip Planner" hangs off "Travel" without a
  `listPages` read.
- **A batched write must bring its own position.** The four Space creators and
  `createDeal` compute a default (`nextPagePosition`, `nextPosition`,
  `nextBoardOrder`) by reading the database when no repo is bound, so with a batch
  open and no value given they would read pre-wipe rows — or throw `"… store
  required"` in a unit test. Each now refuses that up front (`createPage needs an
  explicit \`position\` when its writes are collected into a batch`), which both the
  seeds and the tests exercise. Found by the quality review, not by a failing test.
- **`insert` is collected without `.returning()`.** The row is built (with its id) in
  application code before it is collected, so the seed can keep using the returned
  row to build its children — the same reason signup generates the tenant id itself.
- **ADR-0002 got a one-line tense fix** in this PR: the "known deviation" it names
  (`defaultRunInTransaction` being a no-op) is the thing 7.2 closes, and leaving it
  reading "today's `resetDemo`" would have made an accepted record false. No decision
  in any ADR changed.

### Deliberate limits

- **Two files are beyond the spec's "Files to create" / "Files to modify" lists, and
  both are consequences of the mechanism the spec describes.** `opts?: WriteOpts` had
  to be threaded through the 18 `createX` helpers in `lib/{crm,space,rolodex}/queries.ts`,
  because collecting an insert instead of awaiting one *is* a branch in the write path —
  the spec's Include list says "collects statements and executes `db.batch`" without
  naming the modules that make that possible. `lib/db/batch-test-helpers.ts` is the
  offline `Database` recorder the batch tests need (the spec allowed
  `batch-transaction.ts` "or similar"). The Exclude line "speeding up seed beyond
  batching" is the third: the position refactor is *required* by batching, not a speed
  project, though it does drop the reads.
- **The rollback itself is Neon's, not ours.** Unit tests prove the collection, the
  single-call shape, and that a failure reaches the caller with no statement-by-statement
  retry; they cannot prove that Postgres rolled a partly-applied batch back. That
  guarantee is Neon's transaction endpoint, reached through `drizzle-orm/neon-http`
  `session.batch` → `client.transaction`. Deliberately **not** exercised by injecting a
  failing statement into the live path: a real failure would have to come from a
  deliberate corruption of the seed, and the failure mode it would test (does Neon roll
  back?) is the same one signup has relied on since 6.1. The test names were tightened
  so they claim what they can observe — a stub `db.batch` that throws rejects and is
  attempted once, nothing more.
- **A caller that injects a runner passing neither a store nor a batch gets three
  per-app batches.** `resetX` self-flushes when it is handed something that is neither
  a memory repo nor a `WriteBatch`, which is what the standalone Drizzle path and the
  `"… store required"` test need. Production cannot reach it — the default runner
  always hands over a batch — but a future injected runner that passed `undefined`
  would restore a three-transaction reset. Making the resetters throw in that case is
  the tightening to consider if another runner ever appears.
- **Nothing asserts the statement count stays sane.** 717 is measured, not pinned; if a
  future seed doubles it, no test complains. A ceiling assertion (say, "fewer than
  2,000 statements") would be the cheap guard if that ever looks likely.
- **The two `deleteTenantRows` helpers and the three `wipeTenant` copies are the same
  function three times.** Colocating them belongs with 7.4's query-module split; doing
  it here would have meant touching every app's reset for a cosmetic gain.
- **`db.transaction()` is still forbidden**, and the batch is the only atomic write;
  the runner is synchronous collection followed by one call, so a resetter cannot read
  a row and decide its next statement. Nothing in the three resetters needs to.
- **The source-grep tests are the only thing pinning the production default.** The
  behavioural tests inject `createBatchRunner` themselves, so `reset-demo.test.ts`
  asserts the string `createBatchRunner(getDb)` as well — the same bargain 5.7 and 7.1
  struck, and it breaks on a reformat that changes that call, not on a behaviour
  change. A `defaultRunInTransaction` export would let a test drive the real one.
