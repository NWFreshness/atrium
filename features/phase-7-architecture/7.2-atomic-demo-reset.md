# Feature 7.2: Atomic demo reset

**Phase:** 7 — Architecture
**Status:** specced
**Estimated effort:** 4–6 hours
**Depends on:** 0.5
**Blocks:** none (7.3–7.5 do not require it; do not start them in parallel)

## Goal

Reset demo is one Neon HTTP transaction. If any wipe or reseed statement fails, the demo tenant is left as it was. CRM wipe matches Space and Rolodex (`DELETE WHERE tenantId`), not per-row deletes.

## Scope

Include:

- A real `runInTransaction` for production that collects statements and executes `db.batch([...])` (same atomicity signup already uses)
- Authenticated layout’s `resetDemo` call uses that runner (today it does not pass one; `defaultRunInTransaction` is `await work(undefined)`)
- CRM reset wipes with tenant-scoped deletes, like `lib/space/reset.ts` / `lib/rolodex/reset.ts`
- Memory-repo path unchanged: tests still inject an in-memory store / fake transaction
- Unit tests: a failing resetter does not keep earlier wipes; CRM no longer loops `listX` + `deleteX` on the Drizzle path
- Source-grep: `defaultRunInTransaction` is not a no-op

Exclude (for now):

- RLS (7.3 indexes only; RLS is a phase non-goal)
- Speeding up seed beyond batching; no new seed content
- Reset for owner or member
- Changing who sees the Reset demo button
- `db.transaction()` (the driver throws)
- Playwright that clicks Reset demo unless an existing spec already covers it — this feature’s gate is unit tests + build. Say so in Verification.

## Files to create

- Optional: `lib/db/batch-transaction.ts` (or similar) — the Neon HTTP batch runner, tested with a stub `Database` like signup’s 23505 tests
- `lib/tenancy/reset-demo` tests extended; `lib/crm/reset.test.ts` for the wipe shape

## Files to modify

- `lib/tenancy/reset-demo.ts` — production runner
- `app/(authenticated)/layout.tsx` — pass the runner into `resetDemo`
- `lib/crm/reset.ts` — tenant-scoped deletes on the Drizzle path
- `lib/space/reset.ts`, `lib/rolodex/reset.ts`, `lib/crm/seed.ts`, `lib/space/seed.ts`, `lib/rolodex/seed.ts` — only as needed so wipe+reseed statements participate in the batch (do not rewrite seed content)
- `lib/crm/reset.test.ts`, `lib/tenancy/reset-demo.test.ts`

## Spec

1. `resetDemo(getSession, extra)` still: `requireTenant`; throw `Forbidden` unless `role === "demo"`; ignore client `tenantId`.
2. When `extra.runInTransaction` is omitted, the default runner must run the resetters’ writes as one `db.batch`. It must not be `await work(undefined)` with each resetter calling `getDb()` on its own.
3. The batch includes, for the demo `tenantId` only: delete CRM rows, delete Space rows, delete Rolodex rows, then the seed inserts for those three apps. Owner data is unreachable (role check + that `tenantId`).
4. CRM Drizzle wipe is `delete from organizations/contacts/deals/activities where tenantId = ?` (order that respects FKs, same idea as Space’s `views → … → pages`). Do not `listActivities` then `deleteActivity` per id on the Drizzle path.
5. Memory repo: wipe in memory then `seedX(tenantId, repo)` as today. Injected `runInTransaction` in existing tests still rolls back on a thrown resetter.
6. If `db.batch` throws, the helper throws and the layout still returns `{ ok: false, message: "Reset failed." }`. No partial commit from that batch.
7. Do not log row contents. Do not take `tenantId` from the form.

If Neon’s batch has a practical size limit, chunk into successive batches only after documenting it in the spec’s Shipped notes, and keep wipe-all-three in the first batch so a failed seed cannot sit on a half-wiped CRM while Space still has old rows. Prefer one batch.

## Implementation notes

- Copy signup’s batch pattern: build every statement up front; generate seed ids in application code if a later insert needs them.
- Space/Rolodex already `delete().where(eq(table.tenantId, tenantId))`. Reuse that. CRM is the outlier.
- Module-load `registerCrmDemoResetter()` stays. Do not rename exports while `next dev` is running without restarting it (stale-export half-wipe).
- Unit tests must pass without `DATABASE_URL`. Do not claim the live Neon batch is proven until a later hand walk or e2e; write that limit in Shipped notes.
- After merge, a demo user should Reset demo once on the dev branch to confirm; do not paste `DATABASE_URL`.
