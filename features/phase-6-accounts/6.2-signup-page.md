# Feature 6.2: Signup page and auto sign-in

**Phase:** 6 — Accounts
**Status:** completed
**Estimated effort:** 3–5 hours
**Depends on:** 6.1
**Blocks:** 6.4

## Goal

When the flag is on, a Workroom-styled `/signup` creates a member and signs them in. When it is off, nothing is created and login does not advertise signup.

## Scope

Include:

- `/signup` page cloning the login stage (brass A watermark, brand row, `atrium-field` / `atrium-btn-primary`)
- Server action: `signUp` then `signIn("credentials", { email, password, redirectTo: "/" })`
- Login footer: “Create an account” link only when `isSignupEnabled`; drop “Two accounts · no signup”
- `auth.config` `authorized`: unauthenticated `/signup` is allowed; authenticated `/signup` redirects to `/` (same pattern as `/login`)
- Closed state: no insert; no create-account link; `/signup` shows closed copy or redirects to `/login`

Exclude (for now):

- `changePassword` / `/settings` (6.3)
- Playwright journey (6.4) — unit/component tests here are enough
- OAuth, captcha, mailer

## Files to create

- `app/signup/page.tsx`
- `app/signup/signup-form.tsx` (client) if the page is a server component
- `app/signup/actions.ts`
- Reuse `app/login/login.module.css` (or extract a shared unauth-stage module). Do not invent a `signup-` CSS namespace.

## Files to modify

- `auth.config.ts` — public `/signup`
- `app/login/page.tsx` — footer / link
- `middleware.ts` — only if the matcher would block `/signup` (today it uses `authorized`; prefer config, not a new matcher exception list)

## Spec

1. Form fields: Email, Password, Confirm password. Labels stay accessible (`getByLabel`). Submit button “Create account”.
2. Confirm mismatch: stay on `/signup`, specific “Passwords do not match”, no session.
3. Map `signUp` codes: `weak_password` and `invalid_email` may be specific; `password_too_long` should name the limit rather than reuse the minimum-length copy; `unavailable` and `closed` are generic (“Could not create account” / closed page). Never echo “email already exists”.
4. Happy path: member session, land on `/`. Launcher is empty of demo seed. No “Reset demo” control (`role !== "demo"`).
5. Authenticated GET `/signup` → `/`.
6. Flag off: action must not call `signUp` successfully (helper already throws `closed`); the page must not show the create form as if it would work. Prefer a closed message over a working-looking form.
7. `signIn` after a successful `signUp` uses the same Credentials provider as login. If `signIn` throws `AuthError`, show a generic failure — do not leave an orphaned session.

## Acceptance criteria

1. [x] Unauthenticated GET `/signup` does not redirect to `/login` when the flag is on
2. [x] Flag on: valid form creates a member, sets a session, and lands on `/`
3. [x] Flag on: login shows a “Create an account” link to `/signup`
4. [x] Flag off: login has no create-account link; `/signup` does not insert a user
5. [x] Duplicate email shows the generic could-not-create message and stays unsigned-in
6. [x] Confirm mismatch and short password stay on `/signup` with specific copy
7. [x] Authenticated `/signup` redirects to `/`
8. [x] Signup chrome uses Workroom login tokens/classes; no new CSS namespace
9. [x] `env -u DATABASE_URL npm test` and `AUTH_SECRET=ci-build-placeholder npm run build` pass

## Implementation notes

- Copy `app/login/actions.ts` for the `signIn` / `AuthError` catch. NextAuth `signIn` with `redirectTo` throws a redirect that must be rethrown (same as login).
- Read `isSignupEnabled(process.env)` per request; do not cache “open” at module load.
- Do not add signup to the top-nav app list.

## Shipped notes

Verified against the running app and the Neon dev branch, not just unit tests. `npm run db:migrate` was applied to the dev branch first (6.1's migration 0004).

Live walk (agent-browser, dev server with `AUTH_SIGNUP_ENABLED=true`):

- short password → `Password must be at least 12 characters.`, stays on `/signup`, and the email field keeps its value
- confirm mismatch → `Passwords do not match.`, stays on `/signup`
- valid form → creates the member, signs in, lands on `/` with the member's email in the identity chip and **no Reset demo**
- logout → `/login`, footer now reads `Create an account`
- reusing the same email → `Could not create account.`, no session
- authenticated `GET /signup` → redirects to `/`
- flag off (plain `npm run dev`) → `/signup` serves `Signups closed` with **zero** form fields, and `/login` has no `/signup` link and reads `Signups closed` in the footer
- owner login still works after the login page changes; owner still sees no Reset demo

Database read-back for the created member: `role: member`, its own tenant named after the email, `passwordHash` starts `$2b$` and is not the plaintext, `users` is owner + demo + member, and the new tenant holds `0` organizations / contacts / pages / people. **This is the first real execution of 6.1's `db.batch` insert and its 23505 mapping**, so that previously-unproven path is now exercised — the duplicate attempt above is the pre-check path, not the constraint path.

Two things worth knowing:

- `/signup` and `/login` needed `export const dynamic = "force-dynamic"`. Without it both prerendered, so `isSignupEnabled(process.env)` was baked at build time and a closed build would keep serving whatever it built with. A source-grep test in `app/signup/signup.test.ts` locks the export.
- `app/login/login.module.css` became `app/auth-stage.module.css`, imported bound by both pages. Login's alert and submit button also moved off inline styles onto `auth-alert` / `auth-submit`, so the two pages cannot drift.
- The dev database still contains the `e2e-62-…@atrium.local` member and its tenant from this walk. Leave it or wipe it — 6.4 creates a fresh one per run by design.
