# Feature 6.2: Signup page and auto sign-in

**Phase:** 6 — Accounts
**Status:** specced
**Estimated effort:** 3–5 hours
**Depends on:** 6.1
**Blocks:** 6.4

## Goal

When the flag is on, a Workroom-styled `/signup` creates a member and signs them in. When it is off, nothing is created and login does not advertise signup.

## Scope

Include:

- `/signup` page cloning the login stage (brass A watermark, brand row, `atrium-field` / `atrium-btn-primary`)
- Server action: `signUp` then `signIn("credentials", { email, password, redirectTo: "/" })`
- Login footer: “Create an account” link only when `isSignupEnabled`; drop “Two accounts · no signup”
- `auth.config` `authorized`: unauthenticated `/signup` is allowed; authenticated `/signup` redirects to `/` (same pattern as `/login`)
- Closed state: no insert; no create-account link; `/signup` shows closed copy or redirects to `/login`

Exclude (for now):

- `changePassword` / `/settings` (6.3)
- Playwright journey (6.4) — unit/component tests here are enough
- OAuth, captcha, mailer

## Files to create

- `app/signup/page.tsx`
- `app/signup/signup-form.tsx` (client) if the page is a server component
- `app/signup/actions.ts`
- Reuse `app/login/login.module.css` (or extract a shared unauth-stage module). Do not invent a `signup-` CSS namespace.

## Files to modify

- `auth.config.ts` — public `/signup`
- `app/login/page.tsx` — footer / link
- `middleware.ts` — only if the matcher would block `/signup` (today it uses `authorized`; prefer config, not a new matcher exception list)

## Spec

1. Form fields: Email, Password, Confirm password. Labels stay accessible (`getByLabel`). Submit button “Create account”.
2. Confirm mismatch: stay on `/signup`, specific “Passwords do not match”, no session.
3. Map `signUp` codes: `weak_password` and `invalid_email` may be specific; `password_too_long` should name the limit rather than reuse the minimum-length copy; `unavailable` and `closed` are generic (“Could not create account” / closed page). Never echo “email already exists”.
4. Happy path: member session, land on `/`. Launcher is empty of demo seed. No “Reset demo” control (`role !== "demo"`).
5. Authenticated GET `/signup` → `/`.
6. Flag off: action must not call `signUp` successfully (helper already throws `closed`); the page must not show the create form as if it would work. Prefer a closed message over a working-looking form.
7. `signIn` after a successful `signUp` uses the same Credentials provider as login. If `signIn` throws `AuthError`, show a generic failure — do not leave an orphaned session.

## Acceptance criteria

1. [ ] Unauthenticated GET `/signup` does not redirect to `/login` when the flag is on
2. [ ] Flag on: valid form creates a member, sets a session, and lands on `/`
3. [ ] Flag on: login shows a “Create an account” link to `/signup`
4. [ ] Flag off: login has no create-account link; `/signup` does not insert a user
5. [ ] Duplicate email shows the generic could-not-create message and stays unsigned-in
6. [ ] Confirm mismatch and short password stay on `/signup` with specific copy
7. [ ] Authenticated `/signup` redirects to `/`
8. [ ] Signup chrome uses Workroom login tokens/classes; no new CSS namespace
9. [ ] `env -u DATABASE_URL npm test` and `AUTH_SECRET=ci-build-placeholder npm run build` pass

## Implementation notes

- Copy `app/login/actions.ts` for the `signIn` / `AuthError` catch. NextAuth `signIn` with `redirectTo` throws a redirect that must be rethrown (same as login).
- Read `isSignupEnabled(process.env)` per request; do not cache “open” at module load.
- Do not add signup to the top-nav app list.
