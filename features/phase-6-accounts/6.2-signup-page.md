# Feature 6.2: Signup page and auto sign-in

**Phase:** 6 — Accounts
**Status:** completed
**Estimated effort:** 3–5 hours
**Depends on:** 6.1
**Blocks:** 6.4

## Goal

When the flag is on, a Workroom-styled `/signup` creates a member and signs them in. When it is off, nothing is created and login does not advertise signup.

## Scope

Include:

- `/signup` page cloning the login stage (brass A watermark, brand row, `atrium-field` / `atrium-btn-primary`)
- Server action: `signUp` then `signIn("credentials", { email, password, redirectTo: "/" })`
- Login footer: “Create an account” link only when `isSignupEnabled`; drop “Two accounts · no signup”
- `auth.config` `authorized`: unauthenticated `/signup` is allowed; authenticated `/signup` redirects to `/` (same pattern as `/login`)
- Closed state: no insert; no create-account link; `/signup` shows closed copy or redirects to `/login`

Exclude (for now):

- `changePassword` / `/settings` (6.3)
- Playwright journey (6.4) — unit/component tests here are enough
- OAuth, captcha, mailer

## Files to create

- `app/signup/page.tsx`
- `app/signup/signup-form.tsx` (client) if the page is a server component
- `app/signup/actions.ts`
- Reuse `app/login/login.module.css` (or extract a shared unauth-stage module). Do not invent a `signup-` CSS namespace.

## Files to modify

- `auth.config.ts` — public `/signup`
- `app/login/page.tsx` — footer / link
- `middleware.ts` — only if the matcher would block `/signup` (today it uses `authorized`; prefer config, not a new matcher exception list)

## Spec

1. Form fields: Email, Password, Confirm password. Labels stay accessible (`getByLabel`). Submit button “Create account”.
2. Confirm mismatch: stay on `/signup`, specific “Passwords do not match”, no session.
3. Map `signUp` codes: `weak_password` and `invalid_email` may be specific; `password_too_long` should name the limit rather than reuse the minimum-length copy; `unavailable` and `closed` are generic (“Could not create account” / closed page). Never echo “email already exists”.
4. Happy path: member session, land on `/`. Launcher is empty of demo seed. No “Reset demo” control (`role !== "demo"`).
5. Authenticated GET `/signup` → `/`.
6. Flag off: action must not call `signUp` successfully (helper already throws `closed`); the page must not show the create form as if it would work. Prefer a closed message over a working-looking form.
7. `signIn` after a successful `signUp` uses the same Credentials provider as login. If `signIn` throws `AuthError`, the member exists but has no session: say so plainly, and stop offering to create the account again (see the Shipped notes — the state gained `accountCreated` for this).

## Acceptance criteria

1. [x] Unauthenticated GET `/signup` does not redirect to `/login` when the flag is on
2. [x] Flag on: valid form creates a member, sets a session, and lands on `/`
3. [x] Flag on: login shows a “Create an account” link to `/signup`
4. [x] Flag off: login has no create-account link; `/signup` does not insert a user
5. [x] Duplicate email shows the generic could-not-create message and stays unsigned-in
6. [x] Confirm mismatch and short password stay on `/signup` with specific copy
7. [x] Authenticated `/signup` redirects to `/`
8. [x] Signup chrome uses Workroom login tokens/classes; no new CSS namespace
9. [x] `env -u DATABASE_URL npm test` and `AUTH_SECRET=ci-build-placeholder npm run build` pass

## Implementation notes

- Copy `app/login/actions.ts` for the `signIn` / `AuthError` catch. NextAuth `signIn` with `redirectTo` throws a redirect that must be rethrown (same as login).
- Read `isSignupEnabled(process.env)` per request; do not cache “open” at module load.
- Do not add signup to the top-nav app list.

Database read-back for the created member: `role: member`, its own tenant named after the email, `passwordHash` starts `$2b$` and is not the plaintext, `users` is owner + demo + member, and the new tenant holds `0` organizations / contacts / pages / people. **This is the first real execution of 6.1's `db.batch` insert.** The `23505` → `unavailable` mapping was *not* exercised by any of this — the duplicate attempt is caught by the case-insensitive pre-check, so that branch is still covered only by the stub-`Database` unit tests from 6.1. Do not claim otherwise.

### Changes made in response to review

- **Login is now case-insensitive on both sides** (`lib/auth/users.ts` uses `lower(email) = lower(input)`). Signup treats a case-variant as the same mailbox but stores the address verbatim, so a byte-exact login would have stranded a member who signed up as `Tyler@Example.com` and later typed `tyler@example.com` — and this phase has no password reset. Verified live: signing in with the uppercase form of an existing member's address reached `/`. This is outside the "Files to modify" list below; it is a one-line change to the login lookup that 6.1's verbatim-store decision made necessary.
- **`/login` echoes the typed email after a failed attempt** (`app/login/actions.ts` now returns `{ error, email }`, the form sets `defaultValue={state.email}`). React 19 clears uncontrolled fields when a form action completes, so every fumble used to wipe both fields. The password field is still cleared. The error string is unchanged (`Invalid email or password`) because `e2e/login.spec.ts` asserts it.
- **`accountCreated` in `SignUpState`.** When `signUp` succeeds and `signIn` then throws, the form is replaced by the alert plus a `Sign in` link, instead of offering `Create account` again — a second submit would have answered `Could not create account.`, contradicting the first message.
- **The confirmation mismatch is now caught in the browser before the round trip** (`onSubmit` + `event.preventDefault()`, same shared copy). React 19's post-action reset otherwise forces the member to retype two long passwords. The server still compares them; the client check is an optimization, and the live walk confirmed no `POST /signup` is sent for a mismatch.
- **`signUp` reads `deps.repo` once.** `createDefaultSignUpDeps` builds the repo lazily, so the previous `deps.repo.findByEmail` + `deps.repo.createMember` created two Neon clients per signup.
- New tests: `app/login/login.test.ts` (labels/autocomplete contract, email echo, generic copy, the redirect rethrow, flag-gated signup link) and three added cases in `app/signup/signup.test.ts` that assert the flag ternaries and the `accountCreated` CTA swap — the earlier checks only used `toContain`, which a link rendered unconditionally would have passed.

Still open, deliberately:

- **`app/signup/actions.ts` and `app/login/actions.ts` have no automated test.** Both are `"use server"` modules that import `@/auth`, and neither takes an injectable seam, so unit-testing them needs a mocking layer this phase did not add. Their behaviour is covered by the live walk and, for login, by `e2e/login.spec.ts`; the mapping and validation logic they call is unit-tested in `lib/auth/`.
- **`/signup` and `/login` needed `export const dynamic = "force-dynamic"`.** Without it both prerendered, so `isSignupEnabled(process.env)` was baked at build time and a closed build would keep serving whatever it built with. A source-grep test locks the export.
- **`app/login/login.module.css` became `app/auth-stage.module.css`**, imported bound by both pages, and login's alert/submit moved off inline styles onto `auth-alert` / `auth-submit`.
- The `users_email_unique` index is still case-sensitive, so concurrent case-variant signups can race the pre-check. A `lower(email)` unique index closes it; that is a schema change this spec did not authorize.
- The dev database now holds two walk-created members (`e2e-62-…`, `e2e-62b-…`). 6.4 creates a fresh one per run by design.
