# Feature 6.3: Change password and settings

**Phase:** 6 — Accounts
**Status:** specced
**Estimated effort:** 3–4 hours
**Depends on:** 6.2
**Blocks:** 6.4

## Goal

Every signed-in role can change their password from `/settings` without a mailer.

## Scope

Include:

- `changePassword(userId, { current, next }, deps)` in `lib/auth/`
- Unit tests without `DATABASE_URL`
- Authenticated `/settings` page: current password, new password, confirm
- Identity-chip email becomes a link to `/settings` (not a fifth app tab)
- Reuse the 6.1 12-character rule and bcrypt `verifyPassword` / `hashPassword`

Exclude (for now):

- Forgot-password, change-email, delete account
- Playwright (6.4)
- New CSS namespace; Settings is not in the Home/CRM/Space/Rolodex/Groove strip

## Files to create

- `lib/auth/change-password.ts`
- `lib/auth/change-password.test.ts`
- `app/(authenticated)/settings/page.tsx`
- `app/(authenticated)/settings/actions.ts`
- settings form client component if needed

## Files to modify

- `components/atrium-nav.tsx` — email → `/settings`
- `e2e/workroom.spec.ts` — only if the identity chip link would break the existing top-nav walk (it must not: walk is Home/CRM/Space/Rolodex/Groove by exact name)

## Spec

1. `changePassword` loads the user by `userId` (not email, not client tenant). Missing user → fail closed.
2. Wrong current password → `wrong_current`. Do not reveal whether the user id existed beyond that.
3. `next` shorter than 12 → `weak_password`. `next === current` → `unchanged`.
4. Success: write a new bcrypt hash; do not write plaintext. Session JWT stays valid (no forced logout).
5. Settings form maps: `wrong_current` → generic “Could not update password”; mismatch confirm / weak / unchanged → specific. Success banner stays on `/settings`.
6. Unauthenticated `/settings` → `/login` (authenticated route group).
7. Owner, demo, and member all may use it. Demo reset is unrelated and stays demo-only.
8. Nav: the identity email is a `Link` to `/settings`. Accessible name is the email (or “Account settings” plus visually the email). Do not add a “Settings” item to `APPS`.

## Acceptance criteria

1. [ ] Wrong current password does not change the hash
2. [ ] Valid change updates the hash so `verifyPassword(next, hash)` is true and the old password is not
3. [ ] Weak and unchanged next passwords are rejected
4. [ ] `/settings` is behind auth and uses Workroom field/button classes
5. [ ] Identity chip links to `/settings`; top-nav app labels unchanged
6. [ ] Reset demo still renders only for `role === "demo"`
7. [ ] `env -u DATABASE_URL npm test` and `AUTH_SECRET=ci-build-placeholder npm run build` pass
8. [ ] Existing login/launcher Playwright still pass (run if env is set)

## Implementation notes

- Inject lookup + verify + hash in unit tests (same style as `authorizeCredentials`).
- Do not take `userId` from the form; take it from `requireTenant(() => auth())`.
- Confirm-password matching can stay in the action; `changePassword` does not need a confirm argument.
