**Phase:** 6 — Accounts
**Status:** completed
**Estimated effort:** 3–4 hours
**Depends on:** 6.2

## Goal

Every signed-in role can change their password from `/settings` without a mailer.

## Scope

Include:

- `changePassword(userId, { current, next }, deps)` in `lib/auth/`
- Unit tests without `DATABASE_URL`
- Authenticated `/settings` page: current password, new password, confirm
- Identity-chip email becomes a link to `/settings` (not a fifth app tab)
- Reuse the 6.1 12-character rule and bcrypt `verifyPassword` / `hashPassword`

Exclude (for now):

- Forgot-password, change-email, delete account
- Playwright (6.4)
- New CSS namespace; Settings is not in the Home/CRM/Space/Rolodex/Groove strip

## Spec

1. `changePassword` loads the user by `userId` (not email, not client tenant). Missing user → fail closed.
2. Wrong current password → `wrong_current`. Do not reveal whether the user id existed beyond that.
3. `next` shorter than 12 → `weak_password`. `next === current` → `unchanged`.
4. Success: write a new bcrypt hash; do not write plaintext. Session JWT stays valid (no forced logout).
5. Settings form maps: `wrong_current` → generic “Could not update password”; mismatch confirm / weak / unchanged → specific. Success banner stays on `/settings`.
6. Unauthenticated `/settings` → `/login` (authenticated route group).
7. Owner, demo, and member all may use it. Demo reset is unrelated and stays demo-only.
8. Nav: the identity email is a `Link` to `/settings`. Accessible name is the email (or “Account settings” plus visually the email). Do not add a “Settings” item to `APPS`.

## Acceptance criteria

1. [x] Wrong current password does not change the hash
2. [x] Valid change updates the hash so `verifyPassword(next, hash)` is true and the old password is not
3. [x] Weak and unchanged next passwords are rejected

5. [x] Identity chip links to `/settings`; top-nav app labels unchanged
6. [x] Reset demo still renders only for `role === "demo"`

## Implementation notes

- Inject lookup + verify + hash in unit tests (same style as `authorizeCredentials`).
- Do not take `userId` from the form; take it from `requireTenant(() => auth())`.
- Confirm-password matching can stay in the action; `changePassword` does not need a confirm argument.

## Shipped notes

Verified against the running app and the Neon dev branch, not just unit tests.

Two independent subagent reviews ran before the commit: spec compliance PASS on all 8 criteria with no scope violation, and a quality review that raised one blocking defect plus three should-fix items — all four fixed, and this section records the corrected state.

Live walk (agent-browser, dev server with `AUTH_SIGNUP_ENABLED=true`), as a fresh throwaway member:

- unauthenticated `GET /settings` → `307` to `/login?callbackUrl=/settings`
- the identity chip is a `Link` to `/settings`; the member sees no Reset demo
- wrong current password → `Could not update password.`, stays on `/settings`
- mismatched confirmation → `Passwords do not match.`, and the dev-server log holds **exactly two** `changePasswordAction` requests for the whole session (the wrong attempt and the successful one) — the mismatch never reached the server, and the fields were not reset
- valid change → `Password updated.`, still signed in, fields cleared
- logout → the **new** password reaches `/`; the **old** password gets the generic `Invalid email or password`

Database read-back (`tsx` script against the dev branch, deleted after running): the member row's `passwordHash` is `$2b$10$…`, 60 chars, equal to neither plaintext.

**This is the first real execution of the Drizzle `updatePasswordHash` path** — the live change wrote the hash through `createDrizzleChangePasswordRepository`, so the write is proven, not just the memory repo. The `unavailable` branch (a 0-row update) is reachable only in the read-then-write race and is covered by a stub repository test.

Deliberate limits and open items:

- **No session revocation, per spec §4.** A successful change leaves the current JWT and every other device's 30-day JWT valid; there is no `passwordChangedAt` claim and no session table. Recorded as the phase's session decision in `CURRENT_FEATURE.md`. "Sign out everywhere" needs an adapter or a token-version claim.
- `password_too_long` is an extra code beyond the three the spec names. It exists because 6.1 found that bcrypt silently truncates at 72 bytes, so without it two long passphrases would verify against each other; it maps to its own copy so the form does not call it "too short".
- The length rule counts UTF-16 units (`next.length`), inherited verbatim from 6.1's `assertPasswordStrength`: `"😀".repeat(6)` is 6 visible characters and passes as ≥12. Pre-existing, not a 6.3 regression — a `codePointAt`-based counter is the follow-up for both surfaces.
- Settings has no CSS module of its own (the spec excludes a new namespace); it composes the shared `atrium-` classes. Three classes were added to `app/workroom.css` — `.atrium-alert`, `.atrium-alert-ok`, `.atrium-narrow` — and `.atrium-panel` gained padding it had never had (repo-wide, only `/settings` uses it, so no cross-app blast radius).
- `lib/auth/change-password-messages.ts` + test and `app/(authenticated)/settings/settings.test.ts` are beyond the spec's "Files to create" list. The messages module exists for the reason `signup-messages.ts` does: `change-password.ts` imports Drizzle, and the client form must not reach that graph for a sentence — so the copy lives in a pure module and the type import is `import type` (now asserted, because dropping `type` would ship Drizzle to the browser while the old test still passed).
- The dev database now holds a third walk-created member (`e2e.63.…@atrium.local`) whose password was rotated by the walk. 6.4 creates a fresh one per run by design.
- **Found while reviewing 6.3, not fixed here (pre-existing, unrelated):** `components/rolodex/circles-board.tsx` (`"use client"`) value-imports `circleColumnStats` from `lib/rolodex/move-person.ts`, which value-imports `getPerson`/`updatePerson` from `queries.ts` — so `/rolodex/circles`'s client chunk carries `drizzle-orm` and `@neondatabase/serverless`. Same rule this feature's test enforces; it belongs to a Rolodex follow-up, not to Accounts.

### Changes made in response to review

- **The success banner could co-render with a later mismatch (blocking).** `mismatch` (local state) and `state.changed` (the last server return) are independent, and a client-blocked submit never runs the action — so after a successful change, a mismatched resubmit showed `Password updated.` in green next to `Passwords do not match.` in red: a success banner for a write that never happened. The success block is now gated `state.changed && !mismatch && !state.error`, with a test asserting the guard.
- **The browser-bundle test guarded the wrong file.** It only checked the form's direct imports, so the regression it names would slip through at the messages module, which is the form's actual gateway to the domain graph. The test now asserts every import in `change-password-messages.ts` is `import type`.
- **The auth-gate test tested a proxy.** It scanned `auth.config.ts` for the literal `"/settings"`, which would still pass if the middleware matcher stopped covering the route. It now asserts `PUBLIC_AUTH_PATHS` excludes `/settings` (the real constant) and that `middleware.ts` holds no `/settings` exception, and points at `auth.config.test.ts`, which already drives the real `authorized` callback for `/settings` in both session states.
- **The identity chip rendered permanently underlined.** It became a `<Link>` and `globals.css` has no anchor reset, so the email sat underlined at rest while the new hover rule was dead weight. `.atrium-nav-identity` now sets `text-decoration: none`.
- Also from the review: the `password_too_long` test now asserts the stored hash is untouched (the weak/unchanged tests already did), new cases accept the exact boundaries (12 characters, 72 bytes), and the copy test asserts the specific codes stay distinct from the generic failure.
