## Spec

1. Unique email per run (`e2e.accounts.<timestamp>@atrium.local`). Password ≥ 12 chars, not the owner/demo passwords.
2. Flag on: `/login` → Create an account → fill signup → land `/` → no Reset demo button → CRM/Space empty of demo seed names used in existing smokes (spot-check: demo org “Northwind” absent, or simply that Reset demo is absent and launcher is visible).
3. Same member: identity link → `/settings` → change password → logout → login with the **new** password reaches `/`. Old password fails with the generic login error.
4. Owner login still reaches `/`. Demo login still reaches `/` and still sees Reset demo.
5. Unauthenticated `/settings` → `/login`. Unauthenticated `/` still → `/login`.
6. `{ exact: true }` on nav labels. Do not add Settings to the 5.7 top-nav walk list.
7. `next build` typechecks `e2e/`, so run the build after editing the spec. Playwright `expect` timeout goes on the matcher, not the `expect()` second argument.

The suite cannot flip the flag mid-run (one Next process). Open-signup tests `test.skip` unless `AUTH_SIGNUP_ENABLED === "true"`. Closed UI can be asserted when the flag is not `true`. Unit tests already cover `signUp` throwing `closed`.

## Shipped notes

`e2e/accounts.spec.ts` (6 tests) plus the flag contract documented in `playwright.config.ts` and `.env.example`. `npm run db:migrate` was applied to the Neon dev branch first. Writing the journey also fixed a defect in already-merged 6.3 code: `change-password-form.tsx` carried a `//` comment among its JSX children, which renders as visible text on `/settings` — now a `{/* … */}` block, with an e2e guard that the page shows no `//`.

The matrix is two runs, because one Next process cannot flip the flag mid-suite:

- **Flag off** — `npx playwright test e2e/accounts.spec.ts` → 4 passed, 2 skipped. The open-signup journeys skip; the closed state is asserted: `/login` has no `Create an account` link and reads `Signups closed`, and `/signup` serves the closed heading with no form and no password field.
- **Flag on** — `AUTH_SIGNUP_ENABLED=true npx playwright test` (criterion 5) → **37 passed, 1 skipped, 1.4 m**, i.e. the whole suite, not just this file. The one skipped test is the closed one, which cannot run in the same process as the open journeys.

What the two journeys prove that no unit test can:

- signup writes a real member and its own tenant through the Drizzle `db.batch` path, and the session lands on `/` with that member's address as the identity chip, **no** Reset demo, and none of the demo seed in their tenant — `/crm/organizations` lists no `Northwind Logistics`, `Bluepeak Software`, or `Harbor & Lane` link. That assertion is on the organizations list rather than the dashboard on purpose: the dashboard only names an org through its open-deals chart, so it would stay green on a leak that never reached that one series.
- change-password runs end to end: wrong current password → `Could not update password.`; correct → `Password updated.` with the session still on `/settings` (no sign-out, no redirect — spec §4); repeating the current password → `Choose a password different from your current one.`; logout; the **old** password gets the generic login error; the **new** one reaches `/`. That last login is a bcrypt comparison against the hash the Drizzle repository wrote, so 6.3's write path — previously proven only by a hand walk — is now covered by an automated test, in a step that actually runs (see below).

Each journey signs up its own member on a fresh `Date.now()` address. That is deliberate: a retry that reused one member would land on a password the first attempt had already rotated and read as a product failure. With "unique email per run" and "do not delete the member", the dev tenant list grows by two per run; the `e2e.accounts.` prefix is what makes those rows identifiable.

Timeouts: navigations get 20 s (the loaded dev DB exceeds the 5 s default) and each journey raises the test-level cap to 120 s. Playwright's `expect()` second argument accepts only `{ message }`, so the timeout goes on the matcher — `npm run build` typechecks `e2e/`, which is the thing that catches a mistake there.

Deliberate limits:

- The suite cannot assert signup while the flag is off (no form exists) and cannot assert the closed page while it is on. The halves are mutually exclusive by process, which is why each carries its own `test.skip` rather than a shared guard.
- `AUTH_SIGNUP_ENABLED` is **not** forced in `playwright.config.ts`. Setting it in `webServer.env` would not even work: the spec reads the *runner's* env to choose its half, so the closed test would then run against an open server and fail. The config documents the two-run contract instead, including the `reuseExistingServer` caveat (an already-running dev server decides the flag, not the runner).
- **CI runs both halves.** `.github/workflows/ci.yml` gained a second Playwright step — `AUTH_SIGNUP_ENABLED=true npx playwright test e2e/accounts.spec.ts` — under the same secrets gate as the existing one. Without it the e2e job's `Run Playwright` would skip both signup journeys on every run (the flag is absent there), so a total regression of `signUp`/`changePassword` would have shipped green. That file is outside the spec's "Files to modify" list; it is here because criterion 5 is otherwise unenforceable. Note the `e2e` job remains inert until the repo has Actions secrets — every Playwright step in it is gated on `steps.e2e.outputs.ready`.
- Out of scope, as the spec says: OAuth click-through, visual diffs, deleting the members a run creates.

### Defects this feature's own run found

Writing the journey surfaced two things that no earlier test had caught:

- **6.3 shipped a visible code comment on `/settings`.** `change-password-form.tsx` carried a `//` explanation among the form's JSX children, where it is a text node rather than a comment, so the page rendered it verbatim above the success banner. Found from this journey's DOM snapshot, not from an assertion. Fixed to a `{/* … */}` block, and guarded: the journey now asserts `/settings` contains no `//` text at all. (The other `//` comments in the repo are inside function bodies — real comments — so this was the only occurrence.)
- **The first cut of the change-password helper was silently toothless.** After a successful change, React 19's post-action reset can land on top of Playwright's `fill`. The inputs are `required`, so a wiped field makes the browser block the submit with **no request at all**: the click reads as a no-op and the previous banner stays on screen. The `unchanged` assertion failed with "element not found" while the DOM still showed `Password updated.` — i.e. the test looked like a product bug and was a harness bug. The helper now waits for the reset, fills, asserts each value stuck, and only then clicks. This is the repo's own React-19 template lesson with the failure mode spelled out: a *required* field that empties out is worse than an empty value, because nothing reaches the server to be logged.

### Changes made in response to review

Two subagent reviews ran before the commit: spec compliance **PASS** on all 7 criteria and all 7 Spec rules, with no scope violation, and a quality review that raised one blocking item plus four should-fix. What changed:

- **The journeys would never have run in CI (blocking).** Both signup tests skip without `AUTH_SIGNUP_ENABLED=true`, and the `e2e` job's Playwright step never set it — so the two tests this feature exists for could not fail, and the recorded flag-on run was a manual one. Fixed by the second CI step above, which is the only way both halves are covered (adding the flag to the existing step would instead break the closed test).
- **Post-action assertions used the 5 s default while the file declared 20 s for exactly that latency.** The three assertions that wait on a server action (bcrypt + a Neon round trip) now use a `TEXT` timeout, matching the `NAV` timeout already used for navigations.
- **The tenant-leak spot-check was weaker than the notes claimed.** `getByText("Northwind Logistics")` on `/crm` could only ever match an open-deals chart tick, so it would pass on a leak that did not reach that series. It now asserts the `/crm/organizations` list has no seed link, the way `e2e/crm.spec.ts` does.
- **The config comment justified itself with the weaker reason.** "It would change other specs' `/login`" is not the real constraint — the spec reads the runner's env, so `webServer.env` would make the closed test fail against an open server. Reworded, with the `reuseExistingServer` caveat added.
- Added from the review's suggestions: an explicit no-sign-out assertion after a successful change (still on `/settings`, chip still visible), coverage for the `unchanged` code — a 6.3 branch that had no e2e coverage at all — and the CI/job-inertness caveat, so the spec no longer implies the suite runs it automatically when it does not.
