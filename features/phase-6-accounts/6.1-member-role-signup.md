# Feature 6.1: Member role and signUp helper

**Phase:** 6 — Accounts
**Status:** completed
**Estimated effort:** 3–5 hours
**Depends on:** 0.3, 0.5

## Goal

A third role `member` exists in the schema, and a tested `signUp` helper can create an empty personal tenant when the env flag is on. No UI.

## Scope

Include:

- `userRoles` becomes `["owner", "demo", "member"]` (Postgres enum + TS type)
- Generated Drizzle migration that **adds** the enum value (do not drop/recreate `user_role` — existing owner/demo rows must survive)
- `isSignupEnabled(env)` — only the string `true` is on; missing / anything else is closed
- Password helper: at least 12 characters (shared with 6.3)
- `signUp({ email, password }, deps)` — flag check, trim email, validate, hash, insert tenant + user in one transaction, return `{ id, email, tenantId, role: "member" }`
- Memory repository so tests pass with `env -u DATABASE_URL npm test`
- `requireTenant` accepts `member` (it follows `userRoles`; update tests)
- `.env.example` lists `AUTH_SIGNUP_ENABLED` (name only, commented off)

Exclude (for now):

- `/signup` page, login link, auto sign-in (6.2)
- `changePassword` / `/settings` (6.3)
- Playwright (6.4)
- OAuth, mailer, forgot-password, delete account
- Seeding members; Reset demo for members

## Spec

1. Tenant name for a member is the trimmed email. Unique, like `users.email`. Seed names `"Owner"` and `"Demo"` stay reserved by not being valid emails.
2. Callers never pass `tenantId`. Duplicate email (unique constraint or pre-check) throws a generic unavailable error, not “email taken”.
3. Empty email or email without `@` throws invalid-email. Password shorter than 12 throws weak-password. Flag off throws closed. Closed must not insert a tenant or a user.
4. If the user insert fails, the tenant insert rolls back (transaction on the real repo; memory repo simulates the same).
5. `npm run db:seed` still upserts only owner/demo and does not delete other tenants or users.
6. Do not log the password. Do not write `accounts` / `sessions` rows (JWT stays as today).

Typed errors (names can match the module, codes must be these):

- `closed`
- `invalid_email`
- `weak_password` (under 12 characters)
- `password_too_long` (over 72 bytes — the bcrypt input limit; added during 6.1 review, see Shipped notes)
- `unavailable` (duplicate or conflict)

## Shipped notes

An independent spec-compliance review and a quality review both ran before this was committed. All ten acceptance criteria passed; the quality review raised four should-fix items, all fixed here. The code as committed differs from the first draft in these ways:

- **Duplicate detection is case-insensitive** (should-fix from review). `Tyler@Example.com` and `tyler@example.com` are one mailbox: `findByEmail` uses `lower(email)` on the Drizzle side and a lowercased compare in the memory repo. The stored value stays verbatim. _(Amended by 6.2: login moved to the same `lower(email) = lower(input)` match in `lib/auth/users.ts`. As first committed here, login was byte-exact — which would have stranded a member over a case slip, since this phase has no password reset.)_ **Residual gap:** the `users_email_unique` index is still case-sensitive, so two *concurrent* case-variant signups could both pass the pre-check. A `CREATE UNIQUE INDEX ... ON users (lower(email))` closes that race; it is deliberately left as a follow-up because it is a schema change this spec did not authorize. Say the word and it is a two-line migration.
- **`password_too_long` added** (nit from review, but a real aliasing bug): bcrypt truncates at 72 bytes, so two different long passphrases would verify against each other. `assertPasswordStrength` now rejects over 72 bytes, measured with `Buffer.byteLength`, and the code is separate from `weak_password` so the form can say the right thing.
- **`createDefaultSignUpDeps()` builds the repo lazily.** Eager `getDb()` meant a deploy with the flag off and no `DATABASE_URL` threw `DATABASE_URL is required` instead of `closed` — the opposite of fail-closed.
- **The email regex is anchored on the domain labels** (`/^[^\s@]+@[^\s@.]+(?:\.[^\s@.]+)+$/`), so `a@b.c.` and `a@.b.c` no longer pass as "looks like an address".
- **The memory repo's "rollback" test was renamed.** It asserts that a repeat insert leaves the first member and tenant intact — the earlier name claimed a rollback path the memory repo cannot reach. The Drizzle duplicate mapping now has its own tests with a stub `Database` (23505 by code, by message, and an unrelated error rethrown).
- **The migration is idempotent**: `ADD VALUE IF NOT EXISTS`, as this spec asked.
- `drizzle-kit generate` produced the single `ALTER TYPE` statement on its own.
- The atomic insert is `db.batch([insert tenant, insert user])`, not `db.transaction()`: the Neon HTTP driver throws `No transactions support in neon-http driver`. Neon's `batch` runs the statements in one transaction, so a failing member insert leaves no orphan tenant. The tenant id is generated in application code so both statements can be built up front.
- **Was unproven at 6.1, now exercised:** the batch path had never executed against a real database here. _(Amended by 6.2: `npm run db:migrate` was applied to the dev branch and a real signup created a member — `role: member`, own tenant, `$2b$` hash, empty tenant — so the insert is proven. The `23505` → `unavailable` mapping is still only covered by the stub-`Database` unit tests, because a duplicate is caught by the pre-check before the constraint.)_
- `createDefaultSignUpDeps()` is the single wiring point 6.2's server action uses.
