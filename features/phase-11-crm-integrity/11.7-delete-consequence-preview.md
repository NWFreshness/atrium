# Feature 11.7: Delete-consequence preview

**Phase:** 11 — CRM integrity, dead-ends, and list/task surface
**Status:** specced
**Estimated effort:** 2–3 hours
**Depends on:** nothing
**Blocks:** nothing

## Goal

Close **G11** for the three record types: a user deleting an organization today
gets `confirm("Delete Acme?")` and no idea that four relationships just went
blank.

`SET NULL` is the right referential choice — deleting an organization must not
delete its contacts. It is silent. `components/crm/org-table.tsx:63`,
`components/crm/contact-table.tsx:86` and `components/crm/deal-table.tsx:117`
each confirm with one name, and after the delete the dependents render as `""`
(`components/crm/deal-table.tsx:82-85`, `app/(authenticated)/crm/deals/[id]/page.tsx:56`).

There are **five** `onDelete: "set null"` foreign keys across **three** parent
types, not three as the ideas doc's G11 line claims:

| FK | Location | Unlinked when |
| --- | --- | --- |
| `contacts.organizationId` → `organizations.id` | `lib/crm/schema.ts:51-53` | an organization is deleted |
| `deals.organizationId` → `organizations.id` | `lib/crm/schema.ts:72-74` | an organization is deleted |
| `deals.contactId` → `contacts.id` | `lib/crm/schema.ts:75-77` | a contact is deleted |
| `activities.contactId` → `contacts.id` | `lib/crm/schema.ts:100-102` | a contact is deleted |
| `activities.dealId` → `deals.id` | `lib/crm/schema.ts:103` | a deal is deleted |

So: an organization unlinks **contacts and deals**; a contact unlinks **deals and
activities**; a deal unlinks **activities**. This feature counts them and says so
in the confirm message. It changes no schema, no referential action, and no
delete behaviour.

## Scope

Include:

- **`cascadePreview`** — one new query helper per entity kind, in the barrel
  pattern of 7.4: a dispatcher in `lib/crm/queries.ts` plus an implementation in
  **both** `queries-memory.ts` and `queries-drizzle.ts`. Never `db.*` in the
  barrel.
- **`cascadePreviewForSession`** + three `*Action` wrappers in the three
  `*-actions.ts` modules, following the existing `getXForSession` / `getXAction`
  shape exactly.
- **One pure formatter** for the message, in a client-safe module, so the three
  tables share one implementation of the copy.
- **The `confirm()` string** in all three tables: byte-identical to today when
  every count is zero; a second `\n`-separated line when any count is non-zero.
- Tests: memory-repo policy for all three kinds, tenant scoping, the formatter
  table, the tenant-id guard, and a browser journey asserting the message.

Exclude (for now):

- **"Detach instead."** Cut by the design and by the PM. Re-parenting five
  relationship types has its own semantics (what happens to a deal's
  probability, to a contact's history) and is a different feature wearing a
  checkbox. Do not render the words "detach" or "move to" anywhere.
- **A bespoke confirm dialog.** The phase's non-goals list bans a `confirm()`
  replacement. The CRM would get its first non-V4 dialog, and it would have to
  solve focus trap, Escape, initial focus and `aria-describedby` — three of the
  four gaps the existing `crm-dialog` still has. A6's own implementation note
  says the same.
- **Activity delete.** 11.3 owns it, and its confirm is `Delete this activity?`
  with no consequence line, because an activity has no downstream rows. 11.3
  truncates the row-action names; it does not call `cascadePreview`.
- **Counts riding along with the list payload.** Overruled: the list pages do not
  fetch activities (`components/crm/deal-table.tsx` receives only
  `deals`/`organizations`/`contacts`), so client-side counting under-counts two
  of the five relationships. The counts are a **server** answer, on click.
- **A pending state on the button** that the user sees for a long time — see
  §2. The button is disabled for the duration of **one** round trip and the
  `aria-busy` is not rendered; this is the design's decision, recorded with its
  cost.
- **Any change to `onDelete`.** It stays `"set null"`. `lib/crm/queries.test.ts:1051-1085`
  ("sets related contact and deal organizationId to null instead of
  cascade-deleting") must pass unmodified.
- **Soft deletes, a recycle bin, an undo toast.** Phase non-goals. There is no
  `toast` primitive anywhere in the repo to reuse.
- **A 23505 / `isUniqueViolation` extraction.** 11.6's decision, not this one's.
- **`lib/crm/schema.ts`.** Not modified. Read only, to justify the count.

## Spec

### 0. `CascadePreview` — the shape, in `lib/crm/queries-shared.ts`

```ts
export type CascadePreview = {
  contacts: number;
  deals: number;
  activities: number;
};
```

Three named counts, always all three keys present, always integers `>= 0`.
**Not** a generic `{ [relation: string]: number }` — the three tables each read
a fixed subset, and a fixed type means the formatter cannot be handed a key it
does not have a noun for.

Placed after `ListActivitiesOpts` (`:79-82`). `queries-shared.ts` already
imports nothing beyond `drizzle-orm` types and `./constants` (`:1-8`), so no new
import is needed. It is re-exported from the barrel's `export type { … }` block
(`lib/crm/queries.ts:72-89`) like every other shared type.

### 1. The three helpers

Naming follows the existing store split (7.4): dispatcher in the barrel, one
implementation per store.

**Barrel, `lib/crm/queries.ts` — after `deleteOrganization` (`:163-173`):**

```ts
export async function organizationCascadePreview(
  tenantId: string,
  id: string,
  repo?: CrmRepository,
): Promise<CascadePreview> {
  const scoped = requireTenantId(tenantId);
  if (repo) {
    return organizationCascadePreviewInMemory(repo, scoped, id);
  }
  return organizationCascadePreviewInDrizzle(scoped, id);
}
```

and the same shape for `contactCascadePreview` (after `deleteContact`,
`:240-250`) and `dealCascadePreview` (after `deleteDeal`, `:333-343`). The
entity name comes first, matching `getOrganization` / `deleteOrganization`, so a
reviewer can find all four by grepping one word. `tenantId` first, then the id,
then the optional `repo` — the BRIEF rule 8 order, with no `opts` trailing
object because there is nothing optional to filter.

**What each counts, and only this:**

| Helper | `contacts` | `deals` | `activities` |
| --- | --- | --- | --- |
| `organizationCascadePreview` | rows where `organizationId === id` | rows where `organizationId === id` | always `0` |
| `contactCascadePreview` | always `0` | rows where `contactId === id` | rows where `contactId === id` |
| `dealCascadePreview` | always `0` | always `0` | rows where `dealId === id` |

**Every count is tenant-scoped and id-scoped together.** An activity in another
tenant that points at this id must not appear — the ids are UUIDs so a collision
is not the concern, but the tenant predicate is the invariant the whole repo
runs on and a `count` that forgot it would be a data leak. Every implementation
filters on `tenantId === scoped` **and** the FK equals `id`, exactly as
`deleteOrganizationInMemory` does at `queries-memory.ts:98-106` when it nulls the
same rows.

**Memory implementations** — add three exported functions in
`lib/crm/queries-memory.ts`, one beside each existing `delete…InMemory` (after
`:109`, `:189`, `:278` respectively). They read the same arrays the delete
mutates:

```ts
export function organizationCascadePreviewInMemory(
  repo: CrmRepository,
  scoped: string,
  id: string,
): CascadePreview {
  return {
    contacts: repo.contacts.filter(
      (row) => row.tenantId === scoped && row.organizationId === id,
    ).length,
    deals: repo.deals.filter(
      (row) => row.tenantId === scoped && row.organizationId === id,
    ).length,
    activities: 0,
  };
}
```

**This proves policy, not SQL.** The memory repository is what
`env -u DATABASE_URL npm test` exercises; the Drizzle repository is never
executed by CI. Stated again in Recorded limits.

**Drizzle implementations** — three exported functions in
`lib/crm/queries-drizzle.ts`, one beside each `delete…InDrizzle`. Use
`count()` from `drizzle-orm` (the module already imports from
`drizzle-orm` at `:1`; add `count` and `gte`/nothing-else to that import).
`nextBoardOrderInDrizzle` (`:247-256`) is the in-file precedent for a
`select({ … })` aggregate returning `0` for the empty case:

```ts
export async function organizationCascadePreviewInDrizzle(
  scoped: string,
  id: string,
): Promise<CascadePreview> {
  const [contacts] = await requireCrmDb()
    .select({ n: count() })
    .from(contacts)
    .where(and(eq(contacts.tenantId, scoped), eq(contacts.organizationId, id)));
  const [deals] = await requireCrmDb()
    .select({ n: count() })
    .from(deals)
    .where(and(eq(deals.tenantId, scoped), eq(deals.organizationId, id)));
  return {
    contacts: contacts?.n ?? 0,
    deals: deals?.n ?? 0,
    activities: 0,
  };
}
```

A `count()` aggregate always returns one row, so `?? 0` is defensive rather than
reachable — keep it, because `nextBoardOrderInDrizzle:255` sets the same
precedent and a nullable count would surface as `undefined` in a template.

**Three sequential `await`s, not one `Promise.all`.** The three stores in this
repo batch with `Promise.all` when they are independent
(`queries-drizzle.ts:279-293` is one query; `lib/crm/dashboard.ts:259-263` uses
`Promise.all` across three barrel calls). Here the two aggregates for a contact
and the one for a deal are already **separate statements inside one function**,
and `neon-http` sends one HTTP request per query. Either shape is defensible;
`Promise.all` is the house style and is what an implementer should write. Do
**not** add `db.batch` — it is a write primitive
(`lib/db/batch-transaction.ts:5-13`), and a read does not belong in a
transaction wrapper.

**No new `opts`, no new list helper, no `listDealsByStage`-style
parallel-helper.** The BRIEF rule 8 and the shared-invariant checklist both
forbid it, and there is nothing to filter: the preview is a per-row count, not a
list.

### 2. The session actions

One per entity, in the file that already owns that entity's actions. The shape is
`getXForSession` (`lib/crm/org-actions.ts:29-36`) exactly:

```ts
export async function organizationCascadePreviewForSession(
  getSession: GetSession,
  id: string,
  repo?: CrmRepository,
): Promise<CascadePreview> {
  const { tenantId } = await requireTenant(getSession);
  return organizationCascadePreview(tenantId, id, repo);
}
```

plus the `Action` wrapper, which is the same three lines as every other one
(`lib/crm/org-actions.ts:73-78`):

```ts
export async function organizationCascadePreviewAction(
  id: string,
): Promise<CascadePreview> {
  const { auth } = await import("@/auth");
  return organizationCascadePreviewForSession(auth, id);
}
```

**`requireTenant(getSession)` with no second argument** — matching every
`deleteXForSession` in the repo (`org-actions.ts:62`, `contact-actions.ts:104`,
`deal-actions.ts:128`). The preview takes an id the **client** already holds, so
there is no input object at all and therefore nothing for a client to smuggle a
`tenantId` into. This is the structural answer to the injection question: there
is no `ClientTenantInput` on these functions and none may be added.

### 3. `lib/crm/cascade-preview.ts` — the message

Pure, no imports except the type. This is the client-safe module the design
named, and it is the only place the copy lives.

```ts
import type { CascadePreview } from "./queries-shared";

export function pluralize(n: number, singular: string): string;

export function consequenceMessage(
  name: string,
  preview: CascadePreview,
): string;
```

**`pluralize(n, singular)`** returns `` `${n} ${singular}` `` when `n === 1`
and `` `${n} ${singular}s`` `` otherwise. It is exported and unit-tested on its
own, because the three nouns are all regular and a reviewer should not have to
read the caller to see that.

**`consequenceMessage(name, preview)` — the four cases, exact:**

| Non-zero counts | Return |
| --- | --- |
| none | `` `Delete ${name}?` `` |
| exactly one | `` `Delete ${name}?\nThis will unlink ${pluralize(n, noun)}.` `` |
| two | `` `Delete ${name}?\nThis will unlink ${a} and ${b}.` `` |
| three | `` `Delete ${name}?\nThis will unlink ${a}, ${b}, and ${c}.` `` |

Order is fixed by `CascadePreview`'s declaration order: **contacts, deals,
activities**. Two items join with `" and "`; three use the Oxford comma
(`", "` then `", and "`). The nouns are `contact`, `deal`, `activity`.

Worked examples, which the tests copy verbatim:

- `{ contacts: 0, deals: 0, activities: 0 }` → `"Delete Acme?"`
- `{ contacts: 2, deals: 0, activities: 0 }` → `"Delete Northwind Logistics?\nThis will unlink 2 contacts."`
- `{ contacts: 2, deals: 2, activities: 0 }` → `"Delete Northwind Logistics?\nThis will unlink 2 contacts and 2 deals."`
- `{ contacts: 0, deals: 0, activities: 1 }` → `"Delete Northwind fleet tracking?\nThis will unlink 1 activity."`
- `{ contacts: 1, deals: 0, activities: 0 }` → `"Delete Acme?\nThis will unlink 1 contact."`
- all three non-zero → `"Delete Acme?\nThis will unlink 1 contact, 2 deals, and 3 activities."`

**The zero-case line is byte-identical to today's string.** This is the load-
bearing constraint of the whole feature: `confirm(\`Delete ${name}?\`)` at
`org-table.tsx:63`, `contact-table.tsx:86`, `deal-table.tsx:117` is what ships,
and a zero-consequence delete must produce exactly those bytes so 11.1's
already-written `e2e/crm-deals.spec.ts` Journey F — which registers
`page.once("dialog", …)` and accepts without asserting the message, and 11.2's
Journey F likewise — and any future exact-message assertion keep working. The
test for this is `expect(consequenceMessage("Acme", empty)).toBe("Delete Acme?")`
— an exact string equality, not a regex, not a `toContain`.

**The message never says "cascade", "delete", or the word "orphan".** Nothing is
deleted; the relationship is dropped, and `unlink` is the plain word for it. The
UX copy table bans `unlink` **in a form error** and explicitly permits it in the
11.7 confirm. No table name, no column name, no `contactId`, no `SET NULL` in
user-facing text.

### 4. The three table handlers

Identical change in all three files. `org-table.tsx:59-69` today:

```tsx
<button
  type="button"
  aria-label={`Delete ${org.name}`}
  onClick={async () => {
    if (!confirm(`Delete ${org.name}?`)) {
      return;
    }
    await deleteOrganizationAction(org.id);
    router.refresh();
  }}
>
```

becomes:

```tsx
<button
  type="button"
  aria-label={`Delete ${org.name}`}
  disabled={pendingDelete === org.id}
  onClick={async () => {
    setPendingDelete(org.id);
    try {
      const preview = await cascadePreviewAction(org.id);
      if (!confirm(consequenceMessage(org.name, preview))) {
        return;
      }
      await deleteOrganizationAction(org.id);
      router.refresh();
    } finally {
      setPendingDelete(null);
    }
  }}
>
```

- **`pendingDelete` is one new `useState<string | null>(null)` per table
  component**, declared beside the existing `editing` state
  (`org-table.tsx:21`, `contact-table.tsx:27`, `deal-table.tsx:37`). It is
  per-row keyed by id, so clicking Delete on one row does not disable every
  other row's Delete. This is the same shape as `ActivityTimeline`'s
  `pendingId` (`components/crm/activity-timeline.tsx:44`), which is the in-repo
  precedent for a per-row pending id.
- **The `finally` always clears it**, including on the cancel path — a `return`
  inside `try` runs the `finally`. The design accepts a disabled destructive
  control for one round trip (the ruling was fetch-on-click, over the UX
  alternative of list-payload counts) and the cost of that ruling is that the
  button is inert while the query is in flight. That is stated, not hidden.
- **The `aria-label` is unchanged.** `aria-label={`Delete ${`}` must survive
  byte-for-byte: `components/crm/crm-pnw.test.ts:229-235` asserts that exact
  template string in all three table files, and every e2e delete locator is built
  on it. Do not append the count, the consequence, or anything else to it.
- **The `Edit` button and its handler are untouched.**
- **The import** is `import { consequenceMessage } from "@/lib/crm/cascade-preview";`
  and `import { cascadePreviewAction } from "@/lib/crm/org-actions";` (or
  `contact-actions` / `deal-actions`). Both are legal: the first is a pure module
  with only a type import, the second is a `"use server"` boundary that
  `lib/client-boundary.test.ts:329-332` stops walking at.
- **No new CSS.** The `disabled` attribute on a `.crm-row-actions button` is
  styled by nothing in `components/crm/org.module.css:190-213`; the browser's
  default disabled styling applies. Do **not** add a `:disabled` rule — the
  10.3 gate at `crm-pnw.test.ts:220-227` reads that block by selector and a new
  declaration inside `.crm-row-actions button` is a change to a gated rule. If a
  disabled look is wanted, it is a follow-up.
- **`router.refresh()` after the delete is unchanged.** After a cancel, no
  refresh happens, exactly as today.

`e2e/crm-delete-preview.spec.ts`, **one test**, demo tenant. House style copied
from `e2e/crm.spec.ts` exactly as 11.2 §5 describes it (`beforeAll` throws

The seed gives the counts for free — read from `lib/crm/seed.ts` at
implementation time, not from a memory of it:

- `Northwind Logistics` (`:27-36`) has **1** contact, `Ana Ruiz` (`:58-69`).
- `Northwind` has **2** deals, `Northwind fleet tracking` (`:126-133`) and
  `Northwind warehouse rollout` (`:134-141`).
- `Bluepeak Software` (`:37-46`) has **2** contacts (`:70-81` Marcus Chen,
  `:94-105` Jordan Hale) and **2** deals (`:142-157`).
- `Harbor & Lane` (`:47-56`) has **1** contact, `Priya Shah` (`:82-93`), and
  **2** deals (`:158-173`).
- `Northwind fleet tracking` has **1** activity (`:175-187`, linked to both
  `ana.id` and `fleet.id`).

**The test must not delete seeded rows.** The demo tenant is shared with every
other spec (`playwright.config.ts:11` `fullyParallel: false`, one worker, one
tenant), and 11.1/11.2's cleanup rule is that the tenant accumulates but nothing
breaks it. Deleting `Northwind Logistics` would break
`e2e/crm-pipeline.spec.ts`'s Journey A, which asserts the six seeded deals are in
their seeded columns, and `e2e/crm.spec.ts:62-64`, which asserts the three seed
org names are visible. **So the journey mints its own organization**, links a
contact and a deal to it, and deletes that:

1. Create an organization named `` `E2E Cascade ${Date.now()}` `` through the
   `Add organization` dialog (the pattern at `e2e/crm.spec.ts:82-87`).
2. Create a deal named `` `E2E Cascade Deal ${Date.now()}` `` through the
   `Add deal` dialog with that organization selected in the `Organization`
   select (`components/crm/deal-form.tsx:214-234`). Use the `Add deal` helper
   shape from 11.2 §5, or re-declare it here; see Implementation notes.
3. **Non-zero, two-noun case.** Register
   `page.once("dialog", d => { seen = d.message(); void d.accept(); })`
   **before** clicking
   `` getByRole("button", { name: `Delete ${orgName}`, exact: true }) ``.
   Assert `seen === \`Delete ${orgName}?\nThis will unlink 1 deal.\``.
4. **Zero-count case.** Now the organization has no contact and no deal (the
   deal was unlinked by the delete, not destroyed). Create a **second**
   organization with the same fixture pattern and immediately delete it, with
   no dependents. Assert `seen === \`Delete ${org2}?\`` — the exact
   byte-identical string, and the assertion that proves the design's rule.
5. **Three-noun case.** Mint an organization, a contact (via `Add contact`
   with the `Organization` select, `components/crm/contact-form.tsx:165-185`),
   and a deal linked to the same contact. Deleting the **contact** produces
   `{ contacts: 0, deals: 1, activities: 0 }` → one noun, not three. To get
   three nouns from a **single** parent you need an organization with a contact,
   a deal, and an activity: but an activity attaches to a contact or a deal, not
   to an organization (`lib/crm/schema.ts:100-103` — there is no
   `activities.organizationId`). **Therefore no single delete can ever produce
   three non-zero counts**, and the three-noun branch is unit-tested only. Say
   this in the test as a comment naming `lib/crm/schema.ts:100-103`, and record
   it as a limit. The two-noun case (organization → contacts and deals) is the
   one a user actually hits.
6. **Cancel path.** Register a handler that calls `void d.dismiss()` and delete a
   freshly minted organization. Assert the row is still there after a reload.
   The design requires this assertion: `confirm()` is the only guard before an
   unrecoverable delete, and nothing in the phase replaces it.
7. `afterEach` deletes anything the test created, in a loop that re-reads the
   button list each pass, and asserts the test's own names are gone.

**Copy discipline for the test:** `{ exact: true }` on every role name derived
from a `Date.now()` fixture. No CSS-module class selector. No
`waitForTimeout`. The only `page.once` handlers are the three above, each
registered immediately before the click that opens `confirm()`.

### 6. Tests (written first)

`lib/crm/cascade-preview.test.ts` — the table, verbatim from §3:

- the six worked examples, each with `toBe(exactString)`;
- the zero case asserted as the literal `"Delete Acme?"`, with a comment saying
  it must stay byte-identical to `org-table.tsx:63`;
- `pluralize(1, "contact") === "1 contact"`, `pluralize(0, "contact") ===
  "0 contacts"`, `pluralize(2, "activity") === "2 activities"` — the last one
  is the irregular-looking case worth pinning;
- the message contains no forbidden token:
  `expect(message).not.toMatch(/cascade|orphan|tenantId|contactId|SET NULL/i)`.

`lib/crm/queries.test.ts`, new `describe("cascadePreview")`:

- **Organization, all three relationships.** Create an org with 2 contacts and
  2 deals in tenant A, plus an org with 1 contact and 1 deal in tenant B.
  `expect(await organizationCascadePreview(tenantA, orgA.id, memory)).toEqual({ contacts: 2, deals: 2, activities: 0 })`.
  The tenant-B rows exist so the assertion is about the count and not about
  there being nothing to leak.
- **Contact.** Org-less contact with 1 deal and 2 activities →
  `{ contacts: 0, deals: 1, activities: 2 }`.
- **Deal.** Deal with 1 activity → `{ contacts: 0, deals: 0, activities: 1 }`.
- **Unrelated rows are not counted.** A second org with its own dependents does
  not change the first org's numbers.
- **A missing id returns zeros, not a throw** —
  `expect(await organizationCascadePreview(tenantA, "missing", memory)).toEqual({ contacts: 0, deals: 0, activities: 0 })`.

## Implementation notes

- **Why the counts come from the server on click, not from the list payload.**
  The UX alternative was rejected by the design: the org list page fetches only
  organizations (`app/(authenticated)/crm/organizations/page.tsx:11`), the deals
  page fetches deals + organizations + contacts but **not** activities
  (`deals/page.tsx:13-17`), and no page fetches activities at all. A
  client-side count over the list payload would therefore report `0` for both
  activity relationships and lie in exactly the case the feature exists for. The
  cost of the ruling is the one-round-trip pending state in §4.
- **Five relationships, three nouns, and a structural reason the three-noun
  branch is unreachable.** `activities` has no `organizationId`
  (`lib/crm/schema.ts:100-103`), so an organization delete can never unlink an
  activity; and a contact or a deal delete can never unlink a contact. The
  three-noun message therefore exists as formatter code and unit test only. Do
  not "fix" this by adding a sixth relationship.
- **`Promise.all`, not `db.batch`.** `db.batch` is documented as a write
  primitive (`lib/db/batch-transaction.ts:5-13`) and `neon-http` has no
  `db.transaction()` at all. Two or three read aggregates go in `Promise.all`,
  the same shape as `lib/crm/dashboard.ts:259-263`.
- **The `finally` on the cancel path is the easy bug.** `return` inside `try`
  runs the `finally` in JS, so the shape in §4 is correct — but a reviewer should
  see that it was considered, because a variant that calls `confirm` *outside*
  the `try` leaves the button permanently disabled after a cancel. The
  journey's cancel assertion exists to catch that.
- **Do not touch `aria-label`.** It is the single most load-bearing string in
  the CRM's test suite: `crm-pnw.test.ts:229-235` gates the exact template, and
  every e2e delete locator in 11.1's and 11.2's specs is built from it. Adding
  the count to the accessible name would be a genuine product improvement and a
  genuine break of four files.
- **`confirm()` is synchronous and the counts must be in hand before it opens.**
  That is the whole reason for the two-step (fetch, then confirm) shape. Do not
  "optimise" it by opening the dialog first and updating the text — a native
  dialog's message is fixed at creation.
- **The message is one string with a `\n`.** Playwright's `dialog.message()`
  returns it with the newline intact, so a `toBe` on the exact string works. Do
  not split on `\n` in the test; the point is that the bytes are right.
- **Memory repo proves policy, not SQL.** `env -u DATABASE_URL npm test` runs
  `createMemoryCrmRepository()`; `queries-drizzle.ts` is never executed. Every
  Drizzle `count()` claim here is a claim about the barrel's placement, proven by
  the browser journey against dev Neon and by reading the fragment. Say so in the
  shipped notes rather than writing a test named "drizzle counts".
- **This file and 11.8 both touch `lib/crm/deal-actions.ts`.** They touch
  disjoint regions (this one appends to the bottom, 11.8 edits the
  `listDealsForSession` re-projection at `:61-65`) but the board rule is one
  `in_progress` feature at a time, so they must be sequential. If the controller
  wants them merged into one PR to avoid the collision, that is a scheduling
  decision, not a spec change.
- **Do not run prettier on a directory.** Explicit paths only, and only to the
  files this feature creates (`lib/crm/cascade-preview.ts`,
  `lib/crm/cascade-preview.test.ts`, `e2e/crm-delete-preview.spec.ts`).
- **Local Playwright needs `AUTH_SECRET` in the process env** and a free
  `:3000` that is this app — `playwright.config.ts:31` reuses an existing
  server, so a foreign `next-server` silently hijacks the run. Kill by PID.
- **Shipped notes are evidence.** Every `path:line` was read in the working tree.
  No `git` was run, so any "this is unchanged since" claim is unverified against
  history.

## Recorded limits

1. **The Drizzle `count()` fragments are unexecuted in CI.** Job `ci` runs
   `npm test` with no `DATABASE_URL` (memory repo) and `npm run build`. The
   counts are proven by the memory-repo policy test and by the browser journey
   against dev Neon; the SQL itself is verified by reading it, not by running it
   under CI.
2. **The three-noun message is unreachable through the UI.** An organization
   cannot unlink an activity (`lib/crm/schema.ts:100-103` has no
   `activities.organizationId`), and a contact or deal cannot unlink a contact.
   The branch is formatter code and a unit test, nothing more. A reviewer should
   not treat its coverage as evidence that the product can produce it.
3. **The destructive control is disabled for one round trip.** The design
   overruled the UX recommendation to count client-side, and the price is that
   `Delete` is inert between the click and the `confirm()`. There is no spinner
   and no `aria-busy`. On a slow Neon round trip the button simply does nothing
   for a moment. Accepted and recorded, not fixed.
4. **The preview is a point-in-time count with no transaction.** Between the
   count and the delete another tab could add a dependent. The message would
   then understate. Making it exact would need a serializable transaction,
   which `neon-http` does not have (`lib/db/batch-transaction.ts:5-13`), and the
   delete itself is a single statement with no batch today.
5. **Counts are counted, not named.** The message says `2 contacts`; it does not
   say which two, and there is no link to them. Richer copy would need a bespoke
   dialog, which is a phase non-goal.
6. **`SET NULL` orphans are still created.** This feature warns; it does not
   prevent. The dependents still render as `""`
   (`components/crm/deal-table.tsx:82-85`,
   `app/(authenticated)/crm/deals/[id]/page.tsx:56`), and the fix for that blank
   is not in this phase.
7. **No undo and no toast.** There is no `toast` primitive in the repo. After
   the confirm, the delete is unrecoverable — the same limit 11.3 records for
   activity delete.
8. **Copy quality is not proven.** Whether a user reads `This will unlink 2
   contacts and 2 deals.` as a warning or as noise is a human read. The spec
   fixes the bytes so the string cannot drift; it cannot tell you the sentence
   works.
9. **The seed's counts were read from `lib/crm/seed.ts` at spec time.** If the
   seed changes, the journey's expectations are stale — and the journey does not
   depend on them, because it mints its own rows. The seed counts are quoted in
   §5 for the implementer's information, not as an assertion.
10. **Screen-reader behaviour of the native dialog is the browser's, not the
    app's.** `confirm()`'s focus order, Escape and announcement are
    implementation-defined. Nothing in this feature can assert them, and nothing
    in it can improve them.
11. **Line numbers are a snapshot** read from the working tree. No `git` was run,
    so "unchanged since" claims are unverified against history.
