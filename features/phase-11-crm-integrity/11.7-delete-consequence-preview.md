# Feature 11.7: Delete-consequence preview

**Phase:** 11 — CRM integrity, dead-ends, and list/task surface
**Status:** specced
**Estimated effort:** 2–3 hours
**Depends on:** nothing
**Blocks:** nothing

## Goal

A delete that will blank other records says so before it happens. Closes
**G11 / A6**. `SET NULL` stays the referential action; this feature only names
what will be unlinked.

## Verified gap (opened on the working tree)

The ideas doc cited `lib/crm/schema.ts:51,65,76`. Those line numbers have
moved. Current FKs, all `onDelete: "set null"`:

| FK | Location | Unlinked when |
| --- | --- | --- |
| `contacts.organizationId` → `organizations.id` | `lib/crm/schema.ts:51-53` | organization deleted |
| `deals.organizationId` → `organizations.id` | `lib/crm/schema.ts:72-74` | organization deleted |
| `deals.contactId` → `contacts.id` | `lib/crm/schema.ts:75-77` | contact deleted |

| `activities.dealId` → `deals.id` | `lib/crm/schema.ts:103` | deal deleted |

Five FKs, three parent kinds. An organization unlinks **contacts + deals**; a
contact unlinks **deals + activities**; a deal unlinks **activities**.

Confirm copy today is name-only:

- `components/crm/org-table.tsx:63` — `confirm(\`Delete ${org.name}?\`)`
- `components/crm/contact-table.tsx:86` — `confirm(\`Delete ${contact.name}?\`)`
- `components/crm/deal-table.tsx:117` — `confirm(\`Delete ${deal.name}?\`)`

The gap is open. Spec it.

## Scope

### Include

- A `cascadePreview` query helper (barrel + memory + drizzle) returning
  tenant-scoped counts of what a delete will unlink.
- One pure formatter for the confirm string, in a client-safe module (no
  value-import of `lib/crm/queries.ts`).
- The three table Delete buttons call the preview, then `confirm()` with the
  formatted string, then the existing delete action.
- Tests: counts, tenant isolation, zero-count byte-identical message, formatter
  table.

### Exclude (for now)

- **A bespoke confirm component.** Keep the browser `confirm()` so existing
  tests and the e2e create/delete path stay on the platform dialog. Use a real
  dialog only if the copy cannot fit in `confirm()` — it can. Do not build a
  CRM confirm primitive in this feature.
- **"Detach instead."** Nice-to-have, not acceptance. Do not render "detach"
  or "move to".
- **Any change to `onDelete`.** It stays `"set null"` in `lib/crm/schema.ts`.
  `lib/crm/queries.test.ts` already covers "sets related contact and deal
  organizationId to null instead of cascade-deleting" — that test must pass
  unmodified.
- Activity delete. 11.3 owns it; an activity has no downstream rows.
- Soft delete, recycle bin, undo toast.
- Schema / migration. 11.6 is the only Phase 11 schema change.

## Spec

1. **Shape.**

   ```ts
   type CascadeKind = "organization" | "contact" | "deal";

   type CascadePreview = {
     contacts: number; // unlinked when kind === "organization"
     deals: number;    // unlinked when kind is organization or contact
     activities: number; // unlinked when kind is contact or deal
   };
   ```

   Unused keys are `0`. Callers do not guess; the helper always returns all
   three.

2. **Counts.**

   - organization: `contacts` where `organizationId = id AND tenantId = scoped`;
     `deals` where `organizationId = id AND tenantId = scoped`; `activities = 0`.
   - contact: `deals` where `contactId = id AND tenantId = scoped`;
     `activities` where `contactId = id AND tenantId = scoped`; `contacts = 0`.
   - deal: `activities` where `dealId = id AND tenantId = scoped`; others `0`.

   Another tenant's rows never increment a count. A missing id returns zeros
   (the subsequent delete already returns `null`).

3. **Message.** Pure function, one implementation:

   - When every count is `0`: exactly `` `Delete ${name}?` `` — byte-identical
     to today (`org-table.tsx:63`, `contact-table.tsx:86`, `deal-table.tsx:117`).
   - When any count is non-zero: that same first line, then a newline, then a
     second line that names only the non-zero counts, in a stable order
     (contacts, deals, activities), English plural:

     `Delete Acme?` + `\n` + `This will unlink 4 contacts and 2 deals.`

     `Delete Ada?` + `\n` + `This will unlink 1 deal and 3 activities.`

     `Delete Widget?` + `\n` + `This will unlink 1 activity.`

   Do not mention zeros. Do not mention `SET NULL`. Do not mention other
   tenants.

4. **UI.** The Delete `onClick` remains async. Order: preview action →
   `confirm(message)` → existing `deleteXAction` → `router.refresh()`. Cancel
   on `confirm` still no-ops. No pending chrome beyond disabling the button
   for that one round trip if the table already does that; do not add a
   spinner component.

5. **`onDelete` stays `"set null"`.** This feature does not open
   `lib/crm/schema.ts`. After the user confirms, behaviour is the behaviour
   already tested: dependents remain, FKs become null.

## Acceptance criteria

1. [ ] `cascadePreview` returns the counts in Spec §2, and a second tenant's
       matching rows do not appear in the first tenant's preview.
2. [ ] Confirm message is **unchanged** (`Delete {name}?`) when every count is
       zero.
3. [ ] Confirm message names affected counts **when they are non-zero**, using
       the formatter in Spec §3.
4. [ ] `onDelete: "set null"` is still the schema text at
       `lib/crm/schema.ts:51-53, 72-77, 100-103`. No migration.
5. [ ] No new dialog component. `confirm(` still appears in all three tables.
6. [ ] `lib/client-boundary.test.ts` still passes (formatter module is
       client-safe; tables still `import type` from the queries barrel).
7. [ ] Existing delete unit tests still pass unmodified.
8. [ ] `env -u DATABASE_URL npm test` and
       `AUTH_SECRET=ci-build-placeholder npm run build` pass.

## Verification

```bash
env -u DATABASE_URL npm test
AUTH_SECRET=ci-build-placeholder npm run build
```

Injection probes, each reversed byte-identically:

1. Hard-code the formatter to always return `` `Delete ${name}?` `` → the
   non-zero-count unit test fails.
2. Drop `tenantId` from one drizzle count predicate → the cross-tenant test
   fails.
3. Change one `onDelete: "set null"` to `"cascade"` → out of scope, but if a
   later edit does this the existing SET NULL query test must still be red;
   this feature must not be the one that changes it.

## Recorded limits

1. **No browser journey in this feature.** 11.1 / 11.2 own CRM e2e. A
   Playwright `dialog` listener asserting the second line is allowed if cheap
   but is not acceptance.
2. **Activity delete copy is 11.3.** `Delete this activity?` stays there.
3. **"Detach instead" is not built.** Re-parenting five relationship types is
   a different feature.
4. **Detail-page deletes, if any, are not wired.** Grep
   `deleteOrganizationAction` / `deleteContactAction` / `deleteDealAction` at
   implement time; if a detail page also confirms, give it the same formatter.
   The three tables are the cited gap.
5. **Count request on every click.** No caching. Fine at current list sizes
   (B5 bounded lists is deferred).
