## Goal

Close **G10**: a deal can be saved with a negative value or a probability of 101,
and every number the product shows afterwards inherits the lie.

Verified 2026-09-29 against the files, not the ideas-doc line numbers:

- `createDeal` (`lib/crm/queries.ts:284-317`) asserts `name` via `short()` at
  `:299` and then copies `value` and `probability` straight into the row
  (`:303-304`). There is no money or percent contract.
- `updateDeal` (`lib/crm/queries.ts:319-331`) asserts **only** `name`
  (`:326`). `value` and `probability` on the patch are unvalidated.
- Columns are `doublePrecision` and `integer` with no CHECK
  (`lib/crm/schema.ts:79-80`).
- The client check at `components/crm/deal-form.tsx:89-93` is a silent
  `return` on `!Number.isFinite`. A negative value and `101` are both finite,
  so they reach the server. (The ideas doc cited `:88-92`; the live check is
  `:89-93`.)
- Pipeline cards render `{deal.probability}%`
  (`components/crm/pipeline-board.tsx:149`). A float is a latent display bug
  against a Postgres `integer` column.

## Spec

### 1. `lib/input/numbers.ts`

Mirror `lib/input/text.ts`. The module imports nothing from `lib/crm`.

```ts
export const MAX_MONEY = 1e12;

export function assertMoney(
  value: unknown,
  opts: { min?: number; max?: number } = {},
): number {
  const min = opts.min ?? 0;
  const max = opts.max ?? MAX_MONEY;
  if (typeof value !== "number" || !Number.isFinite(value)) {
    throw new Error("invalid money");
  }
  if (value < min || value > max) {
    throw new Error("invalid money");
  }
  return value;
}

export function assertPercent(
  value: unknown,
  opts: { min?: number; max?: number } = {},
): number {
  const min = opts.min ?? 0;
  const max = opts.max ?? 100;
  if (typeof value !== "number" || !Number.isInteger(value)) {
    throw new Error("invalid percent");
  }
  if (value < min || value > max) {
    throw new Error("invalid percent");
  }
  return value;
}
```

Contracts, verified against the column types:

| Field | Rule | Why |
| --- | --- | --- |
| `value` | finite number, `>= 0`, `<= 1e12` | `deals.value` is `doublePrecision` (`schema.ts:79`); `MAX_SHORT_TEXT` is the parallel ceiling on text. |
| `probability` | **integer** `0–100` inclusive | `deals.probability` is `integer` (`schema.ts:80`); pipeline renders `{deal.probability}%` (`pipeline-board.tsx:149`). A float is a latent display bug. |

`NaN`, `Infinity`, `-Infinity`, strings, `null`, and `undefined` are invalid
when the field is being written. On **update**, omitted fields are not
asserted — `updateDeal` only asserts `value` when `input.value !== undefined`,
and `probability` when `input.probability !== undefined`. That is how `name`
already works (`queries.ts:326`).

Throw messages stay short, like `"invalid text"` / `"text too long"` in
`lib/input/text.ts:17-20`. Do not interpolate the bad number into the
message; tests match the string.

Money is **not** required to be an integer. Probability is.

### 2. Barrel placement

In `createDeal`, after `requireTenantId` and the batch `boardOrder` guard
(`queries.ts:290-295`), before the row is built:

```ts
const value = assertMoney(input.value, { min: 0, max: MAX_MONEY });
const probability = assertPercent(
  input.probability ?? STAGE_PROBABILITY[input.stage],
  { min: 0, max: 100 },
);
```

Defaulting probability from `STAGE_PROBABILITY` (`queries.ts:304`) happens
**before** the percent assert, so a missing probability still has to be a
legal integer. Today's map is (`lib/crm/constants.ts:12-19`):

```
New: 10, Qualified: 25, Proposal: 50, Negotiation: 75, Won: 100, Lost: 0
```

Every one of those values must pass. The ideas doc's "0/10/25/50/75/100"
set is this map; New is **10**, not 0.

In `updateDeal`, next to the existing `short(input.name)` call:

```ts
if (input.name !== undefined) short(input.name);
if (input.value !== undefined) assertMoney(input.value, { min: 0, max: MAX_MONEY });
if (input.probability !== undefined) {
  assertPercent(input.probability, { min: 0, max: 100 });
}
```

Do **not** assert inside `createDealInMemory` / `updateDealInDrizzle`. The
barrel is the one gate both stores share — the 9.6 rule.

#### 1. Timing constants

Playwright's default per-assertion timeout is 5 s and the default **per-test**
budget is **30 s**. Both are wrong here, for different reasons:

- **Per-assertion:** a dev-server action against Neon RTTs takes seconds on a
  cold route. `e2e/workroom.spec.ts:211` already defines
  `const NAV_TIMEOUT = { timeout: 20_000 }` for this reason and
  `e2e/workroom.spec.ts:205-209` explains it. Use a `NAV_TIMEOUT`-style constant
  on every assertion that follows a navigation or a server action.
- **Per-test:** a journey that mints a deal, walks to the board, drags, reloads,
  and re-asserts is a multi-screen walk, and the 30 s cap is the **whole test's**
  budget, not one assertion's. `e2e/workroom.spec.ts:212` sets
  `WALK_TEST_TIMEOUT = 180_000` and calls `test.setTimeout(WALK_TEST_TIMEOUT)`
  at the top of the walk (`e2e/workroom.spec.ts:230`, `:286`). Do the same: each
  pipeline and deal journey starts with `test.setTimeout(60_000)`, and the
  deal create/delete journey, which visits four screens, uses `120_000`.
- **Never sleep to wait for a render.** Poll the URL or the assertion. A cold
  dev route can take ~10 s; `await expect(...).toBeVisible({ timeout })`
  retries for you, a `waitForTimeout` does not.

#### 2. Fixtures — per test, never shared

**The trap:** CI sets `retries: 1` (`playwright.config.ts:13`). On a retry, the
previous attempt's rows are still in the demo tenant. A fixture shared across
tests, or any assertion written as "the table now has exactly 7 rows", lands on
state its own previous attempt created.

The rules, written into the spec so an implementer cannot get them wrong:

1. **Every mutating test mints its own rows inside the test body**, from a name
   built at run time: `` const stamp = `E2E Deal ${Date.now()}` `` — the exact
   pattern at `e2e/crm.spec.ts:81`.
2. **No `test.beforeAll` that writes.** A `beforeAll` that creates a fixture and
   a retry both run it, which is how suites end up asserting on a
   half-cleaned tenant.
3. **No assertion on an exact row count.** `await expect(page.getByRole("row")).toHaveCount(7)`
   is forbidden. Assert **presence** (`toBeVisible`), **absence**
   (`toHaveCount(0)` scoped to the test's own unique name), and **relative
   movement** (a count captured before an action and compared after). The demo
   tenant accumulates rows across every run and every retry; the existing
   `e2e/crm.spec.ts:67-95` already leaks an `E2E Org` per run and has never
   cared.
4. **`afterEach` deletes what the test created.** `page.on("dialog", d => void d.accept())`
   (the pattern at `e2e/space.spec.ts:158`) and then click the row's
   `Delete {name}` button, which is `aria-label`-addressable at
   `components/crm/deal-table.tsx:114`. Use a loop that re-reads the button list
   each pass rather than caching locators — I hit exactly this bug while
   probing: a cleanup loop that only ever looks at `.first()` deletes one row
   and silently leaves the rest. If cleanup itself fails, the test must not be
   reported as green.
5. Cleanup is best-effort **but verified**: assert the test's own name is gone.

#### 3. The selectors — exact, and verified against the live DOM

I drove the real `/crm/pipeline` board to confirm these rather than inferring
them. Verified on the running app:

- **A stage column**: each is a `<section>` containing an `<h2>` with the stage
  name. Use
  ```ts
  const column = (stage: string) =>
    page.locator("section").filter({
      has: page.getByRole("heading", { name: stage, exact: true, level: 2 }),
    });
  ```
  `exact: true` matters — without it a column lookup for `New` also matches
  nothing else here, but the heading assertion `getByRole("heading", { name: "New" })`
  is a substring match by default and `e2e/groove.spec.ts:154` shows the repo
  already uses `exact: true` where it matters.
- **A deal card**: an `<article>` whose text contains the deal name and whose
  parent carries `data-rfd-droppable-id="{stage}"`. So
  ```ts
  const card = page.locator("article").filter({ hasText: name });
  ```
  is unique for a freshly minted name.
- **The card's meta line** (`components/crm/pipeline-board.tsx:146-150`):
  `"${formatMoney(value)} · ${formatMoney(expected)} expected · ${probability}%"`
  → for value `1000` and a Qualified deal: `$1,000.00 · $250.00 expected · 25%`.
  Assert on `· 25%` (or `25%`) rather than the whole string, so a
  `formatMoney` change does not break the drag test. Use `exact: false`
  deliberately here, and say so in a comment.
- **Nav labels need `{ exact: true }`.** `getByRole` performs a **substring**
  match by default. The CRM subnav contains "Organizations", "Contacts",
  "Deals", and "Pipeline"; a `getByRole("link", { name: "Deals" })` will also
  match any link whose accessible name contains "Deals" — including a deal row
  link on a detail page. The existing `e2e/crm.spec.ts:54` gets away without
  `exact: true` because it is on the list page; **these journeys are not all on
  the list page**, so `exact: true` is mandatory here.
- **Paths with parentheses** need quoting in prose and in any shell command:
  `"app/(authenticated)/crm"`. This affects the docs and any `grep` an
  implementer types, not the spec file itself.
- **Never assert on a CSS-module class** (`.crm-dialog`, `.card`). The classes
  are hashed. `e2e/groove.spec.ts` can select `.groove-master-leds` only because
  5.6 deliberately kept those as `:global` literals — the CRM classes are not,
  and `components/groove/groove-pass.test.ts` guards that contract.

#### 9. Journey F — a deal is created, appears on the board, and is deleted

**Shipped in 11.2, not 11.1.** This section is the written contract 11.2 copies

**Shipped in 11.2, not 11.1.** Same status as Journey F.
