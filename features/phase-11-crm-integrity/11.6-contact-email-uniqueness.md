# Feature 11.6: Contact email uniqueness + duplicate pre-check

**Phase:** 11 — CRM integrity, dead-ends, and list/task surface
**Status:** specced
**Estimated effort:** 4–6 hours
**Depends on:** nothing
**Blocks:** nothing

This is the **only Phase 11 feature that changes the schema.** No sibling may
emit a `drizzle/0008_*` (or later) migration.

## Goal

Two contacts in one database cannot hold the same email in any casing, and the
person who tries to create the twin is told which contact already owns it
instead of getting a 500. Closes **G9 / A1**. CRM copies the exact uniqueness
shape 8.1 shipped for `users.email`.

## Verified gap (opened on the working tree)

Opened, not assumed:

- `lib/crm/schema.ts:48` — `email: text("email")` is nullable, no `.unique()`.
- `lib/crm/schema.ts:59` — the only index on `contacts` is
  `index("contacts_tenantId_idx").on(table.tenantId)`. `uniqueIndex` does not
  appear in this file.
- `lib/crm/queries.ts:210` — `createContact` stores `short(input.email ?? null) ?? null`
  with no duplicate lookup.
- `components/crm/contact-form.tsx:22-25, 57, 102-115` — empty email becomes
  `null` via `emptyToNull`; the Email field has no duplicate message.
- `lib/crm/contact-actions.ts:64-79, 121-126` — `createContactAction` returns
  `Contact | null`; a unique-violation today would be an uncaught 500.
- `drizzle/0004_heavy_earthquake.sql`, `0005_uneven_prodigy.sql`,
  `0006_sleepy_preak.sql` — the IF NOT EXISTS + **name-not-definition** caveat
  this migration must copy.
- `lib/db/schema.ts:56` — 8.1's live shape:
  `uniqueIndex("users_email_lower_idx").on(sql\`lower(${table.email})\`)`.
- `lib/db/seed.ts:104-124` — `upsertUserByEmail` now looks up on `lower(email)`
  and updates by id. 8.1's shipped notes record why: the previous
  `onConflictDoUpdate({ target: users.email })` died with **42P10** once
  uniqueness moved to an expression index. CRM has no `onConflict` on contacts
  (`lib/crm/seed.ts:58-105` is a plain `createContact` insert). Do not add one.

The gap is open. Spec it.

## Scope

### Include

- The unique index, declared next to `contacts_tenantId_idx`:
  `uniqueIndex("contacts_email_lower_idx").on(sql\`lower(${table.email})\`)`.
  **Nullable columns are exempt from unique indexes in Postgres** (`NULL` is
  distinct from `NULL`), so contacts with no email are unaffected. That is why
  the migration is safe against the existing seed and against any tenant that
  already has several emailless contacts.
- Generated migration `drizzle/0008_*.sql`, then hand-edited `IF NOT EXISTS`
  with the **name-not-definition caveat written into the file**, exactly as
  0004/0005/0006 do.
- Two layers on write, and they are not redundancy (see Spec §3):
  1. a tenant-scoped pre-check on `lower(email)` that returns the existing row
     so the dialog can name it;
  2. a `23505` → typed error-code mapping on insert and update, because a race
     can land between the select and the insert.
- Memory-repo parity: the same case-insensitive rule, on create and on update
  (excluding the row being updated), same typed code.
- Trim on write; `""` becomes `NULL` (the form already does this at
  `contact-form.tsx:22-25`; the query layer must too, or two empty strings
  collide on `lower('')`).
- Dialog copy, exact: `A contact with that email already exists`, with a link
  to `/crm/contacts/{id}` of the existing record. `role="alert"` under the
  Email field.

### Exclude (for now)

- Email format / MX / deliverability. A1 is uniqueness, not RFC validation.
- Lowercasing stored addresses. Casing is preserved; comparison is `lower()`.
- A merge-duplicate-contact flow.
- `onConflictDoUpdate({ target: contacts.email })` — banned. It is the 42P10
  trap (Spec §3).
- Any change to `lib/db/seed.ts`, `e2e/crm.spec.ts`'s create-org flow, or the
  contact form's existing labels / `titleId`.
- Tenant-scoped composite uniqueness `(tenantId, lower(email))`. 8.1's index
  is global on the expression; this feature copies that shape. Cross-tenant
  address collisions are a recorded limit, not a reopen.

## Spec

1. **Index.** `contacts` extras become:

   ```ts
   (table) => [
     index("contacts_tenantId_idx").on(table.tenantId),
     uniqueIndex("contacts_email_lower_idx").on(sql`lower(${table.email})`),
   ]
   ```

   Postgres unique indexes do not consider `NULL` equal to `NULL`, so any
   number of contacts with `email IS NULL` continue to coexist. That is the
   reason this migration does not need a data backfill.

2. **Migration.** `npm run db:generate` is the source of the SQL. Read it.
   Expected statement, then made idempotent by hand:

   ```sql
   -- drizzle-kit does not emit IF NOT EXISTS; it is added by hand (as 0004,
   -- 0005, 0006 did). Postgres matches an existing index by NAME only, not by
   -- definition, so IF NOT EXISTS will keep whatever contacts_email_lower_idx
   -- already exists even if its expression differs.
   CREATE UNIQUE INDEX IF NOT EXISTS "contacts_email_lower_idx"
     ON "contacts" USING btree (lower("email"));
   ```

   No `DROP TABLE`, no enum rewrite, no RLS, no Groove table. After generate +
   hand-edit, `env -u DATABASE_URL npm run db:generate` prints "No schema
   changes, nothing to migrate".

3. **The 42P10 trap — why two layers are not redundancy.**

   8.1 shipped `upsertUserByEmail` as
   `onConflictDoUpdate({ target: users.email })`. After uniqueness moved to
   `users_email_lower_idx` on `lower(email)`, Postgres **cannot infer an
   expression index from a column-name conflict target**. It raises SQLSTATE
   **42P10** (*there is no unique or exclusion constraint matching the ON
   CONFLICT specification*). Proven on a real cluster in 8.1's shipped notes;
   the seed had to be rewritten to a `lower(email)` lookup + update-by-id.

   CRM copies the index shape, so it copies the trap. Therefore:

   - **Never** `onConflictDoUpdate({ target: contacts.email })` and never
     `onConflictDoNothing({ target: contacts.email })`. There is no unique
     constraint on the raw column to infer.
   - **Layer 1 (UX):** before insert/update, `SELECT` the session tenant's
     contact where `lower(email) = lower(trimmed)` and `id <> current` on
     update. If found, return typed code `duplicate_email` plus `{ id, name }`
     so the dialog can say "A contact with that email already exists" and link
     to `/crm/contacts/{id}`.
   - **Layer 2 (race):** if the insert/update still hits the index, map
     SQLSTATE `23505` (message may name `contacts_email_lower_idx`) to the
     **same** typed code. Do not 500. Between the pre-check and the insert
     another request can write the same address; 8.1 states this in as many
     words at `lib/auth/signup.ts:234-237`. Copy `isUniqueViolation` into the
     CRM drizzle module rather than importing it from `lib/auth/signup.ts`
     (auth must not become a CRM dependency).

   The pre-check is not "the" protection. The index is the invariant. The
   `23505` map is the backstop. The pre-check exists so the UI can name the
   other person.

4. **Memory repo.** `createContactInMemory` / `updateContactInMemory` refuse a
   case-variant duplicate with the same typed code. Comparison is
   `a.email && b.email && a.email.toLowerCase() === b.email.toLowerCase()`
   inside the same store (memory tests have one tenant at a time unless the
   test seeds two; still filter `tenantId`). Null emails never collide.
   Updating a contact to its own current email (any casing) succeeds.

5. **Action result.** Server actions return a serializable object, e.g.

   ```ts
   type ContactWriteResult =
     | { ok: true; contact: Contact }
     | {
         ok: false;
         code: "duplicate_email";
         existingId: string;
         existingName: string;
       };
   ```

   The client never value-imports `lib/crm/queries.ts`
   (`lib/client-boundary.test.ts:155-166` forbids it). `import type` from
   `queries-shared` is allowed.

6. **UI.** Under `#contact-email`, on submit (and on blur of a non-empty
   email if that is cheap): if `code === "duplicate_email"`, render
   `role="alert"` with the exact sentence **A contact with that email already
   exists** and a link whose accessible name is the existing contact's name,
   `href=/crm/contacts/{existingId}`. Clicking the link closes the dialog.
   A race fallback with no `existingId` still uses that sentence without a
   broken link.

7. **Seed / e2e.** `lib/crm/seed.ts` emails are unique already
   (`ana.ruiz@northwind.example` etc.). No seed change. `e2e/crm.spec.ts`
   create-org flow is untouched.

## Recorded limits

1. **The index is global on `lower(email)`, like `users_email_lower_idx`.** Two
   tenants cannot store the same address. Demo seed uses `@*.example`
   mailboxes (`lib/crm/seed.ts:58-105`); an owner adding one of those exact
   strings is refused. Per-tenant uniqueness would be `(tenantId, lower(email))`
   and is a different migration — `IF NOT EXISTS` matches by name, so changing
   the definition later requires `DROP INDEX`, not a silent recreate. Out of
   scope.
2. **No live concurrent race is proven in CI.** Vitest uses the memory repo.
   The honest gates are the index existing, the `23505` map, and the 42P10
   demonstration above.
3. **Pre-existing twins on a dirty Neon branch block migrate.** There is no
   merge tool in this feature.
4. **Format validation is not this feature.** `type="email"` in the form is
   unchanged.
5. **`WriteBatch` seed inserts cannot map `23505` the same way** (batch has no
   returning error per row). Seed data does not collide. Do not invent an
   onConflict to "fix" that — 42P10.
6. **This feature does not add `ListContactsOpts` fields** and does not touch
   deal filters, `/crm/tasks`, or QuickFind.
