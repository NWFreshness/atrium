# Feature 11.6: Contact email uniqueness and duplicate pre-check

**Phase:** 11 — CRM integrity, dead-ends, and list/task surface
**Status:** specced
**Estimated effort:** 4–6 hours
**Depends on:** nothing (scheduled after 11.2 in the calendar because it is the phase's only migration)
**Blocks:** nothing (11.10's QuickFind reaches contacts through `listContacts`, which is untouched)

## Goal

Two contacts in one tenant cannot hold the same email address in any casing, and
the person who tries to create the twin is told which contact already owns it
instead of silently making one. `contacts.email` is a bare nullable
`text("email")` at `lib/crm/schema.ts:48` with exactly one index,
`contacts_tenantId_idx` at `lib/crm/schema.ts:59`, so `Ana@x` and `ana@x` are two
rows today, and `createContact` passes `input.email` through untouched
(`lib/crm/queries.ts:210`). Contact search then returns both
(`lib/crm/queries-shared.ts:122-131`) and the top-organizations chart counts
against the twin. Closes **G9**; it is the CRM mirror of 8.1, which shipped
`users_email_lower_idx` for exactly this class of defect
(`features/phase-8-integrity/8.1-case-insensitive-email.md`).

**Three layers, and saying which is which is the point of this spec.** The
pre-check is **UX** — it produces the message that names the existing contact
and the link that opens it. The `23505` mapping is the **real guard**, because
between a `select` and an `insert` another request can write the same address;
8.1 states this in as many words at `lib/auth/signup.ts:234-237`. The unique
index is the **invariant**. Nothing below calls the pre-check "the" protection.

## Scope

Include:

- **The tenant-scoped composite unique index**, declared on the CRM table and
  generated as `drizzle/0008_*.sql`:
  `uniqueIndex("contacts_email_lower_idx").on(table.tenantId, sql\`lower(${table.email})\`)`.
  **This is the design-doc ruling** (Decision 4 in
  `docs/superpowers/specs/2026-09-29-crm-integrity-design.md`) **and it
  overrules a global `lower(email)`**, which matched `users_email_lower_idx`
  at `lib/db/schema.ts:56`. `users.email` is a login identity (platform-unique);
  `contacts.email` is tenant data. Owner and Demo are separate tenants
  (`lib/db/seed.ts:67`); the CRM seed puts four fixed addresses in the demo
  tenant (`lib/crm/seed.ts:58-105`). A global index would mean an owner can
  never add a contact at an address the demo seed already uses. The data lane
  proved that posture on PG 16.15: a second tenant inserting the same address
  was refused `23505` under the global shape. That is a tenancy bug, not a
  feature. The abort mechanics they measured still apply *inside* a tenant.
- **Trim on write** for `email` in `createContact` and `updateContact`, in the
  barrel, and `""` becoming `NULL` (see §1.3 — without it two empty strings
  collide in one tenant under `lower('')`, and the browser's email field sends
  `null` today via `emptyToNull`, `components/crm/contact-form.tsx:22-25`).
  No historical rewrite migration, and **no format regex** — A1 is uniqueness,
  not RFC validation.
- **The pre-check**, a `lower(email)` lookup scoped to the **session** tenant,
  run from the action on the email field's `onBlur` and on submit.
- **The `23505` mapping**, with `isUniqueViolation` **copied** into
  `lib/crm/queries-drizzle.ts` (not extracted to a shared module — see
  Implementation notes), applied in both `insertContact` and
  `updateContactInDrizzle`.
- **Memory-repo parity**: the memory store enforces the same rule with the same
  typed code, on create **and** on update, excluding the row being updated.
- **The dialog copy**: a `role="alert"` message under the Email field naming the
  existing contact, with a link that opens it and closes the dialog; plus the
  distinct race-fallback sentence. The action returns a **serializable result
  object**, never a thrown class across the wire, and the client never
  value-imports the error class.
- **Schema and migration tests** in `lib/db/schema.test.ts`, plus a rendered-SQL
  test proving the pre-check's predicate is `lower(email)` **and** carries the
  tenant, and a `null`/tenant/`""` policy test set in `lib/crm/queries.test.ts`
  and `lib/crm/contact-actions.test.ts`.
- **The operator runbook** (§7) and the browser journey in
  `e2e/crm-contacts.spec.ts`, including the cross-tenant case that the composite
  index exists to permit.

Exclude (for now):

- **Email format validation** (regex, MX, deliverability) and lowercasing stored
  addresses. Uniqueness is the feature; A1's own acceptance says nothing about
  shape. No `normalizeEmail`-style rewrite, unlike `lib/auth/signup.ts`.
- **A merge-duplicate-contact flow.** The design's Non-goals list names it. This
  feature refuses the second row and links to the first; it does not offer to
  combine them.
- **Auto-dedupe of pre-existing twins.** Collisions fail loudly (§7); nothing in
  this feature merges, picks a winner, or rewrites history. The phase never
  destroys data.
- **`onConflict` on `contacts.email`.** Banned twice over: naming a column as a
  conflict target while its only uniqueness is an expression index raises
  `42P10` (reproduced on the dev branch in `04-data-design.md`), and an
  `onConflictDoUpdate` would silently overwrite a real person — the exact class
  of loss the guard exists to prevent.
- **Any change to `lib/db/seed.ts`.** Its only conflict targets are
  `tenants.name` (`lib/db/seed.ts:150`, a byte-exact constraint that survives)
  and the untargeted form at `:202`. There is no CRM `onConflict` anywhere, so
  8.1's 42P10 trap does not recur here.
- **Cross-tenant duplicate detection.** Two tenants may hold the same address
  and that is correct; a global index is the thing being overruled.
- **Last-contacted, `occurredAt`, sorting, deal filters, `/crm/tasks`,
  QuickFind.** Those are 11.3, 11.4, 11.5, 11.8, 11.9, 11.10. **No
  `ListContactsOpts` field is added**, so the re-projection trap at
  `lib/crm/contact-actions.ts:48-52` has nothing to drop; 11.8 owns its twin at
  `lib/crm/deal-actions.ts:61-65`.
- **Escape-to-close and `useId()` on the contact dialog.** 11.5 owns Escape and
  focus restoration on the three existing record forms, and the design is
  explicit: do not refactor `titleId` on the three forms unless 11.5 touches
  that line. `const titleId = "contact-form-title"`
  (`components/crm/contact-form.tsx:47`) stays byte-identical in this feature.

## Spec

### 1. The data layer

#### 1.1 The index

```ts
// lib/crm/schema.ts — contacts table extras, replacing the single line at :59
(table) => [
  index("contacts_tenantId_idx").on(table.tenantId),
  // Uniqueness is per tenant on `lower(email)`, not on the raw column: `Ana@x`
  // and `ana@x` are one mailbox. Two properties make it safe on a nullable
  // column — Postgres treats NULL as distinct from every value *including
  // another NULL*, so email-less contacts are unconstrained; and the expression
  // contributes a NULL key rather than colliding with anything. Do NOT "fix"
  // this with `coalesce(lower(email), '')`, which would make every email-less
  // contact in a tenant collide with every other one.
  //
  // Tenant-scoped, unlike `users_email_lower_idx` (`lib/db/schema.ts:56`):
  // `users.email` is a login identity, this is tenant data. Owner and Demo are
  // separate tenants and the seed fixes four demo addresses
  // (`lib/crm/seed.ts:58-105`), so a global index would make those addresses
  // permanently unusable to the owner.
  //
  // Postgres cannot infer this index from `on conflict ("email")` — naming the
  // column raises 42P10. Every CRM contact write is a plain insert/update
  // (`insertContact`, `updateContactInDrizzle`, and `WriteBatch.insert` at
  // `:203`), so nothing in the repo does. Do not add one.
  uniqueIndex("contacts_email_lower_idx").on(
    table.tenantId,
    sql`lower(${table.email})`,
  ),
],
```

`tenantId` **leads**. The pre-check is `where tenantId = ? and lower(email) = ?`,
and a composite that merely *includes* `tenantId` does not serve a leading
`tenantId` equality the way the existing single-column index does. The test in
§5.1 pins the column order, not just the set.

`lower(email)` is not a data rewrite. Addresses keep the casing they were typed,
exactly as 8.1 kept `users.email` casing — see the shipped note at
`features/phase-8-integrity/8.1-case-insensitive-email.md:113-117`.

#### 1.2 The error class, and why it is not in the action file

```ts
// lib/crm/contact-errors.ts
export type ContactErrorCode = "duplicate_email";

export class ContactError extends Error {
  readonly code: ContactErrorCode;
  constructor(code: ContactErrorCode) {
    super(code);
    this.name = "ContactError";
    this.code = code;
  }
}
```

Two rules force this file to exist rather than sitting inside
`lib/crm/contact-actions.ts` where `04-data-design.md` proposed it:

1. A `"use server"` module may only export async functions. That file
   currently honours that (its only exports are the `*ForSession` and `*Action`
   functions, `lib/crm/contact-actions.ts:42-139`); a class export makes
   `next build` fail. The gate that catches it is the build, not a test.
2. The memory store (`lib/crm/queries-memory.ts`) and the Drizzle store
   (`lib/crm/queries-drizzle.ts`) both raise this error, and neither may import
   from a `"use server"` module — that would make the barrel's data layer depend
   on the action layer.

The file is a plain module with no imports, so `lib/client-boundary.test.ts`'s
`FORBIDDEN` pattern at `:155-166` does not match it (it matches
`lib/{crm,space,rolodex}/{queries,schema,seed,reset}`, and `contact-errors` is
none of those). That is a fact to be aware of, **not a licence**: the client
takes the code as a type only, per §3.

#### 1.3 Trim, in the barrel, and `""` → `NULL`

```ts
// lib/crm/queries.ts, beside `short` and `long` at :92-98
/**
 * The address is the uniqueness key, so it is normalised on the way in: a
 * trailing space is invisible to `lower(email)` but visible to the user as
 * "I entered that address and it let me". An empty string is not an address —
 * two contacts with `email: ''` in one tenant collide under `lower('')`, and
 * the form already sends `null` for an empty field
 * (`components/crm/contact-form.tsx:22-25`), so `''` is a client that skipped
 * `emptyToNull`, not a value to store.
 */
function normalizeContactEmail(value: unknown): string | null {
  if (value === null || value === undefined) {
    return null;
  }
  const text = assertText(value, MAX_SHORT_TEXT);
  return typeof text === "string" && text.trim() !== "" ? text.trim() : null;
}
```

Then, in `createContact` (replacing `:210`):

```ts
email: normalizeContactEmail(input.email),
```

and in `updateContact` (replacing `:231`'s `short(input.email)`), building a new
input object rather than mutating the caller's:

```ts
const normalized =
  input.email === undefined
    ? input
    : { ...input, email: normalizeContactEmail(input.email) };
```

…then dispatching `normalized` to the store instead of `input`. The
`phone` / `jobTitle` / `name` assertions at `:230-233` are untouched. Order is
**trim, then length**, so a 500-character address with a trailing space is
accepted as 500.

This is a behaviour change to **new writes only**. Existing untrimmed rows stay
untouched until they are edited, which is why the runbook's pre-flight groups on
`lower(btrim(email))` (§7) rather than `lower(email)`: it shows the operator the
collisions the index is about to hit, not the ones the current seed happens to
avoid.

### 2. The stores — the invariant half

#### 2.1 Drizzle: `23505` → `ContactError`

```ts
// lib/crm/queries-drizzle.ts
const UNIQUE_VIOLATION = "23505";

/**
 * Copied from `lib/auth/signup.ts:211-225` rather than extracted: the shared
 * module is a drive-by edit to a shipped auth file for a fifteen-line
 * predicate, and this phase takes no such refactor. Two copies until a later
 * cleanup — if you change this, change that one in the same commit, and if you
 * extract, delete both in the same commit.
 *
 * Asserts the SQLSTATE or the message. **Never the index name**: the constraint
 * name appearing in the error has already broken this repo once (8.1's shipped
 * notes), and renaming the index must not change behaviour.
 */
export function isUniqueViolation(error: unknown): boolean {
  if (typeof error !== "object" || error === null) {
    return false;
  }
  const candidate = error as { code?: unknown; message?: unknown };
  if (candidate.code === UNIQUE_VIOLATION) {
    return true;
  }
  return (
    typeof candidate.message === "string" &&
    candidate.message.includes("duplicate key value")
  );
}
```

The export exists so the predicate is unit-testable: `insertContact` calls
`requireCrmDb()` → `getDb()`, which builds a real Neon client from
`process.env.DATABASE_URL` (`lib/db/index.ts:7-19`), so there is no seam to
inject a throwing database through. The predicate is the testable unit, and it
is the unit the "never match the index name" rule lives in.

`insertContact` (`:198-212`) becomes:

```ts
export async function insertContact(
  row: Contact,
  opts?: WriteOpts,
): Promise<Contact> {
  if (opts?.batch) {
    opts.batch.insert(contacts, row);
    return clone(row);
  }

  try {
    const [inserted] = await requireCrmDb()
      .insert(contacts)
      .values(row)
      .returning();
    return inserted;
  } catch (error) {
    if (isUniqueViolation(error)) {
      throw new ContactError("duplicate_email");
    }
    throw error;
  }
}
```

`updateContactInDrizzle` (`:214-234`) gets the same `try`/`catch` around its
`await`, and **keeps rethrowing anything that is not a unique violation** — an
offline database must not be reported to a user as "that email may already be in
use".

The `opts?.batch` branch is unchanged and **cannot** map the violation: it
collects a statement and returns. See Recorded limits.

#### 2.2 Memory: the same policy, the same code

```ts
// lib/crm/queries-memory.ts — createContactInMemory, replacing the bare push
export function createContactInMemory(
  repo: CrmRepository,
  row: Contact,
): Contact {
  if (findContactByEmailInMemory(repo, row.tenantId, row.email, null)) {
    throw new ContactError("duplicate_email");
  }
  repo.contacts.push(row);
  return clone(row);
}
```

and, in `updateContactInMemory` (`:145-163`), **after** `findScoped` has resolved
the row and **before** any field is assigned:

```ts
if (input.email !== undefined) {
  const clash = findContactByEmailInMemory(repo, scoped, input.email, id);
  if (clash) {
    throw new ContactError("duplicate_email");
  }
}
```

The exclusion by id is load-bearing. Without it, editing a contact's job title
while it keeps its own address raises a false duplicate, and 11.5's
edit-from-detail journey — which submits the whole form, address included —
would start failing on every save. That is the defect class, so it gets its own
test case (§6, `queries.test.ts`).

`findContactByEmailInMemory` is the policy twin and lives next to the other
memory helpers:

```ts
export function findContactByEmailInMemory(
  repo: CrmRepository,
  tenantId: string,
  email: string | null,
  excludeId: string | null,
): Contact | null {
  if (email === null) {
    return null;
  }
  const needle = email.toLowerCase();
  const hit = repo.contacts.find(
    (row) =>
      row.tenantId === tenantId &&
      row.id !== excludeId &&
      row.email !== null &&
      row.email.toLowerCase() === needle,
  );
  return hit ? clone(hit) : null;
}
```

`row.email !== null` reproduces Postgres's NULL-is-distinct rule in memory. Drop
it and two email-less contacts collide in the memory repo but not in the
database — the parity this whole half exists to protect.

#### 2.3 The pre-check query, dispatcher plus both stores

One new helper, following binding rule 7 (dispatcher in the barrel, an
implementation in each store, never `db.*` in `queries.ts`):

```ts
// lib/crm/queries.ts
export async function findContactByEmail(
  tenantId: string,
  email: string,
  repo?: CrmRepository,
): Promise<Contact | null> {
  const scoped = requireTenantId(tenantId);
  const needle = email.trim();
  if (needle === "") {
    return null;
  }
  if (repo) {
    return findContactByEmailInMemory(repo, scoped, needle, null);
  }
  return findContactByEmailInDrizzle(scoped, needle);
}
```

`tenantId` first, then a required argument, then the optional `repo` — the same
order every other helper uses. `requireTenantId` throws on a blank tenant
(`lib/crm/queries-shared.ts:84-89`), so this is a second line of defence behind
`requireTenant`.

```ts
// lib/crm/queries-drizzle.ts
/** The pre-check's predicate, exported so its shape is assertable without a database. */
export function contactEmailMatchSql(tenantId: string, email: string) {
  return and(
    eq(contacts.tenantId, tenantId),
    sql`lower(${contacts.email}) = ${email.toLowerCase()}`,
  );
}

export async function findContactByEmailInDrizzle(
  scoped: string,
  email: string,
): Promise<Contact | null> {
  const [row] = await requireCrmDb()
    .select()
    .from(contacts)
    .where(contactEmailMatchSql(scoped, email))
    .limit(1);
  return row ?? null;
}
```

**`lower(email) = $2`, never `eq(contacts.email, $2)`.** A plain equality is the
easiest way to ship a guard that does not work: it misses `Ana@x` when the user
types `ana@x`, and the insert then dies on `23505` — which is the correct
outcome, but every user sees the vague race-fallback sentence instead of the
specific one. `lib/db/seed.ts:176` and `lib/auth/signup.ts:245` are the in-repo
precedents for the `sql\`lower(...)\`` shape, and the planner uses an expression
index for exactly this predicate (measured in `04-data-design.md`).

The tenant predicate is not optional. This is a lookup whose **result** is
another person's row, and the session `tenantId` is the only thing scoping it.

**Why not reuse `listContacts({ q })`.** Its search is a substring `ILIKE` over
name, email and job title (`lib/crm/queries-drizzle.ts:71-81`) — unbounded, no
index usable, and it would match `x-ana@…` and `Ana@…-plus`. Post-filtering an
unbounded list in memory to get an exact key is the "claim about arrays" failure
the design warns about. The named helper is the fix.

### 3. The action — the friendly half

#### 3.1 The result type

```ts
// lib/crm/contact-actions.ts
export type ContactResult =
  | { ok: true; contact: Contact }
  | {
      ok: false;
      code: ContactErrorCode;
      existing?: { id: string; name: string; email: string };
    };
```

`ContactErrorCode` is imported from `./contact-errors` and re-exported as a
**type only** (`export type { ContactErrorCode } from "./contact-errors";`) so a
client can narrow on it without a value import. `ContactResult` is exported as a
type; types are erased at build time, so the `"use server"` export rule is not
touched.

One code, not two. The copy table has exactly two duplicate sentences and the
second is chosen by `existing` being absent — so the client never needs to
distinguish "the pre-check found it" from "the index caught the race", it only
needs to know whether it may name a record. A second `"unavailable"` code would
need a third sentence, and no third sentence is copy for this phase.

#### 3.2 Exact validation order in `createContactForSession`

Unchanged steps, then the new one, then dispatch. The order is the contract:

1. `const { tenantId } = await requireTenant(getSession, input);` (`:69`)
2. `if (!isContactStatus(input.status)) return failure;` (`:70-72`)
3. `if (!(await requireSessionOrganization(...))) return failure;` (`:73-77`)
4. **new** — resolve the address and pre-check:
   ```ts
   const email =
     input.email === undefined ? null : normalizeContactEmail(input.email);
   if (email !== null) {
     const existing = await findContactByEmail(tenantId, email, repo);
     if (existing) {
       return {
         ok: false,
         code: "duplicate_email",
         existing: { id: existing.id, name: existing.name, email: existing.email },
       };
     }
   }
   ```
5. dispatch, and map the store's typed error:
   ```ts
   try {
     return { ok: true, contact: await createContact(tenantId, input, repo) };
   } catch (error) {
     if (error instanceof ContactError) {
       return { ok: false, code: error.code };
     }
     throw error;
   }
   ```

Step 5's `catch` is the **race fallback path**: the pre-check missed, and the
index — memory's explicit guard or Postgres's `23505` — refused. `existing` is
absent, so the client renders the generic sentence. A re-lookup there would
narrow the window to a fraction of a millisecond and add a query to the rare
path; the design's copy for this case is explicitly the one that "must not imply
a specific record exists when the server may not know which".

`updateContactForSession` (`:81-98`) is the same shape, with the contact's own
id as the exclusion:

```ts
const existing = await findContactByEmail(tenantId, email, repo);
if (existing && existing.id !== id) { /* return the same failure */ }
```

The exclusion lives in the action as well as in the memory store, because the
Drizzle pre-check has no `NOT id = ?` clause and the action must not report the
row the user is editing as its own duplicate.

`normalizeContactEmail` is **not exported from `queries.ts`**; the action uses
the trimmed string for the pre-check and lets the barrel normalise again on the
way in. Trimming twice is idempotent, and a second trim is cheaper than a second
export.

#### 3.3 The pre-check action

```ts
export async function checkContactEmailAction(
  email: string,
  excludeId?: string,
): Promise<
  | { ok: true }
  | {
      ok: false;
      code: ContactErrorCode;
      existing: { id: string; name: string; email: string };
    }
> {
  const { auth } = await import("@/auth");
  const { tenantId } = await requireTenant(auth);
  const needle = typeof email === "string" ? email.trim() : "";
  if (needle === "") {
    return { ok: true };
  }
  const existing = await findContactByEmail(tenantId, needle);
  if (existing && existing.id !== excludeId) {
    return {
      ok: false,
      code: "duplicate_email",
      existing: {
        id: existing.id,
        name: existing.name,
        email: existing.email,
      },
    };
  }
  return { ok: true };
}
```

There is no `repo` parameter on this action: it always reads the real store, so
the branch a blur takes is the branch a submit takes. Injectable-repo parity is
covered by `*ForSession` (§3.2), which is where the tests are.

`excludeId` is a string comparison against an id the pre-check **already scoped
to the caller's own tenant**, so a foreign id reveals nothing: the answer is
either "that address is free in your tenant" or "here is one of your contacts".
It is not a data leak and it is not a tenant-id input.

- `onSubmit` branches (§4.1). `onBlur` on the email input runs the pre-check

#### 4.1 Submit


Two changes from today (`:63-74`): the result is inspected, and
`router.refresh(); onClose();` no longer run unconditionally. On a duplicate the
dialog **stays open with the typed values intact** — closing it would discard
what the user entered and make the message's "open the other record" advice
useless.

`createContactAction` / `updateContactAction` change their declared return type
from `Contact | null` to `Promise<ContactResult>` (`:121-134`). Every other
caller of those two functions is in this file, and every other `*Action` in
`lib/crm/` keeps its `T | null` shape, so this is a local signature change, not
a pattern change.

#### 4.2 Blur

```ts
async function onEmailBlur() {
  const typed = values.email.trim();
  if (typed === "") {
    setDuplicate(null);
    return;
  }
  if (contact && typed.toLowerCase() === (contact.email ?? "").toLowerCase()) {
    setDuplicate(null);
    return;
  }
  const result = await checkContactEmailAction(typed, contact?.id);
  setDuplicate(result.ok ? null : result);
}
```

The unchanged-address short-circuit is not an optimisation, it is correctness of
tone: re-checking a value the user did not change asks the server a question
whose answer cannot have changed while the dialog was open, and the extra
round trip on every field exit is the cost of getting the wrong answer.

Blur **does not** move focus. The `role="alert"` announcement is the feedback;
stealing focus out of the field the user is still in is a worse trade. Focus
moves only on submit (§4.3).

### 7. The migration and the operator runbook

**Order, and each step's evidence:**

1. `npm run db:generate` with the schema change in place. Read the generated
   `drizzle/0008_*.sql` and the new `drizzle/meta/0008_snapshot.json`. The
   snapshot should show one new index on `contacts`, `isUnique: true`, with
   `expression: lower("email")` and the `tenantId` column — 8.1 read its own
   snapshot the same way (`:97-99`).
2. **Hand-edit the SQL** (0004/0005/0006 each did; see the comment at
   `drizzle/0005_uneven_prodigy.sql:4-7` and `drizzle/0006_sleepy_preak.sql:4-8`):
   - add `IF NOT EXISTS` after `INDEX` — drizzle-kit does not emit it, and a
     branch that already carries the name would otherwise wedge the migrator;
   - write the caveat above the statement, in the file, in the 0006 voice:
     *Postgres matches an existing index by **name** only, not by definition, so
     `IF NOT EXISTS` will keep whatever `contacts_email_lower_idx` already
     exists even if its expression differs.*
   - there is **no `ALTER TABLE`** — nothing byte-exact exists to drop, so the
     file is one statement. Unlike 0006, which needed
     `ALTER TABLE "users" DROP CONSTRAINT`.
   - keep `-->` statement-breakpoint formatting if the generator emitted it.
3. **Second generate must be a no-op.** `env -u DATABASE_URL npm run db:generate`
   prints drizzle-kit's "No schema changes, nothing to migrate" (8.1's criterion
   5, `:52`) and creates **no** `0009_*` file; `drizzle/meta/_journal.json` is
   unchanged at eight entries. The wording is drizzle-kit's; the check that
   matters is that no new file appears.
4. **Pre-flight, and it stops the run if it finds anything:**
   ```sql
   SELECT "tenantId", lower(btrim(email)) AS email_key, count(*) AS rows
   FROM contacts
   WHERE email IS NOT NULL
   GROUP BY "tenantId", lower(btrim(email))
   HAVING count(*) > 1
   ORDER BY rows DESC, email_key;
   ```
   `btrim` because the trim is new: an untrimmed existing row and a trimmed one
   are the collision the index is about to reject, and grouping on `lower(email)`
   *without* `tenantId` would mix tenants. **Any row returned means stop.** Do
   **not** `DELETE` a twin — `deals.contactId` and `activities.contactId` are
   `ON DELETE SET NULL` (`lib/crm/schema.ts:75-77`); the data lane verified
   that deleting the loser silently orphaned 1 deal and 1 activity. The
   data-minimal, children-safe option is `UPDATE … SET email = NULL` on the
   loser. Which contact survives a *merge* (re-pointing children) is a product
   decision this feature must not make. No auto-dedupe.
5. `npm run db:migrate` on the **dev** branch, on the feature branch,
   **pre-merge** (the design's "Who migrates 11.6" ruling). Never paste or
   print the connection string; assert presence by boolean.
6. **Read back the name and the definition — mandatory**, because
   `IF NOT EXISTS` can keep a wrong definition:
   ```sql
   SELECT indexname, indexdef
   FROM pg_indexes
   WHERE tablename = 'contacts'
   ORDER BY indexname;
   ```
   The row must be UNIQUE, must mention `lower(` and the quoted `tenantId`, and
   `contacts_tenantId_idx` must still be there and still non-unique. Record the
   output in the shipped notes.
7. **Prove the invariant on real Postgres**, not on the memory repo: insert a
   contact, then insert a case-variant in the **same** tenant and confirm
   `23505`; confirm the same address in a **different** tenant succeeds (this is
   the tenant composite, live); confirm two contacts with `email = NULL` both
   insert.
8. Post-merge, the controller migrates prod per the `HANDOFF.md` rule.

**Controller-measured, in this session, on the dev branch** (asserted by boolean
and by counts; no value read): the branch is migrated through all eight
migrations, so `__drizzle_migrations` carries `0000`–`0007` and there is no
"fresh branch" surprise; `contacts.email` has **zero** collisions under
`lower(email)` across the tenant's contacts, so `CREATE UNIQUE INDEX` will not
fail on dev today; and the count of contacts with a NULL email is **zero**, so
**the seed gives every contact an address and the NULL-is-exempt property is not
covered by any existing fixture**. That is why §6 case 2 exists and why step 7
proves it on the database. If a developer adds a colliding pair between now and
step 4, the pre-flight finds it and the feature stops — which is the design
saying so, not a defect.

## Implementation notes

- **The `tenantId indexes` gate failure is the first thing that will happen when
  you run the suite**, and it is not a mistake in your work. Narrow the
  predicate as §5.1 says and say why in a comment. If you instead widen the
  expectation to two indexes, the block's own docstring — "the B-tree index that
  makes `where tenantId = ?` cheap" — stops being true, and the next
  feature that adds a composite on a tenant-scoped table will inherit a gate
  that cannot tell a leading index from a trailing one.
- **`IF NOT EXISTS` matches by name, not by definition.** The read-back in §7
  step 6 is therefore not ceremony: it is the only thing that catches a branch
  already carrying a *different* index under the same name. 0006's comment says
  the same in its own file (`drizzle/0006_sleepy_preak.sql:4-8`).
- **`lower()` is not a rewrite.** Addresses keep their typed casing, matching
  8.1's shipped decision for `users.email`. Do not add a normalisation migration.
- **`""` → `NULL` is not cosmetic.** Without it, a client that skips
  `emptyToNull` stores `''`, and two such contacts in one tenant are a real
  `23505` on the very insert the pre-check approved. This is the same class of
  bug as 11.8's inverted date window: the guard and the write must agree.
- **`isUniqueViolation` is copied, not extracted.** The design ruled this twice
  (the DRY extract would edit a shipped auth file for fifteen lines; two copies
  until a later cleanup). The copy's comment names its origin so the eventual
  cleanup can find both. If you extract, it is its own feature with its own
  tests, not a drive-by in this PR.
- **The `WriteBatch` path cannot map `23505`.** `insertContact`'s
  `opts?.batch` branch returns a collected statement, and the violation surfaces
  when the batch is flushed — so the demo reset's reseed (and `seedCrm`'s, at
  `lib/crm/reset.ts:47-51`) fails at `batch.flush()` with an untyped Postgres
  error if the tenant holds a colliding contact. That is the invariant asserting
  itself; do not weaken the index to make a reset succeed, and do not add an
  `onConflict` to the batch insert.
- **The pre-check is a `select` that returns another person's row.** The only
  thing scoping it is the session `tenantId`, which is why the SQL assertion in
  §5.2 exists as a literal test and not a comment.
- **Memory repo proves policy, not SQL.** Every `describe` block here runs
  under `env -u DATABASE_URL npm test` against
  `createMemoryCrmRepository()`. `lib/crm/queries-drizzle.ts` is never executed
  in CI — job `ci` runs `npm test` and `npm run build`
  (`.github/workflows/ci.yml:22-25`) with no Postgres. **Zero of this feature
  is proven by CI.** Job `e2e` now gates on all six secrets (PR #90,
  `76e4d35`); the repository currently has **zero** Actions secrets, so the
  job honestly reports `ready=false` and skips. Do not make a second `ci.yml`
  edit. Read the `e2e` job log for `ready=true` and a non-zero Playwright count.
- **The race is not testable here.** Two concurrent writers both pass a
  pre-check; that is what 8.1 recorded and what `lib/auth/signup.ts:234-237`
  still says. The honest gate is the index existing, the `23505` mapping being
  unit-tested, and the live probe in §7 step 7.
- **Shipped notes are read as evidence.** Every claim above is `path:line` into
  the working tree at `main`. A claim about history (`git show main:<path>`) is
  not made anywhere in this spec. `features/phase-1-crm/1.4-contacts.md` is the
  contact feature's spec; the ideas doc's `lib/crm/schema.ts:47` line reference

### Migration safety — proven on a real PostgreSQL 16 cluster (commit `ab63591`)

Every claim below was run on a throwaway `postgres:16-alpine` 16.15 instance
that took all eight repo migrations in order (`0000`→`0007`, `psql -f`, each
exit 0), then a fixture of two case-variant contacts, two null-email contacts,
and a deal + activity attached to each duplicate. Not unit tests, not theory.
`DATABASE_URL` was never touched. The probe used the **global** index shape;
the abort / rollback / `CONCURRENTLY` / SET NULL / nullable / 42P10 /
memory-repo facts still hold. The composite chosen above only changes *which*
duplicates collide (same tenant, not every tenant).

**1. The index create aborts, and it aborts the whole migration.** With
`Ana@Northwind.Example` and `ana@northwind.example` both present in one tenant:

```
BEGIN
ERROR:  23505: could not create unique index "contacts_email_lower_idx"
DETAIL:  Key (lower(email))=(ana@northwind.example) is duplicated.
CONSTRAINT NAME:  contacts_email_lower_idx
ROLLBACK
```

`pg_indexes` afterwards still lists only `contacts_pkey` and
`contacts_tenantId_idx` — **no `contacts_email_lower_idx`**. Because the
migrator runs each migration inside a transaction, the `23505` rolls the
statement back and the index is simply absent; the next migrate retries and
fails identically. This is a deploy-stopping loop, not a warning. Under the
composite the DETAIL key is `(tenantId, lower(email))`; the loop is the same.

**2. Remediation order** (each step verified):

1. Read-only audit *before* merging (the `GROUP BY "tenantId", lower(btrim(email))` query in §7). Zero rows → migrate is safe as written.
2. Dedupe **before** the index, never after. Verified: `UPDATE contacts SET email = NULL WHERE id = 'c_ana2';` then the create → `CREATE INDEX`, exit 0.
3. Nulling the loser's email is the data-minimal, children-safe option (nulls are exempt).
4. **Deleting the loser is a trap.** Both `contactId` FKs are `ON DELETE SET NULL`. Verified: deleting `c_ana2` left 1 deal and 1 activity NULL — no error, no cascade. Do not delete. Re-pointing children is a merge, and merge policy is product's call, not this spec's.
5. Then and only then run the 11.6 migration.

**3. `CONCURRENTLY` is not available.** The pg migrator wraps every migration
in one transaction (`drizzle-orm/pg-core/dialect.js:60`). Verified:

```
BEGIN
ERROR:  25001: CREATE INDEX CONCURRENTLY cannot run inside a transaction block
```

Follow 7.3: plain `CREATE UNIQUE INDEX`, accept the write lock. Same driver
limit as 8.1: `@neondatabase/serverless` cannot reach plain TCP Postgres, so
this probe ran drizzle's SQL through `psql`.

**4. Nullable exemption verified.** After the index existed, 5 NULL-email
contacts coexisted. Case-variant insert failed `23505`. A different address
inserted fine.

**5. 42P10 is live for any future `onConflict` on contacts.** With only the
expression index, `ON CONFLICT ("email") DO UPDATE` fails `42P10`.
`ON CONFLICT ((lower("email")))` works (or the composite equivalent). Today
no CRM `onConflict` exists (`insertContact` is a bare insert at
`lib/crm/queries-drizzle.ts:207-211`). Guard, not a fix.

**6. Memory repo parity is currently FALSE.** `lib/crm/queries-memory.ts` has
no `toLowerCase` / `lower(` — whole-file grep is empty.
`createContactInMemory` (`:137-143`) is a bare `push`;
`updateContactInMemory` (`:155-156`) assigns `row.email = input.email` with
no duplicate check. Acceptance criteria 6–10 are the work that closes this,
not a claim about current code.

**7. Add a spec-test on the migration's SQL**, not just the schema — already
required above (criterion 4).

## Recorded limits

1. **The index is structurally unprovable in CI.** Job `ci` has no Postgres
   (`.github/workflows/ci.yml:22-25`) and job `e2e` may skip on secrets
   (`ci.yml:46`). A reviewer reading a green checkmark for this feature is
   reading a memory-repo policy test and a migration-string test. The real
   evidence is §7's runbook output, recorded in the shipped notes.
2. **A concurrent race is unproven.** Vitest cannot stage two writers. The
   `23505` predicate is unit-tested and the index is proven live in §7 step 7;
   the interleaving itself is not.
3. **The `WriteBatch` path has no typed duplicate mapping.** A demo reset that
   reseeds into a tenant with a colliding contact fails at `batch.flush()` with
   a raw Postgres error. That is correct behaviour — the invariant asserting
   itself — but it is an unhandled error, and nothing in this feature makes it
   friendlier.
4. **Existing untrimmed addresses are not rewritten.** A stored `"ana@x "` stays
   that way until the contact is edited. The §7 pre-flight groups on
   `lower(btrim(email))` precisely so the operator sees the collision the index
   is about to raise, and the migration will fail loudly if one exists. No
   historical data migration ships in this feature.
5. **The `tenantId indexes` gate was narrowed.** That is a real change to a
   shipped assertion and a reviewer should treat it as one: the filter no
   longer sees any index that *includes* `tenantId`. A future composite that
   leads on `tenantId` would be invisible to that gate — which is why criterion
   2 pins this table's composite explicitly instead of relying on the general
   one.
6. **Nothing here is an email-quality check.** `"nope"` is a legal, unique
   address in this schema. Uniqueness is the feature; shape validation is
   excluded in `## Scope` and belongs to a feature that says so.
7. **Copy quality is not proven.** Whether
   `Ana Ruiz already uses ana.ruiz@…` is the right sentence, and whether the
   link's placement in the alert paragraph is the right one, are human reads.
   The two strings are pinned so a reviewer can judge them side by side with the
   signup vagueness they deliberately depart from.
8. **Accessibility of the new pair is unverified in a browser.** `role="alert"`,
   `aria-describedby` and `aria-invalid` are the ARIA contract; no screen
   reader was run, and no contrast number was measured by this feature — the
   `--clay-ink` on `--bg-1` pair is inherited from the gate that already checks
   it. A manual NVDA/VoiceOver pass over the duplicate message, and a 375 px
   look at the alert's wrapping, are the checks this feature cannot perform.
9. **`e2e/crm-contacts.spec.ts` is new and therefore unproven in CI as it
   stands.** After 11.1's readiness fix it runs only when the demo pair is
   present; with zero repo secrets, a green `e2e` job means every test in it skipped.
10. **Pre-existing twins on a dirty branch block migrate.** Verified on PG 16.15
    (`ab63591`): `CREATE UNIQUE INDEX` aborts `23505` and leaves no index, so
    migrate fails identically on retry. Audit first; dedupe before the index.
11. **Deleting a duplicate contact is a trap.** Both `contactId` FKs are
    `ON DELETE SET NULL`. Verified: 1 deal + 1 activity left NULL, no error.
    Null the loser's email. Which contact survives a merge is product's call
    (not decided here).
12. **`CREATE UNIQUE INDEX CONCURRENTLY` is unavailable.** Migrator wraps
    migrations in one transaction (`drizzle-orm/pg-core/dialect.js:60`) →
    `25001`. Follow 7.3.
13. **The index is per-tenant, not global.** Two tenants may store the same
    address. `IF NOT EXISTS` matches by name; changing the definition later
    requires `DROP INDEX`. Do not silently recreate.
