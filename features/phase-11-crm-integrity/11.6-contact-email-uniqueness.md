# Feature 11.6: Contact email uniqueness + duplicate pre-check

**Phase:** 11 — CRM integrity, dead-ends, and list/task surface
**Status:** specced
**Estimated effort:** 4–6 hours
**Depends on:** nothing
**Blocks:** nothing

This is the **only Phase 11 feature that changes the schema.** No sibling may
emit a `drizzle/0008_*` (or later) migration.

## Goal

Two contacts in one database cannot hold the same email in any casing, and the
person who tries to create the twin is told which contact already owns it
instead of getting a 500. Closes **G9 / A1**. CRM copies the exact uniqueness
shape 8.1 shipped for `users.email`.

## Verified gap (opened on the working tree)

Opened, not assumed:

- `lib/crm/schema.ts:48` — `email: text("email")` is nullable, no `.unique()`.
- `lib/crm/schema.ts:59` — the only index on `contacts` is
  `index("contacts_tenantId_idx").on(table.tenantId)`. `uniqueIndex` does not
  appear in this file.
- `lib/crm/queries.ts:210` — `createContact` stores `short(input.email ?? null) ?? null`
  with no duplicate lookup.
- `components/crm/contact-form.tsx:22-25, 57, 102-115` — empty email becomes
  `null` via `emptyToNull`; the Email field has no duplicate message.
- `lib/crm/contact-actions.ts:64-79, 121-126` — `createContactAction` returns
  `Contact | null`; a unique-violation today would be an uncaught 500.
- `drizzle/0004_heavy_earthquake.sql`, `0005_uneven_prodigy.sql`,
  `0006_sleepy_preak.sql` — the IF NOT EXISTS + **name-not-definition** caveat
  this migration must copy.
- `lib/db/schema.ts:56` — 8.1's live shape:
  `uniqueIndex("users_email_lower_idx").on(sql\`lower(${table.email})\`)`.
- `lib/db/seed.ts:104-124` — `upsertUserByEmail` now looks up on `lower(email)`
  and updates by id. 8.1's shipped notes record why: the previous
  `onConflictDoUpdate({ target: users.email })` died with **42P10** once
  uniqueness moved to an expression index. CRM has no `onConflict` on contacts
  (`lib/crm/seed.ts:58-105` is a plain `createContact` insert). Do not add one.

The gap is open. Spec it.

## Scope

### Include

- The unique index, declared next to `contacts_tenantId_idx`:
  `uniqueIndex("contacts_email_lower_idx").on(sql\`lower(${table.email})\`)`.
  **Nullable columns are exempt from unique indexes in Postgres** (`NULL` is
  distinct from `NULL`), so contacts with no email are unaffected. That is why
  the migration is safe against the existing seed and against any tenant that
  already has several emailless contacts.
- Generated migration `drizzle/0008_*.sql`, then hand-edited `IF NOT EXISTS`
  with the **name-not-definition caveat written into the file**, exactly as
  0004/0005/0006 do.
- Two layers on write, and they are not redundancy (see Spec §3):
  1. a tenant-scoped pre-check on `lower(email)` that returns the existing row
     so the dialog can name it;
  2. a `23505` → typed error-code mapping on insert and update, because a race
     can land between the select and the insert.
- Memory-repo parity: the same case-insensitive rule, on create and on update
  (excluding the row being updated), same typed code.
- Trim on write; `""` becomes `NULL` (the form already does this at
  `contact-form.tsx:22-25`; the query layer must too, or two empty strings
  collide on `lower('')`).
- Dialog copy, exact: `A contact with that email already exists`, with a link
  to `/crm/contacts/{id}` of the existing record. `role="alert"` under the
  Email field.

### Exclude (for now)

- Email format / MX / deliverability. A1 is uniqueness, not RFC validation.
- Lowercasing stored addresses. Casing is preserved; comparison is `lower()`.
- A merge-duplicate-contact flow.
- `onConflictDoUpdate({ target: contacts.email })` — banned. It is the 42P10
  trap (Spec §3).
- Any change to `lib/db/seed.ts`, `e2e/crm.spec.ts`'s create-org flow, or the
  contact form's existing labels / `titleId`.
- Tenant-scoped composite uniqueness `(tenantId, lower(email))`. 8.1's index
  is global on the expression; this feature copies that shape. Cross-tenant
  address collisions are a recorded limit, not a reopen.

## Spec

1. **Index.** `contacts` extras become:

   ```ts
   (table) => [
     index("contacts_tenantId_idx").on(table.tenantId),
     uniqueIndex("contacts_email_lower_idx").on(sql`lower(${table.email})`),
   ]
   ```

   Postgres unique indexes do not consider `NULL` equal to `NULL`, so any
   number of contacts with `email IS NULL` continue to coexist. That is the
   reason this migration does not need a data backfill.

2. **Migration.** `npm run db:generate` is the source of the SQL. Read it.
   Expected statement, then made idempotent by hand:

   ```sql
   -- drizzle-kit does not emit IF NOT EXISTS; it is added by hand (as 0004,
   -- 0005, 0006 did). Postgres matches an existing index by NAME only, not by
   -- definition, so IF NOT EXISTS will keep whatever contacts_email_lower_idx
   -- already exists even if its expression differs.
   CREATE UNIQUE INDEX IF NOT EXISTS "contacts_email_lower_idx"
     ON "contacts" USING btree (lower("email"));
   ```

   No `DROP TABLE`, no enum rewrite, no RLS, no Groove table. After generate +
   hand-edit, `env -u DATABASE_URL npm run db:generate` prints "No schema
   changes, nothing to migrate".

3. **The 42P10 trap — why two layers are not redundancy.**

   8.1 shipped `upsertUserByEmail` as
   `onConflictDoUpdate({ target: users.email })`. After uniqueness moved to
   `users_email_lower_idx` on `lower(email)`, Postgres **cannot infer an
   expression index from a column-name conflict target**. It raises SQLSTATE
   **42P10** (*there is no unique or exclusion constraint matching the ON
   CONFLICT specification*). Proven on a real cluster in 8.1's shipped notes;
   the seed had to be rewritten to a `lower(email)` lookup + update-by-id.

   CRM copies the index shape, so it copies the trap. Therefore:

   - **Never** `onConflictDoUpdate({ target: contacts.email })` and never
     `onConflictDoNothing({ target: contacts.email })`. There is no unique
     constraint on the raw column to infer.
   - **Layer 1 (UX):** before insert/update, `SELECT` the session tenant's
     contact where `lower(email) = lower(trimmed)` and `id <> current` on
     update. If found, return typed code `duplicate_email` plus `{ id, name }`
     so the dialog can say "A contact with that email already exists" and link
     to `/crm/contacts/{id}`.
   - **Layer 2 (race):** if the insert/update still hits the index, map
     SQLSTATE `23505` (message may name `contacts_email_lower_idx`) to the
     **same** typed code. Do not 500. Between the pre-check and the insert
     another request can write the same address; 8.1 states this in as many
     words at `lib/auth/signup.ts:234-237`. Copy `isUniqueViolation` into the
     CRM drizzle module rather than importing it from `lib/auth/signup.ts`
     (auth must not become a CRM dependency).

   The pre-check is not "the" protection. The index is the invariant. The
   `23505` map is the backstop. The pre-check exists so the UI can name the
   other person.

4. **Memory repo.** `createContactInMemory` / `updateContactInMemory` refuse a
   case-variant duplicate with the same typed code. Comparison is
   `a.email && b.email && a.email.toLowerCase() === b.email.toLowerCase()`
   inside the same store (memory tests have one tenant at a time unless the
   test seeds two; still filter `tenantId`). Null emails never collide.
   Updating a contact to its own current email (any casing) succeeds.

5. **Action result.** Server actions return a serializable object, e.g.

   ```ts
   type ContactWriteResult =
     | { ok: true; contact: Contact }
     | {
         ok: false;
         code: "duplicate_email";
         existingId: string;
         existingName: string;
       };
   ```

   The client never value-imports `lib/crm/queries.ts`
   (`lib/client-boundary.test.ts:155-166` forbids it). `import type` from
   `queries-shared` is allowed.

6. **UI.** Under `#contact-email`, on submit (and on blur of a non-empty
   email if that is cheap): if `code === "duplicate_email"`, render
   `role="alert"` with the exact sentence **A contact with that email already
   exists** and a link whose accessible name is the existing contact's name,
   `href=/crm/contacts/{existingId}`. Clicking the link closes the dialog.
   A race fallback with no `existingId` still uses that sentence without a
   broken link.

7. **Seed / e2e.** `lib/crm/seed.ts` emails are unique already
   (`ana.ruiz@northwind.example` etc.). No seed change. `e2e/crm.spec.ts`
   create-org flow is untouched.

### Migration safety — answered against a real PostgreSQL 16 cluster

Every claim below was run on a throwaway `postgres:16-alpine` 16.15 instance
that took all eight repo migrations in order (`0000`→`0007`, `psql -f`, each
exit 0), then a fixture of two case-variant contacts, two null-email contacts,
and a deal + activity attached to each duplicate. Not unit tests, not theory.
`DATABASE_URL` was never touched.

**1. The index create aborts, and it aborts the whole migration.** With
`Ana@Northwind.Example` and `ana@northwind.example` both present:

```
BEGIN
ERROR:  23505: could not create unique index "contacts_email_lower_idx"
DETAIL:  Key (lower(email))=(ana@northwind.example) is duplicated.
CONSTRAINT NAME:  contacts_email_lower_idx
LOCATION:  comparetup_index_btree, tuplesortvariants.c:1361
ROLLBACK
```

`pg_indexes` afterwards still lists only `contacts_pkey` and
`contacts_tenantId_idx` — **no `contacts_email_lower_idx`**. Because the
migrator runs each migration inside a transaction, the `23505` rolls the
statement back and the index is simply absent; the next migrate retries and
fails identically. This is a deploy-stopping loop, not a warning.

**2. Recommended remediation order** (each step verified, in this order):

1. **Report first, change nothing.** Run a read-only audit on the target
   branch *before* merging, e.g.
   `SELECT lower(email) AS k, count(*), array_agg(id ORDER BY id) FROM contacts
   WHERE email IS NOT NULL GROUP BY 1 HAVING count(*) > 1;`
   If it returns zero rows the migration is safe as written. Most branches
   will.
2. **Dedupe before the index, never after.** The index cannot be created while
   twins exist, so remediation has to be its own earlier migration (or a manual
   pre-migrate step). Verified: `UPDATE contacts SET email = NULL WHERE id =
   'c_ana2';` then the create → `CREATE INDEX`, exit 0.
3. **Nulling the loser's email is the data-minimal remediation**, and it is
   safe because nulls are exempt (see 4). It loses the address on the losing
   row but never orphans a child.
4. **Deleting the loser instead is a trap.** `deals.contactId` and
   `activities.contactId` are both `ON DELETE SET NULL`
   (`lib/crm/schema.ts:75-77` and the activities table). Verified: deleting
   `c_ana2` left `d_ana2.contactId` and `a_ana2.contactId` as NULL — 1 deal and
   1 activity silently orphaned, no error, no cascade. Children must be
   re-pointed **before** the delete; verified that
   `UPDATE deals SET "contactId" = <survivor> ...; DELETE FROM contacts ...;`
   keeps them attached.
5. **Then and only then** run the 11.6 migration.

**3. `CONCURRENTLY` is not available here — do not use it.** The pg migrator
wraps every migration in one transaction
(`node_modules/drizzle-orm/pg-core/dialect.js:60`,
`await session.transaction(async (tx) => { ... })`). Verified:

```
BEGIN
ERROR:  25001: CREATE INDEX CONCURRENTLY cannot run inside a transaction block
LOCATION:  PreventInTransactionBlock, xact.c:3497
```

So `CREATE UNIQUE INDEX CONCURRENTLY` **cannot** be expressed in a migration
file for this repo's migrator. This is the same deliberate limit 7.3 recorded;
follow that precedent. Use the plain `CREATE UNIQUE INDEX` and take the
blocking window on a small table. (Note this also means the Drizzle *runtime*
path cannot be exercised against a local Postgres with this repo's
`@neondatabase/serverless` driver — the same limit 8.1 hit. The probe ran
drizzle's own SQL through `psql` instead.)

**4. Nullable exemption is verified, not assumed.** `contacts.email` is
nullable. After the index existed, `null_email_contacts` reached **5** — the
original two plus two more inserted post-index — with no violation. A
case-variant insert *did* fail (`23505 ... duplicate key value violates unique
constraint "contacts_email_lower_idx"`, `DETAIL: Key (lower(email))=(ana@northwind.example)
already exists`), and a different address still inserted fine. So: `NULL` never
collides, non-null case-variants always do.

**5. The 42P10 trap is live for any future `onConflict` on contacts.** With
only the expression index present, `ON CONFLICT ("email") DO UPDATE` fails
with `42P10: there is no unique or exclusion constraint matching the ON
CONFLICT specification` (`LOCATION: infer_arbiter_indexes, plancat.c:920`).
`ON CONFLICT ((lower("email")))` works, as does untargeted
`ON CONFLICT DO NOTHING`. **Today no code breaks** — a whole-tree grep for
`onConflict` returns only `lib/db/seed.ts:150` (`target: tenants.name`, a real
column unique, unaffected) and `lib/db/seed.ts:202` (untargeted), plus
`lib/db/seed.test.ts:337-339` stubbing the same untargeted call. `lib/crm/`
has none: `insertContact` is a bare
`.insert(contacts).values(row).returning()` at
`lib/crm/queries-drizzle.ts:207-211`. So acceptance criterion 11 holds
today and is a guard, not a fix. Do not "helpfully" add an onConflict.

**6. The index is global, not per-tenant — confirmed, and it is a recorded
limit.** A second tenant (`t_other`) inserting the same address was refused
with `23505 ... contacts_email_lower_idx`. That is the 8.1 shape
(`users_email_lower_idx` is also global) and Recorded limit 1 already says so.
Worth stating that the *pre-check* in Spec §3 is tenant-scoped while the index
is global: a cross-tenant duplicate is therefore refused by the database with
no `existingId` to name, so the dialog must tolerate a 23505 fallback with
nothing to link (Spec §6 already requires that; this is why).

**7. Memory repo parity is currently FALSE and 11.6 must fix it.**
`lib/crm/queries-memory.ts` has no `toLowerCase`/`lower(` anywhere — a
whole-file grep is empty — and `createContactInMemory` (`:137-143`) is a bare
`repo.contacts.push(row)`, `updateContactInMemory` (`:155-156`) assigns
`row.email = input.email` with no duplicate check at all. So today memory
accepts case-variant twins while the Drizzle repo will reject them once the
index lands. Criterion 5 is not currently satisfied; Spec §4 is the work that
closes it. This is the same reason 8.1 changed its memory repo: the memory
repo must simulate the *database's* behaviour, not the old one.

**8. Add a spec-test on the migration's SQL, not just the schema.** 8.1's
migration test parses the committed file so a name swap or a reintroduced
`DROP TABLE` fails. 11.6 should do the same for `drizzle/0008_*.sql`.

## Recorded limits

1. **The index is global on `lower(email)`, like `users_email_lower_idx`.** Two
   tenants cannot store the same address. Demo seed uses `@*.example`
   mailboxes (`lib/crm/seed.ts:58-105`); an owner adding one of those exact
   strings is refused. Per-tenant uniqueness would be `(tenantId, lower(email))`
   and is a different migration — `IF NOT EXISTS` matches by name, so changing
   the definition later requires `DROP INDEX`, not a silent recreate. Out of
   scope.
2. **No live concurrent race is proven in CI.** Vitest uses the memory repo.
   The honest gates are the index existing, the `23505` map, and the 42P10
   demonstration above.
3. **Pre-existing twins on a dirty branch block migrate, and the fix is a
   product decision this feature must not make.** Verified on a real cluster:
   the create aborts with `23505` and leaves no index, so migrate fails
   outright (see Implementation notes §1). Nulling the loser's email is the
   data-minimal remediation and is safe; **deleting** the loser silently
   orphans its deals and activities because both `contactId` FKs are
   `ON DELETE SET NULL` (verified: 1 deal + 1 activity left NULL, no error).
   Which contact survives a merge, and whether its children are re-pointed or
   left orphaned, is **product's call, not the implementer's** — escalate it
   before writing any dedupe migration. This feature ships the index only; the
   audit query in Implementation notes §2.1 is the safe pre-merge check.
4. **The migrator runs every migration in one transaction, so `CREATE UNIQUE
   INDEX CONCURRENTLY` is unavailable.** `25001`, verified. The index build
   takes a write lock on `contacts` for its duration. On a large table that is
   a real maintenance window — schedule it, or push back on adding the index
   at all. This repeats 7.3's recorded limit rather than re-litigating it.
5. **Format validation is not this feature.** `type="email"` in the form is
   unchanged.
6. **`WriteBatch` seed inserts cannot map `23505` the same way** (batch has no
   returning error per row). Seed data does not collide. Do not invent an
   onConflict to "fix" that — 42P10.
7. **This feature does not add `ListContactsOpts` fields** and does not touch
   deal filters, `/crm/tasks`, or QuickFind.
8. **The Drizzle runtime path was not exercised against the local cluster.**
   `@neondatabase/serverless` cannot reach a plain TCP Postgres — the same
   limit 8.1 recorded. Every claim here is drizzle's own SQL run through
   `psql` on a real PG16, plus source evidence for the transaction wrapper
   (`node_modules/drizzle-orm/pg-core/dialect.js:60`). The `23505`-mapping
   tests still need the implementer's unit tests; this probe did not stand in
   for them.
