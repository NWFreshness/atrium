# Feature 11.3: Activity correct-and-complete

**Phase:** 11 — CRM integrity, dead-ends, and list/task surface
**Status:** specced
**Estimated effort:** 5–7 hours (the merged former 11.3 + 11.8; the phase table's 3–4h + 3–4h)
**Depends on:** 11.1 (its `e2e/crm-activities.spec.ts` is the file this feature appends to)
**Blocks:** 11.9 (a `/crm/tasks` row is an activity with a `dueDate`; it mounts the same timeline)

This is the merged spec (ideas A2 + B4, gaps G1 + G7 + G8). Former "11.8
activity delete" does not exist as its own file; **11.8 in this phase is Deal
filters.** The truncated done-checkbox `aria-label` below is the contract that
**changes 11.1 Journey E's locator** in `e2e/crm-activities.spec.ts`. Do **not**
edit `11.1-crm-e2e-coverage.md`; the living locator is the test file 11.1 creates.

## Goal

Close G1, G7, and G8: a logged activity can be **corrected** and **removed**, it can be
**backdated**, and a contact's last contact is **visible** — three dead-ends that share one
data model and one dialog.

Today `deleteActivity` exists at `lib/crm/queries.ts:408` and has no caller anywhere in
`lib/crm/` or `components/crm/` — the query is written, memory-tested, and unreachable.
`updateActivity` (`lib/crm/queries.ts:394`) is reachable only for the boolean `done`, via
the checkbox at `components/crm/activity-timeline.tsx:75-79`. `ActivityForm`
(`components/crm/activity-form.tsx:57-111`) has no `occurredAt` field, so
`createActivityForSession` stamps `new Date()` at `lib/crm/activity-actions.ts:103-104`
and a call logged on the wrong day cannot be redated. And
`compareActivitiesNewestFirst` (`lib/crm/queries-shared.ts:168`) is **live** — imported at
`lib/crm/queries-memory.ts:16` and used to sort at `lib/crm/queries-memory.ts:293` — so
what is missing is a last-contacted *use*, not a comparator.

## Scope

Include:

- **Delete.** `deleteActivityForSession` / `deleteActivityAction` in
  `lib/crm/activity-actions.ts`, following the exact `deal-actions.ts` shape
  (`*ForSession(getSession, …, repo?)` then a thin dynamic-importing `*Action`).
  A `Delete` control on each `ActivityTimeline` row behind the native `confirm()` the
  tables use, with the message **`Delete this activity?`** and nothing else.
- **Edit.** `updateActivityForSession` / `updateActivityAction`, and an `Edit` control on
  each row that opens the **existing** `ActivityForm` prefilled, inside the existing
  dialog chrome. Fields: Type, Date, Description, Due date, Done.
- **Backdate.** A `Date` field in `ActivityForm`, second position (after Type), defaulting
  to today. It is sent on create **and** on edit. This is the merged former 11.8's 8a.
- **Last contacted.** Derived, never a column. Contact detail gains a `Last contacted`
  `<dt>`/`<dd>` row; the contacts table gains a `Last contacted` column. Computed from
  each contact's activity list with `compareActivitiesNewestFirst`. This is the merged
  former 11.8's 8b.
- **Accessible-name cleanup on the Done checkbox**, in the same change, per the phase
  decision: a truncated `Edit activity: …` sitting next to a full-description
  `Mark … done` is worse than either consistent form.
- **Dialog a11y on the new dialog**: `useId()` title id, Escape-to-close, focus restore to
  the button that opened it, focus moved to the `Type` select on open.
- **The Timeline test file** extended to a real source gate, and the two new pure helpers
  unit-tested.

Exclude (for now):

- **Activity creation UI anywhere new.** The inline `Add activity` form on the contact and
  deal detail pages stays exactly as it is except for the new `Date` field. The dialog mode
  is what is new.
- **Any edit/delete control on the dashboard feed or the follow-up panels.** A delete
  control on a dashboard panel is a surprise. `components/crm/dashboard-followups.tsx:36-59`
  and `app/(authenticated)/crm/page.tsx:64-96` are **not** modified by this feature.
- **Anything about `/crm/tasks`**, the follow-up surface, or a See-all link — **11.9**.
- **Re-parenting an activity.** The edit dialog edits the activity's own fields. It does
  **not** offer an `Organization`/`Contact`/`Deal` picker, and it does not change
  `contactId` / `dealId`. Moving a note from one person to another is a different feature;
  the FKs are nullable `SET NULL` (`lib/crm/schema.ts:100-103`) and a mis-click there
  silently orphans the row.
- **Undo / a toast.** There is no toast primitive in the repo (zero matches for `toast`
  across `app/`, `components/`, `lib/`), and this phase adds no component library. A
  deleted activity is unrecoverable after the confirm; that is a recorded limit, not an
  oversight.
- **Time-of-day precision on `Date`.** The field is a `type="date"` input and the value is
  midnight UTC (see §3.4). 11.3 does not become a timezone feature.
- **A "last contacted" filter, or any use of the 30-day threshold other than the cell's
  visual flag** — 11.8 owns deals filtering; a contacts filter is out of this phase.
- **Deal number validation, deal filters, table sorting, detail-page edit, delete preview,
  QuickFind, and the unique email index** — 11.2, 11.4, 11.5, 11.7, 11.10, 11.6. In
  particular this feature does **not** touch the three table components, so it shares no
  file with 11.4 and can run while 11.4 is not in progress.
- **Screenshot goldens**; still deferred.

## Spec

### 0. Ordering, and the one file this feature shares with 11.4

`contact-table.tsx` is touched by both this feature and 11.4 (which adds sorting to every
header). The board rule is one `in_progress` feature at a time, so this is a calendar
constraint, not a code conflict. The locked long pole is `11.1 → 11.4 → 11.5`, then
`11.3 → 11.9`, so **11.4 ships first**:

1. 11.4 adds sorting to the columns that already exist.
2. 11.3 then adds the `Last contacted` column **last** in `contact-table.tsx`,
   between `Status` and `Organization`, with **no** sort options on it — a `display`
   column reading a prop, exactly like today's `organizationId` column.
3. Do not run 11.3 and 11.4 in parallel. If a session must interleave, 11.3's column
   still lands last so 11.4's mechanical per-column pass has a stable shape.

The 11.3 column must carry the data it sorts by on the **row**, not in an `accessorFn`
(see §3.5 and Implementation notes). Concretely: the column is a `display` column whose
`id` is `lastContactedAt` and whose `cell` reads a name map resolved at render time — no,
read §3.5, which is more specific and is the shape that survives sorting.

- `deleteActivity` — `lib/crm/queries.ts:408-418`
- `updateActivity` — `lib/crm/queries.ts:394-406`, which already asserts

### 2. `lib/crm/activity-actions.ts` — the four new functions

Match the file's existing shapes exactly. `toggleActivityDoneForSession`
(`lib/crm/activity-actions.ts:110-122`) is the pattern: read the row, return `null` if it is
not in the tenant, then dispatch.

```ts
export async function updateActivityForSession(
  getSession: GetSession,
  id: string,
  input: UpdateActivityInput,
  repo?: CrmRepository,
): Promise<Activity | null> {
  const { tenantId } = await requireTenant(getSession);
  const existing = await getActivity(tenantId, id, repo);
  if (!existing) {
    return null;
  }
  return updateActivity(tenantId, id, input, repo);
}

export async function deleteActivityForSession(
  getSession: GetSession,
  id: string,
  repo?: CrmRepository,
): Promise<Activity | null> {
  const { tenantId } = await requireTenant(getSession);
  const existing = await getActivity(tenantId, id, repo);
  if (!existing) {
    return null;
  }
  return deleteActivity(tenantId, id, repo);
}
```

Validation order inside `updateActivityForSession`, and it is this order:

1. `requireTenant(getSession)` — **no `input` is passed**, so a client-supplied
   `tenantId` field cannot ride in on the update payload. `requireTenant`
   (`lib/tenancy/index.ts:27-30`) takes the tenant from the session only.
2. `getActivity(tenantId, id, repo)` → `null` return on miss. This is the tenant check:
   `getActivityInMemory` uses `findScoped(repo.activities, scoped, id)`
   (`queries-memory.ts:301`) and `getActivityInDrizzle` uses
   `and(eq(activities.tenantId, scoped), eq(activities.id, id))`
   (`queries-drizzle.ts:389`). A cross-tenant id returns `null`, so the action is a no-op
   the user cannot cause.
3. `updateActivity(...)` / `deleteActivity(...)`.

**Do not** validate `input.type` in the action. `createActivityForSession` does
(`lib/crm/activity-actions.ts:88-90` via `isActivityType`) because the client controls the
type on create. On update the client also controls it, so — **yes**, validate it, using
the same `isActivityType` helper already in the file, and return `null` when it fails:

```ts
if (input.type !== undefined && !isActivityType(input.type)) {
  return null;
}
```

That check goes **between steps 2 and 3**. A bad type from a stale client is a `null`, not
a Postgres enum error. The description needs no action-level check: `updateActivity`
(`queries.ts:401`) already throws on `> MAX_LONG_TEXT` = 8,000
(`lib/input/text.ts:2`), which is the 9.6 `assertText` contract, and the textarea's
`maxLength` is a hint on top of it.

Then the two thin actions, byte-for-byte in the file's shape:

```ts
export async function updateActivityAction(
  id: string,
  input: UpdateActivityInput,
): Promise<Activity | null> {
  const { auth } = await import("@/auth");
  return updateActivityForSession(auth, id, input);
}

export async function deleteActivityAction(id: string): Promise<Activity | null> {
  const { auth } = await import("@/auth");
  return deleteActivityForSession(auth, id);
}
```

**Tenant id never from the client.** `UpdateActivityInput` is
`Partial<CreateActivityInput>` (`lib/crm/queries-shared.ts:65`) and has no `tenantId`
field, so there is nothing to strip. Unlike
`listActivitiesForSession` (`lib/crm/activity-actions.ts:57-67`), which re-projects
`{ contactId, dealId }` field by field, these two take their arguments positionally and
cannot forward a `tenantId`. Do **not** "fix" that by adding a `ClientTenantInput`
intersection — it would create a hole that does not exist today.

### 3. `components/crm/activity-form.tsx` — one component, two modes

#### 3.1 Props

```tsx
export function ActivityForm({
  contactId,
  dealId,
  activity,
  onClose,
}: {
  contactId?: string;
  dealId?: string;
  activity?: Activity | null;
  onClose?: () => void;
}) {
```

`onClose` is the **mode switch**: present → dialog chrome; absent → the inline form, whose
markup is byte-identical to today's except for the new `Date` field. Both call sites that
exist today (`app/(authenticated)/crm/deals/[id]/page.tsx:74`,
`app/(authenticated)/crm/contacts/[id]/page.tsx:77`) pass neither prop and are unchanged.

#### 3.2 Title and submit label

- Dialog title: **`Edit activity`** — a literal string. Not `Edit {description}`.
- Submit: **`Save`** in dialog mode, **`Add activity`** inline
  (today's label at `activity-form.tsx:107-109`).
- Cancel: `Cancel` in dialog mode only, as `type="button"`, matching
  `org-form.tsx:137-139`.

```tsx
const isDialog = onClose !== undefined;
const titleId = useId();
```

The existing three forms use hardcoded title ids (`org-form.tsx:40`,
`contact-form.tsx:47`, `deal-form.tsx:81`). **This new dialog does not.** It is the only
CRM dialog that can appear alongside another `crm-dialog` on the same page (the list table
dialog is not mounted there, but the id must not be a collision waiting to happen), and
`useId()` is what makes the id unique per instance.

#### 3.3 Field order and values

Dialog order, which is also the inline order: **Type, Date, Description, Due date, Done.**

`Date` is second, between `Type` and `Description`. A chronological form reads: what
happened, when, what it was, when it is due, whether it is done.

| Field | Inline (create) | Dialog (edit) |
| --- | --- | --- |
| `Type` | `"note"` (`activity-form.tsx:26`) | `activity.type` |
| `Date` | today (see §3.4) | `dateToInputValue(activity.occurredAt)` |
| `Description` | `""` | `activity.description` |
| `Due date` | `""` | `dateToInputValue(activity.dueDate)` |
| `Done` | `false` | `activity.done` |

Labels are exactly `Type`, `Date`, `Description`, `Due date`, `Done` — the first, second,
fourth, and fifth are today's labels verbatim (`activity-form.tsx:60, 75, 85, 96`); `Date`
is new. **No `min` and no `max`** on the `Date` input: a future-dated activity ("the call
scheduled for Thursday") is a real record, and `max="today"` would manufacture a new
dead-end, which is the class of defect this phase exists to close. The existing `Due date`
input carries neither (`activity-form.tsx:86-92`).

The `id`/`htmlFor` pairs must be **unique per mounted form**. Today they are fixed
literals (`activity-type`, `activity-description`, `activity-due-date`, `activity-done`).
With a dialog mounted alongside the inline form on the same page, two elements share an
id. Derive them from the same `useId()` value:

```tsx
const fieldId = (name: string) => `${titleId}-${name}`;
<label htmlFor={fieldId("type")}>Type</label>
<select id={fieldId("type")} …>
```

This is a change to the inline form's attributes too, and it is required: without it, the
dialog and the inline form on `deals/[id]` both ship `id="activity-type"`, and
`getByLabel("Type")` in Playwright resolves to two elements and throws a strict-mode
violation. **Say so in the commit body.**

#### 3.4 The date parse — the UTC-midnight rule, and the one hazard

Two helpers, both copied from the shapes already in the file and in
`components/crm/deal-form.tsx`:

```tsx
function dateToInputValue(date: Date | string | null | undefined): string {
  if (!date) return "";
  const parsed = date instanceof Date ? date : new Date(date);
  if (Number.isNaN(parsed.getTime())) return "";
  return parsed.toISOString().slice(0, 10);
}
```

(`deal-form.tsx:32-41`, verbatim.) The existing `inputValueToDate`
(`activity-form.tsx:9-15`) already builds `new Date(\`${trimmed}T00:00:00.000Z\`)`. **Keep
it exactly.** The `Z` is load-bearing: `"2026-09-29T00:00:00"` without it is *local* time
and shifts 7 hours on this host. `new Date("2026-09-29")` is UTC (ES date-only semantics)
and is not the hazard; the missing `Z` is.

"Today" for the default, computed the same way `deal-form.tsx:40` does, so the two date
fields in this same form agree:

```tsx
const todayValue = new Date().toISOString().slice(0, 10);
```

**Known limit, stated not solved:** this is UTC, so for a user west of Greenwich after
17:00 local the form's default is tomorrow. The existing `closeDate` field
(`deal-form.tsx:201-212`) and `dueDate` (`activity-form.tsx:86-92`) have the same
property. Pre-existing; not doubled by 11.3; not fixed here.

#### 3.5 Submit

```tsx
async function onSubmit(event: FormEvent<HTMLFormElement>) {
  event.preventDefault();
  const trimmed = description.trim();
  if (!trimmed) return;
  const input = {
    type,
    description: trimmed,
    occurredAt: inputValueToDate(date),   // Date | null — a cleared field clears it
    dueDate: inputValueToDate(dueDate),
    done,
  };
  setPending(true);
  try {
    if (activity) {
      await updateActivityAction(activity.id, input);
    } else {
      await createActivityAction({ ...input, contactId, dealId });
    }
    router.refresh();
    onClose?.();
  } finally {
    setPending(false);
  }
}
```

Three points that are not interchangeable:

- **`contactId` / `dealId` are sent on create only.** The edit dialog does **not** send
  them, because §Exclude rules out re-parenting. `UpdateActivityInput` is a `Partial`, so
  omitting them is a no-op rather than a null-out.
- **Order is `router.refresh()` then `onClose?.()`** — the same order every form in the
  repo uses (`org-form.tsx:61-62`, `contact-form.tsx:70-71`, `deal-form.tsx:110-111`).
- **A cleared `Date` sends `null`**, which writes `occurredAt = NULL`. That is
  intentional: it is the honest representation of "I don't know when this happened", and
  the timeline already renders an absent date as `""` (`formatDate` returns `""` for
  `null`, `lib/crm/format.ts:9-11`).

After a successful **create**, reset `type` to `"note"`, `description` to `""`, `date` to
today, `dueDate` to `""`, `done` to `false` — the existing reset block
(`activity-form.tsx:47-50`) plus the new field.

#### 3.6 Dialog chrome and keyboard

When `onClose` is present, the form renders inside the existing classes:
`styles["crm-dialog-backdrop"]` → `styles["crm-dialog"]` with
`role="dialog" aria-modal="true" aria-labelledby={titleId}` — byte-identical to
`org-form.tsx:69-76`. The backdrop **does not** get a click-to-close handler: the three
record forms do not have one, and adding it here would make this dialog's affordances
differ from the dialog it visually copies. (11.10's palette has one, but that is a
different component with a different job.)

Keyboard contract, and it is new behaviour in the CRM — the existing three forms have
hardcoded title ids and no Escape handler:

- On open, focus the `Type` select. Implement with a `useRef` on the select and a
  `useEffect` keyed on mount (the pattern at `components/space/quick-find.tsx:45-50`).
- `Escape` on the dialog element closes it: `onKeyDown` on the `crm-dialog` div, matching
  `quick-find.tsx:88-93` (`event.preventDefault()` then close).
- After close, focus returns to the button that opened it. The **timeline** owns that
  (it is the thing that mounted the form), so `ActivityTimeline` keeps a `ref` to the
  clicked Edit button and focuses it in a `useEffect` that runs when `editing` transitions
  to `null`. Do not put the restore in `ActivityForm` — the form does not own the opener.
- **No focus trap.** A trap library is a non-goal for this phase. The dialog is two to
  five fields; `Tab` can leave it, which is a recorded limit, not a silent one.

### 4. `components/crm/activity-timeline.tsx` — the two row controls

#### 4.1 Control placement

Each `<li>` is already four lines (`activity-timeline.tsx:64-85`). The two buttons go on
the **same last line as the Done checkbox**, in DOM and visual order:

```
Done ☐    Edit    Delete
```

They go in a new `styles["crm-activity-actions"]` wrapper with
`display: flex; gap: 0.5rem; align-items: center`, replacing nothing — the `<label>` at
`:70-85` stays exactly where it is and the two buttons are its siblings.

**Visible at rest.** Not `opacity: 0`. The tables hide their row actions to protect grid

Hover-revealing here costs a hover, breaks touch, and would put this feature's Playwright
journeys behind the same opacity gate the tables are already behind.

#### 4.2 Accessible names — exact strings

```
aria-label={`Edit activity: ${truncateActivityLabel(activity.description)}`}
aria-label={`Delete activity: ${truncateActivityLabel(activity.description)}`}
```

and the Done checkbox, changed in this same commit:

```
aria-label={
  activity.done
    ? `Mark activity: ${truncateActivityLabel(activity.description)} not done`
    : `Mark activity: ${truncateActivityLabel(activity.description)} done`
}
```

`truncateActivityLabel` appends the U+2026 `…` **only** when
`value.length > ACTIVITY_LABEL_MAX` (60). `activity.description` is bounded by `long()` =
8,000 (`queries.ts:382`, `lib/input/text.ts:2`); an 8,000-character accessible name, three
times per row, is unusable — and useless, because the full text is already in the row's own
`<p>` at `activity-timeline.tsx:65`, one node away.

**The Done-checkbox name changes deliberately and it breaks a locator.** 11.1's Journey E
matches `Mark {description} done` (scratch `11.1-crm-e2e-coverage.md:398`). This feature
updates that journey to the new string. Do not leave the split — `Mark Follow-up on
warehouse rollout timeline. done` beside `Edit activity: Follow-up on warehouse
rollout…` is worse than either consistent form. **The implementer must edit
`e2e/crm-activities.spec.ts` in the same commit as the component.** A feature that changes
a shipped accessible name and leaves the test matching the old one ships a red suite.

Accepted cost: two activities sharing a 60-character prefix are indistinguishable by name.
They are visually adjacent, the visible `<p>` is the disambiguator, and this is recorded
in Recorded limits.

#### 4.3 Delete

```tsx
onClick={async () => {
  if (!confirm("Delete this activity?")) return;
  await deleteActivityAction(activity.id);
  router.refresh();
}}
```

`confirm()` is registered by Playwright with `page.once("dialog", d => void d.accept())`
**before** the click. The message is exactly `Delete this activity?` and nothing else — no
description, no count, no second line. An activity has no downstream rows (the FKs point
**at** it from nothing; `activities` is a leaf, `lib/crm/schema.ts:90-113`), so a
consequence preview would always be zero, and 11.7's preview does not apply here.

### 5. `lib/crm/activity-labels.ts` — and why it is its own module


### 6. Last contacted — derived, on two surfaces

**Gate, checked before writing anything:** `lastContactedAt` must be **absent** from
`lib/crm/schema.ts`. It is, and it stays absent. A stored column drifts from the

#### 6.1 `lib/crm/last-contacted.ts`

```ts
import type { Activity } from "./queries-shared";
import { compareActivitiesNewestFirst } from "./queries-shared";
```

Wait — the second import is a **value** import of a module `client-boundary.test.ts`
forbids to components. `last-contacted.ts` is imported by a **server component**
(`contacts/[id]/page.tsx`), which is not under `components/`, so the walk never reaches
it from there. But `contact-table.tsx` is a client component and needs the same function.

Two options, and the spec picks one:

**Chosen: the value-import lives here, and `contact-table.tsx` does not import this
module.** The contacts page (`"app/(authenticated)/crm/contacts/page.tsx"`) computes the
map server-side and passes it to `ContactTable` as a new prop
`lastContacted: Record<string, Date | null>`. That keeps the client component's import
graph free of `queries-shared` entirely, and it is the shape that is correct under
sorting anyway (§6.3).

```ts
// lib/crm/last-contacted.ts  — server-side only. Not imported by components/.
import {
  compareActivitiesNewestFirst,
  type Activity,
} from "./queries-shared";

export function lastContactedAt(activities: Activity[]): Date | null {
  const sorted = [...activities].sort(compareActivitiesNewestFirst);
  for (const activity of sorted) {
    if (activity.occurredAt) {
      return activity.occurredAt;
    }
  }
  return null;
}

export function daysSinceContacted(at: Date | null, now: Date): number | null {
  if (!at) return null;
  const from = Date.parse(`${at.toISOString().slice(0, 10)}T00:00:00.000Z`);
  const to = Date.parse(`${now.toISOString().slice(0, 10)}T00:00:00.000Z`);
  return Math.round((to - from) / 86_400_000);
}

export function isStaleContacted(at: Date | null, now: Date): boolean {
  const days = daysSinceContacted(at, now);
  return days !== null && days > LAST_CONTACTED_STALE_DAYS;
}
```

`lastContactedAt` sorts before reading, so it does not assume the caller handed it a
sorted array. A `null` `occurredAt` never wins over a dated one — which is exactly
`compareActivitiesNewestFirst`'s own rule (`queries-shared.ts:174-179`), and the loop makes
it explicit rather than implicit.

`daysSinceContacted` is **calendar-day** based, not millisecond based, and it slices both
sides to `YYYY-MM-DD` before parsing — the `utcDateOnly` convention at
`lib/crm/dashboard.ts:86-88`. A 30-day flag that fires at 30.5 elapsed days (because
`occurredAt` is `15:00:00Z`) is a flag nobody trusts.

`LAST_CONTACTED_STALE_DAYS` is imported from `./activity-labels` (a value import of a
module with no forbidden dependency — legal in both directions).

**Stale means strictly greater than 30 days.** `days > 30`, not `>= 30`.

#### 6.3 The contacts table column

Placement: after `Status`, before `Organization` — the same relative position as the detail
row. This is the **one table file** 11.3 touches.

The column must be sortable **by its rendered value** and must not re-introduce the
derived-column trap. The shape that is safe under both rules:

- `contact-table.tsx` already has `orgNames`, a `useMemo`'d `Map` at `:28-34`, in the
  `columns` dependency array at `:100`. **That dependency array keeps its shape and gains
  `lastContactedById`.** Dropping either map to satisfy a lint is the defect this feature
  exists to prevent.
- The contacts page computes `lastContactedById: Map<string, Date>` server-side and passes
  it as a new prop. `ContactTable`'s prop type becomes
  `{ contacts: Contact[]; organizations: Organization[]; lastContactedById: Map<string, Date> }`.
  `Map` is a structured-clone-safe value for a Server→Client boundary in React 19? **No
  — a `Map` is not serializable across the RSC boundary by default.** Use a plain record:

  ```tsx
  lastContacted: Record<string, string>;  // contactId -> "YYYY-MM-DD" or absent
  ```

  The page maps `Date` → `toISOString().slice(0, 10)` server-side, and the table parses
  back with `new Date(\`${value}T00:00:00.000Z\`)` — the same rule, the same `Z`. Plain
  object, plain string, no `Date` over the wire, no `Map`.

  **This is a real constraint the design doc did not name** (it did not specify how the
  derived map reaches the client). It is stated here in the Spec rather than left to the
  implementer, and repeated in Implementation notes.

- The column definition:

  ```tsx
  columnHelper.display({
    id: "lastContactedAt",
    header: "Last contacted",
    cell: ({ row }) => { /* read the record, render "" or the date or "Never" */ },
  })
  ```

  A `display` column has no `accessorFn`, so `column_getCanSort` returns `false`
  (`rowSortingFeature.utils.js:248-250`: `!!column.accessorFn`). **That is correct for
  11.3** — 11.3 does not sort it. 11.4's job is to convert it to an accessor plus a
  `sortFn` that reads the same record, and 11.4's spec must say so.

  **Stated plainly in the 11.3 spec so 11.4 does not discover it late:** this column ships
  **unsortable** and the 11.4 e2e must not assert it sorts. 11.4 makes it sortable as part
  of its own per-column pass. If 11.4 lands first, 11.3's column picks up 11.4's
  per-column options in the same edit.

- The cell renders, in order of preference:
  - no record / no date → **`Never`**
  - stale → `{formatDate(date)} · {days} days ago` with `styles["crm-stale"]` on the
    wrapper
  - fresh → `{formatDate(date)}`

  `Never` (one word) in the table; `No activity yet` (a sentence) on the detail page.
  A table cell is scanned, not read, and a two-word sentence in a 150px column is worse
  than one word.

## Implementation notes

- **The v8 fossils.** `getSortedRowModel`, `onSortingChange`, `useState<SortingState>`,
  `sortingFn`, `SortingFns` are all **v8 names and none of them appear in this feature**,
  because this feature does not sort. 11.4's spec says the same about `getSortedRowModel`
  as a config surface — the installed package is `@tanstack/react-table@9.2.4`
  (`package.json:23`), and the sorting API is `rowSortingFeature` +
  `createSortedRowModel()`. If an implementer copy-pastes the ideas doc's A3 sentence while
  writing this feature's "the table already has sorting" comment, it ships a fossil into a
  comment. That is how fossils get reinstated.

- **`compareActivitiesNewestFirst` is live — do not "fix" it.** The ideas doc's G8 calls it
  caller-less. It is not: `lib/crm/queries-memory.ts:16` imports it and `:293` sorts with
  it, and `lib/crm/queries-drizzle.ts:375-379` implements the same order in SQL
  (`occurredAt DESC NULLS LAST, createdAt DESC, id`). 11.3 **uses** the helper and adds a
  use. It changes nothing about the helper and asserts nothing is broken.

- **A `Map` does not survive the Server→Client boundary.** The contacts page must hand the
  table a plain `Record<string, string>` of `contactId -> "YYYY-MM-DD"`, not a `Map` and
  not a `Date`. This is the single most likely thing to get wrong in §6.3, and it fails at
  **runtime in a browser**, not in `npm test` and not in `npm run build`. Budget a real
  Playwright run for it.

- **`useId()` is a React 19 hook, not a Next.js one.** `react@19.2.8`
  (`package.json:26`) exports it from `react`. It has zero matches in `components/` today
  — this feature is the first CRM user. Do not reach for a hand-rolled id counter; it
  breaks on hydration and on two dialogs.

- **Two `crm-dialog` ids.** §3.3's `fieldId` change alters the **inline** form's
  `id`/`htmlFor` pairs, which are currently fixed literals
  (`activity-form.tsx:60-61, 75-76, 85-86, 95-96`). Leaving them literal puts
  `id="activity-type"` on the page twice when the dialog is open, and
  `page.getByLabel("Type")` throws a strict-mode violation. The e2e in criterion 11 is the
  test for this; the change is easy to skip because nothing on the inline form looks
  wrong until two of them exist.

- **The Done-checkbox rename is a breaking change to a shipped string, on purpose.** It
  breaks 11.1's Journey E locators. That is the plan, not a surprise — the phase design
  says "Truncate in **the same 11.3 change** as Edit/Delete. Do not leave
  `Mark {full description} done` next to a truncated Edit." The cost of the split exceeds
  the cost of the rename. The implementer who finds a red `e2e/crm-activities.spec.ts`
  after the component edit has found the *expected* red and must fix the locators, not
  revert the name.

- **`confirm()` and the `…` character.** `Delete this activity?` is ASCII, so no test
  encoding question arises. The `…` in the accessible names is U+2026 in **source**, not
  three dots. `crm-pass.test.ts:23-27` already forbids retired glyph literals in the
  subnav; a test that greps for `"..."` in a label is not the same assertion as one that
  greps for `\u2026`, and the accessible name must carry the real glyph. Write the test
  against the exported `truncateActivityLabel` output rather than a literal.

- **Memory repo proves policy, not SQL.** `env -u DATABASE_URL npm test` uses
  `createMemoryCrmRepository()`; `lib/crm/queries-drizzle.ts` is not executed. Every new
  Drizzle fragment in this feature is `updateActivity`'s and `deleteActivity`'s existing
  `.set({...})` / `.delete().returning()` shapes, which are already exercised by
  `lib/crm/queries.test.ts`. **No new SQL is added**, so the SQL risk in this feature is
  low — but the e2e journeys against dev Neon are still the only thing that proves
  `updateActivityAction` writes through Neon at all.

- **`neon-http` has no `db.transaction()`.** This feature writes one row at a time and
  never batches, so it does not hit that. Stated because the temptation in a future
  "delete the activity and renumber" idea is real and this is the line.

- **Shipped notes are read as evidence.** Any claim this spec makes about current
  behaviour was read from the working tree at the paths and lines cited. The implementer
  who finds one wrong must check it against the file, not against this document, and
  correct the spec in the same PR if the file has moved.

- **The 30-day number is a constant with a name and a home** — `LAST_CONTACTED_STALE_DAYS`
  in `lib/crm/activity-labels.ts`. The detail page, the table, and any future filter read
  one number. It is not inlined in a component, and it is not configurable.

## Recorded limits

Known, and **not** covered by this feature. Written down rather than left to be
discovered.

1. **Deletion is unrecoverable.** Native `confirm()` with no undo and no toast — the repo
   has no toast primitive and this phase adds no component library. A mis-click on the
   wrong row loses the note.
2. **Two activities sharing a 60-character description prefix are indistinguishable by
   accessible name.** The visible `<p>` is the disambiguator. Accepted deliberately; the
   full 8,000-character alternative is worse.
3. **No focus trap in the new dialog.** `Tab` can leave it. A trap library is out of scope
   for this phase. The dialog is at most five fields.
4. **The dialog's `Date` default is UTC.** For a user west of Greenwich after 17:00 local
   the prefilled value is tomorrow. Pre-existing in `closeDate` (`deal-form.tsx:40`) and
   `dueDate`; 11.3 does not double it and does not fix it.
5. **The re-parenting question is unanswered.** A note logged against the wrong contact
   can be re-typed and re-created, but not moved. The FKs are nullable `SET NULL`
   (`lib/crm/schema.ts:100-103`), so a picker that a user mis-fills silently orphans the
   row. Left for a future feature with its own acceptance criteria.
6. **"Last contacted" is derived and therefore an extra read on the contacts list.** The
   contacts page now fetches every activity for the tenant to build the map. On a large
   tenant that is a real cost, and unbounded lists are a known non-goal (B5) for this
   phase. The demo tenant's four activities make it invisible, which is not an argument
   that it is invisible in general.
7. **The cross-app copy divergence is unresolved.** CRM says `No activity yet` (detail)
   and `Never` (table); Rolodex renders an empty `<dd>` on the person page
   (`app/(authenticated)/rolodex/people/[id]/page.tsx:69`) and `Never contacted` on its
   boards (`components/rolodex/circles-board.tsx:127`). Three strings and a blank for one
   fact. Rolodex is out of this phase's scope and is not edited.
8. **The `Last contacted` column ships unsortable.** 11.3 adds it as a `display` column
   with no `accessorFn`, and `column_getCanSort` requires one
   (`node_modules/@tanstack/table-core/dist/features/row-sorting/rowSortingFeature.utils.js:248-250`).
   11.4 makes it sortable. Stated here so 11.4's e2e does not assert a sort on a column
   that cannot sort yet, and so a reviewer of 11.3 does not read "unsortable" as an
   oversight.
9. **The stale tone's contrast on the row-hover surface is unverified until the gate
   re-runs.** `--clay-ink` on `--bg-2` is a gated pair
   (`tests/theme-contrast.test.ts:27-37`). If it fails, the words stay and the colour
   goes; the threshold does not move.
10. **No screen-reader pass.** The dialog's `aria-labelledby` points at a `useId()` value
    and Escape restores focus — both are asserted structurally by the source gate and by
    the e2e focus assertion. Whether NVDA announces the dialog usefully is unverified.
    What would verify it: a manual pass over `/crm/contacts/[id]` with three activities.
11. **The timeline's 44px-row and 375px-layout claims are unverified.** A3-4 in the UX
    spec asks for a 375px and a 1280px screenshot of a contact detail with three
    activities. No browser was run while writing this spec. The Playwright viewport is
    `Desktop Chrome` (`playwright.config.ts:18`), so the e2e journeys prove neither.
12. **CI does not prove this feature, even after 11.1's readiness fix.** Job `ci` runs
    `npm test` (vitest, memory repo, **no Postgres**, **no Playwright**) and
    `npm run build`. Job `e2e` runs Playwright only if all six secrets in `.github/workflows/ci.yml`
    (after 11.1 adds the demo pair) are present; an unset demo pair is an honest skip,
    which is still a green run in which every CRM journey silently did not execute. A
    reviewer must read the log for `ready=true` and a non-zero Playwright count. What
    remains a local-or-Neon check: the three e2e journeys, the `Date`-field strict-mode
    uniqueness, the focus restore, and every Drizzle write.
13. **`vitest` does not typecheck.** A green `npm test` after this feature does not mean
    TypeScript is green; `next build` is the only thing that says so, and it typechecks
    `e2e/` too.
