# Feature 11.8: Deal filters

**Phase:** 11 — CRM integrity, dead-ends, and list/task surface
**Status:** specced
**Estimated effort:** 4–5 hours
**Depends on:** nothing
**Blocks:** nothing (11.4's client-side sort composes with these filters but does not depend on them)

This is **Deal filters (B2 / G4)**. It is not the absorbed former-11.8 activity
delete / edit / backdate work; that lives in 11.3.

## Goal

Close **G4**: the deals table can only be searched by text, so "what's in
Negotiation closing this quarter, for one account" is a question the page
cannot answer.

Half of the capability already exists and is unreachable.
`ListDealsOpts` is `{ q?, organizationId?, contactId? }`
(`lib/crm/queries-shared.ts:73-77`) and both stores already implement both
id filters (`lib/crm/queries-memory.ts:215-217`,
`lib/crm/queries-drizzle.ts:266-272`) — but
`app/(authenticated)/crm/deals/page.tsx:11-12` parses **only** `q`, so a user
has no way to set them. `stage` and a close-date window are new query surface.

The second half of the goal is honesty about the empty state. Today
`/crm/deals?q=zzz` renders `No deals` (`components/crm/deal-table.tsx:143`) —
the same sentence a genuinely empty tenant gets, which is a lie. This feature
adds four more ways to reach that branch and fixes the lie at the same time, on
all three list pages, because leaving `/crm/contacts?q=zzz` saying one thing and
`/crm/deals?q=zzz` another is the drift this phase exists to stop.

## Scope

Include:

- **`ListDealsOpts` gains `stage?` and `closeAfter?` / `closeBefore?`** — three
  optional fields, extending the existing `opts` object. No parallel helper.
- **A pure client-safe parser module** `lib/crm/deal-params.ts` with
  `parseStage`, `parseCloseDate`, `closeBeforeExclusive`. Not under
  `lib/crm/queries*.ts`, and it value-imports nothing.
- **The memory and Drizzle filter implementations** for `stage` and the
  half-open close window, keeping the no-`q` vs `q`-join branch at
  `lib/crm/queries-drizzle.ts:273-293` intact.
- **`lib/crm/deal-actions.ts:61-65`** — the field-by-field re-projection gains
  the three new fields. This is the silent bug that makes the rest of the
  feature typecheck and not work.
- **Four new fields on the existing GET form** on the deals page: `Stage`,
  `Close from`, `Close to`, `Organization`.
- **A filter summary line** with a `Clear filters` link, rendered only when at
  least one filter is active.
- **The conditional empty state** on all three tables.
- Tests: memory-repo policy for each filter, the parser, the barrel and the
  action re-projection, and a browser journey.

Exclude (for now):

- **Filtering the pipeline board.** G5 is real — `pipeline/page.tsx:5` calls
  `listDealsAction()` with no opts — but the phase table puts pipeline filtering
  out of scope. Do not pass opts from the pipeline page.
- **A `contactId` control.** The query supports it and
  `app/(authenticated)/crm/contacts/[id]/page.tsx:26` uses it, but a contact
  picker on the deals list is a second filter UI on top of an organization
  picker and the product gain is unproven. It stays query-only.
- **Sorting.** 11.4. No `?sort=`, no sort control in the toolbar, and this
  feature must not imply that a sort survives a reload — it does not, and
  nothing in the filter summary may suggest it does.
- **Pagination or a bounded list.** B5 is a phase non-goal. `listDeals` stays
  unbounded (`lib/crm/queries-drizzle.ts:258-294` has no `limit`).
- **Auto-submit on change.** The contacts precedent is an explicit `Search`
  button (`app/(authenticated)/crm/contacts/page.tsx:63`) and this feature
  copies it. Five fields that re-query per keystroke is a worse experience and
  makes `Clear filters` arrive after the filter it clears.
- **A filter count, a faceted sidebar, a saved view, a share link.**
- **A new route.** All state is query params on `/crm/deals`. No
  `/crm/deals/filtered`.
- **A server-side error state.** An unknown `stage` renders the full table.
- **Touching `ListContactsOpts` or `ListOrganizationsOpts`.** The conditional
  empty state is a UI string, not a query change; the other two list pages keep
  their single `q` (and `?status=` on contacts).

## Spec

### 0. `ListDealsOpts` — the exact extension

`lib/crm/queries-shared.ts:73-77`, today:

```ts
export type ListDealsOpts = {
  q?: string;
  organizationId?: string;
  contactId?: string;
};
```

becomes:

```ts
export type ListDealsOpts = {
  q?: string;
  organizationId?: string;
  contactId?: string;
  stage?: DealStage;
  closeAfter?: Date;
  closeBefore?: Date;
};
```

`DealStage` is already imported at `lib/crm/queries-shared.ts:6`. **No new
import.** The field names are the design's, not the ideas doc's: the doc says
`closeBefore` / `closeAfter` and so does this, and the order in the type is
`after` then `before` because a range reads low-to-high.

**Two-argument callers stay valid.** `listDeals(tenantId, repo)` is called that
way in six places (`lib/crm/dashboard.ts:260`, `lib/crm/move-deal.ts:29`,
`app/(authenticated)/crm/pipeline/page.tsx:5` via `listDealsAction()` with no
argument, and three test files). Every new field is optional, so none of them
changes. This is the type-level acceptance criterion.

**`closeDate` is nullable** (`lib/crm/schema.ts:81`), and a NULL `closeDate` is
**excluded** by any active close window. A deal with no close date is not "in
the range"; it has no position in it. A test pins this.

### 1. The window is half-open, and that is the whole trap

`closeDate >= closeAfter` **and** `closeDate < closeBefore`.

`closeAfter` is the picked day at `00:00:00.000Z`, inclusive.
`closeBefore` is **the next day's UTC midnight**, exclusive.

Why not `lte` on the picked day: `closeDate` is `timestamp withTimezone`
(`lib/crm/schema.ts:81`), so a deal saved with a time component exists.
`components/crm/deal-form.tsx:43-49` happens to write UTC midnight, which makes
an inclusive `lte 23:59:59.999` *look* correct against the seed — but a deal
created through any other path, or a deal whose `closeDate` was written by
`moveDeal`, can carry a time. An inclusive upper bound on the day drops the
final day of the range whenever a timestamp is not exactly midnight. Half-open
is correct for every timestamp and costs one derived `Date`.

### 2. `lib/crm/deal-params.ts` — the parser

Pure. **Not** under `lib/crm/queries*.ts`, and it must not be — a module under
`components/` that imports `lib/crm/queries-shared` as a **value** would trip
`lib/client-boundary.test.ts:155-166`, whose regex matches the `queries` prefix
(`/(?:^|\/)lib\/(?:crm|space|rolodex)\/(?:queries|schema|seed|reset)\b/`).
This module is only imported by a **server component**
(`app/(authenticated)/crm/deals/page.tsx`), so the boundary is not in play — but
it lives outside the `queries*` family anyway, because the design named it that
and because a future client component should be able to import it.

```ts
import { DEAL_STAGES, type DealStage } from "./constants";

export function parseStage(raw: string | string[] | undefined): DealStage | undefined;
export function parseCloseDate(raw: string | string[] | undefined): Date | undefined;
export function closeBeforeExclusive(raw: string | string[] | undefined): Date | undefined;
```

**`parseStage` — copies `parseStatus` from
`app/(authenticated)/crm/contacts/page.tsx:8-19` exactly, including the
`Array.isArray(raw) ? raw[0] : raw` unwrap and the `(DEAL_STAGES as readonly
string[]).includes(value)` membership test.** Returns `undefined` for anything
unknown. `/crm/deals?stage=Bogus` renders the full, unfiltered table with `All`
selected in the `<select>` and a 200. It must never throw and never 500.

**`parseCloseDate` — the UTC-midnight rule, and the two failures it exists to
stop:**

```ts
function parseCloseDate(raw: string | string[] | undefined): Date | undefined {
  const value = Array.isArray(raw) ? raw[0] : raw;
  if (typeof value !== "string" || !/^\d{4}-\d{2}-\d{2}$/.test(value)) {
    return undefined;
  }
  const date = new Date(`${value}T00:00:00.000Z`);
  // "2026-02-31" passes the shape test and rolls to March 3. Round-trip it.
  if (Number.isNaN(date.getTime()) || date.toISOString().slice(0, 10) !== value) {
    return undefined;
  }
  return date;
}
```

- The **`Z` is the load-bearing character.** `new Date("2026-09-29")` is UTC by
  the ES date-only rule, but `new Date("2026-09-29T00:00:00")` — the form an
  implementer writes by reflex, and the form
  `components/crm/deal-form.tsx:48` almost uses — is **local time** and shifts
  seven hours on this host's `America/Los_Angeles`, silently moving a filter
  boundary. Write it with `T00:00:00.000Z` and put a comment on the line naming
  the missing-`Z` failure so nobody "simplifies" it later.
- The **round-trip** rejects `"2026-02-31"`, which satisfies the regex and rolls
  forward to March 3. Without it, a hand-edited URL produces a filter for a day
  that does not exist.
- **`closeBeforeExclusive`** is the same parse with `+ 1` day:
  `new Date(date.getTime() + 86_400_000)`, after the round-trip check. Adding a
  fixed 24 h in **UTC** is exact; there is no DST in UTC, so this is not a
  calendar-arithmetic hazard. It runs **after** the validation, so a rejected
  date never produces a `Date` from a rolled-over March 3.
- Both return `undefined` rather than throwing. An unparseable date is ignored,
  exactly like an unknown `stage` — the page renders 200 with that one filter
  inactive.
- **Inverted window (`from > to`) returns `[]`.** Not "ignore the window", not
  "swap them": `closeAfter` is `Sep 30` and `closeBefore` is `Sep 1` and no
  timestamp satisfies both, so the honest result is the empty list, and the
  conditional empty state plus the summary line say why. Stated as a test.

### 3. Memory implementation

`listDealsInMemory` (`lib/crm/queries-memory.ts:205-220`) gains two conditions
in the existing `.filter(...)` chain, in this order — after the two id
predicates, so the chain reads scope → search → org → contact → stage → window:

```ts
(opts?.stage === undefined || row.stage === opts.stage) &&
(opts?.closeAfter === undefined ||
  (row.closeDate !== null && row.closeDate >= opts.closeAfter)) &&
(opts?.closeBefore === undefined ||
  (row.closeDate !== null && row.closeDate < opts.closeBefore))
```

**The explicit `row.closeDate !== null` guard is not redundant, and it is not
cosmetic either.** Postgres gets the right answer for free: `closeDate >= $1`
against a NULL yields NULL, and `WHERE NULL` is false, so the row is excluded.
JavaScript does **not** get it for free in a way anyone should rely on —
`null >= someDate` runs a relational comparison that coerces, and whether it
throws, coerces `null` to `0`, or coerces the `Date` to a number depends on
which operand is the object. Do not reason about it. Write the explicit guard
so the two stores are provably equal rather than accidentally equal, and write
the test at criterion 9 that pins it.

### 4. Drizzle implementation

`listDealsInDrizzle` (`lib/crm/queries-drizzle.ts:258-294`) extends the
`filters` array at `:262-272` with the same conditional-spread shape already used
for `organizationId` and `contactId`:

```ts
...(opts?.stage !== undefined ? [eq(deals.stage, opts.stage)] : []),
...(opts?.closeAfter !== undefined ? [gte(deals.closeDate, opts.closeAfter)] : []),
...(opts?.closeBefore !== undefined ? [lt(deals.closeDate, opts.closeBefore)] : []),
```

`gte` and `lt` are added to the `drizzle-orm` import at `:1` (both are exported
from `drizzle-orm` and typed as `BinaryOperator` in
`node_modules/drizzle-orm/sql/expressions/conditions.d.ts:124` and `:139`).
Nothing else in that import line changes.

**The two return branches at `:273-293` are not restructured.** The `filters`
array is shared by both: the no-`q` branch selects from `deals` alone, the
`q` branch left-joins `organizations` and `contacts` for the ILIKE across
`deals.name` / `organizations.name` / `contacts.name`
(`lib/crm/queries-drizzle.ts:83-93`). Adding to `filters` therefore works in
both branches with no change to the branch itself, and the left-join cannot
duplicate a `deals` row because the join keys are `deals.organizationId` and
`deals.contactId`, both unique targets.

**No new ILIKE.** `q` still goes through `dealSearchSql` →
`ilikeContains` → `escapeIlike` (`:40-56`), so 9.6's escape discipline is not
bypassed. Do not hand-roll a `like` for the organization filter — that is an id
equality, `eq`, exactly as `organizationId` is handled today.

### 5. `lib/crm/deal-actions.ts:61-65` — the silent bug

Today:

```ts
export async function listDealsForSession(
  getSession: GetSession,
  input: ListDealsOpts & ClientTenantInput = {},
  repo?: CrmRepository,
): Promise<Deal[]> {
  const { tenantId } = await requireTenant(getSession, input);
  return listDeals(tenantId, repo, {
    q: input.q,
    organizationId: input.organizationId,
    contactId: input.contactId,
  });
}
```

The literal re-projects field by field. **Add the three new fields explicitly:**

```ts
  return listDeals(tenantId, repo, {
    q: input.q,
    organizationId: input.organizationId,
    contactId: input.contactId,
    stage: input.stage,
    closeAfter: input.closeAfter,
    closeBefore: input.closeBefore,
  });
```

**Do not replace the literal with `...input` or `return listDeals(tenantId, repo, input)`.**
Both would work today, because `requireTenant(getSession, input)` **ignores its
second argument entirely** (`lib/tenancy/index.ts:27-30`, parameter named
`_client`) — but `input` is typed `ListDealsOpts & ClientTenantInput`, so
spreading it forwards the client-supplied `tenantId` into the opts object. It
does not reach SQL today (nothing in `listDeals` reads a `tenantId` from opts),
but it puts an attacker-controlled tenant id inside a value that is about to be
handed to a query, and the next person to add a filter to `ListDealsOpts` may
read it. The explicit literal is the invariant; the design named it and this
spec repeats it.

**Field order in the literal matches `ListDealsOpts`'s declaration order** —
`q`, `organizationId`, `contactId`, `stage`, `closeAfter`, `closeBefore` — so a
reviewer can diff the two blocks by eye.

`ClientTenantInput` (`:21-23`) is unchanged, and the `*Action` wrappers
(`:146-183`) are unchanged. `listDealsAction(opts?)` already forwards the whole
opts object to `listDealsForSession`, so the page's call site needs no change
beyond the arguments it passes.

**The page's own query call, rewritten:**

```ts
const { q: rawQ, stage: rawStage, closeFrom, closeTo, organizationId } =
  await searchParams;
const q = Array.isArray(rawQ) ? rawQ[0] : rawQ;
const stage = parseStage(rawStage);
const closeAfter = parseCloseDate(closeFrom);
const closeToDate = parseCloseDate(closeTo);
const closeBefore = closeBeforeExclusive(closeTo);
const org = organizations.some((o) => o.id === organizationId)
  ? organizationId
  : undefined;
const [deals, contacts] = await Promise.all([
  listDealsAction({ q, stage, closeAfter, closeBefore, organizationId: org }),
  listContactsAction(),
]);
```

**`organizations` is fetched before it is used for the `organizationId`
check**, so the `Promise.all` is restructured: `listOrganizationsAction()`
and `listContactsAction()` resolve first, then `listDealsAction` is called with
the validated id. The alternative — passing a raw `organizationId` through and
letting the query return `[]` — is the "stale link shows an empty table" failure
the UX spec named, and the fix is cheap: a syntactically valid id that matches
no organization in this tenant is treated as **no filter** (the select shows
`All`, the summary line omits it, the full table renders). Note the ordering
change is forced by the data dependency, not a preference — and the page is a
server component, so the second `await` is not a client round trip.

### 7. The summary line

Rendered **inside `.crm-toolbar`, after the form and before `Add deal`**,
only when at least one filter is active. Active means: a non-blank `q` (after
trim), a parsed `stage`, a parsed `closeAfter`, a parsed `closeBefore`, or a
validated `organizationId`.

```tsx
{summary ? (
  <p className={styles["crm-filter-summary"]}>
    {summary} <Link href="/crm/deals">Clear filters</Link>
  </p>
) : null}
```

**The summary string, built in the page from the parsed values, in this order:
`q` → `stage` → the date window → organization. Four shapes, exact:**

| Active | String |
| --- | --- |
| `q` only | `Showing deals matching "ana" · Clear filters` |
| `stage` only | `Showing deals in Negotiation · Clear filters` |
| a date window (either or both ends) | `Showing deals closing Jul 1 – Sep 30, 2026 · Clear filters` |
| `organizationId` only | `Showing deals for Northwind Logistics · Clear filters` |

When more than one is active the parts are joined with `, ` and the
`· Clear filters` suffix is appended **once**, at the end:

```
Showing deals matching "ana" in Negotiation closing Jul 1 – Sep 30, 2026 · Clear filters
```

Rules that are not negotiable:

- **Dates are rendered through `formatDate`** (`lib/crm/format.ts:8-18`), which
  is `Intl.DateTimeFormat("en-US", { month: "short", day: "numeric", year:
  "numeric", timeZone: "UTC" })` → `Sep 30, 2026`. The `timeZone: "UTC"` is why
  this is safe: the filter boundary is a UTC midnight, and formatting it in
  local time would render the wrong calendar day for a user west of Greenwich
  in the evening. The en dash between the two dates is U+2013.
- **A half-open window** renders one end when only one is active:
  `Showing deals closing from Jul 1, 2026 · Clear filters` (only `closeAfter`)
  or `Showing deals closing through Sep 30, 2026 · Clear filters` (only
  `closeBefore`). No em dash with a missing operand.
- **`Clear filters` is a `<Link href="/crm/deals">`, not a button.** The
  filter state *is* the URL, so the way out of the state is a URL, and it
  should be middle-clickable. It is the only link in the toolbar.
- **No live region.** `role="status"`, `aria-live`: none. The line changes on
  navigation, not in place. It is a live summary of what is on screen and it is
  the only thing that tells a screen-reader user *why* the table is short, so it
  is rendered as text and left in the accessibility tree.
- **The `q` term is inserted between straight double quotes** as part of the
  string. It is React-rendered from a server component, so it is escaped by
  React; there is no `dangerouslySetInnerHTML` anywhere in this feature.
- **No count.** `Showing 4 deals · Clear filters` is *not* this design — a
  count is a fourth thing that goes stale between the summary and the table
  under 11.4's client-side sort, and the table itself shows the rows.

### 9. The conditional empty state

**The rule, applied to all three tables, in this PR:**

> If any filter is active, the table's empty state is `No {noun} match these
> filters.` If none is, it is the shipped string, unchanged.

| Table | No filter active | Filter active |
| --- | --- | --- |
| `deal-table.tsx:142-143` | `No deals` (unchanged) | `No deals match these filters.` |
| `contact-table.tsx:111-112` | `No contacts` (unchanged) | `No contacts match these filters.` |
| `org-table.tsx:88-89` | `No organizations` (unchanged) | `No organizations match these filters.` |

**One new optional prop per table component, named `filtered`:**

```ts
export function DealTable({
  deals,
  organizations,
  contacts,
  filtered = false,
}: {
  deals: Deal[];
  organizations: Organization[];
  contacts: Contact[];
  filtered?: boolean;
})
```

and in the render:

```tsx
{deals.length === 0 ? (
  <p className={styles["crm-empty"]}>
    {filtered ? "No deals match these filters." : "No deals"}
  </p>
) : (
```

A **default of `false`** is what keeps the other two pages working with no
change to their call sites beyond passing the prop, and what keeps 11.5's
mounted tables and 11.4's rewritten `<thead>` unaffected by the ternary.

- **The three sentences are the binding UX copy table's rows 11.8-12, 11.8-13 and
  11.8-14**, including the periods. They are sentences, not labels, which is
  why they differ from `No deals` — the shipped strings keep their exact
  no-period form.
- **`.crm-empty` is unchanged** (`org.module.css:215-221`). Only the string is
  conditional.
- The three pages compute their own `filtered` flag:
  - deals: the same `summary` truthiness as §7;
  - contacts: `q` non-blank **or** `status` parsed
    (`app/(authenticated)/crm/contacts/page.tsx:24-29`);
  - organizations: `q` non-blank after trim (`organizations/page.tsx:9-11`).
- This **fixes a pre-existing lie** for `?q=`, which is in scope and stated:
  `/crm/contacts?q=zzz` currently says `No contacts` and after this feature
  says `No contacts match these filters.`

## Implementation notes

- **`lib/crm/deal-actions.ts:61-65` is the whole reason 11.8 is on the board
  as its own row.** Adding `stage` to `ListDealsOpts` and to the page's call
  site typechecks, renders, filters nothing, and shows up as "the filter does
  nothing" with no error anywhere. The re-projection is a deliberate
  tenant-scoping defence (it stops `ClientTenantInput.tenantId` reaching
  `opts`), and the cost is that the type is not the contract. Criterion 11 and
  the criterion 29 probe 1 exist to keep that cost visible.
- **Half-open, not inclusive.** `gte` + `lt` against a derived next-day midnight.
  The seeded `closeDate` happens to be UTC midnight
  (`components/crm/deal-form.tsx:43-49`) which makes `lte 23:59:59.999` *look*
  right; it is coincidence, not a reason. Criterion 24 is the test that would
  fail with the inclusive bound, and it is an e2e because the memory store
  cannot catch it.
- **The `Z` in the date parser is the highest-risk character in this feature.**
  `new Date("2026-09-29T00:00:00")` is **local** and shifts seven hours on this
  host. The comment naming it is not decoration; it is the thing that stops the
  next implementer from "simplifying" the template literal.
- **`formatDate`'s `timeZone: "UTC"` is load-bearing for the summary, not just
  for the table.** A filter boundary is a UTC midnight; rendering it in local
  time would show the previous day to a user west of Greenwich in the evening.
  Do not add a second formatter.
- **Do not spread `input` into the opts literal**, even though
  `requireTenant` ignores its second argument (`lib/tenancy/index.ts:27-30`).
  See §5.
- **`Promise.all` restructuring on the deals page is forced, not stylistic.**
  The `organizationId` validation needs the organizations array, so the deal
  query cannot be in the same `Promise.all` as the organization query. Two
  sequential awaits in a server component, not a client round trip.
- **TanStack Table is v9 (`package.json:23` `"@tanstack/react-table": "^9.2.4"`)
  and this feature does not touch it.** No `getSortedRowModel`, no
  `onSortingChange`, no `SortingState`. The only change to `deal-table.tsx` is
  the `filtered` prop and the ternary at `:142-143`. 11.4 owns the header.
- **The demo tenant has no `closeDate` on any seeded deal.** Recorded at
  criterion 25. Do not add one to `lib/crm/seed.ts` — that would make 11.1's
  and 11.2's seed-order assertions depend on a field they have no reason to
  care about, and `lib/crm/seed.test.ts` would need updating for a change no
  feature asked for.
- **The seeded stage distribution is the test fixture**: `Won`,
  `Negotiation`, `Proposal`, `Lost`, `Qualified`, `New`
  (`lib/crm/seed.ts:126-173`) — one deal per stage. That is why the stage test
  can assert a specific deal is visible and a specific other deal is not, by
  name, without any count.
- **Do not run prettier on a directory.** Explicit paths, only for the files
  this feature creates (`lib/crm/deal-params.ts`,
  `lib/crm/deal-params.test.ts`, `e2e/crm-deal-filters.spec.ts`).
  `features/INDEX.md` and `CURRENT_FEATURE.md` are already unformatted at HEAD;
  do not reflow them.
- **Shipped notes are evidence.** Every `path:line` in this spec was read in the
