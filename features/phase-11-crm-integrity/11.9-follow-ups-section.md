# Feature 11.9: Tasks section

**Phase:** 11 — CRM integrity, dead-ends, and list/task surface
**Status:** specced
**Estimated effort:** 6–8 hours
**Depends on:** 11.3
**Blocks:** 11.10 (its acceptance is "⌘K opens from any CRM section", which is five sections until this one exists)

## Goal

Give the CRM one list of everything the signed-in user owes someone, grouped by
when it is due, so a `dueDate` stops being a field on an activity and becomes a
thing with a surface. `followUps` is already live
(`lib/crm/dashboard.ts:192-214`) and is consumed by exactly one caller —
`DashboardFollowUps` on the dashboard (`app/(authenticated)/crm/page.tsx:98-101`)
— and it answers one question with two buckets: overdue, or not yet. There is no
place in the app that shows what is due **today**, this week, or later, and no
place to go from a panel to the whole list. Closes **G6**.

The destination is **`/crm/tasks`, tab label `Tasks`** — the design doc's ruling,
which overrules the UX doc's `/crm/follow-ups` / `Follow-ups`. A tab whose label
and URL disagree is a permanent papercut, and both the ideas doc's B3 acceptance
and 11.10's acceptance name `/crm/tasks`. The dashboard's own copy keeps saying
"follow-ups" (`No overdue follow-ups`, `components/crm/dashboard-followups.tsx:77`)
— that is a deliberate, recorded inconsistency, because renaming shipped
dashboard strings inside this feature is more expensive than the papercut.

## Spec

### 1. `lib/crm/tasks.ts` — the pure aggregation

One module, no imports except types. `import type { Activity } from
"./queries-shared"` — the type-only path, so nothing here can reach
`drizzle-orm` or `lib/db`, and so a client component may import it by value if a
future feature needs to.

```ts
import { type Activity } from "./queries-shared";

export type TaskWindow = "overdue" | "today" | "next7" | "later";

/** In display order. The array is the order the page renders sections in. */
export const TASK_WINDOWS: readonly TaskWindow[] = [
  "overdue",
  "today",
  "next7",
  "later",
];

export type Task = {
  activity: Activity;
  /** Whole days past due, or null outside the overdue window. */
  overdueByDays: number | null;
};

export type TaskBucket = {
  key: TaskWindow;
  heading: string;
  empty: string;
  items: Task[];
};

const HEADINGS: Record<TaskWindow, string> = {
  overdue: "Overdue",
  today: "Today",
  next7: "Next 7 days",
  later: "Later",
};

const EMPTIES: Record<TaskWindow, string> = {
  overdue: "Nothing overdue",
  today: "Nothing due today",
  next7: "Nothing due this week",
  later: "Nothing scheduled later",
};

const DAY_MS = 86_400_000;
const NEXT_SEVEN_DAYS = 7;

/**
 * The UTC day number of a Date. Whole days, so it is exact: every bound in this
 * module is a UTC day boundary, and no local-time or DST transition can make a
 * day 23 or 25 hours long.
 *
 * UTC is the shipped convention, not a new one: `utcDateOnly`
 * (`lib/crm/dashboard.ts:86-88`) is `toISOString().slice(0, 10)` and
 * `followUps` compares those strings. `new Date("2026-09-29")` is UTC by the ES
 * spec; the hazard is a form string **without** the `Z`, which is local and
 * shifts 7 hours on this host.
 */
export function dayNumber(date: Date): number {
  return Math.floor(date.getTime() / DAY_MS);
}
```

`taskBuckets`:

```ts
/**
 * Every undone activity with a due date, bucketed by window. The clock is
 * injected — this module never calls `new Date()` — for the same reason
 * `followUps(activities, today)` takes one (`lib/crm/dashboard.ts:192-195`).
 *
 * Always returns four buckets in `TASK_WINDOWS` order, empty ones included: a
 * window with nothing in it is information, and a section that disappears is a
 * different product decision from one that is empty.
 */
export function taskBuckets(activities: Activity[], now: Date): TaskBucket[] {
  const today = dayNumber(now);
  const pending = activities.filter(
    (activity) => activity.dueDate !== null && !activity.done,
  );
  const grouped: Record<TaskWindow, Task[]> = {
    overdue: [],
    today: [],
    next7: [],
    later: [],
  };
  for (const activity of pending) {
    const due = dayNumber(activity.dueDate!);
    const task: Task = {
      activity,
      overdueByDays: due < today ? today - due : null,
    };
    if (due < today) {
      grouped.overdue.push(task);
    } else if (due === today) {
      grouped.today.push(task);
    } else if (due <= today + NEXT_SEVEN_DAYS) {
      grouped.next7.push(task);
    } else {
      grouped.later.push(task);
    }
  }
  for (const key of TASK_WINDOWS) {
    grouped[key].sort(compareByDueDateThenId);
  }
  return TASK_WINDOWS.map((key) => ({
    key,
    heading: HEADINGS[key],
    empty: EMPTIES[key],
    items: grouped[key],
  }));
}

function compareByDueDateThenId(a: Task, b: Task): number {
  const byDate = a.activity.dueDate!.getTime() - b.activity.dueDate!.getTime();
  if (byDate !== 0) {
    return byDate;
  }
  return a.activity.id < b.activity.id
    ? -1
    : a.activity.id > b.activity.id
      ? 1
      : 0;
}
```

Five decisions inside that, each of which an implementer would otherwise have to
invent:

1. **`pending` is the same predicate `followUps` uses** — `dueDate != null` and
   `!done` (`lib/crm/dashboard.ts:197-198`). An activity with no due date is not
   a task; a done one is not owed anything. So checking a task off **removes it
   from the list**, which is B3's acceptance and the product's expectation.
2. **Bounds are half-open by construction on integer day numbers**, not on
   `Date` comparisons: `due < today`, `due === today`, `due <= today + 7`,
   otherwise later. "Next 7 days" therefore covers days `+1` through `+7`
   inclusive — seven days, and `+8` is `Later`. `+7` at `00:00:00.000Z` is the
   boundary case and it belongs to `next7`; the test pins it, because an
   off-by-one here silently moves a task between two visible sections.
3. **`dayNumber` floors the timestamp**, so a `dueDate` of
   `2026-09-06T23:59:59.000Z` is the day **before** a `now` of
   `2026-09-07T15:00:00.000Z` and reports `overdueByDays: 1`. That is the exact
   pair the shipped `followUps` test uses
   (`lib/crm/dashboard.test.ts:378-393`), so the two aggregations agree by
   construction on the same input.
4. **Ordering inside a bucket is `dueDate` ascending, then `id` ascending** —
   the comparator `followUps` inlines at `lib/crm/dashboard.ts:199-205`. The
   `id` tie-break is what makes the order total and the tests deterministic;
   the alternative, Postgres-unspecified order, is exactly G15.
5. **The heading and empty strings are data in this module**, not JSX in the
   page. Four sections, four headings, four empties, all named once, so the page
   has no literals to drift and the component has no copy at all.

`dayNumber` is exported so a test can assert the day arithmetic directly rather
than inferring it from bucket membership.

### 2. `app/(authenticated)/crm/tasks/page.tsx`

```tsx
import { TaskList } from "@/components/crm/task-list";
import styles from "@/components/crm/org.module.css";
import { listActivitiesAction } from "@/lib/crm/activity-actions";
import { listContactsAction } from "@/lib/crm/contact-actions";
import { listDealsAction } from "@/lib/crm/deal-actions";
import { taskBuckets } from "@/lib/crm/tasks";
import Link from "next/link";

export default async function TasksPage() {
  const [activities, contacts, deals] = await Promise.all([
    listActivitiesAction(),
    listContactsAction(),
    listDealsAction(),
  ]);
  const buckets = taskBuckets(activities, new Date());
  const contactNames: Record<string, string> = {};
  for (const contact of contacts) {
    contactNames[contact.id] = contact.name;
  }
  const dealNames: Record<string, string> = {};
  for (const deal of deals) {
    dealNames[deal.id] = deal.name;
  }
  const isEmpty = buckets.every((bucket) => bucket.items.length === 0);
  // …
}
```

Six decisions:

1. **Three existing `*Action` wrappers, no new server action module.** Each
   takes the session tenant through `requireTenant` inside itself
   (`lib/crm/activity-actions.ts:124-128`, `lib/crm/contact-actions.ts:109-114`,
   `lib/crm/deal-actions.ts`); the page never sees a `tenantId`. The design's
   module table names only `lib/crm/tasks.ts` for this feature, and adding a
   `tasks-actions.ts` that forwards to three existing actions would be a fourth
   layer of the same three calls.
2. **Names are resolved on the server into plain objects** and passed to the
   client component. `Record<string, string>` is serialisable across the
   server/client boundary; a `Map` is not the shape React props handle well, and
   a `useMemo`'d `Map` in the client is a second copy of the same data. This is
   the same pattern 11.4 depends on in the three tables
   (`components/crm/contact-table.tsx:28-34`).
3. **`new Date()` is read once, in the page body, and only passed into the pure
   function.** The clock never reaches the client, so server and client never
   disagree about which bucket a task is in — there is no hydration surface.
   `getDashboard` does exactly this (`lib/crm/dashboard.ts:264`).
4. **When every bucket is empty, render `No follow-ups` and nothing else.** One
   mechanism per condition: the four per-window empties then only ever describe
   a *window* being empty, and the page never says the same thing twice. This is
   the copy table's `No follow-ups` row, used for the whole-page state.
5. **No `searchParams`.** A server component may declare the prop and not read
   it; this one does not declare it, so a query string on the URL is inert and
   nothing implies a filter exists.
6. **Page identity is V6**: `atrium-pagetitle` + `<h1>Tasks</h1>` +
   `<p className="atrium-sub">Everything you owe, across every contact and
   deal</p>`. `h1` is exactly `Tasks` because `e2e/crm.spec.ts:55` walks the
   subnav names and asserts `getByRole("heading", { name: section, level: 1 })`
   for each one — the tab label and the heading are the same string, which is
   what makes that walk work at all.

The body, once the buckets exist:

```tsx
<main>
  <div className="atrium-pagetitle">
    <h1>Tasks</h1>
    <p className="atrium-sub">Everything you owe, across every contact and deal</p>
  </div>
  {isEmpty ? (
    <p className={styles["crm-empty"]}>No follow-ups</p>
  ) : (
    buckets.map((bucket) => (
      <section key={bucket.key}>
        <div className={styles["crm-task-head"]}>
          <h2>{bucket.heading}</h2>
          {bucket.items.length > 1 ? (
            <span className={styles["crm-task-count"]}>{bucket.items.length}</span>
          ) : null}
        </div>
        {bucket.items.length === 0 ? (
          <p className={styles["crm-empty"]}>{bucket.empty}</p>
        ) : (
          <TaskList
            tasks={bucket.items}
            contactNames={contactNames}
            dealNames={dealNames}
          />
        )}
      </section>
    ))
  )}
</main>
```

**The count lives outside the `<h2>`'s text, and a single-item window shows no
count at all.** Both are the strict-locator hazard in
`components/crm/crm-pnw.test.ts:295-318` — a heading whose accessible name is
`Overdue 3` cannot be matched as `Overdue`, and a `1` beside `1` row is noise.
`Overdue` also collides with the dashboard panel's heading, which is fine
because no test asserts both at once and neither screen is the other's; if a
future test does, scope it to the page.

**The clock cannot make two sections claim one task.** `dayNumber` is a total
function and the four branches are exhaustive and disjoint, so a task appears
exactly once on the page. That is worth a test (§6) because the alternative —
three overlapping predicates — is the likeliest way this feature ships a task
twice.

### 3. `components/crm/task-list.tsx`

`"use client"`. One `<ul>` of `<li>`, no wrapper chrome — the page supplies the
section and heading, exactly as `ActivityTimeline` is handed nothing but
activities (`components/crm/activity-timeline.tsx:42`).

**The import list is the client-boundary contract, and it is not negotiable.**
`lib/client-boundary.test.ts` walks the value-import graph from everything under
`components/` and forbids `lib/{crm,space,rolodex}/{queries,schema,seed,reset}`
(note the `\b` makes the pattern match `queries-shared` too, `:159`), `lib/db`,
`drizzle-orm`, and `@neondatabase/serverless` (`:155-166`). `Activity` therefore
arrives as an **`import type`**, which is erased at build time
(`:189-211`). `truncate` comes from `lib/crm/activity-labels.ts`, which the
design names for exactly this: a client-safe module with no value imports.
`formatDate` (`lib/crm/format.ts:8-18`) is already client-imported by
`components/crm/activity-timeline.tsx:7`, so the precedent is established.

The row:

```tsx
export function TaskList({
  tasks,
  contactNames,
  dealNames,
}: {
  tasks: Task[];
  contactNames: Record<string, string>;
  dealNames: Record<string, string>;
}) {
  const router = useRouter();
  const [pendingId, setPendingId] = useState<string | null>(null);

  async function onToggle(activity: Activity) {
    setPendingId(activity.id);
    try {
      await toggleActivityDoneAction(activity.id, !activity.done);
      router.refresh();
    } finally {
      setPendingId(null);
    }
  }

  return (
    <ul>
      {tasks.map((task) => {
        const { activity, overdueByDays } = task;
        const contactName = activity.contactId
          ? contactNames[activity.contactId]
          : undefined;
        const dealName = activity.dealId ? dealNames[activity.dealId] : undefined;
        return (
          <li key={activity.id}>
            <p>{activity.description}</p>
            <p>
              Due {formatDate(activity.dueDate)}
              {overdueByDays !== null
                ? ` · Overdue by ${overdueByDays} day${overdueByDays === 1 ? "" : "s"}`
                : ""}
            </p>
            <label>
              <input
                type="checkbox"
                checked={activity.done}
                disabled={pendingId === activity.id}
                aria-label={
                  activity.done
                    ? `Mark ${truncate(activity.description, 60)} not done`
                    : `Mark ${truncate(activity.description, 60)} done`
                }
                onChange={() => {
                  void onToggle(activity);
                }}
              />{" "}
              Done
            </label>
            {contactName ? (
              <Link
                className={styles["crm-table-link"]}
                href={`/crm/contacts/${activity.contactId}`}
              >
                {contactName}
              </Link>
            ) : dealName ? (
              <Link
                className={styles["crm-table-link"]}
                href={`/crm/deals/${activity.dealId}`}
              >
                {dealName}
              </Link>
            ) : null}
          </li>
        );
      })}
    </ul>
  );
}
```

The decisions a reader would otherwise have to guess:

- **`toggleActivityDoneAction` then `router.refresh()`** — the existing
  sequence, copied from `ActivityTimeline` (`:46-54`) and `FollowUpList`
  (`components/crm/dashboard-followups.tsx:20-28`). `setPendingId` is the
  per-row disabled mechanism both already use; a second one would be drift.
- **The checkbox's accessible name is 11.3's, byte-for-byte.** The design rules
  that 11.3 truncates the Done label in the same change as Edit and Delete, and
  11.3's exact template is not pinned in any Phase 11 document — the UX doc
  says leave it (A3-2) and the design overrules that. So the rule here is
  mechanical: **read
  `components/crm/activity-timeline.tsx`'s `aria-label` template at
  implementation time and copy it exactly**, including its `truncate` call and
  its argument. The same activity must have the same checkbox name on a contact
  detail page and on `/crm/tasks`; a reviewer diffs the two files. Writing a
  guessed template here would be inventing another writer's copy.
- **The link text is the record's name**, not the word `Contact` or `Deal`. The
  dashboard's recent-activity feed uses the type word
  (`app/(authenticated)/crm/page.tsx:77,87`) and two follow-up rows linked as
  `Contact` would be two links with one accessible name on one screen — the
  collision `crm-pnw.test.ts:302-318` was written for. **Exactly one link per
  row**, contact first, deal second: the job is "everything I owe *someone*", so
  the contact is the destination that answers it, and a row with both ids (the
  first three seeded activities, `lib/crm/seed.ts:175-213`) gets one link
  instead of two.
- **The fall-through chain ends in `null`, never a dead link.** An activity with
  a `contactId` that resolves to no name falls through to the deal, and with
  neither, the row renders its description and its date and **no link at all**.
  Never `<Link href="">`, never a link to a missing id — both foreign keys are
  `SET NULL` (`lib/crm/schema.ts:100-103`), so an unresolvable id should not
  occur, and the chain is what makes that "should not" harmless.
- **The due line keeps the shipped `Due {formatDate(...)}` string**
  (`components/crm/dashboard-followups.tsx:40`) and appends
  ` · Overdue by N days` in the same `·`-joined mono meta style. The `days`
  plural is the only conditional: `1 day`, `4 days`. Past tense, not
  "4 days overdue" — the section heading already says `Overdue`, and saying it
  twice is noise.
- **`formatDate` renders in UTC** (`lib/crm/format.ts:12-17`), which is the same

## Implementation notes

- **The fourth window's boundary is the whole feature.** `next7` is
  `today < due <= today + 7` — seven days, with `+7` inside it. Making it
  `< today + 7` moves a task due in exactly seven days from `Next 7 days` to
  `Later`, which is invisible on the demo tenant (its one seeded task is
  months overdue) and is exactly what case 4 and probe (a) exist for.
- **`dayNumber` floors, and that is the UTC decision.** `new Date("2026-09-29")`
  is UTC by the ES spec — the naive-parse hazard the data engineer expected is
  not the one that bites. The one that does is a **form string without the
  `Z`**: `"2026-09-29T00:00:00"` is local and shifts 7 hours on this host. The
  test in case 7 pins the difference, and §8 formats the fixture date in UTC for
  the same reason.
- **The clock is injected, and the injection is the point.** `taskBuckets`
  never calls `new Date()`; the page passes one. That is what makes the
  boundary tests possible at all, and it is why the page — not the component —
  owns time. `getDashboard` (`lib/crm/dashboard.ts:264`) and `followUps` (`:192`)
  already set the precedent.
- **The count is outside the `<h2>`, and the `1`-row case renders none.** Two
  things, one reason: a heading whose accessible name is `Overdue 3` cannot be
  matched as `Overdue`, and a `1` next to one row is noise. The gate that
  already failed the repo once for a repeated string is
  `components/crm/crm-pnw.test.ts:295-318`.
- **One link per row, contact first.** The dashboard's recent-activity feed
  renders both a `Contact` and a `Deal` link typed by noun
  (`app/(authenticated)/crm/page.tsx:77,87`); copying that here would put two
  same-named links on one screen once two tasks have contacts. The name is the
  link text, and the contact wins because the job is "everything I owe
  *someone*". The deal is a fallback, not a second link. A task with neither
  renders no link at all — the design's explicit requirement, and the reason the
  chain ends in `null` rather than a `None` placeholder.
- **The shared chrome is not touched, and the six-tab strip needs no help.**
  `.crm-subnav-list` already carries `flex-wrap: wrap`
  (`components/crm/crm-subnav.module.css:26`), so the strip wraps below roughly
  700 px of content width and the shared `border-bottom` sits under the last
  row. There is no collapsed-nav precedent anywhere in the repo, and both e2e
  walks click every tab by accessible name — a hamburger would break both.
- **`PAGES` is the existence gate, which is why `tests/crm-shell.test.ts` is not
  in the file list.** `components/crm/crm-pnw.test.ts:33` maps `PAGES` through
  `readFileSync`, so a missing page throws before any assertion runs. That is a
  stronger gate than an `existsSync` entry, and it keeps the feature's edits to
  the four files the design named. The cost is that `tests/crm-shell.test.ts`'s
  `describe("CRM shell")` title and its `it("creates the five section routes…")`
  wording now understate reality; that is a stale label, not a broken
  assertion, and changing it is a one-line call the controller can make.
- **11.3's exact checkbox template is not in any Phase 11 document, so this spec
  does not invent it.** The design rules that 11.3 truncates the Done label in
  the same change; the UX doc says leave it (A3-2). The contract here is
  mechanical — copy the template from
  `components/crm/activity-timeline.tsx` at implementation time — plus a source
  assertion that the row goes through `truncate` and a row-scoped Playwright
  lookup that does not depend on the string at all. If 11.3 landed with a
  different truncation length, this feature tracks it for free.
- **`ActivityTimeline` is not refactored into a shared row component.** It is
  11.3's file and it will carry Edit, Delete, a dialog, an Escape handler and a
  `confirm()`. Importing a row out of it is an edit to another feature's
  deliverable; duplicating three lines of `<ul>`/`<li>` markup is cheaper and
  keeps the two surfaces independent. The shared contract is the accessible
  names and `toggleActivityDoneAction`, both asserted, not the file.
- **`See all` is a link, not a button, and there is no filter behind it.** A
  GET form's state is its URL, so the way out of a filtered view is a URL; and
  `/crm/tasks` reads no query string, so `href="/crm/tasks?window=overdue"`
  would be a lie. Two links with two distinct words, because two identical
  `See all` labels on one screen is the same strict-locator trap as above.
- **The dashboard is untouched underneath.** `getDashboard` still calls the
  unbounded `listActivities` (`lib/crm/dashboard.ts:259-263`) and still computes
  `{overdue, upcoming}`. This feature's page makes the same three calls the
  dashboard already makes, so `/crm/tasks` is no heavier than `/crm` — and
  bounded lists are B5, out of scope for the phase.
- **Memory repo proves policy, not SQL.** `lib/crm/tasks.ts` is pure, so its
  tests are real. Everything else here is rendering and navigation. Job `ci`
  (`.github/workflows/ci.yml:22-25`) runs `npm test` and `npm run build` with
  **no Postgres and no Playwright**, and job `e2e` runs only if `ci.yml:46`'s
  four secrets are present — and before 11.1's readiness fix, an unset demo
  pair yields a green `e2e` job in which **every** CRM test silently skipped.
  Read the job log for `ready=true` and a non-zero Playwright count. Zero of
  this feature is proven by CI as it stands.
- **Shipped notes are read as evidence.** Every claim above is `path:line` into
  the working tree at `main`; no claim is made about history. The ideas doc's
  B3 note says the section "touches `crm-subnav.test.ts`" and that the existing
  tab walks "should not" break — **there is no `crm-subnav.test.ts` in the
  repo**, and both walks are array literals that an extra entry does change.
- **Do not run prettier on a directory.** Pass explicit paths, and only to files
  this feature creates or edits. `features/INDEX.md` and `CURRENT_FEATURE.md`
