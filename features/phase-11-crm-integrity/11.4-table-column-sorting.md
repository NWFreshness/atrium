## Spec

### 1. v9 wiring (not the ideas-doc v8 sentence)

The ideas doc says `useState<SortingState>` + `getSortedRowModel`. Those are
v8. The installed skill file maps them:

| v8 | v9 (9.2.4) |
| --- | --- |
| `getSortedRowModel()` option | `sortedRowModel: createSortedRowModel()` feature slot |
| implicit sorting feature | `rowSortingFeature` in the same `tableFeatures({})` call |

```ts
import {
  createColumnHelper,
  createSortedRowModel,
  rowSortingFeature,
  sortFn_alphanumeric,
  tableFeatures,
  useTable,
} from "@tanstack/react-table";

const features = tableFeatures({
  rowSortingFeature,
  sortedRowModel: createSortedRowModel(),
});
```

> **Correction, applied in the implementation.** The Goal line and AC1 name
> `createSortedHeader gestures()`. **No such export exists in
> `@tanstack/react-table@9.2.4`** — grepping both packages for
> `createSortedHeader` / `sortedHeaderGestures` / `SortedHeader` returns
> nothing. The header control is `header.column.getToggleSortingHandler()`,
> which this spec's own §3 already specifies correctly. An implementer
> following AC1's parenthetical literally gets a build error; the code below
> is what ships.

`createSortedRowModel()` takes no arguments. A `sortedRowModel` without
`rowSortingFeature` is a type error (`ValidateFeatureSlots`) — measured: the
build reports `TS2322 … 'sortedRowModel' requires 'rowSortingFeature' to be
included in this table's features`, plus a `TS2353` for every `sortFn:` and
`enableSorting:` column option, because the column-def type carries no
sorting options without the feature. Do **not** add
`useState<SortingState>` or `onSortingChange` — v9 keeps sorting state on
the table instance, seeded to `[]`. No URL.

`useTable({ features, columns, data, enableMultiSort: false })`.

Leave `enableSortingRemoval` at the default that **removes** the sort on the
third activation (asc → desc → none, or desc → asc → none for desc-first
columns). That is the "back to insertion order" acceptance.

> **Two refinements the implementation measured, both now in the code.**
>
> 1. **`sortFn: "auto"` is data-dependent and should not be relied on.** The
>    auto resolver samples the first ten rows and picks a built-in per
>    column. Over `["Zeta","alpha beta","Alpha","10 x","2 x"]` it returns
>    `10 x, 2 x, Alpha, Zeta, alpha beta`. Text columns pin
>    `sortFn_alphanumeric` instead, so the order is a property of the code.
> 2. **A bare arrow is not a `sortFn`.** An unwrapped function is called as
>    `(rowA, rowB, columnId)`, so a value comparator handed over unwrapped
>    compares two Row objects; `Number(row)` is `NaN` and the column renders
>    unsorted while `aria-sort` claims a direction. Custom comparators are
>    built with `constructSortFn({ sort })`. The Playwright Value journey is
>    what caught it.

### 2. The accessorFn / memoization trap

Carry the ideas doc's warning, verified against this tree:

> derived columns must live on the row data, not in an `accessorFn`

TanStack memoizes its core row model on `data` alone. An accessor that reads
a `useMemo` map (`orgNames` / `contactNames`) keeps stale values when the map
changes and `data` does not.

**Today's code already does the safe thing.** Keep the accessor as the id:

```ts
columnHelper.accessor("organizationId", {
  header: "Organization",
  cell: (info) => {
    const organizationId = info.getValue();
    if (!organizationId) return "";
    return orgNames.get(organizationId) ?? "";
  },
})
```

(`contact-table.tsx:58-67`, `deal-table.tsx:79-98`.)

**Do not** change this to:

```ts
accessorFn: (row) => orgNames.get(row.organizationId ?? "") ?? ""
```

To sort by the **visible name** rather than the UUID, attach a `sortFn` that
compares `orgNames.get(id)` (ascending comparison only; the table reverses
on desc — `node_modules/@tanstack/table-core/skills/sorting/SKILL.md` [HIGH]
"Reversing inside the comparator"). Put that `sortFn` in the same `useMemo`
as `columns`, and keep `orgNames` in the dependency array
(`deal-table.tsx:131` is `[contactNames, orgNames, router]`).

Name columns (`name`, `email`, `stage`, `website`, `industry`) use the
built-in alphanumeric/text sort on the accessor value. `value` is numeric.
`closeDate` is a Date; if using `sortUndefined`, know that v9 compares
`=== void 0` only — CRM stores `null` (`schema.ts:81`). Normalise with
`(row) => row.closeDate ?? undefined` **or** accept that blank dates sort
as epoch.

> **Measured: `?? undefined` and `sortUndefined` are not interchangeable here,
> and `sortUndefined` alone is not enough.** v9's undefined test is
> `aValue === void 0`, so a `null` in the row never triggers it — the shipped
> code uses `sortUndefined: "last"`, which parks blanks last in **both**
> directions (measured over `{null, Jan 14, Feb 28}`: ascending
> `null, Jan 14, Feb 28`; descending `Feb 28, Jan 14, null`). The
> `?? undefined` form works too but requires changing the accessor, which
> would also change the cell's `null` contract that 11.2's Journey G asserts
> on; `sortUndefined` was the smaller change.

### 3. Headers

Every sortable `<th>`:

- `scope="col"`
- `aria-sort="ascending" | "descending" | "none"` at all times (including
  `"none"` when unsorted)
- a `<button type="button">` whose accessible name is the column label
  alone (`Name`, `Value`, …)
- `onClick={header.column.getToggleSortingHandler()}`
- caret `aria-hidden="true"`

The Actions `<th>` has **no** `aria-sort` and no button
(`enableSorting: false`).

> **The Actions gap is enforced, not assumed.** A naive `aria-sort` ternary
> over every `<th>` renders `aria-sort="none"` on Actions, which claims a
> sortable column that cannot sort. Measured in Chromium before the fix.
> Gate the attribute on `getCanSort()` with an `undefined` fallthrough.

First-click direction: text columns ascending; `Value` and `Close date`
descending (`sortDescFirst: true`) so "biggest / latest first" matches the
JTBD ("sort by close date or value without reading every row").

### 4. Empty states and `?q=`

Empty checks are on the **prop** (`org-table.tsx:88`,
`contact-table.tsx:111`, `deal-table.tsx:142`), not the row model. Sorting
cannot hide an empty state and must not be wired such that an empty array
renders a table of headers only. Keep the `length === 0` branch first.

`?q=` still filters on the server. Sort the filtered rows in the browser.
`page.url()` after a header click equals `page.url()` before it.

### 5. Browser gate (in 11.2's file)

Append to `e2e/crm-deals.spec.ts`. House style from 11.2 / 11.1 sections
0–3 (`NAV_TIMEOUT`, no exact row counts, `exact: true`, no
`waitForTimeout`).

On `/crm/deals`:

1. `Value` columnheader `aria-sort` starts `"none"`.
2. Click → `"descending"` (or `"ascending"` if the implementer did not set
   `sortDescFirst`; pick one, pin it, assert it). Then the other direction.
   Then `"none"`.
3. While sorted, money cells are monotone in that direction. Parse
   `$75,000.00` with `Number(text.replace(/[^0-9.-]/g, ""))`. **Do not**
   assert an exact sequence — the demo tenant accumulates rows.
4. `page.url()` unchanged.
5. `?q=` still narrows; then sorting still works on the remaining rows.
6. `/crm/organizations?q=zzzz-no-such-org` still shows `No organizations`.

On `/crm/contacts`, click Organization once and assert rendered org names
are sorted lexicographically (monotone), **not** that they equal a fixed
seed list.

If 11.2 has not landed `e2e/crm-deals.spec.ts`, this feature cannot invent

   the seeded org names sort in the opposite order to their uuids.
   `contact-table.tsx` md5 `0f51ac99…` before and after.

**A defect no source grep could have caught.** `sortNumber` began as a bare
`(a, b) => …` arrow. v9 calls an unwrapped `sortFn` as `(rowA, rowB,
columnId)`, so it compared two Row objects; `Number(row)` is `NaN` and every
pair compared equal-by-fiat, leaving the Value column in server order while
`aria-sort` read `"descending"`. Isolated: `18000 / 5000 / 120000` unsorted
bare, `120000 / 18000 / 5000` wrapped in `constructSortFn`. The Playwright
Value journey found it; `deal-table.test.ts` now fences the wrapping.

**Two e2e traps recorded for whoever appends to `crm-deals.spec.ts` next.**
`innerText` on a `<th>` returns the *rendered* text and
`.crm-table th` sets `text-transform: uppercase`, so a header reads
`"VALUE"`, not `"Value"` — `columnIndex` uses `textContent`. This failed all
four new journeys on their first run while the `aria-sort` assertions above
it passed. And `Edit`/`Delete` live in `<td>`, so a column read pairs a
header-position lookup with `td:nth-child(n)`; both orders come from one
column-def list.

**Pre-existing failure found and proved not ours.** `crm-pipeline.spec.ts:190`
was red because the seeded deal `Harbor & Lane intake` had drifted to stage
`Qualified` (read from Neon; `seed.ts:170` says `New`) — demo-tenant drift
from an earlier drag journey. Confirmed by stashing every change in this card
and re-running: **1 failed on clean `origin/main` too**. Applied the
documented remedy (Reset demo as the demo user); the tenant is back to seed
and all four CRM specs pass together (**15 passed**). The drag journeys

**Siblings verified green after this change:** `crm.spec.ts` (4),
