# Feature 11.5: Edit from the detail pages

**Phase:** 11 — CRM integrity, dead-ends, and list/task surface
**Status:** specced
**Estimated effort:** 3–4 hours
**Depends on:** 11.4
**Blocks:** nothing

## Goal

Close **G2**: the page a user opens to decide something is the page they
cannot change.

Verified 2026-09-29 — all three `[id]` pages render a read-only `<dl>` with
no form and no Edit control:

- `app/(authenticated)/crm/organizations/[id]/page.tsx:30-37` — Website /
  Industry / Notes. Title row is `:26-29`. No Edit.
- `app/(authenticated)/crm/contacts/[id]/page.tsx:36-58` — Email / Phone /
  Job title / Status / Organization. No Edit.
- `app/(authenticated)/crm/deals/[id]/page.tsx:37-72` — Stage / Value /
  Probability / Close date / Organization / Contact. No Edit.

The mechanism already exists on the list pages. Each form takes an optional
existing record plus `onClose`:

- `OrgForm` — `org-form.tsx:24-30`
- `ContactForm` — `contact-form.tsx:27-35`
- `DealForm` — `deal-form.tsx:64-74` (ideas doc cited `:64-80`; the props
  type ends at `:74`, the `onClose` destructure is `:68`, `initialValues`
  at `:77-79`)

List tables mount them as dialogs (`org-table.tsx:120-122`,
`contact-table.tsx:143-149`, `deal-table.tsx:174-181`). Detail pages mount
nothing.

11.1 excluded edit-from-detail journeys; they belong here, appended to
`e2e/crm-deals.spec.ts` (created by 11.2).

## Scope

### Include

- One **Edit** control per detail page, in the page-title row, with
  accessible name **`Edit {name}`** — the same string the list row already
  uses (`org-table.tsx:54`, `contact-table.tsx:77`, `deal-table.tsx:108`).
- Reuse `OrgForm` / `ContactForm` / `DealForm` as dialogs. The `<dl>` needs
  **no** changes: each form already calls `router.refresh()` before
  `onClose()` (`org-form.tsx:61-62`, `contact-form.tsx:70-71`,
  `deal-form.tsx:110-111`).
- **Deal detail fetches the full org and contact lists** for `DealForm`'s
  `<select>`s. Today it fetches one of each by id
  (`deals/[id]/page.tsx:23-29`). Pattern:
  `listOrganizationsAction()` (`lib/crm/org-actions.ts:66-71`) and
  `listContactsAction()` (`lib/crm/contact-actions.ts:109-114`) — already
  how `/crm/deals` loads them (`deals/page.tsx:13-17`).
- Edit-from-detail journeys in `e2e/crm-deals.spec.ts`.

### Exclude (for now)

- **No new route** (`/crm/.../[id]/edit`).
- **No duplicate "Add" affordance on a detail page.** No
  `AddOrganizationButton` / `AddContactButton` / `AddDealButton` on any
  `[id]` page. The activity form's submit stays `Add activity`
  (`activity-form.tsx:107-109`) and stays on contact and deal detail —
  that verb adds an activity *to this record*, which 11.3 owns. This
  feature does not touch `ActivityForm`.
- **No Delete on a detail page.** Deletes stay on list rows until 11.7.
- **Inline editing / autosave.**
- **The three list tables.** 11.4 owns header sorting on those files.
  This feature must not edit `org-table.tsx` / `contact-table.tsx` /
  `deal-table.tsx`. The existing list `Edit {name}` aria-labels keep
  resolving because they are untouched.
- **`DealForm` number validation.** 11.2 owns the barrel asserts and
  leaves `deal-form.tsx:89-93` as a nicety. Do not take that line.
- **Probability `%` suffix** on `deals/[id]/page.tsx:43`. Not this feature.
- **Restructuring the `<dl>`.** 11.3 may already have added `Last
  contacted` on the contact detail `<dl>`; do not reorder or rewrite it.

## Files to create

- A small client island per entity, **or** one shared
  `components/crm/detail-edit.tsx`, that holds dialog open state and
  renders the existing form. Server pages cannot use `useState`.
- **E2e additions in `e2e/crm-deals.spec.ts`** (created by 11.2): one
  journey per entity (org, contact, deal) that opens the detail page,
  clicks `Edit {name}`, saves a change, reloads, and asserts the `<dl>`
  shows it. That file is the deals-and-lists home 11.1 assigned to 11.2;
  11.5 appends rather than creating `e2e/crm-detail.spec.ts`.

- `app/(authenticated)/crm/contacts/[id]/page.tsx`

## Spec

### 0. Sequencing

**Depends on 11.4.** Do not implement in parallel with 11.4. 11.4 rewrites
the three table headers; an overlapping edit to those files is the
collision the phase table exists to prevent. This feature's own diffs are
the three `[id]` pages plus a new client island — stay in those files.

### 1. The Edit control

In the existing `.atrium-pagetitle` block, to the right of the
`atrium-sub` line (or immediately after the `<h1>`), render a button:

```ts
aria-label={`Edit ${organization.name}`}  // or contact.name / deal.name
```

Visible text: `Edit`. `type="button"`.

There will then be **two** elements named `Edit {name}` if the user
navigates from a list that also has that row on screen — but detail pages
do not render the list table, so on `/crm/deals/[id]` the control is
unique. List e2e keeps using the row button on `/crm/deals`. Detail e2e
uses the same accessible name on the detail page.

Do not change the list tables' labels.

### 2. Client island

Pages are async server components. Introduce e.g.
`components/crm/org-detail-edit.tsx`:

```tsx
"use client";
export function OrgDetailEdit({ organization }: { organization: Organization }) {
  const [open, setOpen] = useState(false);
  return (
    <>
      <button type="button" aria-label={`Edit ${organization.name}`} onClick={() => setOpen(true)}>
        Edit
      </button>
      {open ? (
        <OrgForm organization={organization} onClose={() => setOpen(false)} />
      ) : null}
    </>
  );
}
```

`ContactDetailEdit` also takes `organizations` (required by `ContactForm`).
`DealDetailEdit` takes `organizations` and `contacts`.

`OrgForm` / `ContactForm` / `DealForm` already render dialog chrome
(`role="dialog" aria-modal="true"`). Do not wrap a second dialog.

Cancel is the form's existing cancel path (the forms close via `onClose`;
if a form has no Cancel button today, Escape / clicking the existing close
control — read the form and do not invent a second footer). Verified:
`deal-form.tsx` submit is Save; check the form footer for a cancel button
and keep it. If there is none, `onClose` is still called after successful
save only — add a **Cancel** button labelled `Cancel` that calls `onClose`
without writing, **only if the form does not already have one**. Do not
duplicate.

### 3. Deal detail fetches lists

Replace the current Promise.all (`deals/[id]/page.tsx:23-29`) with:

```ts
const [organization, contact, activities, organizations, contacts] =
  await Promise.all([
    deal.organizationId
      ? getOrganizationAction(deal.organizationId)
      : Promise.resolve(null),
    deal.contactId ? getContactAction(deal.contactId) : Promise.resolve(null),
    listActivitiesAction({ dealId: id }),
    listOrganizationsAction(),
    listContactsAction(),
  ]);
```

Pass `organizations` and `contacts` into `DealDetailEdit`. The `<dl>`
continues to use the single `organization` / `contact` for the current
links.

Contact detail already has `listDealsAction` / `listActivitiesAction` /
optional org; it needs `listOrganizationsAction()` for `ContactForm`'s
select — **add that fetch**. Org detail's `OrgForm` needs no extra lists.

### 4. No Add on detail

Source-level assertion: the three `[id]/page.tsx` files do not import
`AddOrganizationButton`, `AddContactButton`, or `AddDealButton`.

### 5. E2e (append to `e2e/crm-deals.spec.ts`)

House style from 11.2 (sections 0–3): `NAV_TIMEOUT`, unique `Date.now()`
names, no exact row counts, `afterEach` cleanup, `exact: true`.

For a minted deal (reuse 11.2's mint helper):

1. `page.goto(\`/crm/deals/${id}\`)` **or** click the row link from
   `/crm/deals` (the name link, `deal-table.tsx:59-64`). Prefer the link
   click so the test does not need the id.
2. `getByRole("button", { name: \`Edit ${name}\`, exact: true })`.
3. Dialog visible; change Name (or Value); Save.
4. `page.reload()`.
5. Assert the `<h1>` or `<dl>` shows the new value.

Repeat for an organization and a contact (mint via their Add dialogs, as
`e2e/crm.spec.ts:82-87` does for orgs).

Cancel: open Edit, change a field, Cancel or close without save, reload,
assert the old value. Skip Cancel if the form has no Cancel and no
backdrop-click-to-close — then record that as a limit rather than adding
backdrop behaviour in this feature.
