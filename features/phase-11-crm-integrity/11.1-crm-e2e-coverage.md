# Feature 11.1: CRM e2e coverage for pipeline and activities

**Phase:** 11 — CRM integrity, dead-ends, and list/task surface
**Status:** in_progress
**Estimated effort:** 4–6 hours
**Depends on:** nothing
**Blocks:** 11.2 (which owns Journeys F/G and the `e2e/crm-deals.spec.ts` home), 11.3, 11.4, 11.5 — the browser net for every later feature that moves the pipeline, activity, or deal surface

Journeys F and G below are the **template for 11.2**, not work for this feature. The
deals half of this spec ships as `e2e/crm-deals.spec.ts` in 11.2, because 11.2 changes
deal write behaviour and a deals e2e written against today's permissiveness would
encode the wrong contract. The phase has **ten** features; 11.3 absorbs former 11.8
(activity delete + edit + backdate + last-contacted). There is no *separate*
former-11.8 activity spec because that work was absorbed into 11.3; **11.8 in this
phase is Deal filters**.

## Goal

Give the CRM the browser coverage it has never had: the pipeline drag (the only
write path with optimistic UI and no other e2e), and the activity form and its
done-toggle — all asserted against **persisted state after a reload**, because in
every one of these surfaces the DOM can be made to look right without a single row
being written.

Today `e2e/crm.spec.ts` is 111 lines and 4 tests: an unauth redirect, a demo
subnav walk, create-an-organization, and tenant isolation. The pipeline board
and the activity timeline have no browser coverage at all
(`docs/crm-feature-ideas.md`, observation after G16). Every later feature in
this phase changes one of those two surfaces.

**This feature ships five tests across two files. The deals half of this document
(Journeys F and G) is the written template for 11.2 and is not implemented here.**

## Spec

### 0. The house style, copied from the existing specs

- `test.beforeAll` throws if `AUTH_OWNER_EMAIL` / `AUTH_OWNER_PASSWORD` are
  missing (the shape at `e2e/crm.spec.ts:14-20`); demo-only tests
  `test.skip(!demoEmail || !demoPassword, "...")`.
- The `login(page, email, password)` helper is copied verbatim from
  `e2e/crm.spec.ts:22-28` — including `await expect(page).toHaveURL("/")`. Do
  **not** use `waitForURL` here: I measured that it does not survive the
  credentials-callback round trip (`/api/auth/callback/credentials` sits
  between the click and the landing), while `toHaveURL` retries and passes.
- `crmNav(page)` is `page.getByRole("navigation", { name: "CRM" })`.
- Errors: `page.on("pageerror", …)` and `page.on("console", m => m.type() === "error" && …)`
  as at `e2e/groove.spec.ts:206-208`.

### 1. Timing constants

Playwright's default per-assertion timeout is 5 s and the default **per-test**
budget is **30 s**. Both are wrong here, for different reasons:

- **Per-assertion:** a dev-server action against Neon RTTs takes seconds on a
  cold route. `e2e/workroom.spec.ts:211` already defines
  `const NAV_TIMEOUT = { timeout: 20_000 }` for this reason and
  `e2e/workroom.spec.ts:205-209` explains it. Use a `NAV_TIMEOUT`-style constant
  on every assertion that follows a navigation or a server action.
- **Per-test:** a journey that mints a deal, walks to the board, drags, reloads,
  and re-asserts is a multi-screen walk, and the 30 s cap is the **whole test's**
  budget, not one assertion's. `e2e/workroom.spec.ts:212` sets
  `WALK_TEST_TIMEOUT = 180_000` and calls `test.setTimeout(WALK_TEST_TIMEOUT)`
  at the top of the walk (`e2e/workroom.spec.ts:230`, `:286`). Do the same: each
  pipeline and deal journey starts with `test.setTimeout(60_000)`, and the
  deal create/delete journey, which visits four screens, uses `120_000`.
- **Never sleep to wait for a render.** Poll the URL or the assertion. A cold
  dev route can take ~10 s; `await expect(...).toBeVisible({ timeout })`
  retries for you, a `waitForTimeout` does not.

### 2. Fixtures — per test, never shared

**The trap:** CI sets `retries: 1` (`playwright.config.ts:13`). On a retry, the
previous attempt's rows are still in the demo tenant. A fixture shared across
tests, or any assertion written as "the table now has exactly 7 rows", lands on
state its own previous attempt created.

The rules, written into the spec so an implementer cannot get them wrong:

1. **Every mutating test mints its own rows inside the test body**, from a name
   built at run time: `` const stamp = `E2E Deal ${Date.now()}` `` — the exact
   pattern at `e2e/crm.spec.ts:81`.
2. **No `test.beforeAll` that writes.** A `beforeAll` that creates a fixture and
   a retry both run it, which is how suites end up asserting on a
   half-cleaned tenant.
3. **No assertion on an exact row count.** `await expect(page.getByRole("row")).toHaveCount(7)`
   is forbidden. Assert **presence** (`toBeVisible`), **absence**
   (`toHaveCount(0)` scoped to the test's own unique name), and **relative
   movement** (a count captured before an action and compared after). The demo
   tenant accumulates rows across every run and every retry; the existing
   `e2e/crm.spec.ts:67-95` already leaks an `E2E Org` per run and has never
   cared.
4. **`afterEach` deletes what the test created.** `page.on("dialog", d => void d.accept())`
   (the pattern at `e2e/space.spec.ts:158`) and then click the row's
   `Delete {name}` button, which is `aria-label`-addressable at
   `components/crm/deal-table.tsx:114`. Use a loop that re-reads the button list
   each pass rather than caching locators — I hit exactly this bug while
   probing: a cleanup loop that only ever looks at `.first()` deletes one row
   and silently leaves the rest. If cleanup itself fails, the test must not be
   reported as green.
5. Cleanup is best-effort **but verified**: assert the test's own name is gone.

### 3. The selectors — exact, and verified against the live DOM

I drove the real `/crm/pipeline` board to confirm these rather than inferring
them. Verified on the running app:

- **A stage column**: each is a `<section>` containing an `<h2>` with the stage
  name. Use
  ```ts
  const column = (stage: string) =>
    page.locator("section").filter({
      has: page.getByRole("heading", { name: stage, exact: true, level: 2 }),
    });
  ```
  `exact: true` matters — without it a column lookup for `New` also matches
  nothing else here, but the heading assertion `getByRole("heading", { name: "New" })`
  is a substring match by default and `e2e/groove.spec.ts:154` shows the repo
  already uses `exact: true` where it matters.
- **A deal card**: an `<article>` whose text contains the deal name and whose
  parent carries `data-rfd-droppable-id="{stage}"`. So
  ```ts
  const card = page.locator("article").filter({ hasText: name });
  ```
  is unique for a freshly minted name.
- **The card's meta line** (`components/crm/pipeline-board.tsx:146-150`):
  `"${formatMoney(value)} · ${formatMoney(expected)} expected · ${probability}%"`
  → for value `1000` and a Qualified deal: `$1,000.00 · $250.00 expected · 25%`.
  Assert on `· 25%` (or `25%`) rather than the whole string, so a
  `formatMoney` change does not break the drag test. Use `exact: false`
  deliberately here, and say so in a comment.
- **Nav labels need `{ exact: true }`.** `getByRole` performs a **substring**
  match by default. The CRM subnav contains "Organizations", "Contacts",
  "Deals", and "Pipeline"; a `getByRole("link", { name: "Deals" })` will also
  match any link whose accessible name contains "Deals" — including a deal row
  link on a detail page. The existing `e2e/crm.spec.ts:54` gets away without
  `exact: true` because it is on the list page; **these journeys are not all on
  the list page**, so `exact: true` is mandatory here.
- **Paths with parentheses** need quoting in prose and in any shell command:
  `"app/(authenticated)/crm"`. This affects the docs and any `grep` an
  implementer types, not the spec file itself.
- **Never assert on a CSS-module class** (`.crm-dialog`, `.card`). The classes
  are hashed. `e2e/groove.spec.ts` can select `.groove-master-leds` only because
  5.6 deliberately kept those as `:global` literals — the CRM classes are not,
  and `components/groove/groove-pass.test.ts` guards that contract.

### 5. Journey B — the mouse drag persists (the core gate)

1. Mint a deal **inside this test**:
   ```ts
   const name = `E2E Drag ${Date.now()}`;
   await page.goto("/crm/deals");
   await page.getByRole("button", { name: "Add deal", exact: true }).click();
   const dialog = page.getByRole("dialog", { name: "Add deal" });
   await expect(dialog).toBeVisible();
   await dialog.getByLabel("Name").fill(name);
   await dialog.getByLabel("Value").fill("1000");
   await dialog.getByRole("button", { name: "Save", exact: true }).click();
   await expect(dialog).toBeHidden({ timeout: NAV_TIMEOUT });
   await expect(page.getByRole("link", { name, exact: true })).toBeVisible(NAV_TIMEOUT);
   ```
   The dialog's accessible name is `Add deal` from `components/crm/deal-form.tsx:80`
   (`const title = deal ? \`Edit ${deal.name}\` : "Add deal"`), and the field
   labels come from the `htmlFor`/`id` pairs at `components/crm/deal-form.tsx:128-213`.
2. Go to `/crm/pipeline`; wait for the card:
   `const card = page.locator("article").filter({ hasText: name });`
   `await expect(card).toBeVisible(NAV_TIMEOUT);`
   Assert it starts in New: `await expect(column("New").getByText(name, { exact: true })).toBeVisible();`
3. **Drag for real.** A `.click()` on a card does nothing — I confirmed this —
   and neither does `dragTo()`. Use the mouse sequence, which measured **13/13**
   across viewports:
   ```ts
   const src = await card.boundingBox();
   const dst = await column("Qualified").boundingBox();
   if (!src || !dst) throw new Error("pipeline: missing bounding box");
   const from = { x: src.x + src.width / 2, y: src.y + src.height / 2 };
   const to = { x: dst.x + dst.width / 2, y: dst.y + 30 };
   await page.mouse.move(from.x, from.y);
   await page.mouse.down();
   await page.waitForTimeout(60);
   for (let s = 1; s <= 8; s += 1) {
     const t = s / 8;
     await page.mouse.move(from.x + (to.x - from.x) * t, from.y + (to.y - from.y) * t);
     await page.waitForTimeout(20);
   }
   await page.waitForTimeout(150);
   await page.mouse.up();
   ```
   The **incremental** moves with real time between them are what the sensor
   needs: `@hello-pangea/dnd`'s mouse sensor lifts only once the pointer has
   travelled past a 5 px threshold, and the drag is `raf`-throttled. A single
   jump does not lift. Do not "optimise" the loop into one `mouse.move`.
4. Wait for the move to land. **Do not assert immediately** —
   `onDragEnd` is async (`components/crm/pipeline-board.tsx:77-86`: optimistic
   rebase → `await moveDealAction` → `router.refresh()`), so the DOM updates
   first and the database second. Use `expect.poll` or a retrying assertion:
   ```ts
   await expect
     .poll(async () => (await column("Qualified").getByText(name, { exact: true }).count()) > 0, { timeout: 15_000 })
     .toBe(true);
   ```
5. **The assertion that makes this feature worth writing.** Reload, then assert
   the deal is still in Qualified:
   ```ts
   await page.reload();
   await expect(page.getByRole("heading", { name: "Pipeline", level: 1, exact: true })).toBeVisible(NAV_TIMEOUT);
   await expect(column("Qualified").getByText(name, { exact: true })).toBeVisible();
   await expect(column("New").getByText(name, { exact: true })).toHaveCount(0);
   ```
   Without the reload this test passes even if `moveDealAction` throws — the
   optimistic rebase has already moved the card. **This is the defect class
   11.1 exists to catch.** State that in a comment above the reload.
6. Assert the probability rebased: `await expect(card).toContainText("25%")`
   (`STAGE_PROBABILITY.Qualified === 25`, `lib/crm/constants.ts:13`). Assert
   this **after** the reload, so it reads the server's value rather than the
   optimistic one.
7. Assert the Deals table agrees — `components/crm/pipeline-board.tsx:85` calls
   `router.refresh()` but the board's own state is local; the cross-check that
   matters is a second surface:
   ```ts
   await page.goto("/crm/deals");
   const row = page.getByRole("row").filter({ hasText: name });
   await expect(row).toBeVisible(NAV_TIMEOUT);
   await expect(row).toContainText("Qualified");
   ```
   This is 1.6's acceptance criterion 3 ("Deals table shows the new stage"),
   which has never had a browser check.

### 6. Journey C — the keyboard drag persists

Same fixture discipline and the same assertions, driven by the keyboard sensor.

1. Mint and locate exactly as in Journey B.
2. **`await card.scrollIntoViewIfNeeded()` before `focus()`. This is not
   optional and it is not noise.** `locator.focus()` does not scroll. I
   measured the target card at `top: 639` in a 720 px viewport — straddling the
   fold — and the keyboard drag failed **0 of 3** at 300 ms between keys and
   **0 of 3** at 800 ms. With `scrollIntoViewIfNeeded()` first, the same
   sequence succeeded **5 of 5** at 1280×720 and **5 of 5** at 1280×1200.
   Without this line the test passes or fails by luck, and the next implementer
   will delete the "redundant" scroll and get a flaky suite. The comment must
   say this, in these words.
3. Sequence, with a settle between each key:
   ```ts
   await card.focus();
   await expect(card).toBeFocused();
   await page.keyboard.press("Space");
   await expect.poll(() => announcement(page)).toContain("You have lifted an item", { timeout: 10_000 });
   await page.keyboard.press("ArrowRight");
   await expect.poll(() => announcement(page)).toContain("You have moved the item", { timeout: 10_000 });
   await page.keyboard.press("Space");
   ```
   500 ms between keys measured reliably; 300 ms did not. The poll on the
   announcement is the honest synchronisation — it waits for the library's own
   live region rather than guessing.
4. Assert the lift is announced with `announcement(page)` reading
   `[aria-live]` text. **This is an accessibility assertion, not a drag
   assertion** — it is why this journey earns its place alongside Journey B
   rather than duplicating it: it exercises the keyboard sensor and the
   screen-reader contract, a different code path from the pointer.
5. Reload and assert Qualified + `25%`, exactly as Journey B steps 5–6.

### 7. Journey D — an activity persists and sorts

On `app/(authenticated)/crm/deals/[id]/page.tsx:74` the deal detail renders
`<ActivityForm dealId={id} />`, and the timeline at
`components/crm/activity-timeline.tsx` renders one `<li>` per activity with the
description in a `<p>`.

1. Mint a deal (same helper), then navigate to its detail page:
   `await page.getByRole("link", { name, exact: true }).click();`
   → `await expect(page.getByRole("heading", { name, level: 1, exact: true })).toBeVisible(NAV_TIMEOUT);`
2. Assert the Activities section exists:
   `await expect(page.getByRole("heading", { name: "Activities", level: 2, exact: true })).toBeVisible();`
3. Fill and submit. The form's labels come from
   `components/crm/activity-form.tsx:59-105`: `Type`, `Description`,
   `Due date`, `Done`, and the submit button is `Add activity`.
   ```ts
   await page.getByLabel("Type").selectOption("call");
   await page.getByLabel("Description").fill(activityText);
   await page.getByRole("button", { name: "Add activity", exact: true }).click();
   ```
4. Assert the description appears in the timeline, **then reload and assert it
   again**. Same reason as the drag: `createActivityAction` then
   `router.refresh()` (`components/crm/activity-form.tsx:39-51`).
5. Assert the timeline is **newest first**. `compareActivitiesNewestFirst`
   (`lib/crm/queries-shared.ts:168-185`) and the Drizzle `ORDER BY
   occurredAt DESC NULLS LAST, createdAt DESC, id`
   (`lib/crm/queries-drizzle.ts:375-379`) both put the newest first. Assert
   relative order rather than absolute index:
   ```ts
   const descriptions = page.locator("h2:has-text('Activities') ~ ul li p:first-of-type");
   ```
   is brittle — instead capture the index of the new description among the
   timeline's `<li>` elements and assert it is the **first** among those whose
   text is non-empty, which is true for a just-created activity and does not
   depend on how many seed activities the detail page has. If the page's seeded
   activity list makes even that unreliable, assert the weaker, still-true
   claim: the new description is the first `<li>` — and if that cannot be made
   true, assert only persistence and record the ordering claim as covered by
   `lib/crm/activity-actions.test.ts` in memory.

## Implementation notes

- **Why two files, not three.** `playwright.config.ts:11` sets
  `fullyParallel: false`, so every spec runs serially in one worker against one
  dev server. Separating the pipelines means a drag flake is attributable. The
  deals file lands with 11.2, which is also where 11.4/11.5 append.
- **The `scrollIntoViewIfNeeded()` line is the single most important thing in
  this spec.** It is the difference between 0/12 and 10/10 on the keyboard path.
  Comment it with the measurement so nobody removes it as redundant.
- **The incremental mouse loop is equally load-bearing.** The library's mouse
  sensor lifts only past a 5 px threshold and is `raf`-throttled
  (`isSloppyClickThresholdExceeded` / the `raf-schd` throttle in the bundled
  `dnd.esm.js`). One `mouse.move` to the target does not lift the card. Do not
  refactor the loop into a single call.
- **Prefer `expect.poll` for anything after a drag or a save.** The optimistic
  path resolves before the server action, so the DOM is briefly ahead of the
  database. Polling the announcement or the column count is the honest way to
  wait; `waitForTimeout` hides the race instead of resolving it.
- **Card locator is `article`, not a class.** The classes are hashed by the CSS
  module. `data-rfd-droppable-id` on the parent is a library implementation
  detail — use it only if a future change makes the column scoping ambiguous,
  and say why in a comment if it is used.
- **The `exact: true` discipline is not stylistic.** A deal row's link name is
  the deal name; the subnav's "Deals" link is also a link whose name contains
  "Deals". On a page with both, a non-exact `getByRole("link", { name: "Deals" })`
  is ambiguous and Playwright will throw rather than pick — which is a good
  failure, but a confusing one. `exact: true` everywhere.
- **Don't assert money strings in the drag tests.** `formatMoney`
  (`lib/crm/format.ts:1-6`) is `Intl.NumberFormat("en-US", { currency: "USD" })`.
  Assert `25%` and the stage, not `$1,000.00`.
- **Run order.** `build` → `test` → `playwright`. This is not a preference:
  `vitest` does not typecheck, and these specs are typechecked by `next build`
  (BRIEF rule 10).
- **The ci.yml six-secret gate already landed** as PR #90 (`76e4d35`). Do not
  edit it again. The repository has **zero** Actions secrets (`gh secret list`
  → `[]`), so CI e2e honestly reports `ready=false` today and always has.
  A green `e2e` job is not evidence the CRM suite ran — read the log for
  `ready=true` and a non-zero Playwright count. 11.1 still owns the
  `playwright.config.ts` comment.
- **Local e2e needs `AUTH_SECRET`.** `.env` does not contain one — I hit a live
  `MissingSecret` failure from `/api/auth/callback/credentials` when starting a
  dev server without it. `playwright.config.ts:3-7` loads `.env` for the
  runner, but the `webServer` inherits the runner's environment, so
  `AUTH_SECRET=… npx playwright test` is the working local invocation. This
  belongs in the spec because the first implementer will hit it.
- **`playwright.config.ts:31` `reuseExistingServer: true` locally.** A foreign
  `next-server` on `:3000` silently hijacks the run. Kill it by PID, never
  `pkill -f next-server` — that matches the dev server you just started too.
- **Watch the CI retry count, not just green.** `retries: 1`
  (`playwright.config.ts:13`) hides a flake in the pass count. If the drag tests
  pass on a retry for the first three CI runs, the mouse sequence needs
  revisiting before it is trusted.

## Recorded limits

These are known and **not** covered by this feature. They are written down
rather than left to be discovered.

1. **The deals surface is still without browser coverage after 11.1.** That is
   deliberate — 11.2 owns `e2e/crm-deals.spec.ts` and the `SET NULL` journey,
   because 11.2 changes deal write behaviour first. Journeys F and G in this
   document are the written contract, not a passing test.
2. **Same-column reorder is not covered in a browser.** `move-deal.test.ts:76-109`
   (probability is not rebased) and `:111-146` (`boardOrder` renumbers 0..n-1)
   cover it in memory. Whether the browser path preserves that is unproven.
3. **Drag to Won or Lost is not covered.** The path that removes a deal from
   `sumValue`/`sumExpected` (`lib/crm/pipeline-metrics.ts`) has a unit test
   (`move-deal.test.ts:201-236`) but no browser test.
4. **Screen-reader announcement quality is not proven.** Journey C proves the
   live region carries "You have lifted an item" / "You have moved the item".
   Whether that is *useful* to a real screen reader, and whether focus order
   around the board is sane, is a review criterion.
5. **Drag ergonomics and drop-affordance are not proven.** 13/13 landed drags
   says a drag goes where it was pointed. It says nothing about discoverability
   or the 375 px layout.
6. **No visual regression coverage.** The sorting and dialog UI that 11.4 and
   11.5 add will change rendered output with no golden to catch it. Screenshot
   baselines remain deferred.
7. **The demo tenant still grows.** Cleanup is implemented and verified, but any
   test that fails *before* its `afterEach` runs leaves rows behind (a failed
   journey's `afterEach` still runs in Playwright; a failed *login* or a
   `beforeAll` throw does not). The spec's no-exact-counts rule is what keeps
   that survivable, and it is not optional.
8. **`n` was small in the measurements behind this spec.** 13 mouse samples,
   22 keyboard samples, one machine, one Chromium build, dev Neon, local dev
   server. The 0/12-vs-10/10 gap is wide enough to act on; a marginal result
   would not have been.
9. **The `[aria-live]` selector is the library's, not the app's.** If
   `@hello-pangea/dnd` changes its announcement markup, Journey C breaks for a
   reason unrelated to Atrium. That is an acceptable, visible failure — but it
   is a coupling worth recording.
10. **CI readiness is not this feature's to prove.** The `ci.yml` edit makes an
    unset demo pair an honest skip. It does not make a green job mean the CRM
    was exercised: job `ci` runs vitest against the **memory** repo with no
    Postgres and no Playwright, and job `e2e` needs a reviewer to read the log
    for `ready=true` and a non-zero Playwright count. Whether GitHub actually
    holds all six secrets is **unverified from this repo** — see
    `gh api …/branches/main/protection` and the last `e2e` log's `ready=` line.
11. **History claims are unverified.** This spec was written from the working
    tree without running git. Any statement of the form "used to do X" is
    absent by design; check with `git show main:<path>` before relying on one.
