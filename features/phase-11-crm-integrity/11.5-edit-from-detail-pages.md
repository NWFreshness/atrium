# Feature 11.5: Edit from detail pages

**Phase:** 11 — CRM integrity, dead-ends, and list/task surface
**Status:** specced
**Estimated effort:** 3–4 hours
**Depends on:** 11.4 (serial, not parallel — see §0) and 11.2 (its `deal-form.tsx` field-error changes are already in the tree)
**Blocks:** none

## Goal

Close G2: the page a user opens to **decide** something is the page they cannot change.

All three `[id]` routes render a read-only definition list and nothing else:
`"app/(authenticated)/crm/organizations/[id]/page.tsx:30-37"`,
`"app/(authenticated)/crm/contacts/[id]/page.tsx:36-58"`,
`"app/(authenticated)/crm/deals/[id]/page.tsx:37-72"`. There is no `Edit` control on any of
them, so correcting a stale field means: remember the name, navigate back to the list,
find the row, click its hover-revealed `Edit`, fill the whole form again, and return.

The mechanism to fix that already exists and is already proven on the list pages. All
three forms accept an optional existing record plus an `onClose` —
`org-form.tsx:24-30`, `contact-form.tsx:27-35`, `deal-form.tsx:64-74` — and all three
tables mount them as dialogs (`org-table.tsx:120-122`, `contact-table.tsx:143-149`,
`deal-table.tsx:174-181`). The detail pages mount nothing.

## Scope

Include:

- **One `Edit` control per detail page**, in the page-title row, right of the
  `atrium-sub` line, with the accessible name **`Edit {name}`** — the same string the list
  row's button carries (`org-table.tsx:54`, `contact-table.tsx:77`, `deal-table.tsx:108`).
- **The existing form component, mounted unchanged as a dialog.** The `<dl>` needs no
  change: the forms already call `router.refresh()` before `onClose()`
  (`org-form.tsx:61-62`, `contact-form.tsx:70-71`, `deal-form.tsx:110-111`) and the `<dl>`
  is server-rendered.
- **Escape-to-close, focus-on-open, and focus restore on all three forms.** This is the
  feature's a11y half and it lands on the **list** pages too, because the list pages
  already mount the same components. That is intended: 11.3 and 11.10 both add dialogs
  whose contract is "Escape closes it and focus comes back", and a dialog without it is
  unusable once a window-level ⌘K handler exists.
- **The deal detail page fetches the tenant's full organization and contact lists**,
  because `DealForm`'s two `<select>`s render `organizations` / `contacts` props
  (`deal-form.tsx:216-254`) and the page today fetches one of each by id
  (`deals/[id]/page.tsx:23-29`).
- **A source gate** for the accessible-name contract and for the "no Add affordance on a
  detail page" rule.

Exclude (for now):

- **No new route, no new page.** The three `[id]` routes are unchanged in path and shape.
  No `/crm/{records}/[id]/edit`.
- **No Add affordance on a detail page.** No "New deal for this contact", no
  `AddOrganizationButton` / `AddContactButton` / `AddDealButton` on any `[id]` page. The
  boundary that matters: the **activity** form's submit stays `Add activity`
  (`activity-form.tsx:107-109`) and stays on the contact and deal detail pages — it adds
  an activity *to this record*, which is a different verb on a different object.
  11.3 owns that form's dialog mode; this feature does not touch it.
- **A Delete control on a detail page.** Every record's delete lives on its list row
  today (`org-table.tsx:59-71`, `contact-table.tsx:82-95`, `deal-table.tsx:113-125`).
  Moving it is 11.7's decision (the `confirm()` copy and the consequence preview), and
  until 11.7 lands the list row is the only place a delete exists.
- **Inline editing** — no contentEditable, no per-field edit, no autosave. The existing
  dialog is the whole mechanism.
- **A focus trap.** A trap library is a non-goal for this phase. The dialogs are four to
  seven fields.
- **Reordering, resizing, or restructuring the `<dl>`.** The three lists keep their
  existing `dt`/`dd` pairs and their order.
- **The `Probability` `%` suffix** on the deal detail `<dd>` at `deals/[id]/page.tsx:43` —
  **11.2 owns that line** and this feature must not take it. See Controller notes.
- **The value/probability field errors** in `deal-form.tsx:89-93` — **11.2 owns those**,
  and the silent `return` they replace is inherited as-is.
- **Table column sorting** on the three list tables — **11.4 owns that.** 11.5 touches
  **none** of the three table files; see §0 for why that is stated as a design decision
  rather than luck.
- **Deal filters, delete-consequence copy, the email unique index, QuickFind, and
  `/crm/tasks`** — 11.8, 11.7, 11.6, 11.10, 11.9.

## Spec

### 0. Serial, and the file sets are disjoint — say both things

The design requires 11.4 then 11.5, never parallel, because "both rewrite header and
action regions of the same three table components". The dependency is real, and it is a
**calendar** constraint: the board rule is one `in_progress` feature at a time
(`AGENTS.md`), so nothing here is safe to run beside anything.

But the **file** overlap is smaller than the design assumes, and the implementer should
know it so they do not go looking for a merge conflict in files they are not touching:

- 11.4 rewrites the `<thead>` region of all three tables
  (`org-table.tsx:93-105`, `contact-table.tsx:116-128`, `deal-table.tsx:147-159`) and
  nothing else.
- **11.5 touches none of the three tables** — see §4.3 for the decision that makes this
  true.

So the two features would not conflict if they were written in parallel. **They must still
not be run in parallel**: they land as two PRs against `main`, and 11.5's e2e journey
asserts the deal detail page while 11.4's asserts the deal list page, so running both at
once against one dev server and one demo tenant produces a failure that is not either
feature's fault. Serial is the design's call and the spec keeps it.

### 1. `components/crm/detail-edit.tsx`

```tsx
"use client";

import { useEffect, useRef, useState, type ReactNode } from "react";
import styles from "./org.module.css";

/**
 * The detail page's Edit control. Owns the open state and the focus restore so the
 * three `[id]` pages stay server components, and so the `Edit {name}` accessible name
 * is written once instead of three times.
 */
export function DetailEdit({
  name,
  children,
}: {
  name: string;
  children: (onClose: () => void) => ReactNode;
}) {
  const [open, setOpen] = useState(false);
  const triggerRef = useRef<HTMLButtonElement>(null);
  const wasOpen = useRef(false);

  useEffect(() => {
    if (wasOpen.current && !open) {
      triggerRef.current?.focus();
    }
    wasOpen.current = open;
  }, [open]);

  return (
    <>
      <button
        ref={triggerRef}
        type="button"
        className={styles["crm-detail-action"]}
        aria-label={`Edit ${name}`}
        onClick={() => setOpen(true)}
      >
        Edit
      </button>
      {open ? children(() => setOpen(false)) : null}
    </>
  );
}
```

Five decisions, each load-bearing:

1. **Render-prop child, not a `form` prop.** A `form: ReactNode` prop cannot be a lazily
   constructed dialog — the dialog must not exist in the tree before the button is
   clicked, or its `useId` / `useEffect` mount would run on page load. `children` as a
   function is called only inside `{open ? … : null}`, so `OrgForm` / `ContactForm` /
   `DealForm` mount on click and unmount on close, which is what makes focus-on-open and
   focus-restore-on-unmount work at all.
2. **`aria-label={\`Edit ${name}\`}`** — the exact template literal the list row uses
   (`org-table.tsx:54`). `getByRole("button", { name: "Edit Northwind Logistics" })`
   resolves on both the list page and the detail page with the same string, which is the
   point of matching it. **It does not create a collision on any single page**: the three
   `[id]` pages render no table, and the list pages render no `DetailEdit`.
3. **The `wasOpen` guard in the focus-restore effect.** Without it, the effect runs on
   mount with `open === false` and calls `triggerRef.current?.focus()` — stealing focus
   from the page on every render of a detail page. The ref records whether this instance
   has been open at least once, so the restore only runs on a true close.
4. **Focus is restored by the wrapper, not by the form.** The form does not know what
   opened it; the wrapper does. This is the decision that keeps 11.5 out of the three
   table files (§4.3).
5. **The visible label is `Edit`; the accessible name is `Edit {name}`.** The `<h2>` dialog
   title is the form's own `` `Edit ${name}` `` (`org-form.tsx:39`,
   `contact-form.tsx:46`, `deal-form.tsx:80`), so the dialog and the trigger share a
   string but sit in different roles — `getByRole("button", …)` and
   `getByRole("dialog", …)` each resolve to exactly one element.

### 2. The page-title row on all three pages

Identical shape on all three, differing only in the record and the form.

```tsx
<div className={styles["crm-detail-title"]}>
  <div className="atrium-pagetitle">
    <h1>{organization.name}</h1>
    <p className="atrium-sub">Organization · tenant-scoped</p>
  </div>
  <DetailEdit name={organization.name}>
    {(onClose) => (
      <OrgForm organization={organization} onClose={onClose} />
    )}
  </DetailEdit>
</div>
```

`DetailEdit` must be a **client** component and the page must stay a **server**
component. The page imports the form and `DetailEdit` and passes server data down; the
`"use client"` boundary is `detail-edit.tsx`, which imports no CRM data module at all —
only React and the stylesheet. `client-boundary.test.ts` therefore has nothing new to
veto here (§5).

### 3. The deal detail page's two extra fetches

`DealForm` renders two `<select>`s from props (`deal-form.tsx:216-254`): `organizations`
and `contacts`, each with a `None` option. The deal detail page today fetches **one**
organization and **one** contact (`deals/[id]/page.tsx:23-29`). Mounting the form without
the full lists gives a select whose current value is not among its options — the browser
renders the select showing nothing while the record says otherwise. That is a data lie
rendered as a control.

The fix, and the shape of it is a decision:

```tsx
const [organizations, contacts, activities] = await Promise.all([
  listOrganizationsAction(),
  listContactsAction(),
  listActivitiesAction({ dealId: id }),
]);

const organization =
  deal.organizationId === null
    ? null
    : organizations.find((row) => row.id === deal.organizationId) ?? null;
const contact =
  deal.contactId === null
    ? null
    : contacts.find((row) => row.id === deal.contactId) ?? null;
```

**This replaces the two `get` calls rather than adding two `list` calls beside them**, and
the reason is worth stating because the additive version is the obvious first draft: the
replacement is the **same number of round trips** (two), not four, and it removes the
possibility of the `<dd>` link and the form's select disagreeing about whether a record
exists. `getOrganizationAction` / `getContactAction` are no longer called from this page.

The imports of `getOrganizationAction` (`deals/[id]/page.tsx:10`) and
`getContactAction` (`:7`) are removed from the deal detail page and
`listOrganizationsAction` / `listContactsAction` are added. **Both `get*Action` functions
remain in `lib/crm/org-actions.ts:73-78` and `lib/crm/contact-actions.ts:115-120`** and are
still used by the other detail pages. Nothing is deleted.

An organization or contact whose row is gone shows `None` in the select. That is
correct, not a defect: the FK is `onDelete: "set null"` (`lib/crm/schema.ts:72-76`,
`:51-53`) so `deal.organizationId` is `null`, and `None` is what the record says.

### 4. The three forms: Escape, focus, restore, `useId`

#### 4.1 What changes, identically in all three files

`org-form.tsx`, `contact-form.tsx`, `deal-form.tsx` get **four** edits. Nothing else in
those files moves.

```tsx
// 1. React imports
import { useEffect, useId, useRef, useState, type FormEvent } from "react";

// 2. a unique title id, and a ref to the first field
const titleId = useId();                 // replaces "org-form-title" / "contact-form-title" / "deal-form-title"
const nameInputRef = useRef<HTMLInputElement>(null);

useEffect(() => {
  nameInputRef.current?.focus();
}, []);

// 3. Escape closes
function onDialogKeyDown(event: ReactKeyboardEvent<HTMLDivElement>) {
  if (event.key === "Escape") {
    event.preventDefault();
    onClose();
  }
}

// 4. the two attributes
<div role="dialog" aria-modal="true" aria-labelledby={titleId}
     className={styles["crm-dialog"]} onKeyDown={onDialogKeyDown}>
```

and the first input carries `ref={nameInputRef}` and keeps its `id={nameInputRef`-free
literal id (`org-name`, `contact-name`, `deal-name`) — those ids are **not** changed,
because each form is the only dialog on a page and `crm-pnw.test.ts` and the e2e
selectors do not need them to be unique. 11.3 changed `activity-form.tsx`'s field ids
because that form is the one that genuinely mounts **twice** on a page; these three mount
once. Do not change them here.

`useEffect` with `[]` is correct because the component mounts fresh on every open (the
parent renders `{open ? children(onClose) : null}`), so the effect runs once per open.
`org-form.tsx` and `contact-form.tsx` are also mounted directly by
`AddOrganizationButton` / `AddContactButton` (`org-form.tsx:158`, `contact-form.tsx:213`),
which are the same conditional-mount pattern — so the autofocus also lands on the Add
dialogs, consistently.

**`useId()` on the title id is a one-line change per file and it is deliberate.** The
three forms today use fixed literals (`org-form.tsx:40`, `contact-form.tsx:47`,
`deal-form.tsx:81`). One form per page means no live collision, so this is hardening, not
a fix. It is included because 11.3's activity dialog and 11.10's palette are also
`crm-dialog`-shaped and a future "edit from a list row while a detail dialog is open"
would collide. A reviewer may reasonably drop it; if they do, nothing in this feature's
acceptance criteria depends on it and the `aria-labelledby` contract is unchanged.

#### 4.2 Why Escape and focus, stated as a requirement not a nicety

11.10 adds a **window-level** ⌘/Ctrl+K handler to the CRM. The design says that handler
must ignore keys while `[role="dialog"][aria-modal="true"]` is open. A modal that
swallows Escape is then a keyboard trap the user cannot leave. 11.3's activity dialog has
the same contract. Three dialogs that cannot be dismissed by the key every dialog uses is
a defect three features deep, and the cost of fixing it now is three small edits.

#### 4.3 Focus restore lives in the wrapper — and why the tables stay untouched

There are two ways to get focus back to the Edit button:

- **(A)** Pass a `ref` for the trigger down into the table's action cell
  (`org-table.tsx:53-55`, `contact-table.tsx:76-78`, `deal-table.tsx:106-112`) so the form
  can focus it. This is what the design's "both rewrite the action regions" phrasing
  anticipates.
- **(B)** Let `DetailEdit` own the trigger `ref` and restore in its effect (§1). The form
  contributes nothing.

**(B) is chosen.** It is the same user-visible behaviour — after the dialog closes, focus
is on the control that opened it, on both the list page and the detail page — and it costs
**zero** edits to the three table files. Under (A), 11.5 would need to thread a ref through
three `useMemo`'d column definitions whose dependency arrays 11.4 is simultaneously
rewriting, and the ref would then have to be in 11.4's `columns` dependency array too or
the closure goes stale. That is the exact class of bug the 1.3 note warns about
(`features/phase-1-crm/1.3-organizations.md:63`).

The alternative that was rejected for the same reason: capturing
`document.activeElement` on mount inside the form and restoring it in a cleanup. It would
also have avoided the table edits, but it restores focus to *whatever* happened to be
focused, which is wrong on a page where the opener unmounted, and it makes the form's
behaviour depend on global document state.

### 5. The client boundary, walked

`detail-edit.tsx` imports: `react` (`useEffect`, `useRef`, `useState`, `type ReactNode`),
`./org.module.css`, and nothing else. It holds no CRM types at all — `name` is a `string`.
`lib/client-boundary.test.ts:155-166` forbids value imports of `lib/db`,
`lib/{crm,space,rolodex}/{queries,schema,seed,reset}`, `drizzle-orm`, and
`@neondatabase/serverless` from anything under `components/`, transitively. This file
triggers none of them, and it needs no `import type` escape hatch because
`@/lib/crm/queries` is not among its imports.

The three `[id]` pages are **server** components and are not walked by the boundary test
at all (`reachableLeaks` seeds its queue from `componentFiles(resolve(ROOT, "components"))`,
`client-boundary.test.ts:316`). They already import `listDealsAction` and friends
(`organizations/[id]/page.tsx:5`), which is legal for a server component.

The three form components gain `useId` / `useRef` / `useEffect` and nothing else. Their
existing `import type { Organization } from "@/lib/crm/queries"` (`org-form.tsx:9`) is
type-only and was already legal (`client-boundary.test.ts:189-211`).

### 7. e2e — two journeys in `e2e/crm-deals.spec.ts`

House style from `e2e/crm.spec.ts` verbatim, as 11.1 fixed it: `test.beforeAll` throws
without the owner pair (`:14-20`); demo tests `test.skip` without the demo pair (`:42-45`);
`login` is copied from `:22-28` **including** `await expect(page).toHaveURL("/")`;
`crmNav(page)` is `page.getByRole("navigation", { name: "CRM" })`;
`NAV_TIMEOUT = 20_000` on every post-navigation assertion; `test.setTimeout(60_000)` on
both journeys; no `waitForTimeout`; **no CSS-module class selector**; **no exact row
count**.

**Journey N — edit from a deal detail page, twice over.**

1. Mint a deal through the Add deal dialog (11.1's helper, §5 of that spec), with a
   `Date.now()`-suffixed name so the locator is unambiguous.
2. Navigate to its detail page and assert the `<h1>` matches, `exact: true`.
3. Assert the `Edit` control resolves to **exactly one** button:
   `const edit = page.getByRole("button", { name: \`Edit ${name}\`, exact: true });`
   `await expect(edit).toBeVisible();`
4. Click it. Assert the dialog opens and is named by the form's own heading:
   `const dialog = page.getByRole("dialog", { name: \`Edit ${name}\` });`
   `await expect(dialog).toBeVisible(NAV_TIMEOUT);`
5. **Assert the autofocus:** `await expect(dialog.getByLabel("Name")).toBeFocused();`
6. Change `Value` from its seeded value to a distinct one, press `Save`, assert the
   dialog is hidden, and assert the `<dd>` for `Value` shows the new formatted money
   string. **Reload, then assert the `<dd>` again** — the whole feature is a persistence
   claim, and `router.refresh()` updating the DOM without a row written is the same lie
   the pipeline's optimistic rebase tells.
7. `afterEach` deletes the minted deal via its list-row `Delete {name}` button
   (`deal-table.tsx:113-125`) with `page.once("dialog", …accept)` registered **before** the
   click, and asserts the name is gone.

**Journey O — Escape, focus restore, and the same control on all three record types.**

1. On the deal detail page from Journey N's setup, open the dialog, assert
   `getByLabel("Name")` is focused, `await dialog.press("Escape")`, assert the dialog is
   **hidden** and `await expect(edit).toBeFocused()` — the restore. This is the one
   assertion with no other surface, which is why it is its own journey.
2. Assert the deal detail page exposes **no** Add affordance:
   `await expect(page.getByRole("button", { name: "Add deal", exact: true })).toHaveCount(0);`
   and the same for `Add organization` and `Add contact`.
3. Open **one organization's** detail page from `/crm/organizations`
   (`page.getByRole("link", { name: orgName, exact: true }).click()`) and assert
   `getByRole("button", { name: \`Edit ${orgName}\`, exact: true })` is visible and that
   clicking it opens `getByRole("dialog", { name: \`Edit ${orgName}\` })`. Change
   `Industry`, save, reload, assert the `Industry` `<dd>`.
4. The same for a contact, changing `Job title`.

Steps 3 and 4 are the "same mechanism on three record types" claim. **Do not assert all
three `<dd>`s are correct after one save** — assert one field per record type, and assert
**after a reload**, which is the load-bearing part.

**The scoping rule, because this is where the locator bites.** `getByRole` is a
**substring** match by default. The detail pages contain the record's name in the `<h1>`,
in the dialog's `<h2>`, and in the Edit button's `aria-label`. So:

- `getByRole("button", { name: \`Edit ${name}\`, exact: true })` — `exact: true` is
  mandatory, and is what keeps the button locator from matching anything else.
- `getByRole("dialog", { name: \`Edit ${name}\` })` — **scoped by role, not by `body`.**
  `getByText` on a name that also appears in a link elsewhere on the page resolves to 2
  and throws a strict-mode violation; this is 10.3's shipped failure at
  `features/phase-10-pnw/10.3-crm-pass.md:84` and the reason the exact-name discipline
  exists.
- 11.1's Journey F clicks `getByRole("button", { name: "Add deal", exact: true })` on the
  **list** page. 11.5 does not add that string to a detail page, so 11.1's locator is
  unaffected — but the reverse is the risk worth naming: if 11.5's journeys ever navigate
  to a list page and then use an un-`exact`'d name, they will break. `exact: true`
  everywhere.

## Implementation notes

- **The design's "11.4 and 11.5 must not run in parallel" is a calendar rule, not a file
  conflict — and this spec makes the second one unnecessary.** 11.4 rewrites the
  `<thead>` of the three tables; 11.5 touches none of them. The serial constraint is kept
  because the design says so and because two PRs' e2e journeys against one dev server
  and one demo tenant produce failures that belong to neither feature. But an implementer
  who goes looking for a merge conflict in `deal-table.tsx` will not find one, and should
  not invent one by adding a trigger `ref` there.

- **The focus restore is the one place 11.5 could have been much worse.** The obvious
  design passes a ref through the table's action cell into the form, which is exactly the
  edit 11.4 is making in the same files, in the same `useMemo` whose dependency array
  carries the name maps 1.3 warned about. `DetailEdit` owning its own `ref` is the same
  behaviour for zero edits to those files. If a reviewer wants the trigger ref inside the
  table instead, the cost is three `columns` dependency arrays that must be exactly right.

- **`getByRole` is a substring match and this feature adds a second control that shares a
  name with an existing one.** The design says "e2e must **scope** (list row vs detail
  control)". The scoping that matters: `getByRole("button", { name: \`Edit ${name}\`, exact: true })`
  resolves to **one** element on the list page (the row's button) and **one** on the
  detail page (`DetailEdit`). They are never on the same page, so there is no real
  collision — but a journey that walks from a list page to a detail page **without a
  `page.goto` in between** could hold two live locators for the same name, and
  `await expect(...)` on the bare name would throw a strict-mode violation. Every journey
  here navigates with `goto` or `click` and re-reads its locators per step.

- **The autofocus lands on the Add dialogs too.** `org-form.tsx:158` and
  `contact-form.tsx:213` mount the same components in the same conditional pattern, so
  `useEffect(..., [])` runs on those mounts as well. That is a behaviour change on the
  list pages: the `Name` field is now focused when "Add organization" is clicked. **It
  does not break 11.1's Journey F or `e2e/crm.spec.ts:82-88`** — both do
  `dialog.getByLabel("Name").fill(name)`, and `fill()` focuses the element itself before
  typing. Verified by reading both. An implementer who finds a broken existing journey
  here should check whether they added a `maxLength` or a validation that blocks `fill`;
  autofocus is not the cause.

- **No `id` change on the three forms' fields, deliberately.** 11.3 changed
  `activity-form.tsx`'s field ids to `useId()`-derived strings because that form genuinely
  mounts **twice** on a page (inline + dialog). These three mount once. Changing
  `org-name` / `contact-name` / `deal-name` would churn `crm-pnw.test.ts` and every e2e
  selector for no gain. The `titleId` is the one id worth hardening (a future
  "list-row dialog over a detail dialog" would collide), and it is a single line per file.

- **`crm-pnw.test.ts:26-32` does not cover the `[id]` pages, before or after.** The
  `atrium-pagetitle` / `atrium-sub` assertion at `:259-266` iterates `PAGES`, which is the
  five section pages. Extending `PAGES` would be a scope improvement and a scope risk in
  the same edit: any pre-existing mismatch on a detail page would surface as an 11.5
  failure. The new block uses its own constant. Recorded as a limit; a QA pass can extend
  `PAGES` in a feature that is about the detail pages wholesale.

- **Replacing the two `get*Action` calls on the deal detail page is a judgement call, and
  the alternative is worse, not equal.** Four parallel fetches (one org, one contact, the
  org list, the contact list) would be correct but would put the `<dd>` link and the form's
  select resolving the same question through two different code paths, which is how they
  come to disagree. Two fetches and one `find` is correct, smaller, and removes the
  possibility. Both `get*Action` functions stay in their modules and are still used by the
  org and contact detail pages.

- **The form's select is the reason the deal page needs the lists at all.**
  `deal-form.tsx:227` renders `<option value="">None</option>` followed by
  `organizations.map(...)` (`:228-232`). A select whose `value` is not among its options
  renders as empty in every browser, so a record that says "Bluepeak Software" would show
  a blank select. This is a data lie rendered as a control, and it is the trap A4's "Watch"
  names.

- **The `<dl>` needs no change, and that is the reason this feature is 3–4 hours rather
  than a day.** All three forms call `router.refresh()` then `onClose()` in that order
  (`org-form.tsx:61-62`, `contact-form.tsx:70-71`, `deal-form.tsx:110-111`), the pages are
  server components, and `router.refresh()` re-renders them. There is no client cache to
  invalidate and no `useState` copy of the record to reconcile.

- **`neon-http` has no `db.transaction()`.** This feature writes exactly one row through
  the existing `update*Action` path. No batch, no rollback question. Stated because the
  temptation in a future "save the deal and its contact" idea is real.

- **Playwright budget.** The default per-test budget is **30 s** for the whole test.
  Journey N visits the list page, a dialog, and a detail page, twice over with a reload;
  Journey O visits three detail pages. Both open with `test.setTimeout(60_000)`, and every
  post-navigation or post-save assertion carries `{ timeout: NAV_TIMEOUT }` with
  `NAV_TIMEOUT = 20_000`. **No `waitForTimeout`** — a dev route against Neon can take ten
  seconds and `toBeVisible({ timeout })` retries where a sleep does not.
  `playwright.config.ts:11` sets `fullyParallel: false`, so this file cannot run beside
  11.4's journeys; `:13` sets `retries: 1` on CI, which hides a flake in the pass count —
  watch the retry count on the dialog-appears assertions, which is where a cold RTT bites.

- **Local Playwright needs `AUTH_SECRET` in the process env.** `.env` does not have one;
  `playwright.config.ts:29-31` starts `npm run dev` with the runner's environment, and
  `reuseExistingServer: !process.env.CI` means a foreign `next-server` on `:3000`
  silently hijacks the run. Confirm `:3000` is this app; kill by PID, not
  `pkill -f next-server`.

- **Shipped notes are read as evidence.** Every claim above was read from the working tree
  at the cited line. An implementer who finds one wrong checks the file, not this
  document, and corrects the spec in the same PR.

## Recorded limits

Known, and **not** covered by this feature.

1. **The two `?id` fetches on the deal detail page are not tenant-scoped in a new way —
   they are scoped exactly as before.** `listOrganizationsAction()` and
   `listContactsAction()` both go through `requireTenant` inside their `*ForSession`

   `getOrganizationAction(id)` / `getContactAction(id)`, which are tenant-scoped the same

   and **every** contact in the tenant on each load. On a large tenant that is a real
   cost, and unbounded lists are a known non-goal (B5) for this phase. The demo tenant's
   three organizations make it invisible, which is not evidence that it is invisible in
   general.
2. **No Delete on a detail page.** Every record's delete lives on its list row. Until 11.7

   is `position: fixed` with a blurred background (`org.module.css:223-232`) but it is not

   fields, and `aria-modal="true"` on all three forms was already the (un-enforced) claim
   before this feature.

   Journey F, both of which `fill()` the field rather than typing into it. A journey that
