# Feature 0.2: Drizzle + Neon users and tenants

**Phase:** 0 — Atrium platform
**Status:** completed
**Estimated effort:** 4–6 hours
**Depends on:** 0.1
**Blocks:** 0.3, 0.5

## Goal

Postgres schema and seed for two tenants and two users, via Drizzle, against Neon.

## Scope

Include:
- Drizzle client + drizzle-kit
- Tables: `tenants`, `users`, Auth.js-shaped `accounts` and `sessions` (empty is fine)
- Seed: owner tenant + demo tenant; owner user + demo user from env
- Idempotent seed (running twice does not duplicate)
- `npm run db:generate` / `npm run db:migrate` / `npm run db:seed` (names can match repo convention)

Exclude (for now):
- Login UI
- CRM/Space/Rolodex tables
- Demo reset action
- PGlite unless CI cannot reach Neon (only then, and document it)

## Files to create

- `drizzle.config.ts`
- `lib/db/index.ts` — Drizzle client from `DATABASE_URL`
- `lib/db/schema.ts` — tenants, users, accounts, sessions
- `lib/db/seed.ts` — bootstrap tenants + users
- `drizzle/` migrations generated by drizzle-kit
- `lib/db/schema.test.ts` and/or `lib/db/seed.test.ts`

## Files to modify

- `package.json` — db scripts and drizzle deps
- `.env.example` — unchanged names; comments that values come from Neon
- `AGENTS.md` — one line: all SQL goes through Drizzle in `lib/db`

## Spec

```ts
tenants: { id, name, createdAt }
users: {
  id,
  email unique,
  passwordHash,
  tenantId → tenants.id,
  role: 'owner' | 'demo',
  createdAt
}
accounts, sessions: Auth.js adapter columns (so 0.3 can plug in without a rewrite)
```

Passwords hashed with a real hasher (bcrypt or Auth.js-compatible). Never store plaintext.

Seed mapping:
- `AUTH_OWNER_EMAIL` / `AUTH_OWNER_PASSWORD` → role `owner`
- `AUTH_DEMO_EMAIL` / `AUTH_DEMO_PASSWORD` → role `demo` (default email `demo@atrium.local` if unset in code defaults, still required in env for real runs)

## Implementation notes

- Live migrate/seed needs `DATABASE_URL` to Neon. If the implementer does not have it, still land schema, migrations, and tests that do not require a live DB where possible; document the migrate command.
- Do not log passwords.
- Do not query by a client-supplied tenant id (no API yet; keep the client free of tenant parameters from the start).
