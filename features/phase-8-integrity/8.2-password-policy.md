# Feature 8.2: Shared password policy

**Phase:** 8 — Integrity
**Status:** completed
**Estimated effort:** 2–3 hours
**Depends on:** 6.3
**Blocks:** nothing

## Goal

The minimum password length is 12 Unicode code points, not 12 UTF-16 code units. Signup and change-password share one policy module, so a third password surface cannot fork the rule. The 72-byte bcrypt ceiling does not change.

## Scope

Include:

- `lib/auth/password-policy.ts` — `MIN_PASSWORD_LENGTH`, `MAX_PASSWORD_BYTES`, and `checkPasswordStrength(password: unknown)` returning `{ ok: true, value: string } | { ok: false, code: "weak_password" | "password_too_long" }`
- Floor: `Array.from(value).length` (Unicode code points). `"😀".repeat(6)` is 6, not 12
- Ceiling: `Buffer.byteLength(value, "utf8") > 72` unchanged
- `signUp` / `assertPasswordStrength` and `changePassword` both call `checkPasswordStrength` and map `code` onto their own error class
- Tests for the emoji floor on both surfaces; existing ASCII 12-char and 73-byte cases still pass

Exclude (for now):

- Grapheheme-cluster counting (`Intl.Segmenter`)
- Complexity rules (digits, symbols, zxcvbn)
- Changing user-facing copy to say “code points”
- Session revocation
- 8.1 email index
- A client-side copy of the checker (the forms may keep a `minLength={12}` attribute; the server is the rule)

## Spec

1. `checkPasswordStrength`:
   - non-strings and missing values are `weak_password` (same as today’s empty-string path)
   - `Array.from(value).length < 12` → `{ ok: false, code: "weak_password" }`
   - `Buffer.byteLength(value, "utf8") > 72` → `{ ok: false, code: "password_too_long" }`
   - otherwise `{ ok: true, value }` with the original string (do not NFC-normalize)
2. The function does not throw and does not import `SignUpError` or `ChangePasswordError`. Those classes stay in their modules. Mapping:
   - signup: `weak_password` / `password_too_long` → `SignUpError(code)`
   - change-password: same codes → `ChangePasswordError(code)`, and only after current-password verification and the `unchanged` check, as today
3. `"😀".repeat(6)` is weak. `"😀".repeat(12)` is 12 code points and 48 bytes — accepted. `"abcdefghijkl"` is accepted. A string of 73 ASCII bytes is `password_too_long`.
4. `MIN_PASSWORD_LENGTH` is 12 and `MAX_PASSWORD_BYTES` is 72, defined once in the policy module. `signup.ts` may re-export them. `change-password.ts` must not duplicate the numbers.
5. Change-password still reports `wrong_current` before judging `next`, and `unchanged` before length. A six-emoji `next` with a wrong current password is still `wrong_current`.
6. No new env vars. No copy change required; “at least 12 characters” remains true for BMP text.

## Implementation notes

- Do not import the policy module from a client component. Messages modules stay copy-only. The forms already round-trip to the server action.
- `Array.from(string)` / `[...string]` splits on UTF-16 surrogate pairs, i.e. code points. That is the 6.3 follow-up. Do not add `Intl.Segmenter`.
- Keep `assertPasswordStrength` as a one-liner wrapper so signup tests that call it directly still compile.
- Do not run prettier on a directory.

## Shipped notes (2026-09-11)

`lib/auth/password-policy.ts` is the policy: `MIN_PASSWORD_LENGTH` 12,
`MAX_PASSWORD_BYTES` 72, and `checkPasswordStrength(password: unknown)` →
`{ ok: true, value }` / `{ ok: false, code }`. The floor is
`Array.from(value).length` — code points, so `"😀".repeat(6)` (twelve UTF-16
units, and accepted until now) is weak while twelve emoji is a legitimate
48-byte password; the ceiling is still `Buffer.byteLength(value, "utf8") > 72`,
which is bcrypt's input limit. It never throws, imports neither `SignUpError` nor
`ChangePasswordError`, and returns the string untouched — no NFC normalization,
because the hash must cover exactly what was typed.

Both surfaces now map the same decision onto their own error class.
`assertPasswordStrength` is a four-line wrapper around `checkPasswordStrength`;
`lib/auth/signup.ts` re-exports the two constants (they used to be *defined*
there) so existing `import { MIN_PASSWORD_LENGTH } from "./signup"` callers keep
compiling without a second source of truth, and `lib/auth/change-password.ts`
imports the policy module directly instead of the numbers from `./signup`. Order
is unchanged: `wrong_current` before anything about `next`, `unchanged` before
the policy, and change-password hashes `strength.value` — the string the policy
validated.

The named hole is closed and the closure is gated on both surfaces: reverting the
floor to `value.length` failed exactly three tests — `password-policy.test.ts`
("counts the floor in code points, not UTF-16 units"),
`signup.test.ts` ("counts the minimum in code points, so six emoji do not clear
it") and `change-password.test.ts` ("counts the floor in code points after the
current password is proved") — and reversing the probe made them green again.
Criterion 4 is a mechanical source check rather than a promise: neither surface
may contain `.length <`, neither may define the two constants, and the policy
module may not import or construct either error class; the same file also asserts
both surfaces call `checkPasswordStrength`.

Copy is unchanged (spec item 6): "at least 12 characters" is still true for BMP
text, and nothing user-facing mentions code points. The forms carry no `minLength` attribute; they round-trip to the server action, which is the rule.

Controller: `env -u DATABASE_URL npm test` **657 passed (102 files)**, up from 646
(101) — nine policy cases plus one on each surface; `AUTH_SECRET=ci-build-placeholder
npm run build` exit 0; no new dependencies, no route, no migration, no env var.

Limits, stated rather than implied. (1) No Playwright: this feature adds no route,
and 6.4's accounts journeys use ASCII passwords of ≥12 characters, so they prove
nothing about the emoji floor — the unit tests are the gate. (2) Grapheme clusters
are still out by decision: a family emoji is several code points and counts as
several, and `Intl.Segmenter` was not added. (3) The module is server-side in
practice because `Buffer` is Node's; nothing under `components/` imports it, and
the policy is never the client's rule.
