# Feature 8.3: Client-safe person field catalog

**Phase:** 8 — Integrity
**Status:** completed
**Estimated effort:** 1–2 hours
**Depends on:** 7.5, 3.4
**Blocks:** nothing

## Goal

Rolodex import has one `PERSON_FIELDS` list. The parser and the import dialog both import it from a module that does not pull Papa, `vcf`, or `queries.ts` into the client graph. The dialog’s copy, which already drifted (`required` missing on `name`), goes away.

## Scope

Include:

- `lib/rolodex/person-fields.ts` exporting `PERSON_FIELDS` (the server’s current catalog, including `required: true` on `name`)
- `lib/rolodex/import.ts` imports that catalog; it keeps `HEADER_SYNONYMS`, Papa, `vcf`, and query writes
- `components/rolodex/import-dialog.tsx` deletes its local array and imports `PERSON_FIELDS` from `@/lib/rolodex/person-fields`
- A test that the dialog file does not declare its own `PERSON_FIELDS` and that `person-fields.ts` value-imports none of `queries`, `schema`, `lib/db`, Papa, or `vcf`
- `lib/client-boundary.test.ts` stays green (the walk will visit the new module from the dialog)

Exclude (for now):

- Moving header synonyms or parse logic into the catalog
- Changing import UX, CSV/vCard behaviour, or duplicate detection
- `lib/rolodex/types.ts` for unrelated row types
- eslint-plugin-boundaries
- Unifying CRM table column defs

## Files to create

- `lib/rolodex/person-fields.ts`
- `lib/rolodex/person-fields.test.ts` — catalog contents + “no forbidden value imports” (or fold the import-graph check into the existing client-boundary walk and only assert contents here)

## Files to modify

- `lib/rolodex/import.ts` — drop the local `PERSON_FIELDS`; re-export from `person-fields.ts` if any server test imports it from `import.ts`
- `components/rolodex/import-dialog.tsx` — import the shared catalog
- Any test that listed fields by copying the dialog array

## Spec

1. `PERSON_FIELDS` is:

   ```
   { key: "name", label: "Name", required: true }
   { key: "email", label: "Email" }
   { key: "phone", label: "Phone" }
   { key: "jobTitle", label: "Job title" }
   { key: "company", label: "Company" }
   { key: "city", label: "City" }
   { key: "birthday", label: "Birthday" }
   { key: "notes", label: "Notes" }
   ```

   Keys, labels, and `name.required === true` match today’s `lib/rolodex/import.ts`. Do not invent fields.

2. `person-fields.ts` has no value import of `./queries`, `./schema`, `../db`, `papaparse`, or `vcf`. `import type` is allowed if a later consumer needs a row type; it is not required.

3. `import-dialog.tsx` contains no `const PERSON_FIELDS = [` (source-grep). It iterates the imported catalog for the mapping `<select>` the way it does today.

4. `lib/rolodex/import.ts` uses the same imported (or re-exported) catalog for `FIELD_KEYS`. Parse behaviour is unchanged: synonyms stay in `import.ts`.

5. If tests import `PERSON_FIELDS` from `import.ts`, keep a re-export so those imports compile. The definition lives in `person-fields.ts` once.

6. `lib/client-boundary.test.ts` still passes. Do not widen that gate.

## Implementation notes

- 7.5 exists so you must not “fix” the dialog by importing `import.ts`. That file value-imports Papa, `vcf`, and `queries.ts`. The new module is the deep interface: one catalog, no parse stack.
- A source-grep on the dialog is enough to prove the local array is gone; the client-boundary walk proves the new edge is safe. Do not add bundle-size claims.
- Do not run prettier on a directory. Format only the files this feature creates or the hunks it owns.
- Existing import unit tests should keep passing without behaviour changes. If one asserted on the dialog’s weaker catalog (`required` absent), update it to the shared one.

## Shipped notes (2026-09-11)

`lib/rolodex/person-fields.ts` is the catalog: the `PersonField` type and the
eight entries, `as const satisfies readonly PersonField[]`, with `required: true`
on `name` exactly as `import.ts` had it. The module carries **no value imports at
all** — it is data, which is why a client component can read it without dragging
Papa, `vcf` or `queries.ts` along.

`lib/rolodex/import.ts` imports `PERSON_FIELDS` from it and keeps everything that
is parse behaviour: `HEADER_SYNONYMS`, Papa, `vcf` and the query writes.
`FIELD_KEYS` is still `PERSON_FIELDS.map((field) => field.key)`. **No re-export
was added**: spec item 5 was conditional on a test importing `PERSON_FIELDS` from
`import.ts`, and `git grep` found no importer of that name anywhere in `lib/`,
`components/`, `app/` or `e2e/` — the only two consumers are the parser and the
dialog, both now importing the shared module.

`components/rolodex/import-dialog.tsx` lost its local array (the copy that had
drifted — it never carried `required: true`) and imports
`@/lib/rolodex/person-fields`. The mapping `<select>` renders the same eight
labels in the same order, so the import UX does not change.

Each gate was proven by injection and reversed byte-identically: putting a local
`PERSON_FIELDS` back in the dialog fails "is the only definition — both consumers
import it"; re-declaring it in `import.ts` fails the same case; dropping
`required: true` fails "marks name as the one required field"; and **a value
import inside the catalog fails both the catalog test and 7.5's
`lib/client-boundary.test.ts`**, which walks the new edge from the dialog and
reports `lib/rolodex/person-fields.ts → ./queries`. That last probe is the one
that matters — the gate that forced the duplicate exists to catch exactly that,
and it does.

Controller: `env -u DATABASE_URL npm test` **661 passed (103 files)**, up from 657
(102); `AUTH_SECRET=ci-build-placeholder npm run build` exit 0 with the route
table unchanged; no new dependencies; `lib/client-boundary.test.ts` was not
touched or widened.

Limits, stated rather than implied. (1) No Playwright: the feature adds no route,
and `e2e/rolodex.spec.ts` does not grow an import journey for a catalog move.
(2) `required` is documentation, not an enforced rule — nothing read it before or
reads it now (the parser enforces the name when it creates the person), which is
precisely why the dialog's copy could drift unnoticed until 7.5 and this feature
made it visible. If the flag should bite, that is a parser change, not a catalog
one. (3) The catalog lists the mapping targets only: header synonyms stay in the
parser, and a third consumer would import this module rather than copy it — the
source test names both current consumers, so adding one is a deliberate edit to
that test, not a silent third copy.
