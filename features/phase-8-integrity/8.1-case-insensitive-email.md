# Feature 8.1: Case-insensitive unique email

**Phase:** 8 — Integrity
**Status:** completed
**Estimated effort:** 2–3 hours
**Depends on:** 6.1
**Blocks:** nothing (8.2 and 8.3 do not need this migration)

## Goal

`Tyler@x` and `tyler@x` cannot both exist as rows in `users`, even when two signups race the application pre-check. The unique index matches the case-insensitive lookup signup and login already use.

## Scope

Include:

- Drop the byte-exact unique on `users.email` (the `.unique()` on the column, constraint name `users_email_unique`)
- Add a unique index `users_email_lower_idx` on `lower(email)`
- Generated migration; read it; make the drop/create idempotent the way 7.3 did (`IF EXISTS` / `IF NOT EXISTS`)
- Schema test: `users` unique indexes are exactly that lower-email index, not `users_email_unique`
- Existing signup unique-violation → `unavailable` mapping still holds (constraint or index name in the error message may change — assert on SQLSTATE `23505` / “duplicate key”, not on `users_email_unique` as the only signal)

Exclude (for now):

- Changing login or signup lookup SQL (already `lower(email)`)
- Lowercasing stored emails
- Unique index on `tenants.name` via `lower(name)`
- RLS, OAuth, mailer, session revocation
- 8.2 password policy
- 8.3 field catalog

## Files to create

- None required beyond `drizzle/` migration files drizzle-kit generates

## Files to modify

- `lib/db/schema.ts` — `users.email` loses `.unique()`; table extras gain `uniqueIndex("users_email_lower_idx").on(sql\`lower(${table.email})\`)` next to the existing `users_tenantId_idx`
- `lib/db/schema.test.ts` — assert the unique index name, that it is unique, and that its expression/columns are `lower(email)` (or the equivalent drizzle-kit emits). Fail if `users_email_unique` returns
- `lib/auth/signup.ts` / `lib/auth/signup.test.ts` — only if a comment or assertion names `users_email_unique` as the live constraint; keep the 23505 mapping
- `drizzle/` — generated SQL + meta

## Spec

1. `users.email` is `text("email").notNull()` with no `.unique()`.
2. The table’s extras array contains `uniqueIndex("users_email_lower_idx").on(sql\`lower(${table.email})\`)` and still contains `index("users_tenantId_idx").on(table.tenantId)`.
3. `npm run db:generate` is the source of the SQL. Read the generated file before committing. Expected shape (names as drizzle-kit emits them, then made idempotent):
   - `ALTER TABLE "users" DROP CONSTRAINT IF EXISTS "users_email_unique";` (or `DROP INDEX` if the old unique was already an index)
   - `CREATE UNIQUE INDEX IF NOT EXISTS "users_email_lower_idx" ON "users" (lower("email"));`
   - No `DROP TABLE`, no enum rewrite, no RLS
4. `IF EXISTS` / `IF NOT EXISTS` are hand edits if drizzle-kit omits them. Document that in the SQL file, including that Postgres matches an existing index by **name**, not definition.
5. After generate, `env -u DATABASE_URL npm run db:generate` must print “No schema changes, nothing to migrate”.
6. A schema test fails if the lower unique index is missing, not unique, or if the byte-exact `users_email_unique` is still declared. Prove it once by injection (remove the new index, watch the assertion name it) and reverse before commit.
7. `isUniqueViolation` in signup still treats `23505` and a “duplicate key value” message as `unavailable`. Do not require the old constraint name. Add a case for the new index name in the message if the current tests hard-code `users_email_unique`.
8. Groove still has no tables. `tenants.name` unique is unchanged.

## Shipped notes (2026-09-11)

`users.email` lost `.unique()`; `users` now declares
`uniqueIndex("users_email_lower_idx").on(sql\`lower(${table.email})\`)` beside
`users_tenantId_idx`. `drizzle/0006_sleepy_preak.sql` is drizzle-kit's two
statements, hand-made idempotent (`DROP CONSTRAINT IF EXISTS` /
`CREATE UNIQUE INDEX IF NOT EXISTS`) with the name-not-definition caveat written
into the file, the way 0004 and 0005 documented theirs. `npm run db:generate`
prints "No schema changes, nothing to migrate", so the committed migration is
exactly the schema's delta, and `drizzle/meta/0006_snapshot.json` shows one
`isUnique: true` index with `expression: lower("email")`, no column change, no
enum change, `tenants_name_unique` untouched.

**The spec's file list missed `lib/db/seed.ts`, and that is a consequence of the
mechanism, not scope creep.** `upsertUserByEmail` was
`.onConflictDoUpdate({ target: users.email })`, and Postgres cannot infer an
expression index from a column-name specification: with the byte-exact unique
gone, that statement dies with *"there is no unique or exclusion constraint
matching the ON CONFLICT specification"* (42P10) — proven, not assumed, below.
Nothing in `npm test` or `npm run build` reaches `npm run db:seed`, so the seed
would have shipped broken and silently. It now looks the row up on
`lower(email)` (the same expression the index and `lib/auth/users.ts:26` use) and
updates it by id, else inserts with an untargeted `on conflict do nothing`; the
stored address keeps the casing it was stored with. The memory repository's
comparison became case-insensitive for the same reason — it is the DB's
behaviour, simulated. `lib/auth/signup.ts`'s doc comment (which still said login
was exact-match *and* that the unique index was case-sensitive — both stale since
6.2 and this feature) was rewritten to describe the index as the race backstop,
not the pre-check. `lib/auth/signup.test.ts`'s hard-coded duplicate-key message
now names the live index.

**Verified against a real Postgres, not only unit tests.** A throwaway local
PostgreSQL 16 cluster took all seven migrations in order (`0000` → `0006`,
`psql -f`, each exit 0), which also exercises 0005's nineteen indexes. Against
that migrated schema: the two statements the new `upsertUserByEmail` builds
(captured from the repository itself with a recording `Database` stub, then bound
and run) inserted once and updated the case-variant row in place — one row,
`owner@atrium.local` / `hash-two`, casing preserved; a case-variant insert was
rejected by `users_email_lower_idx` with `duplicate key value violates unique
constraint "users_email_lower_idx"` / `Key (lower(email))=(owner@atrium.local)`;
and the pre-8.1 `on conflict ("email") do update` failed with 42P10. `pg_indexes`
shows `users_email_lower_idx` UNIQUE on `(lower(email))`.

Both halves of criterion 3 were proven by injection and reversed byte-identically:
deleting the index declaration fails as `expected [] to deeply equal
[ 'users_email_lower_idx' ]`, and putting `.unique()` back on the column fails
`no longer declares the byte-exact unique on users.email` with `expected true to
be false`. The migration test parses the committed file, so a name swap or a
re-added `DROP TABLE` fails too.

Controller on the final bytes: `env -u DATABASE_URL npm test` **646 passed (101
files)**, up from 639 (101) — the two schema-shape cases, the two migration cases
and three `upsertUserByEmail` cases; `AUTH_SECRET=ci-build-placeholder npm run
build` exit 0 with the route table unchanged; `git diff -- package.json
package-lock.json` empty.

Limits, stated rather than implied. (1) The unit tests cannot observe a real
concurrent race: the schema test plus the existing 23505 → `unavailable` mapping
tests are the honest gate, and `e2e/accounts.spec.ts` still covers only the
*sequential* duplicate — no live race was proven. (2) The Drizzle *execution*
path (`neon-http`) was not exercised: the Neon dev branch is deliberately **not**
migrated yet, per this spec, so `npm run db:migrate` + `npm run db:seed` on the
dev URL remain the post-merge step. Running Drizzle against a local Postgres is
impossible with this driver — `drizzle-kit migrate` with `@neondatabase/serverless`
cannot reach a plain TCP server — which is why the local proof ran drizzle's own
SQL text through `psql` instead. (3) No Playwright run; the change adds no route.
