# Feature 8.1: Case-insensitive unique email

**Phase:** 8 — Integrity
**Status:** specced
**Estimated effort:** 2–3 hours
**Depends on:** 6.1
**Blocks:** nothing (8.2 and 8.3 do not need this migration)

## Goal

`Tyler@x` and `tyler@x` cannot both exist as rows in `users`, even when two signups race the application pre-check. The unique index matches the case-insensitive lookup signup and login already use.

## Scope

Include:

- Drop the byte-exact unique on `users.email` (the `.unique()` on the column, constraint name `users_email_unique`)
- Add a unique index `users_email_lower_idx` on `lower(email)`
- Generated migration; read it; make the drop/create idempotent the way 7.3 did (`IF EXISTS` / `IF NOT EXISTS`)
- Schema test: `users` unique indexes are exactly that lower-email index, not `users_email_unique`
- Existing signup unique-violation → `unavailable` mapping still holds (constraint or index name in the error message may change — assert on SQLSTATE `23505` / “duplicate key”, not on `users_email_unique` as the only signal)

Exclude (for now):

- Changing login or signup lookup SQL (already `lower(email)`)
- Lowercasing stored emails
- Unique index on `tenants.name` via `lower(name)`
- RLS, OAuth, mailer, session revocation
- 8.2 password policy
- 8.3 field catalog

## Files to create

- None required beyond `drizzle/` migration files drizzle-kit generates

## Files to modify

- `lib/db/schema.ts` — `users.email` loses `.unique()`; table extras gain `uniqueIndex("users_email_lower_idx").on(sql\`lower(${table.email})\`)` next to the existing `users_tenantId_idx`
- `lib/db/schema.test.ts` — assert the unique index name, that it is unique, and that its expression/columns are `lower(email)` (or the equivalent drizzle-kit emits). Fail if `users_email_unique` returns
- `lib/auth/signup.ts` / `lib/auth/signup.test.ts` — only if a comment or assertion names `users_email_unique` as the live constraint; keep the 23505 mapping
- `drizzle/` — generated SQL + meta

## Spec

1. `users.email` is `text("email").notNull()` with no `.unique()`.
2. The table’s extras array contains `uniqueIndex("users_email_lower_idx").on(sql\`lower(${table.email})\`)` and still contains `index("users_tenantId_idx").on(table.tenantId)`.
3. `npm run db:generate` is the source of the SQL. Read the generated file before committing. Expected shape (names as drizzle-kit emits them, then made idempotent):
   - `ALTER TABLE "users" DROP CONSTRAINT IF EXISTS "users_email_unique";` (or `DROP INDEX` if the old unique was already an index)
   - `CREATE UNIQUE INDEX IF NOT EXISTS "users_email_lower_idx" ON "users" (lower("email"));`
   - No `DROP TABLE`, no enum rewrite, no RLS
4. `IF EXISTS` / `IF NOT EXISTS` are hand edits if drizzle-kit omits them. Document that in the SQL file, including that Postgres matches an existing index by **name**, not definition.
5. After generate, `env -u DATABASE_URL npm run db:generate` must print “No schema changes, nothing to migrate”.
6. A schema test fails if the lower unique index is missing, not unique, or if the byte-exact `users_email_unique` is still declared. Prove it once by injection (remove the new index, watch the assertion name it) and reverse before commit.
7. `isUniqueViolation` in signup still treats `23505` and a “duplicate key value” message as `unavailable`. Do not require the old constraint name. Add a case for the new index name in the message if the current tests hard-code `users_email_unique`.
8. Groove still has no tables. `tenants.name` unique is unchanged.
