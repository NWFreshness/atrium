# 13.1 — Professional UI refresh (Notion/Pipedrive-grade)

## Phase

(proposed) phase-13 — professional UI refresh. NOT in `roadmap/phases.yaml`
(phases 11–12 cover CRM integrity and deal history; no UI-refresh intent exists
there). Phase placement is provisional (new phase-13, accepted under defaults). This spec does not move, rename, or depend on any 11.x / 12.x intent.

## Goal

Make Atrium look like a commercial product in the Notion / Pipedrive class:
calm surfaces, consistent type scale, clear hierarchy, visible focus and hover
feedback — while keeping the Phase 10 token architecture (one token file, shared
`atrium-` layer, per-app `*-` namespaces) and every existing gate green.

## User-visible behavior

(defaults accepted 2026-10-07)

- Direction: light-first refresh. Mist surfaces become the
  default experience; the basalt dark mode keeps working and keeps passing the
  contrast gate. Density and restraint follow Pipedrive (information-dense CRM
  surfaces, one accent per screen); calm and whitespace follow Notion.
- Concrete surfaces change: shared chrome first — top nav, launcher,
  login, subnavs, buttons, form controls, tables, stat tiles — via tokens in
  `app/globals.css` plus shared classes in `app/workroom.css`. Per-app module
  CSS changes only where a surface cannot be reached through tokens/shared
  classes or where contrast fails after the token change.
- What the user observes: consistent spacing rhythm and type scale across the
  four apps; one accent per screen (the Phase 10 `--brass` single-highlight rule
  is kept, retuned if the palette changes); every interactive element shows
  hover and keyboard-focus states; `prefers-reduced-motion` is respected;
  no horizontal scroll at 375 / 768 / 1024 / 1440px.
- Groove keeps its own instrument scope (`--inst-*`); it receives the refresh
  only through shared chrome/tokens, never a bespoke Groove restyle.

## Scope paths

(accepted defaults 2026-10-07; smallest slice first)

- `app/globals.css` (tokens only: color, type scale, spacing, radius, shadow)
- `app/workroom.css` (shared `atrium-` classes only)
- Per-app `*.module.css` under `components/{crm,space,rolodex,groove}/` —
  ONLY files the implementer can prove are unreachable via tokens/shared
  classes or that fail the contrast gate after the token change. Each touched
  file must be listed in the job card.
- `tests/theme-contrast.test.ts`, `tests/workroom-namespace.test.ts` — may gain
  assertions, never weakened (AGENTS.md: never weaken or delete a test to get
  a green run).

## Out of scope

- `lib/` query/auth/tenancy logic, database schema and migrations, seed.
- Auth behavior, tenant scoping, session handling.
- Groove audio engine; no Groove tables, no new routes, no new subnav entries.
- New CSS frameworks or component libraries (no Tailwind, shadcn, or equivalent
  without an explicit decision in Decisions — current default: none; CSS modules
  + tokens only).
- Layout restructuring, information-architecture changes, copy rewrites,
  new features. Pure presentation pass.
- `factory/waves/*`, `factory/ledger/*`, `roadmap/phases.yaml` edits beyond
  registering this feature, `progress.md` except the verify-evidence block.

## Acceptance criteria

(observable)

1. `tests/theme-contrast.test.ts` passes with no weakened assertions; every
   text/background pair used by the refreshed surfaces meets 4.5:1 (body) —
   verified by the named verify command, exit 0.
2. `tests/workroom-namespace.test.ts` passes: no unprefixed or cross-app class
   leaks (`crm-`, `space-`, `rolodex-`, `groove-`, shared `atrium-` only) —
   verified by the named verify command, exit 0.
3. No horizontal scroll and no broken layout at 375px, 768px, 1024px, 1440px on
   the four app landing surfaces — verified by a Playwright pass (new or
   extended spec file, named in the job card).
4. Every button, link, input, and nav item on the refreshed surfaces shows a
   visible `:hover` and `:focus-visible` state, and motion honors
   `prefers-reduced-motion` — verified by Playwright assertions and/or targeted
   unit assertions, not by eyeballing.
5. Zero product-logic diffs: `git diff --stat` for the job shows only `*.css`,
   `*.tsx` className/presentational edits, and test files; no `lib/db`,
   `lib/auth`, or migration changes.

## Failure and edge cases

- Token change breaks contrast somewhere: the contrast gate fails, implementer
  fixes the token or the specific module CSS — never weakens the test.
- A per-app surface cannot be reached via tokens: implementer lists the exact
  module file in the job card and touches only that file (scope audit at review).
- Unknown/older browsers ignoring `prefers-reduced-motion` or custom
  properties: default state must be the calm one (no animation-dependent meaning).
- Baseline red: per AGENTS.md operating loop, fix the baseline first; do not
  layer the refresh on top of failing gates.
- Dark mode is retained (D5): both `color-scheme` branches stay contrast-gated;
  any dark-only assertion updates ship inside this same job.

## Verify command

`env -u DATABASE_URL npm test && AUTH_SECRET=ci-build-placeholder npm run build`

This is the project's definition of working (AGENTS.md). It runs the unit suite
with no `DATABASE_URL` (includes the theme-contrast and namespace gates) plus a
production build. The Playwright layout/focus pass from AC3–AC4 runs in addition
and is named in the job card; it does not replace this command.

## Open questions

None — all four questions (Q1 scope, Q2 light/dark, Q3 type, Q4 interaction
scope) resolved with the proposed defaults, accepted by the user on 2026-10-07.
See Decisions D5.

## Decisions

- D1: No data written by this feature (CSS/presentation only). No auth rule
  change (all surfaces remain behind the existing Auth.js gate; `tenantId`
  handling untouched).
- D2: No new styling framework or dependency. CSS custom properties + existing
  CSS modules. (Revisit only via a new spec.)
- D3: Existing tests are never weakened to get a green run (AGENTS.md hard
  constraint, restated so intake/implement cannot trade it away).
- D4: One feature at a time — this refresh ships as one job; any follow-up
  (e.g. per-app deep passes) becomes a separate spec, never scope creep inside
  this job.
- D5 (defaults accepted by the user 2026-10-07): Q1 app-wide tokens+chrome; Q2
  light-first with dark retained; Q3 keep type system; Q4 visual + interaction
  feedback, no restructuring. Open questions is empty; spec is `spec_ready`.
