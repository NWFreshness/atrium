# 11.5 — Edit from the detail pages

## Phase

Phase 11 — CRM integrity sweep. Closes gap **G2** (the three `[id]` pages are a
read-only `dl`; the only edit UI is a dialog on the list page, so correcting a
close date means navigating back and hunting the row). Depends on **11.4**
`passing` (table sorting; the tables themselves are untouched here). Prior art:
`factory/archive/pre-migration/inbox/JOB-008-edit-from-detail-pages.md`, cited,
never modified — several of its line pins are stale after 11.2/11.3/11.4 landed,
so every citation below was re-grounded in the current tree. Amended 2026-10-06
after cycle-1 BLOCKED: the render-prop mechanism cannot cross the
server/client boundary, so the wrapper takes a component reference instead
(see Decisions).

## Goal

Each CRM detail page (`/crm/organizations/[id]`, `/crm/contacts/[id]`,
`/crm/deals/[id]`) renders a single `Edit {name}` control in the page-title
row. Clicking it opens the **existing** form component as a dialog — already
proven on the list pages — so a user can correct a record without navigating
back to the list. The `<dl>` itself needs no change. The deal detail page gains
the tenant's full organization and contact lists so the form's selects match the
record. All three dialogs gain Escape-to-close, focus-on-open, and focus
restore on close. The server pages pass each form as a component reference
with serializable props; all open/close state lives in the client wrapper.

## User-visible behavior

- Each detail page shows one **Edit** button in the title row, visible at rest.
  Visible label is the word `Edit`; accessible name is `Edit {record name}` —
  the same template the list rows use (`Edit ${org.name}` at
  `components/crm/org-table.tsx:89`).
- Clicking Edit opens the existing form (`OrgForm` / `ContactForm` /
  `DealForm`) as `role="dialog" aria-modal="true"`, headed `Edit {name}`
  (the titles the forms already render), pre-populated with the record's
  values. No new route, no page navigation.
- The deal form's Organization and Contact selects list the tenant's
  organizations and contacts with the record's current values selected; a
  record with no link shows `None` (the `<option value="">None</option>` the
  forms already render at `deal-form.tsx:227,248` and
  `contact-form.tsx:178`).
- **Save** persists and the server-rendered `<dl>` shows the new value after a
  reload. **Cancel** and **Escape** close without saving; focus returns to the
  Edit control. Opening the dialog focuses the form's `Name` input; loading a
  detail page never steals focus.
- No Add affordance appears on any detail page. The inline `Add activity`
  submit stays on the contact and deal detail pages unchanged — it adds an
  activity *to* this record, a different verb on a different object. No Delete
  control is added to any detail page. The `<dl>` keeps its `dt`/`dd` pairs
  and their order.

## Out of scope

- **A new route.** No `/crm/{records}/[id]/edit`. The three `[id]` routes are
  unchanged in path and shape.
- **An Add affordance on a detail page.** No `AddOrganizationButton` /
  `AddContactButton` / `AddDealButton` on any `[id]` page.
- **A Delete control on a detail page.** Every record's delete lives on its
  list row today. Moving it is 11.7's decision.
- **Inline editing.** No contentEditable, no per-field edit, no autosave.
- **A focus trap.** Out of scope; the dialogs are four to seven fields.
- **Reordering, resizing, or restructuring the `<dl>`.**
- **The three table files.** `org-table.tsx`, `contact-table.tsx`,
  `deal-table.tsx` are byte-unchanged by this feature. AC10 enforces that.
- **`components/crm/activity-form.tsx`.** 11.3 owns that form's dialog mode;
  this feature does not touch it.
- **Value/probability validation in `deal-form.tsx:89-93`.** 11.2 owns those;
  the silent `return` is inherited as-is.
- **Deal filters, delete-consequence copy, the email unique index,
  `/crm/tasks`, QuickFind.** 11.8, 11.7, 11.6, 11.9, 11.10.
- **Linting.** Lint is not a gate.

## Failure and edge cases

- **Wrong-tenant record id:** `getOrganizationAction` / `getContactAction` /
  `getDealAction` return `null` and the page calls `notFound()`. Unchanged.
- **Empty name on submit:** the forms' existing `if (!name) return` keeps the
  dialog open with values intact. Inherited, not re-specified.
- **Invalid deal value/probability:** the silent `isFinite` return
  (`deal-form.tsx:89-93`) is inherited as-is per 11.2's server-is-the-gate
  rule; driving a 500 from the dialog is not this feature's UX contract.
- **Duplicate email on contact edit:** allowed until 11.6 lands the unique
  index. Recorded, not fixed here.
- **Wider deal-detail fetch:** resolving org/contact display from the full
  tenant lists is a wider fetch, not a wider scope — both lists are
  tenant-scoped actions. Cost on a large tenant is real and recorded.
- **No focus trap** in the dialogs; `Escape` and Cancel close.
- **Stale select options:** the form receives its lists as props at dialog
  open; a record created elsewhere mid-dialog is not in the select until the
  page refreshes. Recorded limit, not a defect.
- **Non-serializable `formProps`:** any function-valued prop other than the
  `form` reference itself, passed from a server page to `DetailEdit`,
  reintroduces the same serialization crash the amendment removed. The AC15
  read-test is the gate.

## Decisions

- **Slug `11.5-edit-from-detail-pages`** — intent title verbatim; branch
  convention `feat/11.5-edit-from-detail-pages` carried from the archived
  card. No alternative offered.
- **Archived card cited, not modified.** JOB-008 is the source of AC1–AC18's
  shape; this spec is the new system of record. Intake distills this spec,
  not the card, into the wave job. Deltas since the card: 11.2 landed (so
  `e2e/crm-deals.spec.ts` exists and the card's "if 11.2 has not landed"
  conditional is moot), 11.3 landed (activity-form dialog precedent;
  activity-form stays untouched), 11.4 landed (tables sort; AC10 still holds
  them byte-unchanged).
- **"On 11.5" under an invoked factory-spec bundle is the spec-it
  authorization.** The previous session's halt named `/factory-spec` on 11.5
  as the next action; this run answers it. No blocking field was left to a
  question — every decision below has its default written here.
- **DetailEdit takes a component reference, not a render-prop child**
  (`form` + serializable `formProps`; `onClose` created client-side). Reason:
  the three `[id]` pages are async server components, and a function-valued
  `children` prop cannot cross the server/client boundary — cycle-1 probes
  proved the exact render-prop shape fails the build (`Functions cannot be
  passed directly to Client Components`), while a component reference builds
  clean. The wrapper stays the smallest new client boundary and keeps all
  three tables byte-unchanged; user-visible behavior is identical either way.
  Rejected: per-record client hosts (three new files for zero behavior gain),
  element-child + `cloneElement` (prop-override magic; loosens the forms'
  `onClose` contract), and a `wasOpen` focus guard (mount-after-trigger is
  simpler and already pinned in AC6). File layout is non-blocking; intake may
  rename but keeps one wrapper, not three bespoke states.
- **"Amend the 11.5 spec like you said above" under an invoked factory-spec
  bundle is the amendment authorization.** The halt report named this
  mechanism pick as the missing decision; this run makes it. The card
  (`inbox/JOB-002`) still prescribes the render-prop letter — the spec
  station does not touch job cards, so the resumed run re-materializes the
  card from this amended spec before re-dispatching the implementer.
- **Deal detail resolves org/contact display from the fetched lists** instead
  of `get*Action`. Reason: the page must fetch both lists anyway for the
  form selects; one source avoids list-vs-record drift. Same tenant scope,
  wider fetch — cost recorded above.
- **Escape + focus-on-open + focus-restore are added to the three forms**,
  matching the 11.3 activity-dialog contract. No focus trap, no new
  keyboard contract beyond that; list pages inherit the behavior through the
  shared components.
- **Edit control is `Edit` / `Edit {name}` in the title row.** Default taken
  from the list-row template (`org-table.tsx:89`) and the card; placement in
  the `crm-detail-title` wrapper keeps `atrium-pagetitle` shared markup
  untouched.
- **Contact detail fetches the tenant organization list** even though it
  already resolves its own org for display. Reason: `ContactForm` requires
  `organizations: Organization[]` for its select; no prop is optional.
- **Verify is the three-part build + vitest + Playwright command**, a strict
  superset of the AGENTS.md floor — same standing as 11.3's spec. The two
  are not in conflict.
