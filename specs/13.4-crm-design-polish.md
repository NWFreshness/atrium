# 13.4 — CRM design polish (phase-13 follow-up)

## Phase

(provisional) phase-13 — CRM design polish follow-up. NOT in
`roadmap/phases.yaml` (phases 11–12 cover CRM integrity and deal history; no
design-polish intent exists there). Follows 13.1 (shipped PR #104), 13.2
(shipped PR #105), 13.3 (PR #106 OPEN). This spec does not move, rename, or
depend on any 11.x / 12.x intent. Id 13.4 is the next free phase-13 number;
no roadmap edit is made to insert it.

## Goal

Give the CRM one coherent visual pass on top of 13.1/13.2: calm commercial
surfaces, consistent type and spacing rhythm, clear hover/focus feedback —
without restructuring layout, adding routes, or touching data logic. The
aesthetic direction is decided below in Decisions (ui-ux-pro-max wins for
the CRM; frontend-design maximalism is rejected for dense sales surfaces).

## User-visible behavior

(Q1–Q4 answered 2026-10-07; resolutions in Decisions.)

- Decided Q1/Q3 behavior: the CRM (dashboard, tables, pipeline board, detail
  pages, forms) reads as one calm light-first system: near-white neutral
  surfaces, dark slate ink, light gray borders, one accent per screen. Dark
  mode keeps working behind the existing toggle and stays contrast-gated.
- Q2 decided (2026-10-07): layout and information-architecture changes are
  IN scope within the CRM surfaces in Q1; the job card names each layout
  change exactly. No copy rewrite, no new feature. Token + shared `atrium-`
  classes first; per-app module CSS only where unreachable via tokens or
  where contrast fails after the token change (13.1 scope rule).
- Every interactive element shows hover and keyboard-focus states;
  `prefers-reduced-motion` is respected; no horizontal scroll at
  375 / 768 / 1024 / 1440px.
- Groove receives only what arrives via shared tokens/chrome; no bespoke
  Groove restyle. Space/Rolodex receive only shared token/chrome effects
  unless Q1 extends scope.

## Scope paths

## Out of scope

- `lib/` query/auth/tenancy logic, database schema and migrations, seed.
- Auth behavior, tenant scoping, session handling. No `tenantId` handling
  touched; any toggle persistence stays client-side only.
- Groove audio engine; no Groove tables, no Groove demo resetter.
- New CSS frameworks or component libraries (no Tailwind, shadcn, or
  equivalent without an explicit decision in Decisions — current default:
  none; CSS modules + tokens only).
- Copy rewrites and new features. Layout/IA changes inside the CRM scope
  are allowed per Q2 but each must be named in the job card; no new
  top-level route or subnav entry beyond the CRM unless the job card names
  it (intake enforces the exact list).

## Acceptance criteria

(Final — Q1–Q4 answered 2026-10-07. Layout changes permitted by Q2 are
subject to the same gates: any layout change that breaks AC1–AC5 fails.)

- AC1: theme-contrast gate passes in both themes after the retune (no text
  below 4.5:1; usage-rule comments in `app/globals.css` still hold).
- AC2: CSS namespace gate passes (`crm-` per-app, `atrium-nav-` shared nav;
  shared nav classes do not rely on app theme variables).
- AC3: no horizontal scroll at 375 / 768 / 1024 / 1440px on every touched
  CRM surface.
- AC4: every touched interactive element shows a visible hover state and a
  visible keyboard-focus state; `prefers-reduced-motion` disables
  non-essential motion.
- AC5: light remains the first-visit default with the toggle one action
  away and persisting across reloads client-side (13.2 behavior preserved
  unless Q3 answers otherwise).

## Failure and edge cases

- A token change that drops any text below 4.5:1 fails the feature; retune
  or scope-trim, never weaken the contrast test.
- Dark mode must keep working and stay gated after the retune; a pass that
  fixes light at dark's expense is rejected.
- Unknown or malformed theme preference falls back to light (13.2 rule);
  nothing server-side may depend on the stored preference.
- Empty states keep their current honest copy; this pass does not rewrite
  the 11.8 empty-state wording.
- Reduced-motion users get instant state changes with no animation;
  decorative effects never carry meaning alone (color-plus-label, never
  color-only).

## Decisions

- Both requested skills ARE installed — no install needed:
  `frontend-design` (software-development) and `ui-ux-pro-max`
  (ui-ux-pro-max, with the `design-system` subskill) all resolve via
  skills_list. The conditional "search for and install" step is moot.
- Aesthetic choice for a CRM (user delegated: "choose whichever is best"):
  ui-ux-pro-max WINS, frontend-design LOSES as the lead direction.
  Evidence: ui-ux-pro-max `--design-system` query ("CRM sales dashboard
  dense minimal", project "Atrium CRM") returns Flat Design for SaaS/
  dashboards, light+dark supported, professional blue + deal green,
  150–200ms transitions, no gradients/shadows, SVG icons, 4.5:1 contrast,
  375–1440 responsive gates. A CRM is a dense work tool judged by
  legibility, density, and trust (Pipedrive/Notion class per 13.1/13.2),
  not by memorability — frontend-design's brief (bold, unforgettable,
  maximalist-leaning, never-repeat choices) optimizes the wrong objective
  for pipeline/tables/forms and would cost readability. Frontend-design is
  retained ONLY for micro-detail discipline (hover/focus states, type
  rhythm, restrained motion) inside the ui-ux-pro-max direction.
- Token layering follows the design-system skill's three layers
  (primitive → semantic → component) plus the 13.1/13.2 precedent: no raw
  hex in components, semantic surface/text/border tokens, component usage
  only. This is recorded here per factory-spec visual-feature guidance.
- Inter (recommended by the ui-ux-pro-max typography match) is REJECTED:
  it collides with frontend-design's no-generic-Inter rule AND the repo's
  established stack (Outfit headings, Archivo body, Geist Mono data in
  `app/globals.css`). Keep the repo type stack; adopt the palette
  restraint, single-accent, transition, icon, contrast, and responsive
  rules instead.
- Single-highlight rule kept: Phase 10 `--brass` one-accent-per-screen
  usage comments in `app/globals.css` stay authoritative unless Q3 answers
  otherwise. Palette retunes must preserve the "dark moss is a surface;
  light moss is ink" contrast rule.
- Q1–Q4 resolutions (2026-10-07, explicit user answers): Q1 CRM-only
  (default held); Q2 layout/IA allowed within CRM scope, each change named
  in the job card; Q3 keep light-default + toggle inside PNW tokens with
  the `--brass` single-highlight rule; Q4 standard verify command, no new
  Playwright.
- Status is spec_ready (Open questions empty after explicit user answers).
