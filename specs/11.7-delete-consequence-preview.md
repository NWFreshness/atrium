# 11.7 — Preview what a delete will unlink

## Phase

Phase 11 — CRM integrity sweep. Closes gap **G11** (deleting an
organization silently nulls its contacts' and deals' `organizationId` —
`onDelete: "set null"` is the right referential choice, but the confirm
names one row while the database unlinks many). No dependencies;
order-free with 11.8 except for one constraint: both touch
`lib/crm/deal-actions.ts`, so 11.7 and 11.8 run serially, never in
parallel. Prior art:
`factory/archive/pre-migration/inbox/JOB-005-delete-consequence-preview.md`,
cited, never modified — several of its line pins drifted after
11.3–11.6 landed, so every citation below was re-grounded in the current
tree (see Decisions). This spec is the new system of record; intake
distills this spec, not the card.

## Goal

The `Delete {name}` confirm on all three CRM list tables names the count
of rows the delete will unlink. A tenant-scoped `cascadePreview` counts
what a delete will unlink, and the confirm message names the counts when
non-zero while staying byte-identical to today's string when they are
all zero. The `SET NULL` schema is unchanged — this warns, it does not
prevent.

## User-visible behavior

- Clicking Delete on an organization, contact, or deal row first fetches
  that row's preview, then opens the same native `confirm()` the tables
  already use — no bespoke dialog, no "detach instead", no soft delete.
- When nothing will be unlinked, the message is byte-identical to
  today's: `` `Delete ${name}?` `` (currently
  `components/crm/org-table.tsx:98`, `contact-table.tsx:198`,
  `deal-table.tsx:185`).
- When rows will be unlinked, the message is the name line plus one
  consequence line: `` `Delete ${name}?\nThis will unlink ….` ``, e.g.
  `Delete Northwind Logistics?\nThis will unlink 2 contacts and 2
  deals.` and `Delete Acme?\nThis will unlink 1 deal.` The copy never
  uses the words "cascade" or "orphan".
- What each preview counts (all tenant-scoped, all counted, never
  named):
  - organization → contacts (`contacts.organizationId`) and deals
    (`deals.organizationId`); activities are always 0 (there is no
    `activities.organizationId`).
  - contact → deals (`deals.contactId`) and activities
    (`activities.contactId`).
  - deal → activities (`activities.dealId`).
- The same id in a different tenant previews all-zero and the message
  stays the bare form — the copy must never reveal another tenant's
  data.
- Dismissing the confirm deletes nothing; the row is still present
  afterwards.
- Deleting an activity is unchanged: 11.3 owns its confirm (`Delete
  this activity?`, `components/crm/activity-timeline.tsx:67`) with no
  consequence line, because an activity has no downstream rows.

## Out of scope

- **Activity delete.** 11.3 owns it; no consequence line (nothing
  references an activity).
- **A bespoke confirm dialog, "detach instead", soft deletes, recycle
  bin, undo toast.** Phase non-goals; the existing `confirm()` is the
  guard before an unrecoverable delete.
- **Any change to `onDelete`.** All five FKs stay `"set null"`
  (`lib/crm/schema.ts:54, :87, :90, :115, :117`).
- **Editing `lib/crm/schema.ts`.** No schema change, no new migration.
- **Detail pages.** Deletes exist only in the three list tables (verified:
  `deleteOrganizationAction`, `deleteContactAction`, `deleteDealAction`
  are referenced only from `org-table.tsx`, `contact-table.tsx`,
  `deal-table.tsx`); 11.5 added edit dialogs to detail pages, not
  deletes.
- **Styling the pending state.** No `:disabled` or `display: none` rules
  on `.crm-row-actions button` — the 10.3 opacity gate owns that block.
- **Running in parallel with 11.8.** Both touch
  `lib/crm/deal-actions.ts`.

## Acceptance criteria

1. Deleting an organization with 2 linked contacts and 2 linked deals
   shows exactly `Delete {name}?\nThis will unlink 2 contacts and 2
   deals.`; deleting a dependent-free row shows exactly `Delete
   {name}?`, byte-identical to today's string.
2. Every count is filtered on `tenantId` **and** the foreign key: tenant
   A's preview for tenant A's row counts only tenant A's rows while a
   tenant-B row with its own dependents sits in the same repo — the
   assertion that would fail if the tenant predicate were dropped.
3. The three dispatchers take `(tenantId, id, repo?)` in that order,
   call `requireTenantId(tenantId)` first, dispatch to the memory or
   Drizzle store, and contain no `db.*`.
4. Previewing a missing id returns all-zero rather than throwing, while
   deleting a missing id still returns `null`.
5. All three dispatchers reject a blank `tenantId` with `/tenantId/`,
   alongside the existing cases in the same test loop.
6. The message builder imports only `import type { CascadePreview }`
   from the shared module — `lib/client-boundary.test.ts` stays green —
   and its output matches neither `/cascade/i` nor `/orphan/i`.
7. The three `*CascadePreviewForSession` wrappers take `(getSession, id,
   repo?)`, call `requireTenant(getSession)` with no second argument, so
   no client-supplied `tenantId` can reach the query; each
   `*CascadePreviewAction` uses the same dynamic-auth shape as its
   neighbours.
8. Each action test asserts the preview for **another tenant's** row is
   all-zero, and each existing `rejects.toThrow("Unauthenticated")` case
   still passes.
9. All three tables call the message builder inside the `confirm()` call;
   the `aria-label={`Delete ${…}`}` template strings are unchanged (the
   gate at `components/crm/crm-pnw.test.ts:229-235` proves it) and the
   10.3 opacity gate at `:220-227` passes with the CSS files unmodified.
10. `lib/crm/schema.ts` is unmodified and the "sets related contact and
    deal organizationId to null instead of cascade-deleting" test passes
    unmodified.
11. The e2e journey asserts the exact two-noun message on a minted
    organization with one linked deal, the bare message on a minted
    dependent-free organization, and that dismissing `confirm()` leaves
    the row present after reload. It mints every row it touches with a
    `Date.now()` suffix and deletes no seeded row; every
    `page.once("dialog", …)` is registered before the click that opens
    `confirm()`.
12. Injection-proven with two reversed probes recorded in the card notes:
    hard-coding all-zero at the top of the memory preview fails the
    unit tenant test **and** the journey's message assertion (if only the
    unit test fails, the journey is asserting copy, not counts), and
    changing the zero branch fails the bare-message unit assertion.
13. `lib/client-boundary.test.ts`,
    `components/crm/crm-pnw.test.ts`, and the workroom namespace gate
    are green and unmodified.

## Failure and edge cases

- **Preview/delete race.** The preview is a point-in-time count with no
  transaction; rows linked between preview and confirm are still
  unlinked by the delete under unchanged `SET NULL` semantics. The
  message does not re-fetch after confirm.
- **Cross-tenant id.** Preview returns all-zero (never another tenant's
  counts); the delete path itself is untouched.
- **Missing row.** Preview returns all-zero; no throw.
- **Blank tenant / no session.** Dispatcher throws on blank `tenantId`;
  session wrapper throws `Unauthenticated` — tenant always comes from
  the session, never from a request body or query string.
- **Three-noun message unreachable via UI.** No `activities.organizationId`
  exists, so an organization preview always carries `activities: 0`;
  the builder still formats it (unit-covered) for the contact path,
  which can produce all three nouns.
- **Drizzle `count()` fragments unexecuted in CI.** Unit tests run
  against the memory repo with no Postgres; the Drizzle implementations
  are covered by the browser journey plus a source read, recorded in the
  card notes — the 11.6 precedent for unexecuted-store-fragment proof.
- **Native `confirm()` accessibility** is the browser's, not the app's;
  copy quality beyond the exact-string assertions is not proven by
  tests.

## Decisions

- Message composition default: non-zero nouns in fixed order contacts →
  deals → activities, each pluralized (`1 contact`, `2 contacts`, `1
  activity`, `2 activities`, `0 deals`), joined with `", "` and `" and
  "` before the last; zero counts omitted; all-zero yields the bare
  `Delete {name}?`. Exact strings are pinned by unit tests, not by this
  paragraph.
- Noun mapping per parent (from the five `SET NULL` FKs in
  `lib/crm/schema.ts`): org → contacts + deals; contact → deals +
  activities; deal → activities.
- The preview is fetched in the Delete click handler before `confirm()`;
  whether the button also gains a pending/disabled state while fetching
  is left to intake — it is not a user-visible contract.
- Serial-with-11.8 constraint recorded from the archived card and still
  true: `listDealsForSession` still takes `ListDealsOpts &
  ClientTenantInput` with the `requireTenant(getSession, input)` shape
  (`lib/crm/deal-actions.ts:56-67`), so both features append to / edit
  the same file.
- Re-grounded pins (archived card → current tree): confirm calls
  `:63/:86/:117` → `org-table.tsx:98`, `contact-table.tsx:198`,
  `deal-table.tsx:185`; barrel type-export block `:72-89` →
  `lib/crm/queries.ts:77-94`; schema `SET NULL` FKs
  `:52/:73/:76/:101/:103` → `:54/:87/:90/:115/:117`; crm-pnw gates
  `:220-227` (opacity) and `:229-235` (accessible names) confirmed
  current. Remaining card pins (test-loop lines, seed-assertion lines)
  are intake-time re-verification, not spec contracts.
- `spec_ready` with no questions asked: the roadmap intent dictates
  behavior, boundary, auth, and failure handling, and the archived card
  resolves every remaining blocking field; per the station rules only
  blocking fields may prompt questions. The 11.6 spec set the precedent
  for this exact situation.
