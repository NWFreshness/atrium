# 11.6 — Contact email uniqueness and duplicate pre-check

## Phase

Phase 11 — CRM integrity sweep. Closes gap **G9** (two contacts in one
tenant can hold the same email in different casing, and nothing refuses
it — a silent duplicate the user can never be warned about). No
dependencies; order-free with 11.7 and 11.8. Prior art:
`factory/archive/pre-migration/inbox/JOB-004-contact-email-uniqueness.md`,
cited, never modified — several of its pins are stale after 11.2–11.5
landed, so every citation below was re-grounded in the current tree
(see Decisions). This spec is the new system of record; intake distills
this spec, not the card.

## Goal

Two contacts in one tenant cannot hold the same email in any casing. A
case-variant duplicate is refused both at write time (tenant-scoped
pre-check) and at the database (tenant-composite unique index on
`lower(email)`), because the pre-check alone loses a race and the index
alone cannot produce the link to the existing contact. The refusal
names the existing contact and links to it. `NULL` emails are
unaffected; `""` is normalized to `null` before insert so empty strings
cannot collide. The CRM mirror of 8.1's `users_email_lower_idx`.

## User-visible behavior

- Creating a contact whose email matches an existing same-tenant
  contact's email in any casing (compared after trimming) is refused.
  The dialog stays open and shows `{name} already uses {email}.` with a
  link named `Open {name}` to `/crm/contacts/{id}`; clicking the link
  closes the dialog. No save, no refresh, no navigation happens on the
  failed submit.
- The same address in a different tenant is accepted with no warning —
  the error copy must never reveal another tenant's data.
- Contacts with no email are unaffected: any number of email-less
  contacts can coexist in one tenant.
- Editing a contact onto another contact's address is refused. Editing a
  contact while keeping its own address (including correcting its own
  casing, e.g. `ANA@x.test` → `ana@x.test`) succeeds.
- Leading/trailing whitespace is trimmed on create and on update;
  submitting an empty string stores `null`.
- The single fallback the user can see without the link is
  `Could not save that contact. That email may already be in use.` —
  shown only when the store refuses a write the pre-check passed (the
  race), where the existing contact's identity is not available.

## Out of scope

- **A global unique on `contacts.email`.** The index is
  tenant-composite per the design's ruling — a global one refuses tenant
  B's Ana because tenant A already has her.
- **`.unique()` on the `contacts.email` column.** The column stays a
  bare nullable `text("email")`; uniqueness lives only in the composite
  expression index.
- **`onConflictDoUpdate` on `contacts.email`.** Postgres cannot infer an
  expression index from a column-name conflict target, so no upsert
  touches this path; pre-check plus 23505-catch is the whole mechanism.
- **Seed data changes.** `lib/db/seed.ts` is byte-unchanged; the seeded
  contacts stay as they are.
- **`lib/auth/signup.ts`.** That file is 8.1's, with its own
  `lower(email)` lookup; untouched.
- **Renaming 8.1's `users` index.** Different table, different name.
- **A duplicates page, merge UI, soft deletes, or a "detach instead"
  choice.** Phase non-goals; 11.7 owns delete-consequence copy.
- **A second list helper** (`listXBySearch` or similar) — the pre-check
  extends the existing query surface.
- **A new Playwright spec file.** No `e2e/crm-contacts*.spec.ts` exists
  and this feature writes none; the dialog refusal is covered by
  component tests (AC10). Unit-gated, like the card's own Verify section.
- **Deal filters, delete-consequence copy, `/crm/tasks`, QuickFind.**
  11.8, 11.7, 11.9, 11.10.
- **Linting.** Lint is not a gate.

## Failure and edge cases

- **The race.** Two concurrent creates can both pass the pre-check; the
  second hits 23505 and maps to `duplicate_email` with the fallback
  copy and no `existing` link, because the losing write never saw the
  winner's row. Recorded limit, not a defect.
- **`""` vs `NULL`.** SQL `NULL`s are distinct in a unique index so
  email-less contacts are unaffected, but an empty string is not null
  and would collide — hence normalization before insert on both
  create and update paths.
- **Own-address casing correction.** The pre-check excludes the row's
  own id, so `ANA@x.test` → `ana@x.test` on the same record succeeds;
  without the self-exclusion every casing fix reads as a duplicate.
- **Wrong-tenant record id on update.** The existing actions return
  `null` / `notFound()` behavior is unchanged; the pre-check is
  tenant-scoped to the session tenant, never to an id from the form.
- **No cross-tenant oracle.** A tenant probing addresses learns nothing:
  same-tenant duplicates refuse, other-tenant addresses succeed, and the
  error copy names only a same-tenant contact.
- **Memory vs SQL.** The memory store proves policy, not SQL; CI runs no
  Postgres. The live index is proven by the migration file plus the AC17
  dev read-back.
- **Only DDL in the phase.** No other phase-11 intent touches schema, so
  the migration lands alone; the card's "after 11.2" ordering note is
  moot (11.2 already passed).
- **11.5's recorded note** ("duplicate email on contact edit allowed
  until 11.6 lands the unique index") is closed by this feature, not
  carried further.
