# 11.8 — Deal filters

## Phase

Phase 11 — CRM integrity sweep. Closes gap **G4** (the
`organizationId` / `contactId` reach the Drizzle and memory stores but
no UI reaches them, and there is no stage or close-date filtering at
all). No dependencies; order-free with every other intent except one
constraint: 11.7 also appends to `lib/crm/deal-actions.ts`, so 11.8
branches after PR #102 merges (or rebases onto it) — serial, never
parallel. Prior art:
`factory/archive/pre-migration/inbox/JOB-006-deal-filters.md`, cited,
never modified — several of its line pins drifted after 11.3–11.7
landed, and its `§6` / `§7` tables did not survive the migration, so
every citation below was re-grounded in the current tree and every
table it referenced is re-decided here (see Decisions). This spec is
the new system of record; intake distills this spec, not the card.

## Goal

`/crm/deals` filters by **stage**, a **close-date window**, and
**organization**, alongside the existing `q` search, surviving a
reload through the URL. `ListDealsOpts` gains `stage?`,
`closeAfter?`, `closeBefore?` (the `organizationId` / `contactId`
keys already exist and are implemented in both stores). A
client-safe parser validates the params so an unknown stage or a
malformed date is ignored rather than 500ing. The same
empty-state lie (`No deals` for both empty and filtered-empty) is
fixed on all three list pages.

## User-visible behavior

- `/crm/deals` carries one GET form (the existing
  `.crm-search` shape from the contacts-page precedent) with five
  fields and the unchanged `Search` submit:
  - `q` — text, `id="deal-search"` (unchanged).
  - `stage` — select, `id="deal-stage-filter"`, options `All` plus
    the six `DEAL_STAGES` in enum order; `All` carries `value=""`.
  - `closeAfter` — date input, `id="deal-close-after"`, `YYYY-MM-DD`.
  - `closeBefore` — date input, `id="deal-close-before"`, `YYYY-MM-DD`.
  - `organizationId` — select, `id="deal-organization-filter"`,
    options `All` (`value=""`) plus the tenant's organizations.
  - No contact select: `contactId` stays reachable at the
    opts/action/URL level only. Five fields, not six.
- Every control is uncontrolled with `defaultValue`; no `useState`,
  no `onChange`, no client component in the page — the contacts
  page (`app/(authenticated)/crm/contacts/page.tsx:52-79`) is the
  pattern.
- Submitting filters the table server-side and the URL carries the
  params, so a reload preserves the filter.
- The window is half-open: `[closeAfter, closeBefore)`. A deal
  closing exactly on `closeAfter` is included; a deal closing
  exactly on `closeBefore` is excluded. The `closeBefore` the user
  picks is a calendar day and the day is included: the page adds
  one day (`closeBeforeExclusive`) before querying, so picking Dec
  31 keeps Dec-31 deals.
- A deal with a NULL `closeDate` is excluded whenever either bound
  is active, and returned when no window is given.
- `?stage=Bogus` (or any stage outside `DEAL_STAGES`) returns 200,
  renders the unfiltered table with `All` selected, and renders no
  summary line. A malformed date (`2026-02-31`, `2026-2-3`,
  anything not strict `YYYY-MM-DD`) is ignored the same way. A
  stale or foreign `organizationId` renders the unfiltered table
  with `All` selected, never an empty one and never another
  tenant's rows.
- A summary line renders only when at least one filter is active,
  inside `.crm-toolbar`, as
  `Filters: <parts joined with ", "> · Clear filters`, where each
  part is exactly:
  - q → `Search: <raw text>`
  - stage → `Stage: <stage>`
  - window → `Close: <from> – <to>` with each bound rendered by
    `formatDate` (`lib/crm/format.ts`, UTC); a single bound
    renders open-ended (`Close: from Sep 1, 2026`,
    `Close: through Dec 31, 2026`)
  - organization → `Organization: <org name as shown in the select>`
  Parts appear in the order q → stage → window → organization.
  `Clear filters` is a `<Link href="/crm/deals">` with the exact
  accessible name `Clear filters`; clicking it lands on
  `/crm/deals` with an empty query string.
- Empty states: with no filter active the three strings stay
  byte-identical to today's (`No deals`, `No contacts`,
  `No organizations`). With any filter active (including a bare
  `?q=zzz` on contacts/organizations) the strings are exactly
  `No deals match these filters.`,
  `No contacts match these filters.`,
  `No organizations match these filters.`
- 11.4's client-side sort composes after the server returns the
  filtered rows; sorting behavior itself is unchanged and dies on
  reload as before.

## Out of scope

- **Filtering contacts by status/organization/last-contacted.**
  Deals only; the contacts `?status=` filter stays as it is.
- **Filtering activities.** Activities have no list page.
- **A contact select on the deals form.** `contactId` remains an
  opts/URL-level filter, not a sixth form field.
- **Server-side sorting or `ORDER BY`.** 11.4 owns sorting;
  filtered rows sort client-side exactly as unfiltered rows do.
- **Pipeline board filtering.** Deferred; G5 is not in this phase.
- **Touching `ListContactsOpts`, `ListActivitiesOpts`, or
  `lib/crm/dashboard.ts`.** Dashboard aggregations stay full-table.
- **Adding `LIMIT` to any list helper.** Bounded pagination is a
  phase non-goal.
- **Schema or migration work.** `closeDate` already exists
  (`lib/crm/schema.ts`); the file is unmodified.
- **Renaming dashboard copy.** Any wording drift between the
  dashboard and the deals surface is not this feature's to fix.
- **Running in parallel with 11.7.** Serial on
  `lib/crm/deal-actions.ts` while PR #102 is open.

## Acceptance criteria

1. `ListDealsOpts` reads
   `{ q?, organizationId?, contactId?, stage?: DealStage,
   closeAfter?: Date, closeBefore?: Date }` and `queries-shared.ts`
   gains no new import.
2. All existing two-argument `listDeals` call sites
   (`lib/crm/dashboard.ts`, `lib/crm/move-deal.ts`,
   `app/(authenticated)/crm/pipeline/page.tsx`, tests) are
   unmodified and typecheck — proven by the build in the verify
   command.
3. `lib/crm/deal-params.ts` exports `parseStage`,
   `parseCloseDate`, and `closeBeforeExclusive`, imports only from
   `./constants`, and a source-grep test asserts the file contains
   no `queries`, `schema`, `lib/db`, or `drizzle-orm`
   (`lib/client-boundary.test.ts` stays green).
4. `parseCloseDate("2026-09-30")` returns a `Date` whose
   `toISOString()` is exactly `"2026-09-30T00:00:00.000Z"`, with a
   comment naming the missing-`Z` local-time failure;
   `parseCloseDate("2026-02-31")` and `parseCloseDate("2026-2-3")`
   are `undefined`; `parseStage("Bogus")` is `undefined`;
   `closeBeforeExclusive("2026-12-31")` is
   `"2027-01-01T00:00:00.000Z"`.
5. The half-open bound is pinned by id, not by index: a deal at
   exactly `closeAfter` is included, a deal at exactly
   `closeBefore` is excluded, a deal at `closeBefore − 1ms` is
   included.
6. A NULL-`closeDate` deal is excluded by an active `closeAfter`,
   by an active `closeBefore`, and by both — and still returned
   when no window is given.
7. An inverted window (`closeAfter` later than `closeBefore`)
   returns `[]`; one case combining all five opts keys returns
   exactly one row.
8. The memory predicate keeps the existing tenant / search / id
   conditions unmodified; the Drizzle `filters` array gains
   `eq(deals.stage, …)`, `gte(deals.closeDate, …)`,
   `lt(deals.closeDate, …)`, each behind an `!== undefined`
   spread, with the no-`q` vs `q`-join branch structure preserved.
9. `listDealsForSession` re-projects through a literal listing
   `q`, `organizationId`, `contactId`, `stage`, `closeAfter`,
   `closeBefore` in that order — a literal, not a spread of
   `input` — and `ClientTenantInput` is unchanged; the
   tenant-override case (`{ q, tenantId: tenantB }` still scoped to
   the session tenant) and every existing
   `rejects.toThrow("Unauthenticated")` case still pass.
10. The deals form has exactly the five fields named above with
    the exact `name`/`id` pairs, plus the unchanged `Search`
    submit; no `useState`, no `onChange`, no client component in
    the file; the five `id`s collide with none of the
    `deal-form.tsx` control ids.
11. A stale or foreign `organizationId` renders the unfiltered
    table with `All` selected; `?stage=Bogus` returns 200 with the
    unfiltered table, `All` selected, and no summary line; a
    malformed date behaves the same.
12. The summary line renders only with an active filter, inside
    `.crm-toolbar`, in q → stage → window → organization order
    joined with `, ` plus the `· Clear filters` suffix; dates come
    from `formatDate` and the test reads the rendered text rather
    than hand-typing a date; `Clear filters` links to
    `/crm/deals` and lands with an empty query string.
13. The three tables each gain `filtered?: boolean` defaulting to
    `false`; bare strings are byte-identical to today's; filtered
    strings are exactly the three `No … match these filters.`
    sentences; `/crm/contacts?q=zzz` and
    `/crm/organizations?q=zzz` render their filtered sentences.
14. `org.module.css` gains only `.crm-filter-summary`
    (`crm-`-prefixed, no new token, no `display: none`) and is
    otherwise unmodified; the CSS namespace, pnw, pass, shell,
    workroom, and theme-contrast gates are green and unmodified.
15. `e2e/crm-deal-filters.spec.ts` has three journeys: stage +
    organization narrowing surviving a `page.reload()`; the date
    window over minted rows asserting the window's final day is
    visible (an inclusive-`lte` bound fails this); unknown-`stage`
    tolerance (200, unfiltered, `All`, no summary). Every journey
    mints its own rows with `Date.now()`-suffixed names, never
    relies on seeded `closeDate`s (`lib/crm/seed.ts` unmodified),
    asserts no exact row counts, registers every
    `page.once("dialog", …)` before the click that opens it, uses
    `{ exact: true }` for fixture-derived role names, and uses no
    CSS-module selector and no `waitForTimeout`.
16. Injection-proven with three reversed probes recorded in the
    card notes: dropping `stage` from the action literal fails the
    `{ stage: "Qualified" }` action case (the type still compiles
    without it — the silent ship); `lt` → `lte` in
    `queries-drizzle.ts` keeps units green but fails the e2e
    last-day assertion (the recorded unit-only limit); skipping
    `closeBeforeExclusive` in the page fails the same e2e
    assertion.
17. The shipped notes record what CI ran (vitest against the
    memory repo — no Postgres, no Playwright), that the Drizzle
    `gte`/`lt` fragments are proven by the browser journey plus a
    source read rather than by a unit test, and that 11.4's
    client-side sort is not covered by this feature.

## Failure and edge cases

- **Unknown stage / malformed date / stale org id.** Ignored at
  parse time; the page behaves as if the param were absent (200,
  unfiltered, `All`, no summary line for that key). Never a 500.
- **Inverted window.** Returns `[]` with the summary line still
  shown (the filters are active, they just match nothing) and the
  filtered empty-state copy.
- **NULL closeDate.** Excluded by any active bound (both stores),
  included with no window. No null-comparison crash in either
  store.
- **Cross-tenant org id.** The page validates against the
  tenant's own fetched organizations; a foreign id falls back to
  unfiltered — the query never receives another tenant's id, and
  `tenantId` itself always comes from the session, never from a
  body or query string.
- **Missing / unauthenticated session.** The action wrappers call
  `requireTenant(getSession)` unchanged; existing
  `Unauthenticated` cases cover it.
- **Drizzle fragments unexecuted in CI.** Units run the memory
  store with no Postgres; the `eq`/`gte`/`lt` fragments are proven
  by the browser journey plus a source read, recorded in the card
  notes — the 11.6/11.7 precedent for unexecuted-store proof.
- **Concurrent 11.7 branch.** Both features touch
  `lib/crm/deal-actions.ts`; 11.8 branches after #102 merges.
  11.7's preview actions and 11.8's filter literal do not overlap
  semantically, but the file arbiter is git, not this paragraph.

## Decisions

- URL params mirror the opts keys: `q`, `stage`, `closeAfter`,
  `closeBefore`, `organizationId`. The date inputs are
  `type="date"`; the parser accepts only strict `YYYY-MM-DD`
  (shape + calendar round-trip) interpreted as UTC midnight.
  `closeBefore` is user-inclusive via `closeBeforeExclusive`
  (+1 day) so the half-open store comparison keeps the picked
  last day. No other date shape is accepted.
- No contact select (five fields, not six): `contactId` filtering
  already works at the opts/action level and is covered by a
  combined-filters unit case; the form stays at the five controls
  the archived card's field count requires.
- Summary copy shapes (`Search: …`, `Stage: …`,
  `Close: <formatDate> – <formatDate>` with single-bound
  open-ended variants, `Organization: …`) are author decisions —
  the archived card's `§7` table did not survive migration. Exact
  strings are pinned by tests, not by this paragraph.
- Filtered empty-state sentences are taken verbatim from the
  archived card; bare strings stay byte-identical.
- New journey file `e2e/crm-deal-filters.spec.ts` rather than
  appending to `e2e/crm-deals.spec.ts`: the card contradicts
  itself (scope says append, its own AC names the new file) and
  the 11.7 precedent is one journey file per feature.
- Re-grounded pins (archived card → current tree):
  `ListDealsOpts` at `lib/crm/queries-shared.ts:86-90` (still
  `{ q?, organizationId?, contactId? }`);
  `listDealsForSession` re-projection at
  `lib/crm/deal-actions.ts:64-68`; `listDealsInDrizzle` filters at
  `lib/crm/queries-drizzle.ts:324-333` with the no-`q` vs `q`-join
  branches at `:334-355`; `listDealsInMemory` at
  `lib/crm/queries-memory.ts:288-305`; deals page (q-only) at
  `app/(authenticated)/crm/deals/page.tsx:8-17`; contacts GET-form
  precedent at `app/(authenticated)/crm/contacts/page.tsx:52-79`;
  empty states at `deal-table.tsx:217`, `contact-table.tsx:231`,
  `org-table.tsx:131`; `formatDate`/UTC at `lib/crm/format.ts:8-18`;
  `DEAL_STAGES` at `lib/crm/constants.ts:1-8`; `closeDate` column
  at `lib/crm/schema.ts:95`; drizzle-orm import lacking `gte`/`lt`
  at `lib/crm/queries-drizzle.ts:1`. No `deal-params` module
  exists yet. Remaining card pins (test-loop lines,
  seed-assertion lines) are intake-time re-verification, not spec
  contracts.
- `spec_ready` with no questions asked: the roadmap intent
  dictates behavior, boundary, auth, and failure handling, and
  the archived card resolves every remaining blocking field; per
  the station rules only blocking fields may prompt questions.
  The 11.6 and 11.7 specs set the precedent for this exact
  situation, and "next available" is the go-ahead to spec this
  feature.
