# 13.2 — Dashboard readability + light default with dark toggle

## Phase

(provisional) phase-13 — professional UI refresh follow-up. NOT in
`roadmap/phases.yaml` (phases 11–12 cover CRM integrity and deal history; no
UI-refresh intent exists there). Follows 13.1 (shipped as PR #104, `passing`).
This spec does not move, rename, or depend on any 11.x / 12.x intent.

## Goal

Fix the readability defects left by 13.1 on the CRM dashboard and replace the
greenish-tinted surfaces with a calm Notion-like light scheme: no text covered
by the pipeline funnel, body text meeting contrast, Recent activities items
visually separable, light mode the default, dark mode one toggle away.

## User-visible behavior

- CRM dashboard (`/crm`, composed in `app/(authenticated)/crm/page.tsx`):
  pipeline funnel labels are fully legible — no stage value or label is
  covered by or collides with another element at any supported viewport.
- Recent activities items on the CRM dashboard are delineated: each item has a
  visible boundary (divider, border, or card separation plus spacing), so
  adjacent activities never visually run together.
- Light theme is the default on first visit (no stored preference): near-white
  neutral surfaces, dark slate text, light gray borders, one accent per
  screen. The greenish background tint is gone from the dashboard and from
  every shared surface the token change reaches.
- A visible theme toggle in the shared chrome (reached from all four apps)
  switches light/dark; the choice persists across reloads (client-side only,
  e.g. `localStorage`); first visit is always light regardless of OS setting.
- Dark mode keeps working and stays contrast-gated after the retune.
- Design direction (per the design-system skill's semantic-token layering):
  primitive neutrals → semantic surface/text/border tokens → component
  usage; no raw hex in components; Notion-like restraint (white / gray-50
  surfaces, single accent carried over from the 13.1 `--brass` rule).

## Acceptance criteria

(observable)

1. Pipeline funnel on `/crm` shows every stage label/value with no overlap:
   a Playwright pass at 375 / 768 / 1024 / 1440px asserts no two funnel
   label bounding boxes intersect.
2. `tests/theme-contrast.test.ts` passes with no weakened assertions; every
   text/background pair on the refreshed surfaces meets 4.5:1 (body) in BOTH
   light and dark branches.
3. Every Recent-activities item on `/crm` renders a visible separator
   (computed border/divider or card boundary): Playwright asserts each item
   has a non-zero boundary treatment, and adjacent items are separated.
4. First visit (cleared storage) renders light; the shared-chrome toggle flips
   to dark and back; the choice survives reload — asserted by Playwright
   (toggle round-trip + reload persistence).
5. No greenish surface tint remains on the dashboard or shared light
   surfaces — asserted by unit tests on the light-branch token values
   (neutral / low-saturation grays) in addition to eyeballing.
6. Zero product-logic diffs: `git diff --stat` shows only `*.css`,
   presentational `*.tsx` (className/label/layout), the toggle component,
   and test files; no `lib/db`, `lib/auth`, or migration changes.

## Failure and edge cases

- Token tests hardcode dark-as-`:root` (e.g. `app/pnw-tokens.test.ts`
  slices `:root` → `[data-theme="light"]` as dark → light): update them to
  the flipped structure with assertions intact — never weaken the gate.
- Long stage names re-overlap funnel labels: truncate/ellipsize with title
  fallback; keep the `crm-pnw.test.ts` legend trap in mind (no series name
  equal to a tile label on the same screen — it breaks `e2e/crm.spec.ts`).
- Storage unavailable (private mode): render light default, toggle works for
  the session, no exception.
- `prefers-reduced-motion` continues to be honored; no
  animation-dependent meaning.
- Baseline red: per AGENTS.md operating loop, fix the baseline first; do not
  layer this on top of failing gates.

## Decisions

- D1: No server data written by this feature (CSS/presentation only; toggle
  persistence is client-side `localStorage`). No auth rule change; `tenantId`
  handling untouched.
- D2: No new styling framework or dependency. CSS custom properties +
  existing CSS modules. No chart-library change (recharts stays).
- D3: Existing tests are never weakened to get a green run (AGENTS.md hard
  constraint). Tests that assume dark-default structure are updated to the
  flipped structure with equal or stronger assertions.
- D4: One feature at a time — per-app deep passes beyond the CRM dashboard
  become separate specs, never scope creep inside this job.
- D5: First visit is always light (OS `prefers-color-scheme` is NOT
  auto-followed — predictable default per user ask); stored choice wins
  afterwards.
- D6 (user decisions 2026-10-07): Q1 dashboard + global light surfaces; Q2
  CRM dashboard only; Q3 light default with dark-mode toggle in shared
  chrome.
